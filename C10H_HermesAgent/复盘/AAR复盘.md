> 预期是什么？实际发生了什么？为什么有差距？下次怎么做得更好？

## 2. 做对了什么（Keep）

1. **先探测环境再安装**：提前发现 C 盘只剩 16 GB，把安装目录放到 E 盘，避免了 Chromium/Node 把系统盘撑爆。
2. **失败不绕路，先定位根因**：403 是通过 `uv` 进程无字节 + `hermes --version` 的报错交叉确认的，不是猜的。
3. **用官方支持的降级路径**：没有改执行策略注册表、没有关 Job Object、没有改 Hermes 源码；用的是「前台网关」「手动 venv」「override 文件」这些官方文档认可的方式。
4. **demo 保留原始轨迹**：`stream-json` 一行一个事件，比截图更难伪造，也方便统计 tokens。
5. **把失败写进交付物**：幻觉写入的 JSONL 原样保留，没有删掉重来。

## 3. 做错了什么（Problem）

### P1：默认「官方安装器一定顺利」

第一次执行安装器时，没有先做**网络可达性预检**（GitHub API / release assets），导致在 `uv python install` 上白等 12 分钟。

### P2：demo prompt 没有写验收标准

第一版 prompt 只说了「做什么」，没说「怎么证明做完」。小模型于是选择了最省力的路径：**声称完成**。这不是模型坏，是任务设计有漏洞。

### P3：假设「模型会自己从错误中恢复」

`execute_code` 被拒后，模型没有改用 `write_file`，而是直接编了一个成功。说明「工具报错 → 换工具」不是小模型的本能，需要 prompt 明确写「失败后改用什么」。

### P4：低估 Windows 原生的隐性问题

没有预检 bash，导致第一轮 demo 的 `read_file` 全部失败（`No shell found`），浪费了一轮 4 分钟。

### P5：时间预算失真

按云端模型的经验估「一轮 30 秒」，实际本地 4.6B 每轮 1–2 分钟。4 个 demo + 失败重跑，光推理就花了约 10 分钟。

## 4. 五个为什么：为什么差点交了一个假 demo？

**问题**：demo 01 第一版声称写入 `out/summary.md`，但文件不存在。

1. **为什么文件不存在？** 因为模型没有调用 `write_file`。
2. **为什么没调用？** 它先调用 `execute_code` 被拒绝，然后直接在文本里「宣布」完成。
3. **为什么会宣布完成？** 4.6B 模型的指令跟随能力有限，倾向于用最少的 token 结束任务；prompt 里没有「必须回读」的硬约束。
4. **为什么 prompt 没写？** 我把「模型会按工具 schema 行动」当成了默认前提，忽略了小模型的幻觉倾向。
5. **为什么这个前提是错的？** 因为 Hermes 的官方文档已经明确警告「小于 30B 的模型经常声称保存但没调用工具」——我没有在写 prompt 前查这一条。

**根因**：**把「执行」交给模型，却没有把「验收」设计成模型必须完成的动作。**

**如果只改一件事**：每个写操作后面强制加一次 `read_file` 回读，并在回复里引用文件中的一行。

## 5. 改进方案（下次直接照做）

### 5.1 安装前 5 分钟预检清单

```powershell
# 网络：GitHub API 是否可用（决定走官方还是手动）
try { (Invoke-WebRequest https://api.github.com/rate_limit -UseBasicParsing -TimeoutSec 10).StatusCode } catch { 'API 不可用 → 直接走手动 venv' }

# bash：Hermes 的 file 工具依赖它
Test-Path 'E:\hermes\tools\git-*\usr\bin\bash.exe'

# 磁盘：至少 10 GB 可用
Get-PSDrive E | Select-Object @{n='FreeGB';e={[math]::Round($_.Free/1GB,1)}}

# 模型：是否支持 tools
ollama show gemma4:e2b --modelfile | Select-String 'num_ctx'
```

### 5.2 demo prompt 模板（四件套）

```text
角色：你是……
边界：只允许使用 <tools>；只允许写 <dir>；禁止 <tool>
任务：……
验收：写完后必须 <read_file 回读 / 报告 exit_code / 引用一行>
失败处理：如果 <tool> 被拒绝，改用 <alt tool>，不允许声称成功
```

### 5.3 证据链模板

1. `--format stream-json` 落原始 JSONL；
2. 渲染器转 Markdown（保留 tool_use / tool_result / exit_code）；
3. 人工抽检：文件是否真的存在、字节数是否合理、路径是否真实；
4. 失败样本单独归档，不覆盖。

### 5.4 时间预算（本地 4B / 4 GB 显存）

| 动作 | 预算 |
| --- | --- |
| 单轮简单问答 | 40–60 s |
| 单轮 2–3 个工具调用 | 2–3 min |
| 完整 demo（4 场景） | 15–20 min（含 1 次重跑余量） |

## 6. 方法论：驾驭外部 Agent 的 5 条原则

1. **先验证，再信任**：任何「已完成」都要有可检查的副作用（文件、退出码、数据库行）。
2. **工具面最小化**：能给 2 个工具就不给 10 个；`execute_code` 在无人值守时应该直接关掉。
3. **失败留痕**：原始轨迹比总结更有价值；删掉失败，复盘就变成表扬稿。
4. **用官方降级路径**：前台网关、手动 venv、override 文件，都是文档里写过的；改环境/改源码是最后手段。
5. **把验收写进任务**：让 agent 自己回读、自己报退出码，比你事后检查更省力。

这五条不只适用于 Hermes，换任何外部 Agent（Claude Code、Codex CLI、OpenClaw）都一样。
