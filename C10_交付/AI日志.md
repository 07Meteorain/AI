# AI 使用日志 · C10

> **这份日志记录的是「人 + AI 编码代理」的协作过程**，不是"我用了 AI"这句声明。
>
> 记录原则：
> 1. **只写发生过的事**。没有做的实验不写"对比过"，没有的 key 不写"实测了"。
> 2. **AI 出错必须留档**，包括它自己发现并修掉的（见 §5 的 F2–F8）。
> 3. **每条结论都能被复算**：命令、输出、文件路径写在 §7。
>
> 协作形态：学生给出目标与验收标准；AI 代理（DeepSeek Harness 上的编码 agent）
> 负责设计、实现、测试、写文档；学生负责方向、取舍确认与最终验收。

## 1. 原始指令（原文，未删改）

```text
帮我完成C10这个挑战，在C10这个挑战里新建一个文件夹，把完成的内容放到这个文件夹中，
上传到https://github.com/07Meteorain/AI要求：严格按照C10这个挑战的文件里的内容完成C10挑战
```

这条指令里可被机器验收的约束只有四条：**① 做 C10 ② 新建文件夹 ③ 上传到指定仓库
④ 严格按挑战文件**。"严格按挑战文件"意味着交付物名称、评分维度都要能对上 `challenge.json`。
所以第一步不是写代码，而是把"严格"翻译成可检查的条件（见 §2）。

## 2. 工作流设计：把一句话拆成可验收的九步

AI 代理开工前先列了任务清单（原文）：

| # | 任务 | 验收方式 |
| --- | --- | --- |
| 1 | 读挑战材料，确认交付要求与仓库约定 | 能说出必需交付物与 5 个评分维度 |
| 2 | 设计五层架构 + KSTAR 四层记忆规范 | 写进 ARCHITECTURE.md，且每层有对应目录 |
| 3 | 实现 memory 层 | 单元测试通过 |
| 4 | 实现 tools 层 | `doctor` 能列出 12 个工具且可调用 |
| 5 | 实现 skills 层 | 3 个技能可加载、可执行 |
| 6 | 实现 loop 层 + LLM 适配 | 一次 `ask` 能产出 trace |
| 7 | 实现 evolve 层 + CLI | `evolve --apply` 能生成草稿技能 |
| 8 | 写测试并跑到全绿 | `unittest` 全绿 |
| 9 | demo + 文档 + CI + 推送 | 仓库里能看到 |

**为什么先列清单**：不列清单的 AI 会从"写一个 README"开始，写到一半发现代码没有，
然后开始编造代码示例。清单的作用是**让每一轮都有可验证的中间产物**。

## 4. Prompt 设计

### 4.1 给"模型规划器"的 system prompt（产品的一部分）

`brain/llm/provider.py` 里的 `SYSTEM_PROMPT` 只做一件事：把一句话变成
`{"intent", "confidence", "steps"}` 的 JSON。四条约束都是被具体故障逼出来的：

| 约束 | 防的是什么 |
| --- | --- |
| "只输出 JSON，不输出解释文字" | 解析失败；宁可加一次 `_extract_json` 兜底，也不让提示词鼓励闲聊 |
| "只使用上面列出的工具名" | 模型编造 `shell.run` 这类不存在的工具（`_sanitize` 会丢弃并记 `degraded_reasons`） |
| "最多 N 步；不需要工具时 steps 为空数组" | 预算爆炸；空数组是合法答案，否则模型会硬凑步骤 |
| "不确定时选 chat，步数越少越好" | 过度规划。**规划多了比规划少了更难查**：多出来的步骤会污染 trace |

`ANSWER_PROMPT` 只有一句硬要求："证据不足时直接说'记忆里没有'，不要编造。"
这一句来自 C4C 的教训：**一个会编造引用的系统，比一个会说"不知道"的系统危险得多。**

> **诚实说明**：本项目**没有** API key，因此这两段 prompt **未在真实模型上做 A/B 对照**。
> 关于"为什么这么写"的依据是故障模式分析，不是实验结果。这一点写在 `README.md` 的边界里。

### 4.2 给 AI 编码代理的指令（协作层面）

学生只给了一条指令（§1）。AI 代理自己追加的"内部验收标准"是四条：

1. **每一层都要能被单独验证**（否则不算"各层可工作"）；
2. **每个失败都要有一条回归测试**（否则修了也会退回去）；
3. **演示必须可重跑**（否则"能跑"依赖上次的残留状态）；
4. **文档里的数字必须能从产物里查出来**（否则就是在写小说）。

第 4 条在 R10 真的拦下了两处：草稿里曾写"测试 200+ 项"（实际 196）、
曾写"趋势上升"（实际按意图是下降）。**AI 很容易把自己的乐观写成事实**，
所以"数字必须可查"要变成流程，而不是美德。

## 5. AI 出错清单（与 AAR 的 F 编号对应）

| 编号 | AI 错在哪 | 怎么被发现 | 怎么修 | 回归测试 |
| --- | --- | --- | --- | --- |
| F2 | 用 `json.dumps` 生成 Python 源码，`false` 导致 `NameError` | 演示时该步失败 | 改 `repr()` | `test_draft_created_and_importable`（`compile()`） |
| F3 | `evolve` 声称 dry-run 却写了文件 | 单元测试 | `draft_skill(write=False)` | `test_dry_run_changes_nothing` |
| F4 | front matter 的逗号标签被静默丢弃 | 行为不符预期 | `_as_list()` 兼容两种写法 | `test_auto_skill_takes_over_review` |
| F5 | 技能失败被 `skill.run` 包装成成功 | 输出为空但状态 ok | `raise ToolError`；planner 加 `_week_of` | `test_unknown_skill_reports_error`、`test_weekly_review_rejects_bad_week` |
| F6 | 问句回声污染检索，同义词学不到 | 演示里"命中"的是问句本身 | `meta.echo` + 检索过滤 + 用 K 层当标尺 | `test_echo_records_excluded_by_default`、`test_alias_uses_curated_vocabulary` |
| F7 | 用混合意图平均步数判断进化 | 输出与事实相反 | 改为按意图分组 | `test_trend_detects_step_drop`、`test_trend_ignores_mixed_intents` |
| F8 | `--json` 只能写在子命令前 | 单元测试 | `parents=[common]` | `test_capture_and_recall_json` |
| — | 分类器把"回忆 复盘 周末"判成 review | 单元测试 | 句首动词优先 | `test_recall_question` 等 |
| — | 测试自己写错（"星期" vs "周日"、只读 3 行） | 失败输出 | 改测试，不改代码 | — |

**统计**：AI 写出的 5 个真 bug 中，**4 个由自动化测试发现，1 个由演示发现**。
没有一个是由"读代码"发现的——这条数据比任何"我很仔细"的自述都有说服力。

## 6. 哪些事没有交给 AI（或不该交）

| 事项 | 谁做 | 为什么 |
| --- | --- | --- |
| 决定"要不要为了好看引入 `rich`/`click`" | 学生（方向）+ AI（论证） | 这是取舍，不是实现；取舍错了，后面全是补丁 |
| 决定 KSTAR 四层的语义映射 | AI 提议，学生确认 | 术语歧义会污染全部文档，必须有人拍板 |
| 判断"3 步变 1 步"算不算进化 | AI 给度量，人给解释 | 指标能测效率，测不了价值 |
| 验收与推送 | 学生 | 仓库与账号是学生的；AI 不能替人做"对外承诺" |
| 写"诚实边界" | AI 起草，人确认 | AI 天然倾向于把边界写得温和；这条必须由人压住 |

## 8. 成本（估算，非精确）

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 会话时长 | 约 40 分钟 | 15:55–16:35（含文档） |
| 工具调用 | 约 90 次 | 含失败重试（F1）与测试重跑 |
| 返工轮次 | 8 轮 | F2–F8 + 分类器顺序 |
| token | **未统计** | 不写没测过的数字 |
| 金钱成本 | 0（离线模式） | 演示全程未调用付费 API |

**效率上最值钱的一条**：把"演示脚本化"提前到第 9 轮。
如果演示靠手敲，每次验证都要 10 分钟；脚本化之后每次 3 秒，
所以 R8 的 bug 修复才敢反复重跑（一轮改完立刻重放 14 个场景）。
**AI 协作的瓶颈不是写代码的速度，是"验证一次要多久"。**
