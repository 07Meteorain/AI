# KSTAR 记忆规范

> 记忆系统最容易犯的错误不是"存不下"，而是**存了找不到**、或**找到了不敢用**。
> 这份规范定义四层记忆各自存什么、不存什么、怎么被找回、什么时候该被淘汰。

---

## 0. 先说一个术语问题：KSTAR 五个字母，为什么只有四层

`KSTAR` 由 `K` + `STAR` 拼成（Situation / Task / Action / Result）。字面是五个字母，
但**记忆层只分了四层**：`K`、`S`、`T`、`AR`。这是刻意的，不是漏了一个：

| 层 | 名字 | 对应字母 | 为什么合并/独立 |
| --- | --- | --- | --- |
| K | Knowledge 知识 | K | 独立：它是唯一"不随时间失效"的层 |
| S | Situation 情境 | S | 独立：它回答"当时发生了什么" |
| T | Task 任务 | T | 独立：它回答"我答应了什么、做到哪了" |
| AR | Action-Reflection 行动与反思 | A + R | **合并**：一条行动记录如果没有结果与反思，既不能当经验复用、也不能当证据追溯 |

`A` 与 `R` 分开存的唯一后果是**它们会不同步**：有行动没有结果、有结果没有反思。
在数据库里它们是两张表，在认知上它们是一件事。所以合并成一条记录，用
`status`（ok / failed）与 `meta.error` 承载"结果"，用 `text` 承载"做了什么 + 学到什么"。

> 另一种读法是把 R 当作"操作"而不是"层"：K/S/T/A 四层存储 + R（Reflection）作为
> 把 A 提升到 K 的动作。本项目**两种读法都实现了**：四层存储是 `store.py`，
> R 操作是 `promote.py` 的沉淀规则。区别只在于我把 AR 写成了一条记录而不是两条。

## 1. 四层的定义与边界

### K — Knowledge（知识层）

**存**：验证过的结论、决策记录、方法论、已验证流程、已知坑。

```text
结论：检索排序必须是 BM25 × 层先验 × 新近度相乘，不能相加——没命中必须得 0 分
决策 ADR-20261115-xxx：用纯 Python 实现索引，理由：零依赖
已验证流程：memory.search>skill.run>memory.promote，已成功重复 3 次
已知坑：FileNotFoundError（累计 2 次）
```

**不存**：当时的情绪、未验证的猜测、一次性的操作细节。这些属于 S 或 AR。

**关键性质**：**不衰减**。牛顿力学不会因为放了三年就不对。K 的失效只能靠人主动更新
（`memory.update`）或新增一条覆盖它的记录。

### S — Situation（情境层）

**存**：某时某地发生了什么。每次运行的原文输入 + 那次回答的摘要，都会写一条。

**不存**：结论（那是 K）、待办（那是 T）。

**关键性质**：**半衰期 30 天**，且会被归档。理由：情境的价值在"最近"，三个月前的
一次对话几乎只在考古时有用，而它会持续污染检索结果。

### T — Task（任务层）

**存**：目标、承诺、截止日、状态机。

```text
status: open → done
meta.due: 2026-12-31
meta.started: 首次写入时间（用于算耗时）
```

**关键性质**：`done` 不是终点——关闭任务会**自动生成一条 AR**（`promote.task_done_to_action`），
这才是"承诺兑现"这件事进入记忆的方式。

### AR — Action-Reflection（行动与反思层）

**存**：一次运行做了什么、结果如何、耗时多少、失败在哪。

```text
意图 review（命令行 review）｜输入：周复盘｜执行 3 步（成功 3）｜结果：2026-W46 复盘：…
meta: {intent, workflow, steps, ok, error, duration_ms, recall_hits, echo}
```

**关键性质**：`workflow` 字段是"工具调用序列"，它是**技能固化的唯一依据**。
没有它，"重复任务"就只能靠自然语言判断，而自然语言判断会骗人。

## 2. 记录字段

| 字段 | 类型 | 谁维护 | 说明 |
| --- | --- | --- | --- |
| `id` | `k-YYYYMMDD-xxxxxx` | 系统 | 可读日期 + 6 位哈希；前缀区分层 |
| `layer` | K/S/T/AR | 写入时 | 决定存到哪个文件、参与哪种衰减 |
| `title` | str | 写入时（可空则自动取首句） | 进索引；也是人扫库时的唯一抓手 |
| `text` | str | 写入时 | 进索引；K 层会同时生成 md 镜像 |
| `created` / `updated` | ISO8601+08:00 | 系统 | 时区固定 UTC+8，否则按小时聚合会错 |
| `tags` | list[str] | 写入时 | 进索引，也可用于过滤 |
| `source` | str | 写入时 | 溯源：`run-…` / `skill:…` / `human` / `promote` |
| `importance` | 0~1 | 写入时 | 参与排序；不参与过滤 |
| `status` | open/done/ok/failed | T/AR | T 层是状态机，AR 层是结果 |
| `hits` / `last_hit` | int / ISO | 检索时自动 +1 | 判断"写在库里"还是"真的被用上" |
| `meta` | dict | 各层自定义 | `workflow` / `echo` / `covers` / `archived` 等 |

**为什么 `source` 必须有**：没有溯源的记忆，在出问题时无法判断"这条是不是它自己编的"。
KSTAR 的每条记录都能追到一次运行、一个技能或一个人。

## 3. 检索：四因子相乘

```text
score = BM25 × layer_prior × (0.85 + 0.3 × importance) × recency × usage

BM25       = Σ_t idf(t) · tf·(k1+1) / (tf + k1·(1-b+b·|d|/avgdl))     k1=1.5, b=0.75
layer_prior= K 1.25 | T 1.15 | AR 1.00 | S 0.95
recency    = K: 1.0（不衰减）  |  其它: max(0.55, exp(-ln2 · age / 30天))
usage      = 1 + min(0.25, 0.03 × hits)
```

### 为什么相乘而不是相加

相加会让一条"重要度高但完全不相关"的记录胜出。相乘保证了：**没命中任何查询词时，
BM25 = 0，总分必然是 0**。这是硬约束，不是调参偏好。

### 中文怎么切词

没有 `jieba` 依赖，所以用**CJK 二元组 + 拉丁词元**：

```text
"记忆系统 v2" → ["记忆", "忆系", "系统", "v2"]
```

- 单字噪声太大（"的""了""是"到处都是），二元组能保住"记忆""技能""复盘"这类有区分度的词；
- 代价是"记忆系统"被切成 记忆/忆系/系统，所以检索是 **OR 语义 + BM25 权重**，不是布尔匹配；
- 中英混排会被 `NFKC` 归一化，全角转半角。

### 同义词扩展

```json
{"map": {"打分规则": ["检索", "索排", "排序"]}}
```

命中别名键时，用目标词再检索一次，分数 **×0.5 叠加**（不覆盖原分数）。
0.5 是刻意的：扩展命中只能当"辅助证据"，不能盖过原查询的命中。

### 问句回声（`meta.echo`）

`recall` / `chat` 运行写入 S/AR 时会打 `echo=True`，**检索默认跳过**。

原因是一条真实 bug：同一句话问两遍，第二遍"命中"的是第一遍的问句存档，
于是命中率永远 100%，而这个 100% 毫无意义。要查"我问过什么"，用 `recall --echo`。

## 4. 沉淀：让库变短变准

| 规则 | 触发 | 动作 | 代码 |
| --- | --- | --- | --- |
| P1 | T 层任务 `done` | 生成 AR（结果 + 耗时） | `task_done_to_action` |
| P2 | 同一 `workflow` 成功重复 ≥ 3 次 | 提议沉淀 K「已验证流程」 | `collect_proposals` |
| P3 | 同一 `meta.error` 出现 ≥ 2 次 | 提议沉淀 K「已知坑」 | 同上 |
| P4 | S 记录 > 14 天且 `hits == 0` | 标记 `archived`（**不删除**） | 同上 |

**P2 认的是"流程"不是"意图"**：`复盘` 和 `周复盘` 的意图标签可能不同，
但 `memory.search>skill.run>memory.promote` 是同一条流程——可复用的是流程，不是说法。

**为什么归档而不是删除**：记忆系统的删除必须是可撤销的。一次误判就永久弄丢一段经历，
这是不可接受的代价。归档后记录仍在库里，只是不参与默认检索。

## 5. 查不到东西时，按这个顺序排查

```bash
# 1) 索引和记录是否一致
python -m brain doctor            # 看「KSTAR 索引一致」

# 2) 这条记录到底在不在
python -m brain recall "关键词" --echo --layer K

# 3) 换更短的词（二元组匹配，长句会被切碎）
python -m brain recall "复盘" -k 10

# 4) 看 trace 里那次检索返回了什么
python -m brain trace -n 5

# 5) 是不是问句回声被过滤了
python -m brain recall "我上周问过什么" --echo
```

## 6. 边界（不打算解决的）

| 边界 | 后果 | 为什么不做 |
| --- | --- | --- |
| 词面匹配 ≠ 语义匹配 | 换个说法经常找不到 | 语义要向量，向量要依赖 |
| 单进程写 | 两进程同时写会互相覆盖 | 单用户本地工具，加锁的成本大于收益 |
| 无 schema 迁移 | 改字段只能靠 `from_dict` 容错 | 记录量小，迁移脚本本身会成为负债 |
| Markdown 镜像是单向的 | 手改 md 不会回写到 JSONL | 双写必然出现两套真相 |
| 训练出的"同义词"可能不对 | 学错的映射会一直生效 | 每条候选都带原文证据，可手工删 |
