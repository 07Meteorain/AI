# 拿来说明 · 5 个关键取舍

> "拿来说明"回答的是：**你拿了什么、改了什么、为什么这么改。**
> 每一节都是"有另一个看起来更合理的选择，我没选它，理由如下"。
> 只写结论的取舍等于没写——因为读的人无法判断你是想清楚了还是碰巧。

---

## 1. KSTAR 五个字母，为什么只做四层？

**问题**：`KSTAR` = `K` + `STAR`（Situation / Task / Action / Result），字面五层。
但"行动"和"结果"在存储上到底是什么关系？

### 选项

| 方案 | 好处 | 坏处 |
| --- | --- | --- |
| A. 五层（K/S/T/A/R 各一层） | 字面对齐，听起来完整 | **A 与 R 会不同步**：有行动无结果、有结果无反思；检索时要跨两层拼一条经验 |
| B. 四层（A+R 合并为 AR） | 一条记录自带"做了什么 + 结果 + 反思" | 字面少一层，需要解释 |
| C. 三层（S/T/K） | 最简 | AR 是"可复用经验"的唯一来源，压进 S 会让 S 变成垃圾场 |

### 决定：B

理由：**一条行动记录如果没有结果与反思，既不能当经验复用，也不能当证据追溯。**
把它们拆成两条记录，唯一的确定性收益是"表变多了"。

结果载体：`status`（ok/failed）+ `meta.error`（错误签名）+ `text`（做了什么/学到什么）。

### 代价与补偿

- 代价：读文档的人第一眼会问"R 去哪了"。
- 补偿：`docs/KSTAR记忆规范.md` §0 专门解释，并指出**两种读法都实现了**——
  四层是存储（`store.py`），R 是"把 A 提升为 K"的操作（`promote.py`）。

### 后悔吗

不后悔。真正让我确认这个选择的是一次事故：`task.done` 自动生成 AR 时，
如果把"任务完成"和"结果评价"分两条写，中间崩溃就会留下"完成了但没结果"的孤儿记录。
合并成一条，这个状态机在物理上不存在。

## 2. 为什么默认离线，模型只做"规划"？

**问题**：一个"AI 智能体"不接模型，会不会只是脚本？

### 选项

| 方案 | 好处 | 坏处 |
| --- | --- | --- |
| A. 默认接模型 | 看起来更像"AI"，语义理解强 | 评审者 clone 下来第一步就要配 key；不配就跑不了 |
| B. 默认规则，模型可选 | 零配置可跑；规则可测 | 语义理解弱（"帮我想想上次那个事"判不出来） |
| C. 纯 prompt，不写代码 | 最快 | 没有测试、没有 trace、没有度量——三样都没有，就不是系统 |

### 决定：B，并且把模型放在"规划"位置

关键判断：**规划错了，回答再漂亮也没用。**
一个判错意图的系统，你让它生成多流畅的段落都只是把错误包装得更好看。
所以模型优先替换的是 `classify` + `plan`（选工具、填参数），
回答仍以检索证据为底（`ANSWER_PROMPT` 明确要求"证据不足就说没有"）。

### 代价

- 离线回答是**抽取式**的：它把证据排好、标出分数，不生成一句话。回执末尾会写明"未调用大模型"。
- 想体验生成式回答要自己配 key：`BRAIN_PROVIDER=openai BRAIN_API_KEY=... python -m brain ask "…"`。

### 后悔吗

不后悔，但留下了遗憾：**没有 key，所以两条 prompt 没有在真实模型上做 A/B**。
这一条写进了 README 的边界，没有假装验证过。

## 3. 为什么用纯 Python 索引 + JSONL，而不是 SQLite？

**问题**：记忆系统天然该用数据库，为什么用文件？

### 选项

| 方案 | 好处 | 坏处 |
| --- | --- | --- |
| A. SQLite + FTS5 | 查询快、并发好、省内存 | FTS5 依赖 Python 发行版的编译开关；坏了通常整库打不开 |
| B. JSONL + 内存倒排 | 可读、可 diff、可手工修；零依赖 | 全量加载（O(n)），无并发控制 |
| C. 向量库 | 语义检索 | 二进制依赖 + 模型；违背"clone 即跑" |

### 决定：B

三条理由，按重要性排序：

1. **记忆是长期资产，可读性优先于性能**。三年后想看懂一条记忆，`.jsonl` 用记事本就能开。
2. **损坏可恢复**。一行 JSON 坏了只丢一条（`read_jsonl` 跳过坏行）；SQLite 页损坏可能整库报废。
3. **零依赖是首要承诺**。FTS5 在某些发行版/容器里就是没有，而我无法在评审者机器上补装。

### 代价

- 上千条以内毫秒级；**上万条要换实现**（写进 README 的"规模边界"）。
- 两个进程同时更新会互相覆盖（追加安全、更新不安全）。

### 后悔吗

不后悔选了 B，但后悔**没有加文件锁**。这是明确的未解决项（AAR §6-3）。

## 4. 为什么"问句回声"要单独处理，而不是加个过滤？

**问题**：同一句话问两遍，第二遍会"命中"第一遍的问句存档。加个过滤不就行了？

### 这不是一个过滤问题

加过滤能修命中率，但修不了**同义词学习失效**：因为提问本身被写进 S/AR 层，
"没问到的那个词"立刻变成"索引里有的词"，于是"这个词系统没学过"这个判断永远为假。
两个 bug 同一个根因：**同一个存储里混了两种语义——"发生过什么"和"知道什么"。**

### 决定

1. 写入侧：`recall/chat` 写入的 AR/S 打 `meta.echo=True`；
2. 检索侧：默认跳过 echo 记录，`--echo` 可显式查看（"我问过什么"本身是合法查询）；
3. 学习侧：同义词挖掘用 **K 层（人工/技能沉淀）** 当"学过没有"的标尺，而不是全量索引。

### 为什么不是一张新表

四层共用一个存储，才可能"一次查询跨四层排序"。为 echo 单开一层会让层先验失去意义。
**一个字段解决的问题，不要用一张表。**

### 代价

- 想查"我问过什么"要记得加 `--echo`；
- K 层为空时（新库），同义词学习会静默不工作——这是可接受的降级（新库本来也没什么可学的）。

### 后悔吗

后悔的是**发现得太晚**：它是演示阶段才暴露的。如果先写"什么不该进索引"，
这个字段在第一版就会存在（AAR §5-②）。

## 5. 为什么自动生成的技能需要人工启用？

**问题**：既然能自动固化流程，为什么不直接让它生效？

### 选项

| 方案 | 好处 | 坏处 |
| --- | --- | --- |
| A. 全自动：生成即替换 | "更智能" | 系统会在无人察觉时改变自己的行为；出问题无法回滚到"上一版行为" |
| B. 生成到 `_drafts/`，可自动接管但需人工升版 | 又快又可审计 | 需要人"签收"，不是全自动 |

### 决定：B

- 草稿可以**自动接管**（`auto-*` + `status=draft` + tags 匹配意图）——这样"3 步变 1 步"立刻生效；
- 但草稿永远带着 `version: 0.1` 与 `status=draft`，清单里显式标注；
- 升到 1.0、移出 `_drafts/` 必须有人读过 `handler.py`。

理由：**一个会悄悄给自己加代码的系统，迟早会长出没人能审计的行为。**
这句话不是道德判断，是运维判断——你无法回滚一个你不知道存在的行为变更。

### 代价

- 进化不是"零人工"；草稿会越积越多，需要定期复审（`brain evolve` 会列出长期未用的技能）。
- 草稿可能过度拟合某次输入，需要人在升版时把写死的参数改成真正的输入。

### 后悔吗

不后悔。但补一条：**草稿连续失败时应该自动"取消接管"**，现在还没有（AAR §6-4）。
"需要人签收"不该变成"等人来发现它坏了"。

## 6. 额外一条：为什么度量要按意图分组？

这不是"取舍"，是一次被推翻的判断。

最初 `trend` 用前后半段的平均步数判断进化，输出"1.0 → 1.86，步数上升"，
而事实是 review 从 3 步降到 1 步——**平均值把结论说反了**。

改成按意图分组后：

```text
意图     运行数  前   后   变化
review   6       3.0  1.0  -2.00
```

教训：**混算的平均值可以证明任何结论，所以它不能证明任何结论。**
这也是为什么 `metrics` 里保留了"整体（混合意图，仅参考）"这一行——
不是因为它有用，而是因为**删掉它反而会让人以为整体也在变快**。
