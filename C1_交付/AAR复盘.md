# AAR复盘 · C1 课程资料获取与翻译

> **AAR** = After Action Review（行动后复盘）。按「做了什么 / 遇到什么问题 / 学到了什么」三段展开。
> 全部数据来自 `reports/02_qc.json` 与 `reports/00_extraction.json`，可复核；失败经验不修饰。

## 一、做了什么

**目标**：把斯坦福 CS146S《The Modern Software Developer》(Fall 2025) 的课程资料全量翻译成中文，
并产出一条**换一门课也能复跑**的信息处理管线。

### 1. 建成四阶段自动化管线

```
① extract    HTML/PDF 正文 → Block → Segment（按语义分段，48 个代码块识别并原样透传）
② translate  注入术语表 → 分段翻译 → 按原文 sha1 缓存落盘
③ qc         覆盖率 / 术语 / 漏译 / 格式 / 长度比，五项自动检查
④ build      Markdown 资料包 + 中英对照静态文档站
```

### 2. 实际产出（全部实测）

| 指标 | 数值 |
|---|---|
| 收录文档 | **33 篇**（31 篇完整正文 + 2 篇仅标题占位） |
| 英文原文 | **89,729 词** |
| 中文译文 | **148,938 字** |
| Segment 覆盖率 | **100%**（666/666，48 个代码块透传） |
| 术语表 | **172 条**，译法规则 **309 条**（275 禁用译法 + 34 歧义词） |
| 术语硬错误 | **0 处** |
| 质检红灯 / 黄灯 | **0 / 0**（69 条提示不阻塞） |
| 静态文档站 | **35 页**，中英对照可切换 + 页内搜索 |
| 样板块过滤 | 955 / 5,367 块（**17.8%**）识别为导航页脚并剔除 |

### 3. 三个关键设计决策

**① 把「质量」变成脚本而不是承诺**
`03_qc.py` 的五项检查各有阈值、有证据、可复跑。真正让我敢宣称达标的不是"提示词里写清楚了"，
而是这份能被任何人重新跑一遍的检查脚本。

**② 禁用译法是可执行的检查，不是文档里的一句话**
术语表每条含 `forbidden` 字段，被 QC 脚本全文扫描。实测靠这条规则抓出并修掉了
「代码审查 / 提示词工程 / 模型上下文协议 / 大型语言模型」等真实偏差。

**③ 按内容指纹做缓存键**
译文按原文 sha1 落盘。657 个缓存文件对应 666 个 Segment——差9 个是因为 5 组样板段落
（如 `Privacy Policy` 导航残片）在多篇文档重复出现，指纹相同自动共用一份译文。
**重复内容只译一次，且永远不会出现"两份译文不一致"。**

## 二、遇到什么问题

按严重程度排序，全部是真实发生过的。

### 问题 1：质检规则本身有 bug，报出 267 条假违规（最严重）

第一版 QC 报出 **267 条术语违规 + 30 条漏译**。逐条核查后发现**绝大多数是我的规则错了**，
不是译文错了。四轮迭代才压到 0：

| 轮次 | 术语硬错误 | 修了什么 |
|---|---|---|
| 第一版 | 267 | — |
| 第二轮 | 59 | 词边界匹配（`"diff" in "different"`）+ 规范译法并存降级 |
| 第三轮 | 6 | 新增 `ambiguous` 字段（34 条歧义术语降级为提示） |
| 第四轮 | 0 | `strip_code()` 剥离 5 类"必须保持英文"的内容 |

**根因**：我先写翻译流程，最后才写质检，而质检规则未经真实语料验证就上线。

### 问题 2：覆盖率一度虚高到 166%

QC 全绿后报告出现「词级覆盖率 166%」。这**不可能**。查代码发现我用了
「中文字数 ÷ 英文词数」，而 `count_words()` 把每个汉字算作一个词。
改成「已译原文词数 ÷ 全部可译词数」后才是真实的 100%。

### 问题 3：抽取阶段偷懒，把噪声外包给了翻译

PDF 抽取的文本有字符间插空格、页眉页脚残留、内容重复。
**11 个并行 agent 独立报告了同一问题**——当所有执行者都在处理同类噪声时，责任一定在上游。

### 问题 4：`config.json` 里躺着骗人的死配置

复核时发现 `qc.min_length_ratio`（0.55）和 `max_length_ratio`（1.60）**从未被代码读取**——
`03_qc.py` 里硬编码了另一套值（0.75 / 2.4）。更糟的是：按 config 里那个 1.60 上限判定，
会把实测长度比 1.31~1.89 的正常文档**误报成扩写**。

修了主调用路径后又发现 fallback 默认值（0.55 / 0.75 / 1.6）还是旧的——
单独调用该函数会退回错误阈值。**修死配置时，fallback 也要一起对齐。**

### 问题 5：术语表漏了评分标准点名的那个词

Rubric 第 32 行原文点名：「如 **Vibe Coding / Scaffolding / Context Engineering** 的译法统一」。

我逐个回查，发现 `Scaffolding` **根本没收录**。而译文里「脚手架」出现 4 次，
却不受术语表约束——等于这个评分点会丢分。已补入：
`Scaffolding → 脚手架`，禁用译法：支架 / 撑架 / 脚手架代码 / 搭架子。

> **172 条远超 ≥50 的门槛，但缺的恰好是评分标准点名的那个。数量达标 ≠ 覆盖到位。**

### 问题 6：clone 下来跑管线，抽出 0 篇（最接近"交付事故"）

上传 GitHub 后我模拟评审 clone 了一份到干净环境跑：

```
OK 共0 篇可用 /0 个 Segment /0 可译词
```

`config.json` 的 `source_root` 指向 `../../materials`——**仓库外的本机目录**。
这直接违反验收要点「陌生人可独立使用」。评审一按 README 跑就会露馅。

修法：把课程源资料一并提交（`source_materials/`，31 个页面 HTML + 4 份 PDF，29MB），
配置改指仓库内。修完在仓库独立环境实测：33 篇 / 666/666 / 硬错误 0 / 18.4s。

### 问题 7：4 篇资料卡在源头

| 文档 | 状态 | 原因 |
|---|---|---|
| `how-warp-uses-warp` | 无正文 | Notion 页面靠 JS 渲染 |
| `vibe-coding-playbook` | 无正文 | PDF是**扫描版**（14 页无文本层），需 OCR |
| `good-context-good-code` | 仅 9 词 | 原文被付费墙拦截 |
| `peeking-under-the-hood-of-claude-code` | 仅 44 词 | Medium 阻止自动化访问 |

遇到前三类障碍时我选择**跳过并如实记录**，而非硬啃。判断：JS 渲染页和付费墙硬啃
（headless browser / 绕过鉴权）投入产出比极低，且**绕过付费墙的合规风险不值得**。
**但扫描版 PDF 装 OCR 是应该做的，技术上完全可行，我漏了。**

### 问题 8：README 数字对不上

提交前自查发现三处：术语规则写成"296 条"（实际 309 条）；
一边声称"33/33 = 100%"一边列 4 篇没译成的（口径混了）；
漏写"必须用 `.venv/Scripts/python`"这个会导致抽取中断的前置条件。

## 三、学到了什么

### 1. 指标报错时，先怀疑指标

267 条术语违规里绝大多数是我规则错；166% 覆盖率是单位口径错；
死配置和术语表遗漏也都是"指标好看但不可信"的同类。
**当规则和直觉冲突时，先验证规则本身，而不是先怀疑数据。**

### 2. 本机跑通 ≠ 评审能跑通

这是最贵的一课。问题 6 之所以能溜过去，是因为我一直在**自己配好依赖的目录**里跑。
凡验收标准里写着"陌生人可独立使用""clone 后可用"的，
必须以**全新克隆副本**实测——本机配好的依赖、恰好能解析的路径，都会掩盖问题。

### 3. 验收标准里被点名的示例，必须逐个回查

术语表 172 条远超 ≥50 的门槛，数量上完全达标，
但缺的恰好是 rubric 点名的 `Scaffolding`。
**"数量达标"和"覆盖到位"是两件事**，前者容易自欺，后者才是评分依据。

### 4. 多个独立执行者报告同一问题 = 上游设计缺陷

11 个 agent 都在处理 PDF 排版噪声，这不是"翻译要小心"，是"抽取该做干净"。
**责任在共因，不在个体。**

### 5. 自动化的价值在于标注"判不准的"，不是假装全知

34 条歧义词（「背景」= background 还是 context？）脚本判不准，
我就标成提示交给人，而不是调阈值让告警消失。
**调阈值让告警消失是掩盖问题，标注不确定性才是解决问题。**

### 6. 结构指标比质量形容词可靠

"避免翻译腔"不可验证；"段落数必须与输入一致、代码围栏数必须相同"可数对。
把提示词里的"忠实"转成结构约束后，agent 能自我校验，QC 也能自动验。
**能变成可数约束的要求，才是能自动执行的要求。**

### 7. 把易错的技术环节移出人的工作流

人手算 sha1 必然出错，那就别让人算。`batch.py` 的价值不是"提高效率"，
是**消除人类必然犯的错**。

### 8. 诚实度是可复用性的前提

4 篇没译、哪些是误报、哪些质量存疑，全部写进 README。
藏起来的缺口会在别人复用时变成"这个项目说谎"。

## 四、如果重来，我会怎么做

**顺序错了，代价是四轮返工。** 下次按这个顺序：

```
① 定位一手来源 → 确认"哪些拿得到、哪些拿不到"
② 建术语表（基于语料实测）→ 约束前置
③ 先写质检，并用真实语料验证规则本身← 这次跳过了，所以返工四轮
④ 抽取 + 清洗 → 把噪声挡在翻译之前      ← 这次偷懒了，噪声被外包给翻译
⑤ 分段 + 术语按段注入 → 批量翻译
⑥ 自动质检 → 人工抽检
⑦ 单数据源多形态产出 → 文档站 + Markdown
⑧ 交付前：全新克隆副本实测← 这次漏了，评审会跑出 0 篇
```

**最不该跳过的两步是 ③ 和 ⑧**：一个决定返工量，一个决定会不会交付事故。

## 五、可复用结论

### 换个课能不能跑？

**能，但要改两处**：

1. **`pipeline/config.json`**：改 `source_root`、增删 `sources` 列表
   → 抽取/分段/翻译/质检/建站全自动适配，**脚本零改动**
2. **`glossary/terms.json`**：换领域术语 → schema 不变，补条目即可

**已验证**：四阶段管线、缓存幂等、质检规则、站点生成、clone 后完整复跑（实测）。
**未验证**：LLM API 路径（无 key）。

### 三个最该记住的判断

1. **脚本连续报同一个错时，先怀疑脚本。** 33 个源全部"文件不存在"不是文件的问题，
   是配置路径少了一级。
2. **指标漂亮到不可信时，先怀疑指标。** 166% 覆盖率不是超额完成，是单位不一致。
3. **判不准的时候标出来，不要调阈值。** 这才是自动化工具可信的前提。
