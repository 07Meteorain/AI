> 本复盘只写**真实发生过的事**，包括失败。数据均来自 `reports/02_qc.json` 与 `reports/00_extraction.json`，可复核。

把斯坦福 CS146S 课程的公开资料全量翻译成中文，并产出一条**换一门课也能复跑**的信息处理管线。

| 目标 | 验收标准 |

| G1 覆盖课程主体内容 | ≥80% 讲义/资料有对应中文 |
| G2 术语统一 | 术语表 ≥50 条，且全文一致 |
| G3 管线可复跑 | 有脚本、换源可复用、有质量抽检 |
| G4 成果可被他人使用 | 资料包结构清晰、陌生人可独立使用 |

## 三、差异分析（为什么是这个结果）

### 3.1 做得好的，为什么

**①把"质量"变成脚本而不是承诺**

最初我以为"提示词里写清楚要求"就够了。真正让我敢宣称达标的，是 `03_qc.py` 里那五项自动检查——覆盖率、术语违规、残留英文、格式配对、长度比，每项有阈值、有证据、可复跑。

**关键转折点**：第一次跑 QC 报出 267 条术语违规，我的第一反应是"译文质量很差"，但逐条看上下文才发现**是我规则错了**。这个过程让我意识到：**指标报错时，先怀疑指标**。这个判断后来又救了我一次（详见 3.2 覆盖率 166%）。

**② 术语表基于实测而非想象**

我让 AI 列术语，它能轻松给出 100 多条。但我坚持先跑词频统计，只收录在语料中出现 ≥5 次的词。这样每条术语都有"它真的重要"的证据。

**③ 术语约束按段注入**

171 条术语全量塞进每个 prompt 会稀释注意力。改成"只注入本段命中的术语"后，实际注入 20～60 条。agent 反馈证实针对性明显更强。

**④ 批处理粘合层 `batch.py`**

人/AI 写缓存要算sha1 指纹，必然出错。`batch.py export/import` 把指纹计算、包内路径、格式校验全包起来，人只负责"把英文变成中文"。**这是全项目我最满意的设计**——它把最容易出错的技术环节从人的工作流里彻底移除了。

**⑤ 11 个 agent 并行 + 独立文档**

按文档聚成 11 批（7K～10.5K 词/批），并行翻译。一次并发 6 个，两轮完成。独立文档让每个 agent 有完整的术语表和规则上下文，产出质量比让它"自由发挥"高得多。

### 3.2 没做好的，为什么

**① 质检规则本身的质量问题（最严重）**

这是我最真实的失误：**我先写了翻译流程，最后才写质检，而质检规则未经真实数据验证。**

结果第一版QC 报出 267 条术语违规 + 30 条漏译，逐条核查后发现**绝大多数是我规则的误报**。四轮迭代：

| 轮次 | 术语硬错误 | 漏译红灯 | 修了什么 |
|---|---|---|---|
| 第一版 | 267 | 30 | — |
| 第二轮 | 59 | — | 词边界匹配（`"diff" in "different"`）+ 规范译法并存降级 |
| 第三轮 | 6 | — | 新增 `ambiguous` 字段（33 条歧义术语降级为提示） |
| 第四轮 | 0 | 4 | `strip_code()` 剥离 5 类"必须保持英文"的内容 + 绝对数量下限 |
| 第五轮 | 0 | 0 | 覆盖率口径修正 |

**教训**：应该**先写质检并用真实语料验证规则，再开始翻译**。这样能省掉大量返工，也避免"指标好看但不可信"。

**② 覆盖率指标一度虚高到 166%**

QC 全绿后报告里出现「词级覆盖率 166%」。这**不可能**。查代码发现我用「中文字数 ÷ 英文词数」，而 `count_words()` 把每个汉字算一个词。

**教训**：**指标漂亮到不可信时，先怀疑指标，别急着庆祝。** 后来把覆盖率统一成「已译原文词数 ÷ 全部可译词数」，中英长度比单独报告并说明中文天然是英文的 1.5～2 倍。

**③ 抽取阶段偷懒，把噪声外包给了翻译**

PDF 抽取的文本有字符间插空格、页眉页脚、内容重复。**11 个 agent 独立报告了这个问题**——当所有执行者都在处理同一类噪声时，责任一定在上游。

**改进**：抽取阶段应加 PDF 专用清洗（去页眉页脚模式、去重复块、修连字）。

**④ 3 篇资料卡在源头，没能解决**

遇到"需 JS 渲染"、"扫描版 PDF"、"付费墙"三类障碍时，我的选择是**跳过并如实记录**，而不是想办法硬啃。

**判断**：对 Node 渲染页和付费墙，硬啃（headless browser / 绕过鉴权）投入产出比极低，且付费墙绕过的**合规风险**不值得。**但扫描版 PDF 装 OCR 是应该做的**——技术上完全可行，我漏了。

**⑤ 术语表是"事后补"的**

我先写完171 条术语表，译完全部内容后，才从 QC 误报里反推出 33 条歧义术语。**顺序错了**——歧义标记应该在翻译过程中遇到时就记，而不是靠事后统计。

### 3.3 意外的收获

**误报本身是最有价值的资产。**QC 报出的每一条误报都精确暴露了"自动化判断的边界"——比如"脚本无法区分『背景』是 background 还是 context"。这些样本是天然的**回归测试集**：如果将来改进规则，这批误报必须仍然不被误报。

我建议把它们固化成 `qc_regression.json`，但本次未做（见第七节）。

## 四、经验（可迁移的原则）

1. **指标报错时，先怀疑指标。**
   267 条术语违规里绝大多数是我的规则错；166% 覆盖率是我的口径错。**当规则和直觉冲突时，先验证规则本身。**

2. **自动化的价值在于标注"判不准的"，不是假装全知。**
   `ambiguous` 字段的逻辑：常用中文词（背景/光标/秘密）我判不准，就标出来交给人。**调阈值让告警消失，是掩盖问题；标注不确定性，是解决问题。**

3. **结构指标比质量形容词可靠。**
   "避免翻译腔"不可验证；"段落数必须与输入一致、代码围栏数必须相同"可数对。我把提示词里的"忠实"转成结构约束后，agent 能自我校验，QC 也能自动验。

4. **抽象要求要给正反例。**
   "避免翻译腔"没用；"原文 the model is doing X → 译成『这意味着模型在 X』，不要写『模型正在被用来进行 X』"有用。

5. **把易错的技术环节移出人的工作流。**
   人手算 sha1 必然错，那就别让人算。`batch.py` 的价值不是"提高效率"，是"消除人类必然犯的错"。

6. **多个独立执行者报告同一问题 = 上游设计缺陷。**
   11 个 agent 都在处理 PDF 排版噪声，这不是"翻译要小心"，是"抽取该做干净"。

7. **诚实度是可复用性的前提。**
   3 篇没译、哪些是误报、哪些质量存疑——全部写进 README。藏起来的缺口会在别人复用时变成"这个项目说谎"。

## 五、改进方案（下次具体怎么做）

按优先级排序，都可直接落地：

### P0 · 应该立刻做的

**① QC 规则回归测试集**
把本次的 297 条误报（267 术语 + 30 漏译）固化为 `tests/qc_regression.json`。任何 QC 规则改动都必须跑一遍，确保不再误报。

```json
{
  "cases": [
    {"zh": "不同模型对特定格式的响应可能更好", "en": "Different models may respond better",
     "expect": "no_issue", "reason": "「不同」是形容词，不是 diff 的误译"},
    {"zh": "The word \"apples\" appears once", "en": "The word \"apples\" appears once",
     "expect": "no_issue", "reason": "模型原始输出，必须保持英文"},
    {"zh": "把这张照片的背景换成星空", "en": "Change the background of this photo",
     "expect": "no_issue", "reason": "background ≠ context"}
  ]
}
```

**② 抽取阶段加 PDF 专用清洗**
- 检测并去除重复块（相邻段落内容重复率 >80%）
- 去页眉页脚（首尾 5% 位置的短行 + 含页码模式）
- 修连字（PDF 常在字符间插空格：用词典辅助合并，如 `T eam` → `Team`）

**③ 覆盖率口径统一 + 双向指标**
覆盖率只用原文侧口径；同时报告「中英长度比」并写明中文预期区间 1.0～2.1。**任何超过 100% 的指标都必须先质疑。**

### P1 · 显著提升效果的

**④ 术语表顺序调整**
改为「翻译时即时增补」：agent 译到某篇遇到术语歧义，当场写入 `ambiguous`，而不是事后靠统计反推。

**⑤ 引入译后术语对齐检查（反向校验）**
现在的术语检查是"禁用译法有没有出现"（查错译）。应再加一条"规范译法该出现时有没有出现"（查漏译）：

```python
# 原文含 "context rot" 但译文里既无"上下文腐化"也无禁用译法 → 漏译告警
```

**⑥ 抽样人工复核并量化**
当前 69 条歧义提示是人工判定"应该没问题"，但**没有记录复核过程**。应抽 30 段做人工双语对照，记录准确率，作为管线质量的可信基线。

**⑦ PDF 资料接OCR**
对 `Vibe_Coding_Playbook.pdf`（14 页扫描版）跑 OCR，可再增加一篇核心资料。

### P2 · 锦上添花的

**⑧ 译文变更 diff 工具**
课程官网会更新。当 `01_extract.py` 重跑后指纹变化时，应能 diff 出"哪些段落原文变了、译文需重译"。

**⑨ 半自动校对界面**
把 `work/translations.jsonl` 做成一个本地网页，支持并排显示原文/译文、术语高亮、一键标记问题段落。人工复核效率能提升一个量级。

## 七、可复用结论

### 7.1 这套管线换个课能不能跑？

**能，但要改两处**：

1. **`config.json`**：改 `source_root`，增删 `sources` 列表 —— 抽取/分段/翻译/质检/建站全自动适配，**脚本零改动**。
2. **`glossary/terms.json`**：换领域术语 —— schema 不变，补条目即可。

**已验证的部分**：四阶段管线、缓存幂等、质检规则、站点生成，都在真实数据上跑通。
**未验证的部分**：LLM API 路径（无 key）。

### 7.2 沉淀下来的方法论

这套流程的核心不是脚本，是顺序：

```
① 定位一手来源 → 确认"哪些拿得到、哪些拿不到"
② 抽取 + 清洗 → 把噪声挡在翻译之前
③ 建术语表（基于语料实测）→ 约束前置
④ 分段 + 术语按段注入 → 批量翻译
⑤ 自动质检（先验证质检规则本身）→ 人工抽检
⑥ 单数据源多形态产出 → 文档站 + Markdown
```

**其中最容易被跳过、也最不该跳过的是"先验证质检规则本身"。**
我这次是顺序错了，代价是四轮返工。下次会反过来。

### 7.3 三个最值得记住的判断

1. **当脚本连续报同一个错误时，先怀疑脚本。** 33 个源全部"文件不存在"不是文件的问题，是配置路径少了一级。

2. **当指标漂亮到不可信时，先怀疑指标。** 166% 覆盖率不是超额完成，是单位不一致。

3. **当判不准的时候，标出来，不要调阈值。** 33 条歧义术语降级为提示，交给人判断——这是自动化工具可信的前提。
