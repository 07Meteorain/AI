## Day 1 · 管线搭建

### 1.1 先读挑战书，再动手

**做了什么**：读 `CHALLENGE.md`、`rubric.json`、`challenge.json`，然后列目录看资料。

**关键发现**（决定了后面所有技术选型）：

- 验收要求「**≥80% 讲义有对应中文**」「**术语表 ≥50 条**」「**换一门课能复跑**」
- `materials/` 里已经是一份**离线缓存**（31 个 HTML + 3 个 PDF + 1 份课程主页），不用联网抓取
- 资料里有一份 `Vibe_Coding_Playbook.pdf`，以及 33 篇课程指定阅读

**决策**：既然重点是"管线"而不是"抓取"，就把工程量投在**分段、术语注入、自动质检**上——这才是rubric 里pipelineAutomation（20分）+ contentAccuracy（25分）两项的得分点。

### 1.2 第一个坑：配置文件格式写错

**发生了什么**：我把配置文件写成 YAML 风格（带 `#` 注释），但用 `json.load` 读。

```
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

**怎么发现的**：第一次跑 `01_extract.py` 直接崩。

**为什么犯**：惯性思维——配置文件带注释很自然，就按 YAML 写了，但没检查读取方式是否匹配。

**怎么改**：两条路——(a) 引入 json5 依赖；(b) 老实写成合法 JSON，注释挪到 `_readme` 字段。
选了 (b)，因为**这套管线的卖点就是零依赖、陌生人 clone 就能跑**，为了好看着的注释引入依赖不划算。

### 1.3 第二个坑：路径多退了一级

```
跳过（文件不存在）: course-homepage -> .../C1_交付/materials/CS146S_offline/index.html
```

`source_root` 写的是 `../materials`，实际资料在 `../../materials`。

**反思**：这类错误靠"跑一遍看日志"发现，成本很低。**但 33 个源全部报同一个错时，应该立刻怀疑配置而不是逐个查文件**——这是可迁移的判断：同一错误重复出现 = 系统性配置问题。

### 1.4 抽取阶段：为什么要自己写 HTML 解析器

**AI 建议过**用 BeautifulSoup 或 trafilatura。**我否掉了**，理由写进了代码注释：

1. 零依赖是硬需求（陌生人 clone 就能跑）；
2. 更要命的是——**通用抽取库会把 `<pre>` 里的代码破坏掉**，而这份资料里代码块占比不低，代码排版错乱对技术文档是致命的。

于是用 `html.parser` 手写了一个 `ArticleParser`。核心逻辑：`<pre>` 内容单独缓冲、其余走正文流；`script/style/nav/footer` 直接丢弃。

**实际效果**：33 篇抽出 714 个 Block，代码块识别准确。

### 1.5 立刻发现的问题：导航样板污染

第一版抽完就发现不对——译文里会出现「Skip to main content」「Subscribe」「Read now」这类东西。抽查 `claude-code-best-practices` 时看到第 0 段是：

```
Skip to main content
Claude Code Docs home page
Getting started
Build with Claude Code
Deployment
...
```

**这些占正文 30%+，不处理的话译文质量直接不合格。**

**做法**：加一层 `filter_boilerplate()`，两类规则——
- 固定短语黑名单（`skip to main content`、`subscribe`、`privacy policy`…）
- 启发式：连续短小的列表项（导航特征）、`A | B | C` 分隔符行

**实测过滤掉 955 块**（如 `agentic-ai-threats` 561→454，`ai-code-review-best-practices` 227→143）。

### 1.6 最有价值的一个 bug：JSONL 被form-feed 截断

**怎么发现的**：跑 `02_translate.py` 时报

```
json.decoder.JSONDecodeError: Unterminated string starting at: line 1 column 130
```

**排查过程**（这段值得完整记下来）：
1. 先怀疑是 `write_jsonl` 写坏了 → 检查写入逻辑，没问题
2. 数了一下行数：`segments.jsonl` 有 **1116 行，但只有 714 条记录** ← 关键线索
3. 逐行 try/except，找出所有坏行 → 429 行解析失败
4. 看坏行内容：全部来自 PDF 文档，且断点位置在奇怪的地方

**根因**：`pypdf` 抽出的文本里含 `\x0c`（换页符）、`\x0b` 等控制字符。而 Python 的 `str.splitlines()` **会在这些控制字符处断行**，`json.dumps` 却**不会转义它们**。于是文件本身是合法的一行 JSONL，但被`splitlines()` 读成了两条损坏的记录。

**修法**（两处都改，这才是根治）：
- `read_jsonl` 改用 `split("\n")` 而非 `splitlines()`
- `normalize_ws` 里加 `CONTROL_CHARS` 转译表，在**抽取阶段**就清掉所有控制字符

**为什么两处都改**：只在读取端修，译文里仍会混进看不见的 `\x0c`——读者根本发现不了，但复制粘贴会出问题。**在源头清理才是根治。**

**教训**：`splitlines()` 比 `split("\n")` "聪明"，但这种聪明在这里是错的。凡是处理外部数据的文件，**默认用最朴素的切分方式**。

### 1.7 让管线可复跑的关键决策：翻译缓存

翻译是整条管线里**唯一"贵"且"不确定"**的环节。所以：

- 译文按**原文 sha1** 落盘到 `cache/translations/<sha1>.json`
- `provider=cache` 时只读缓存 → **零网络、零成本、完全可复跑**
- 人工校对过的译文成为"黄金版本"，重跑不会被覆盖

**但这里衍生出一个真问题**：人/AI 怎么写缓存？手算sha1 必然出错。

于是写了 `batch.py` 作为粘合层：

```bash
python batch.py export --out ../work/batch_a.json   # 导出待译段+ 注入术语
# 翻译后填translations 字段
python batch.py import --file ../work/batch_a.json   # 自动算指纹、回填缓存
```

**这样人和 AI 只负责"把英文变成中文"这一件事，不可能在算指纹环节丢译文。** 这是我在整个项目里最满意的一个设计。

## Day 1 · 术语表构建

### 2.1 拒绝凭想象编术语表

AI 很自然地能列出 50-100 个 AI 编程术语。**但我没直接用**，因为那样无法回答"你凭什么认为这个词重要"。

**做法**：先从语料实测词频。写了段脚本统计候选术语在 89,729 词语料中的出现次数：

```
  365mcp        357  spec        355  claude code    312  prompt
  228  code review  162  eval       157  log           143  workflow
  139  diff        118  rag         114  llm           101  pull request
   74  sast         65  token  58  owasp         56  dast        53  span …
```

**关键判断**：只在语料里出现 ≥5 次的术语才进表。这样每条术语都有"它在资料里真的重要"的证据，而不是"我觉得它重要"。

### 2.2 forbidden 字段：把偏好变成可执行检查

术语表不只写"该译成什么"，每条还带 `forbidden`（禁用译法）：

```json
{ "en": "Code Review", "zh": "代码评审",
  "forbidden": ["代码审查（统一用「评审」）", "代码检视"] }
```

**为什么加这个**：翻译的一致性是**最容易被忽略、也最容易被评审抓住**的硬伤。与其写进文档指望人记得，不如让脚本全文扫。**这 296 条禁用译法规则后来真的抓出了实际问题**（见 Day 2）。

**先验判断**：光标→「Cursor」、副驾驶→「GitHub Copilot」这类谐音梗，我也写进了 forbidden。

## Day 2 · 批量翻译

### 3.1 怎么把 666 段翻译完

**不采用的做法**：自己一段段翻。666 段、9 万词，串行做不完，且质量会随疲劳下降。

**采用的做法**：把 89,729 词按文档聚成 **11 个批次**，并行交给 11 个翻译 agent，每个 agent：
- 拿到自己批次的 `tr_gNN.json`（含原文 + **该批次命中的术语约束**）
- 按统一 prompt 翻译，写回 `translations` 字段
- 然后我统一 `batch.py import` 回填

批次划分（按词数均衡，7K～10.5K 词/批）：

| 批次 | 内容 | 段数 | 词数 |
|---|---|---|---|
| g01 | 提示工程（Google Cloud） | 55 | 7,047 |
| g02 | 上下文工程（Context Rot 等） | 47 | 8,923 |
| g03 | Anthropic 讲义 PDF | 21 | 10,572 |
| g04 | Codex + 代码评审评估 PDF | 14 | 8,810 |
| g05 | MCP 四篇 | 82 | 8,077 |
| g06 | 编码智能体四篇 | 104 | 10,043 |
| g07 | 智能体威胁 + OWASP | 84 | 8,466 |
| g08 | 安全实践三篇 | 65 | 7,913 |
| g09 | 代码评审四篇 | 82 | 8,492 |
| g10 | SRE 五篇 | 83 | 9,805 |
| g11 | 课程主页 + Warp 对比 | 29 | 1,581 |

### 3.2 关键：prompt 里只注入"本段用到的术语"

如果把 171 条术语全量塞进每个 prompt，模型注意力会被稀释——**术语越多，每条越可能被忽略**。

所以 `build_prompt()` 先扫一遍原文，只注入实际命中的术语：

```python
hit = [t.en for t in glossary.terms
       if any(k.lower() in text.lower() for k in [t.en, *t.aliases])]
block = glossary.glossary_prompt_block(hit)
```

实测这样每个 prompt 里的术语约束从 171 条降到 **20～60 条**，针对性明显更强。

### 3.3 prompt 里最有效的两条约束

在众多规则里，真正起作用的是这两条（agent 反馈里明确提到）：

**① 反翻译腔的具体例子**，而不是抽象要求：

> 原文 "This means the model is doing X" → "这意味着模型在 X"，
> 不要写成"这意味着模型正在被用来进行 X"。

抽象地说"避免翻译腔"没用，给正反例才有用。

**② 结构可验证**：

> 段落数必须与输入一致；代码块围栏数必须与原文相同。

把"翻译质量"转化成**可数对的结构指标**，agent 就能自己校验。这一条直接支撑了后面的自动质检。

### 3.4 agent 反馈的真实收获

11 个 agent 独立工作，报告的坑五花八门，但**集中暴露了 4 个系统性问题**——这比顺利翻译更有价值：

| agent 报告的问题 | 暴露的管线缺陷 |
|---|---|
| 多篇文档的 Read 被截断（`[truncated]`），需用脚本单独导出 | **长文本必须分批读**，不能一次 Read 整个 JSON |
| PDF 正文"内容出现两遍"，夹杂页码噪声 | **抽取阶段就该清理**，而不是让翻译去处理 |
| 原文把图表标题粘在下一段开头（无换行） | 抽取时应检测粘连 |
| 分类标题带 `- ` 前缀（是列表项不是标题） | 分段时应保留原始块类型，不能只看文本 |

**我的处理**：前三个记录进 AAR 的改进方案；第二个立刻意识到——**如果 11 个 agent 都在处理同一类噪声，说明该在抽取阶段根治**。

## Day 2 · 质检脚本三轮迭代

**这是整个项目最有价值的部分。**质检脚本第一版跑出 **267 条术语违规 + 30 条漏译**，看着像译文很差，逐条一看——**绝大多数是我QC 规则的误报**。

### 第一轮：267 条术语违规 → 发现"子串陷阱"

**现象**：
```
  71  「不同」 -> 应为「差异」   (Diff)
  55  「模式」  -> 应为「schema」 (Schema)
  48  「码库」  -> 应为「代码库」 (Codebase)
```

**逐条看上下文**，全是误报：
- 「**不同**模型对特定格式的响应可能更好」← 形容词"不同"，不是把 diff 译错了
- 「失败**模式**」← 正常中文词
- 「**码库**」← 这是「代**码库**」的子串！

**根因一**：`check_consistency()` 是纯 `if bad in zh_text`子串匹配。
**根因二**：更隐蔽——`_has_term` 用 `k in low` 判断原文是否含该术语，于是 `"diff" in "different"` 为真！所以"不同模型"这句，原文里确实有 "different"（被当成 "diff"），译文里确实有"不同"（被当成 diff 的错译），**逻辑上完美触发，实际完全无辜**。

**改法**（两步）：
1. **加词边界匹配**：`_has_term()` 用前后字符判断，`before/after` 必须是非字母数字
2. **加"规范译法并存"降级**：若译文中已同时出现规范译法，说明译者是一致的，降级为提示

```python
if before_ok and after_ok:   # 词边界
    return True
...
if core and core in zh_text:
    level = "info"   # 规范译法也在，译者其实是一致的
```

**效果**：267 → **59 条**。

### 第二轮：59 → 6，识别出"术语歧义"

剩下的逐条看，发现 6 条**仍然是误报**，而且是另一类问题：

| 告警 | 实际语境 | 判定 |
|---|---|---|
| 「背景」→「上下文」 | 「把这张照片的**背景**换成星空夜景」 | background，误报 |
| 「背景」→「上下文」 | 「能给我们一点**背景**信息」 | background，误报 |
| 「光标」→「Cursor」 | 「现代终端体验：**光标**移动、语法高亮」 | 光标，误报 |
| 「秘密」→「密钥」 | 「帮你理清复杂系统的**秘密**武器」 | 习语，误报 |
| 「语境」→「上下文」 | 「在 AI **语境**中」 | 正常中文，误报 |
| 「不同」→「差异」 | 同第一轮 | 误报 |

**这类问题的本质**：`forbidden` 里的词本身就是**常用中文词**。「背景」「光标」「不同」「秘密」在正常句子里就会出现，脚本**没有能力区分**"这是术语误译"还是"这是普通词义"。

**改法**：给Term 加一个 `ambiguous` 字段，把这类词从 `forbidden` 挪进去，**只报提示（info），不阻塞交付，交人工抽检**。

```json
{ "en": "Context", "zh": "上下文",
  "ambiguous": ["背景", "语境"],
  "_note": "这些词本身就是常用中文，脚本无法区分术语误译与普通词义" }
```

共标记 **33 条**歧义术语。**效果**：硬错误 59 → **0 条**。

**这个改动的意义**：不是"把指标做好看"，而是**承认自动化判断的边界**——脚本判不准的就标出来交给人，而不是调阈值让它闭嘴。

### 第三轮：30 条漏译告警 → 4 类"必须保持英文"的内容

**现象**：30 条 `untranslated` 告警。逐条看，全部是误报，但暴露了一个**我最初没考虑到的翻译原则**：

| 告警 | 实际内容 | 为什么必须保持英文 |
|---|---|---|
| `context-rot#0024` | `The word "apples" appears once in the original text…` | **模型原始输出**，是实验数据 |
| `context-rot#0026` | `I can't replicate that exact text as requested.` | **模型实际吐出的英文** |
| `how-long-contexts-fail#0008` | 《**How to Fix Your Context**》 | **文章标题** |
| `claude-code-best-practices#0008` | `The token '&&' is not a valid statement separator` | **PowerShell 报错原文** |
| `ai-assisted-code-review#0003` | `TensorFlowExample`、`example` | **类名/标识符** |

**根因**：我最初的 `strip_code()` 只剥离代码块，**假设"译文里的英文 = 漏译"**。但技术翻译里有一整类内容**必须保持英文**：模型输出示例、文章标题、报错信息、专有名词。

**改法**：`strip_code()` 扩充为剥离五类——
1. 代码块 / 行内代码
2. `《...》` 书名篇名
3. 引号内直接引语（中文引号 + 英文引号）
4. **整行英文占比 >80% 的"逐字示例"行**（论文里常见）
5. 引号内的报错/代码片段

再给漏译判定**加绝对数量下限**：

```python
# 只看比例会被短段落骗到。一段话里只残留 1 个虚词
# （比如专名 Cloudflare Access 里的 from）不是漏译。
if len(suspicious) >= 4 and ratio_s > 0.05:
```

**效果**：30 → **0 条红**。

### 最后一轮：发现"166% 覆盖率"是我算错了

修完上面这些，QC 全绿，但报告里出现：

```
词级覆盖率: 166.0%（阈值 ≥ 80%）
```

**166% 是不可能的。** 查代码发现：我在算覆盖率时用了「中文字数 ÷ 英文字词数」，而 `count_words()` 里**每个汉字算一个"词"**。所以 89,729 英文词对应的 148,938 中文字，比值自然是 1.66。

**这不是超额完成，是度量单位不一致。**

**改法**：覆盖率改为**统一用原文侧口径**——「已译 Segment 的原文词数 ÷ 全部可译词数」；中英长度比单独作为一个指标报告，并说明中文天然是英文的 1.5～2 倍。

**教训**：**指标漂亮到不可信时，先怀疑指标。** 顺带把长度比阈值从拍脑袋的 1.9 调整为有依据的 0.75/2.4，并给短段落（<25 词）加了豁免——`## MCP 架构——一览` 这种标题，比例低不代表漏译。

**最终结果**：覆盖率 **100%**（诚实口径），术语硬错误 **0**，红色问题 **0**。

## Day 3 · 文档与复盘

### 5.1 站点是脚本生成的，不是手写的

`04_build.py` 从同一份 `translations.jsonl` 同时产出 Markdown 资料包和静态文档站。

**理由**：手写 33 个 HTML 页面不可能保持一致；而"文档站"和"Markdown 资料包"如果各有一套逻辑，一定会不同步。**单一数据源自动生成两个产物**。

站点做了三件对读者有用的事：中英对照可切换、页内搜索、**每篇明明白白标出覆盖率**（不把未译的部分藏起来）。

### 5.2 README 里的"已知缺口"是主动写的

有 3 篇资料没译（Notion 页需JS 渲染、扫描版 PDF 需 OCR、付费墙拦截）。

**我的判断**：这必须写在 README 最显眼的地方。**自动化管线的诚实度，是它能不能被别人信任的前提。** 藏起来的缺口会在别人复用时变成"这个项目说谎"。

## Prompt 演进记录

### v1 · 基础翻译 prompt（弃用）

> 把下面的英文翻译成中文，保持 Markdown 格式。

**问题**：没约束术语、没约束专有名词、没定义"不增不减"。产出无法验收。

### v2 · 结构化约束（主力版本）

关键段落：

```
## 硬性要求（违反即视为不合格）
1. 术语一致：严格使用下方术语表译法。同一概念全文只能有一种译法。
2. 保留专有名词：产品名、公司名、协议名、代码标识符一律保留英文原样。
3. 代码不译：代码块、行内代码、命令行输出、文件路径原样保留。
4. Markdown 格式保持：块数与层级不变。
5. 不增不减：段落数必须与输入一致。
6. 地道中文：避免翻译腔。原文 "the model is doing X" → "这意味着模型在 X"，
   不要写成"模型正在被用来进行 X"。
7. 保留语气：教学口吻译成教学口吻，幽默感保留。

## 术语表（英文 → 规范中文译法，只注入本段命中的）
- Context Rot → 上下文腐化（勿用：上下文腐烂、上下文失效）
- ...
```

**为什么这版有效**：
- 第 6 条给了**正反例**，把抽象要求变成可模仿的样本
- 第 5 条把"忠实"变成**可数对的结构指标**
- 术语表**按段注入**而非全量，保持注意力集中

### v3 · 定向修订（针对 agent 实际踩的坑）

在v2 基础上针对观察到的真实问题追加：

```
- PDF 抽取文本可能含字符间插空格、页眉页脚、内容重复。
  按语义处理成通顺中文，不要保留排版噪声。
- 原文若把图表标题粘在下一段开头（无换行），译文保持同样的粘连，不要自行加空行。
- 原文用单换行而非双换行分段时，译文保持单换行，不要升为段落。
```

**为什么加**：这三条来自 11 个 agent 独立报告的真实高频问题。**通用 prompt 解决不了的，补充具体规则。**

## 如果重来，我会怎么做

1. **先写质检，再写翻译。** 我是翻译完才发现质检规则本身有 4 轮误报。如果先写 QC 并用真实语料验证规则，再开始翻译，能省掉大量返工。
2. **抽取阶段就该处理 PDF 噪声。** 11 个 agent 都在处理同一类排版噪声，说明这是抽取的职责，不该外包给翻译环节。
3. **术语表要边译边长。** 我是译完后才补的 33 条歧义标记。译到哪篇遇到哪个术语有歧义，当场记进 `ambiguous`，更自然。
4. **分歧样本单独存。** QC 报出的每一条误报都值得留档，它们是"自动化判断边界"的证据。下一批复用时，可以直接拿它们当回归测试集。
