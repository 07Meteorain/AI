## 软件团队的代码评审要点

2015 年 2 月 9 日

代码评审是任何协作式软件
项目中不可或缺的一部分。大型软件系统通常由不止一个人
编写，因此一个高效运转的软件团队需要一套稳健的
流程，让成员以及代码库本身都朝着正确的方向前进。

代码评审是一件强大的工具，它：

- 帮助团队成员随着系统
的变化调整自己的心智模型

- 确保改动正确地解决了问题

- 为设计的优点和缺点打开讨论

- 在 bug 进入生产之前抓住它们

- 让代码风格和组织结构保持一致

把这些收益看成一组层次递进的需求会很有帮助。

## 让团队成员保持在同一条船上

代码评审最关键的作用，是让团队里的每一位成员
都朝着正确的方向前进。你无法安全地改动一个
你不理解的系统，所以代码评审让团队在心智上
保持同步。当 Bob 为记账子系统提交一个拉取请求时，
Amy 会在评审 Bob 代码的过程中持续更新自己对该
系统的理解。Amy 有机会对自己不理解的部分提问，
而 Bob 既能借此讲清自己的设计决策，也能把
自己的工作讲给别人听。一个月后，当 Amy
要改动记账子系统时，她对这个系统的理解
已经是最新的，可以直接动手。她花在读代码、
在脑海里拼凑系统上的时间更少，花在思考
更高层抽象与设计上的时间更多了。所有人都赢，
因为所有人都保持在同一条船上。

## 执行一个好的拉取请求

在你为改动系统写第一行代码之前，先问问自己以下
问题：

- “这是应该做的那件事吗？” 客户、内部团队成员和其他
 各方的需求永远在互相竞争。在一头扎进去之前，这
 是一个让你在脑子里理清优先级的好办法。迭代 /
 冲刺计划会议之类的其他流程也有助于让这件事
 保持在正轨上。

- “团队是否已经一致认为这个改动是对的？” 如果
 没有，那最好先通过邮件或者当面开启一场设计讨论。
 人们在你动手之前就已经对设计达成一致，你的改动
 才更有可能被接受。

- “我怎样把这次改动拆成容易评审和理解的小块？”
 小改动更容易思考和理解。好的讨论来自团队能够
 快速理解你的改动。如果你的改动非常庞大，
 队友的眼睛会看得发直，你可能只会从他们那里
 得到几条吹毛求疵的风格意见。

- “我打算怎样测试这个改动，以消灭 bug 并确保
 正确性？” 你也许有 QA 部门，但把高质量、能用的软件
 交付出去，仍然是作为开发者的你的职责。容易
 测试的软件通常耦合更低、拆成了更小的
 块，也更容易推理。你需要为所有改动
 准备一份测试计划。

我发现提前回答这些问题从长远来看替我省去了
大量麻烦。你最不希望发生的，就是花几天时间把一个
改动写出来，最后却因为根本性的设计缺陷或团队分歧
而被否掉。或者你的改动因为没人能验证其正确性而
被卡住。再说一次，目标是在改动系统的同时让其他
团队成员了解你的改动。问问自己打算怎样把工作
拆成一口口能吃下的小块并对这些小块做测试，在很多
方面都有好处：

- 它降低风险

- 它让改动更容易推理

- 它推动你做出更好的设计

与其用砍刀划出一道长伤口，你更愿意用手术刀
做出许多小而精准的切口。多数增量式的场景我都更偏好
手术刀式的开发，而把砍刀留到该删除大块死代码的时候。

## 发送拉取请求

好，团队已经认可你的改动，你的目标设计也已经
实现了。那么，怎样才是真正把你的拉取请求发出去的
最有效方式？你在改动上花了很大力气，你希望团队里
的其他成员关注你的拉取请求，并给你快速反馈。你该
怎么做？

还记得我之前说过，代码评审最重要的部分，是让
团队的整体心智模型保持良好一致吗？你的其他队友
很可能在忙完全不同的事，也许在系统里完全不同的
一部分。他们的大脑处在完全不同的上下文中，所以
你必须给他们做好评审所需的有益指引，来弥补这一点。
这意味着要条理清晰地写清你做了哪些改动、为什么
这么做，以及其他光读代码得不到的相关信息。不要
让你的队友做超出必要范围的脑力活。

我们来看几个拉取请求描述的好例子和坏例子：

糟糕的例子：

```
```
Title: Fix uninitialized memory bug
Description: 

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.
```
```
如果你是这个拉取请求的开发者，先停下来，设身处地
站在你的代码评审者的角度想一秒。这个标题含糊其辞，
提出的问题比给出的答案还多：内存 bug 在哪里？这次
改动有多关键？之前你和 Bob 谈的那个 bug 是什么？
编译器给你带来了什么麻烦？描述既没有提供任何有助于
理解问题的背景，也没有提供任何关于你做了哪些改动的
有用说明。如果这个拉取请求很长，评审者就得一头
扎进代码里做一番脑力翻腾，试图先获得足够的上下文，
然后才轮到去思考这次改动如何融入系统连贯的整体设计。

这是一个改进后的例子，能更清楚地说明这次变更：

```
```
Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.
```
```
这个拉取请求描述有几处改进：标题足够有描述性，能给
评审者一些简短背景，并诱使他们点开邮件了解更多。
评审者知道这是进程崩溃（这通常是很糟糕的事），
还有一个 bug 报告编号，如果他们想更深入了解这个
问题，可以去读 bug 报告的更多细节。新的描述还概述了
问题发生在哪里，并提供了关于这个修复有多关键的背景。
其中有一个摘要列出了拉取请求中结构层面的高层改动，
这会让评审者在还没看代码之前就在脑海里形成改动的
图景。代码评审者不该在看到内容时感到意外。这个例子
还列出了做过的测试，这会让评审者相信这些改动经过了
充分思考、充分测试，可以合并。把你的评审者设置成
“注定成功”——让他们点“合并”这件事简单到不用动脑子。

## 评审者：给出建设性反馈

评审流程中接下来要考虑的，是给同伴
建设性反馈。如果目标是清晰和一致，那么给出
高质量的建设性反馈能帮助所有人更好地理解系统，
并推动代码变得更好。

避免说这样的话：

- “这个设计是坏的。” 它坏在哪里？怎么才能改好？
 这类说法会打击信心、伤害自尊。

- “我不喜欢这个改动。” 你为什么不喜欢？你希望
 它变成什么样？不喜欢某样东西没关系，但你应该
 把自己的想法讲清楚，并给出代码可以如何改进的
 有益线索。

- “你能把这个重写得更清楚一点吗？” 我现在这版
 有什么问题？该怎么重写？哪里不清楚？这类
 评论本身就不清楚，也没给出一条简单的
 前进路径。

改成说这样的话：

- “这段代码怎么处理负整数？” 这条反馈很具体，
 会促使开发者自己去推演结果。作为评审者，你可能
 知道这段代码遇到负整数会崩溃，但让开发者
 自己领悟到更好。这类问题也可能意味着测试
 覆盖不足，或者需要进一步明确范围。

- “这一部分让我看不明白，我不理解为什么类 A 要和类 B
 通信” 如果开发者没有提供有帮助的描述、
 代码结构也不够清晰，这类评论能推动设计
 变得更清楚、代码变得更干净。

- “看起来你在这里破坏了一个接口边界。这会怎么
 影响用户？” 你指出了一个注意到的问题，同时
 善意地相信他是有意为之。现在他可以权衡破坏
 接口边界那些看不见的后果，然后要么为
 自己的决定给出理由，要么选择改掉。

总的来说，把反馈包装成问题是推动清晰和
正确性的好办法，同时也能帮助开发者日后
改进自己的设计。优秀的创作型写作小组通常
就是这样互相给反馈的。在写作的场合下，说“我不喜欢
这个人物”是有害的，而同样的意见换个说法可以更清楚：
“第一章里你的人物温暖又体贴，现在他
冷漠又冰冷。在我看来他不像个真人。”这样就有了
具体的反馈，可以进一步追问、把问题弄清楚。

程序员喜欢解决问题、指出问题，所以从本性上
说，他们喜欢发现并指出缺陷。很容易把代码
评审当成一种证明自己有多聪明的办法——在
同伴的代码里找出问题。别这么做。代码评审是
让一次改动多几双眼睛、把关键问题揪出来的方式，
但你的目标应该是以一种能鼓励团队成员在修复
手头问题的同时提升自己技能的方式去做评审。

## 风格问题

大括号位置、变量/函数命名、缩进和空格
问题应该处理，但它们不是好代码评审的核心目的
（注意我把它们放在了代码评审金字塔的最
上面）。如果你发现团队把 90% 的时间
花在挑缩进和变量名的毛病上，那你多半是在
把所有人的时间浪费在一件基本可以自动化的事情上。
写一份风格指南，在代码签入时就强制处理缩进和
空格问题，把时间花在更高价值的问题上。我并不想
贬低一致风格的重要性。恰恰相反，拥有
一致地道的风格，是让你的代码库易于阅读和理解
最省力的方式之一。不过，如果你把全部代码评审都
花在这些简单任务上，那要问问自己：是不是
在回避那些更难也更重要的——让团队在心智上保持一致、
思考更高层次设计的工作。
