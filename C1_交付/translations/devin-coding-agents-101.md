# 编码智能体 101：真正把事情做成的艺术

现在是 2025 年。编码智能体并不是魔法，但它已经是我们手上最接近魔法的东西了。我们注意到，有些工程师——尤其是 senior 到 staff 这一层级的——用它们取得成功的速度明显快于其他人。这里我们分享一些最有价值的经验，它们来自我们的客户和我们自己的实践。

关于本指南：

## 与产品无关

我们讨论的那些建议，能帮助你在任何编码智能体上都取得成功。

## 战术层面

我们给出自己最喜欢的可落地建议。

## 技术层面

虽然编码智能体对很多人来说都很有价值，但本指南是写给工程师看的。

开发者工具这些年来一直在快速演进。十年前，它们是自动补全和 IntelliSense，能建议方法名、执行程序化重构。四年前，它们是副驾驶和 Tab 补全，能替你写出接下来几行代码。两年前，它们是生成式聊天机器人，能辅助你的开发、为你生成整个文件。今天，它们是自主智能体，能从最初的一段描述一路做到最终的拉取请求（PR），几乎不需要人工介入。过去两年，我们一直在通过构建 Devin 来实现这一愿景。如今人们对自主智能体的兴趣达到了新高峰，尤其是近期同类产品接连发布之后。[1] 除了 Devin，近期的同类发布还有 OpenAI 的 Codex 和 Google 的 Jules。Cursor 和 Claude Code 这类本地智能体也可以在并行工作区中运行，达到类似的效果。这些智能体可以以多种形态出现，包括网页应用、移动应用，以及嵌入 Slack、GitHub、Linear、Jira 等常用工具的集成。

一个人类搭配 AI 助手能取得的成果，超过任何单独的 AI；但自主智能体端到端完成任务的能力，带来了一个全新的多任务层次——它让每位工程师都变成一名工程经理。

适应与这些新 AI 同事高效协作需要一些时间。有意思的是，我们观察到 senior 到 staff 层级的工程师往往采用这些工具、并熟练掌握它们的速度最快。归根结底，这些工具会在各个层级的工程师中都变得常见。基于我们的经验和客户反馈，我们希望分享关键的洞察与经验教训，帮助每个人把这些工具成功融入自己的工作流。

## 提示词基础

这些基本准则会帮助你在 2025 年更有效地与编码智能体交互。如果别的什么都不记，至少要记住这些。

### 说明你希望怎么做，而不只是做什么

把智能体想象成一位初级编码搭档，它的决策未必可靠。简单的任务可以直接描述，但更复杂的任务，从一开始就要清晰地勾勒出你偏好的方案。提前把整体架构和逻辑交给智能体，不仅能提高它成功的概率，还能减少你评审代码的时间——因为你对预期做法已经熟悉。

#### 示例：

不要只说「添加单元测试」，而要具体说明要测试的功能，指出重要的边界情况，并说清楚有没有需要 mock 的部分。

### 告诉智能体从哪里入手

想一想如果这件事由你自己来做，你会从哪里开始。即使你不知道具体的文件名或函数名，也要提到相关的仓库、文档和涉及的关键组件。明确指出这些信息能最大限度减少无效努力和困惑。

#### 示例：

「请为我们的代码加上对 Google 模型的支持。你应该参考最新的文档[这里](link)，并在 model groups 目录下创建一个新的实现文件」

### 学会防御性地写提示词

想象一下你把同一段提示词交给一位新来的实习生。困惑或错误最可能出现在哪里？提前想到这些点，主动把指令说清楚，避免歧义。

#### 示例：

「请修复我们搜索模块的 C++ 绑定，让它通过新的单元测试。注意，你很可能每次改完代码、测试之前都需要重新编译绑定。」

### 让它能访问 CI、测试、类型和静态检查

智能体的魔力很大程度上来自它们能自己修正错误、对着报错信息反复迭代。通过类型检查器、lint（静态检查）和单元测试这类工具提供更强的反馈回路，能大幅提升它们的表现。优先考虑带类型的 Python 而非纯 Python，TypeScript 而非 JavaScript。教会你的智能体如何运行常见的检查和测试，确保它拥有所需的全部包和访问权限。如果智能体能与浏览器交互，就清楚说明如何运行你的前端开发环境。

#### 示例：

我们团队从以无类型 Python SDK 为主，全面转为只使用带类型的 SDK（理想情况下，这也正是适合交给编码智能体的任务）。

### 用好你的专业能力

当你对自己的代码库足够熟悉时，上面这一切都会变得更容易。即便是简单的任务，也能从你验证逻辑和结果的能力中获益。人工把关依然不可少——最终，代码是否正确，责任在你身上。即使这些工具越来越成熟，主导和验证仍将是人类工程师的关键职责。

## 把智能体用进你的工作流

等你掌握了与智能体对话的基本要领，就该把这些 AI 帮手带进日常工作了。下面是一些让智能体融入日常工作的实用做法：

### 立刻接下新任务

想象一位同事给你发消息：「嘿，我们能快速做个 X 吗？」或者「我们得改一下 Y。」别让它打断你的心流，直接给自主智能体发一段简短的提示词，让它去调研或完成这个改动。这样你就能专注在主要任务上。想到了有意思的副业项目？需要快速做个原型、抓取数据或复现某项研究？把它派给你的智能体，稍后再回来收结果。

#### 示例：

很多团队在 Slack 上讨论缺陷修复或小功能更新时，直接 @Devin 就完事了。

### 随时随地写代码

想象你在通勤或出差路上，突然冒出一个紧急缺陷，或者你意识到自己可能在代码里留下了一处错误。别担心！自主智能体通常支持移动端访问，让你立刻处理这些问题。无论是通过 Slack 的移动应用还是专门的移动应用，很多智能体都能让你在路途中解决问题，哪怕 wifi 信号很不稳定。

#### 示例：

有了这种可选能力，我们自己团队在开车和坐飞机时的效率高了很多。

### 把杂活交出去

卡在给老提交做二分定位，或为新功能更新文档？把这些重复性的任务交给智能体。你能省下宝贵时间，专注在更有创造性、影响更大的工作上。

#### 示例：

在我们团队，工程师提交改动后，再让智能体更新所有相关文档和面向用户的文案，是很常见的做法。

### 别再纠结到无法行动

拿不准一次重构到底能不能让代码更简单？在两种架构方案之间选不出来？让智能体把两个方案都实现一遍。有具体的例子可比，决策就变得直截了当，而且扔掉其中一个方案也不会伤害任何人的感情。

#### 示例：

在给文本框选 Lexical 还是 Slate 时，我们让智能体各实现了一版。最终 Slate 的交付效果更好，胜出了。

### 搭好预览部署

把你的 CI/CD 流水线配置成每个新拉取请求（PR）都自动创建一次预览部署，这样你立刻就能拿到一个可访问的 URL。评审 AI 智能体完成的前端任务时，这尤其方便。

#### 示例：

Vercel 是一个部署平台，让预览部署变得非常简单。

## 委派更大的任务单

当你的拉取请求（PR）规模和复杂度超过几个文件时，一口气处理完就变得很有挑战了。但把中大型任务（通常是 1 到 6 小时的工作量）委派出去，才是自主智能体回报最高的地方。你省下的不只是几分钟，而是几个小时的效率。小任务可能轻轻松松就完成了，但把智能体的能力拉伸到处理更大任务，带来的回报也最大。

### 让初稿自动化

对于分量较重的任务，用自主智能体先做出拉取请求（PR）的初稿，能快速启动进展、大幅削减你的工作量。成败取决于你是否从一开始就清楚表达了想要的方案。把自己想象成一位指导初级开发者的架构师。清晰、详尽的指令能避免你花不必要的时间，去纠正智能体代码里的根本性误解。

🛑 请记住，大任务还不能完全放手（目前还不行）。对于更有难度的任务，要预期到多个反馈循环，也要预留一些手工打磨的时间。现实的目标是节省约 80% 的时间，而不是彻底自动化；你的专业判断在验证和最终质量把关上依然关键。

### 共同打磨 PRD

对于复杂或定义模糊的任务，与自主智能体协作产出一份详细计划往往非常有效。一开始你并不清楚每个细节或需求，这完全没关系。先用提示词让智能体去探索一些发现问题，比如「我们的认证系统是怎么工作的？」或者「哪些服务可能会受影响？」你也可以让智能体指出具体相关的代码位置，好在早期就确认。

Devin 和 Claude Code 等智能体提供专门的规划模式，重点是阅读和探索现有代码，而不是立刻动手修改。如果你希望在委派任务前做更充分的准备，deepwiki.com 和 Devin Search 这类专业的代码库检索工具能快速给出对你代码库的洞察，让流程更顺。

### 设置检查点

对于多部分任务，尤其是涉及多个代码库的任务，要沿途设立清晰的检查点：

规划 → 实现一个 chunk → 测试 → 修复 → 检查点评审 → 下一个 chunk

明确要求它在每个重要阶段后暂停，尤其是跨多个层面（例如数据库、后端、前端）构建的复杂功能。用这些检查点确保实现符合你的预期、澄清疑点（例如「解释一下认证流程并确认它的安全性」），并及早纠偏，避免问题连锁放大。

#### 示例：

「我希望你实现这个功能，它会横跨我们的数据库、后端和多个前端界面。请先规划出需要的数据库 schema 变更，做完告诉我，我好去应用迁移。」 -> 「现在请实现后端改动，并加上测试确保 XYZ 能正常工作。做完告诉我」 -> 「现在在 web 和移动端界面上都实现改动，调用新的后端接口」

### 教它验证自己的工作

给反馈时，不要只是指出问题（「这个函数不工作」）。要把你的测试流程讲清楚，让智能体在今后的任务中能独立验证。对于你会反复使用的测试模式，把它固化进智能体的永久知识库（参见「把内容加入智能体的知识库」）。

#### 示例：

在 Devin 中，我们会主动提示用户把关键测试流程保存到智能体的长期记忆里，让后续交互更顺畅。

### 在 AI 热点区域加大测试覆盖

目前，智能体还不具备把各种场景都彻底地交互式测试一遍的能力。加大那些被 AI 大量改动区域的测试覆盖率，才能对智能体的输出更有信心。扎实的测试意味着看起来正确的代码可以放心合并。

#### 示例：

我们团队先加强了代码库中某个关键部分的单元测试，然后才把「把实现从 Python 翻译成 C」这件事交给 AI。

## 自动化工作流

智能体响应外部事件的速度远快于人类，而且比人类同事更愿意去做那些枯燥重复的工作。

### 为最重复的工作创建快捷方式

工程团队经常遇到重复性的例行任务。这些正是用智能体自动化的理想对象。常见例子包括：

- 移除 feature flag

- 升级依赖

- 为新功能的 PR 修复并补充测试

要高效搭起这套东西，通常由一位资深工程师写一个稳健、可复用的提示词模板。[2] 在 Devin 中，这被称为 playbooks，可以针对这类场景反复运行。

#### 示例：

我们有一位客户，只要开发了新功能，就会自动触发三个专门负责编写单元测试的智能体。

### 智能代码评审与强制执行

虽然已经有 Greptile、CodeRabbit 这类专门做快速代码评审的工具 [3]，但自主智能体也是一个有意思的选择，能给出更准确的判断，尤其是当它们已经索引过你仓库的功能之后。

#### 示例：

在 Cognition，我们喜欢维护一份「工程师最常犯的错误」清单，并把它提交进代码库。这样一来，我们不用写传统的 lint 规则去捕捉它们（这往往做不到），而是让一个智能体在每个新 PR 上跑一遍，检查这些错误。

### 接入故障事件与告警

你也可以设置自主智能体在特定事件发生时自动触发。例如，Devin 提供了易用的 API，其他智能体则可以通过 CLI 命令接入自定义工作流。这类配置尤其适合与 MCP 搭配，用来摄取第三方错误日志。

⚠️在对生产服务的问题做分诊时，AI 的调试能力并不出色。与其让 AI 从头到尾修 Bug，通常更务实的做法是让 AI 只把最可疑的错误、变更等标出来。

（高级）

## 定制化与提升性能

### 环境搭建

没有什么比不完整或不匹配的环境更能拖慢智能体。为了让一切顺畅运行，要把智能体的环境配置得和团队完全一致。这包括语言版本、包依赖和自动化检查。例如，pre-commit 应当安装在智能体的环境里，环境配置（密钥、语言版本、虚拟环境、浏览器登录态）应当用 .envrc 之类的工具或对 .bashrc 的自定义配置自动加载。

#### 示例：

我们为智能体的浏览器配好了预认证的登录态，免去手动认证的麻烦，测试也容易多了。

### 构建自定义 CLI 工具和 MCP

MCP 已经相当普及，把智能体接到外部工具上也很容易上手，值得快速试一遍 [4]。在 Devin 中，MCP 仍处于 beta 阶段，我们还在摸索最佳的支持方式，欢迎联系我们申请权限！但很多人忽略了给智能体准备一些简单的 CLI 脚本。举个最简单的例子，你可以给智能体一个脚本，让它根据工单 ID 拉取某个 Linear 工单的信息。你也可以给它一个工具，让它可靠地完成工作流中经常重复的环节，比如一个重启本地开发环境的脚本。

#### 示例：

我们有一位客户，做了一个 CLI 工具，只挑出测试套件中第一个失败的用例，效果很好。这个 CLI 会提示智能体只聚焦那一个用例，并附上详细的错误信息；有了它，智能体在长任务上的成功率更高、完成速度也更快。

### 把内容加入智能体的知识库

如果你的智能体总是犯某些常见错误，那就是把你的反馈固化进它知识库的好时机。在 Devin 中有专门的知识管理系统。很多产品提供 .rules 文件、.md 文件，让智能体永久吸收。别只告诉它你用的是哪个框架，还要告诉它项目的整体架构。告诉它不同类型的任务通常该怎么做测试、重要命令怎么跑、你推荐使用哪些工具。

#### 示例：

我们给智能体灌入了「新增一条服务路由时该照做的具体流程」这套知识，包括它在前端和后端每一处需要添加模板代码的位置。结果现在这类任务很容易就委派给 AI 了。

## 自主智能体的局限

### 调试能力有限

缺陷报告往往看着简单。实际上很多 bug 不只需要访问数据库和日志，还需要超过今天多数 AI 智能体水平的调试能力。如果要用 AI 辅助调试，我们建议让它列出一份可能根因的清单，而不是试图自己把所有问题都调试并修好。然后由人根据自身经验判断哪个才是真正的根因。但一旦原因明确，智能体在实现修复上仍然相当能帮上忙。

### 细粒度视觉推理能力较弱

总体来说，今天的模型在「达到设计稿或 Figma 原型截图所需的细节水平」这件事上，视觉推理能力并不出色。对于能用代码描述的视觉内容（例如把 Figma 的代码喂给它），它们才最可靠。如果你希望它匹配你的视觉风格，就该用一套带可复用组件的成熟设计系统。

### 知识截止

每次你想用某个新库时，都应该明确把最新的文档指给它。否则，由于预训练基座模型存在知识截止，多数智能体还是会沿用这些库的旧写法。如果你把文档指给它，一个好的智能体能弥补这一点，但你必须时刻意识到这件事（记住，智能体甚至都不知道这些库出了新版本）。

实务考量

## 管理时间、减少损失

不是每次使用智能体都会成功。2025 年，这些智能体的结果确实存在相当大的差异。这项工作的一部分，就是学会怎样使用智能体，让撞上成功结果的概率最大，同时把浪费的时间和 token 降到最低。

### 要愿意更早止损

刚开始用智能体的人常犯的一个错误是：即便智能体的活儿已经跑偏了，他们仍执着于让这一次交互成功。如果你发现自己在想「它不听我的指令」或者「这东西在原地打转」，那就应该果断结束这段对话，或者亲自接手。继续发更多消息，往往说明你的任务本身复杂程度超出了智能体的能力，而不是某个改得掉的小失误。

### 让你的尝试多元化

如果你是刚开始和智能体打交道，我们建议一开始就把赌注摊开：多试几种不同的提示词和思路。哪些任务你发现智能体天然做得好，就在这些上加大投入；它们做不好的，及早止损。不必要求每次都非让智能体成功不可。

### 没有进展时就重新开始

在人身上，「重头再来」很少是正确的答案；在智能体身上，这个答案要正确得多。如果你交给智能体一个任务，而它怎么都处理不了反馈、纠不了方向，那么换一个全新智能体、把全部指令一次给全，往往能快得多地拿到结果。智能体修复一个已经乱掉的既有环境的能力，远不如它从零吐出新代码的能力。

## 安全与权限

### 为你的智能体创建账号

一个用完即弃的邮箱有助于安全地测试网站。如果智能体需要访问云资源，为它创建自定义 IAM 角色。

### 给它一个开发／预发布环境

理想情况下，智能体应当使用与你团队工程师相同的测试配置。我们建议完全不要给它生产服务的访问权限。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读的 API 密钥

在可能的情况下，只给它只读权限。我们发现，任何与外部服务交互的脚本，仍由人类手动跑一遍会很有帮助。

## 大变革在前

我们坚信软件工程师不会消失。即便编码智能体越来越聪明、越来越强，深厚的技术专业能力和对你代码库的熟稔依然无可替代。对项目、系统和代码的真正主导权，比以往任何时候都更重要。今天在我们团队，工程师要在兼顾多个系统的同时，保持深入的理解和审慎的判断。当自动化放大你的影响力时，同时驾驭多个并行任务的能力不只是「变得可能」——它会变成必需。我们很愿意分享在为自身组织迎接这一转变的过程中收集到的洞察，让你和你的团队也能在不断演变的软件开发世界里蓬勃发展。
