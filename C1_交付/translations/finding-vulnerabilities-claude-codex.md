# 用 Claude Code 和 OpenAI Codex 发现现代 Web 应用中的漏洞

我们深入评测 AI 编码智能体在发现漏洞方面的能力，结果揭示了令人意外的长处、关键的短板，以及一个严重的稳定性问题。

##### 分享

TL;DR：我们评测了 AI 编码智能体在真实代码中发现漏洞的效果到底如何。

- 怎么做的：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行的大型开源 Python Web 应用中寻找漏洞。两者合计产出 400 多条安全发现，由我们的安全研究团队逐一评审。

- AI 编码智能体确实能找到真实漏洞：Claude Code 找到 46 个漏洞（真阳性率 TPR 14%，误报率 FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。其中约 20 个属于高危漏洞。

- AI 抓得住上下文，却卡在数据流上：Claude Code 最擅长发现不安全的直接对象引用（IDOR）问题，真阳性率 22%（13 个正确/59 个报告）；但在跨文件、跨函数做污点追踪时表现吃力，SQL 注入的 TPR 只有 5%（2/38），XSS 为 16%（12/74）。

OpenAI Codex 没能报告出任何正确的 IDOR，TPR 为 0%（0/5）；SQL 注入表现很差，0%（0/5）；XSS 也是 0%（0/28）；但出人意料的是，它报告出的路径遍历问题比 Claude Code 更多，TPR 达 47%（8/17）。

- 非确定性是实打实的难题：在完全相同的代码库上重复运行完全相同的提示词，结果往往差别巨大。在一个应用中，三次相同的运行分别给出了 3 条、6 条和 11 条不同的发现。

核心结论：

- 只需相对简单的安全类提示词，AI 编码智能体就已经能在真实应用中找到真实漏洞。

- 但是：视漏洞类别而定，结果可能相当嘈杂（误报率高），在 SQL 注入、XSS、SSRF 这类传统注入型漏洞上尤其明显。

- 详细的评测和基准测试，是判断一种漏洞发现方法究竟有多有效的关键（这一点一直如此，但在 LLM 这类非确定性工具出现后更甚），也是判断你的改进是否走在正确方向上的依据。

## 引言

在 Semgrep，我们每天都在做应用安全（AppSec）这件事。很长时间以来我们一直在把 AI 产品化（Assistant 背后的技术、用 promptfoo 测试我们的 AI 工作流、借助安全研究员做分类研判来评测自动分类的表现），同时不断研究传统确定性分析与现代 AI 的上下文能力如何最佳组合，而不是盲目追逐热点。

这项研究正是这一使命的延续。我们要公开做一次深入探索，回答一个所有人都在想的问题：LLM 在查找源代码漏洞这件事上究竟有多有效？

## 关于 AI 漏洞挖掘的开放研究问题

为了给调查指明方向，我们把“LLM 擅长找 bug 吗？”这个宽泛的问题拆成了更具体、可度量的子问题。

- 基于 LLM 的漏洞发现，其误报率和漏报率是多少？会因编程语言、框架、代码库规模或漏洞类别而不同吗？对代码写法风格有多敏感？

- 误报和漏报常见的成因是什么？

- 分析结果有多确定？每次运行都能得到相同结果吗？

针对注入类漏洞，我们特别想知道：

- LLM 在追踪“源头”（例如用户提供的值）与“汇聚点”（例如消费原始 SQL 查询的方法）之间的用户输入时，有多有效？

- 它能跨函数、跨文件追踪数据吗？

- 它能对净化函数和其他安全控制机制做推理吗？

- 它能对来自第三方开源依赖的函数做推理吗？

## 常规 SAST 基准测试的问题：缺乏真实性

在深入我们的发现之前，先聊聊我们如何衡量 AI 的表现。当前大量研究和论断依赖基准测试，这些基准测试固然有价值，但并没有完整呈现真实世界代码的复杂性。

- 已知漏洞应用：这类基准测试只使用已知存在漏洞的开源应用；其中很多都能在 vulnerable-apps 上找到，多亏了 Kinnaird McQuade。如果你读这篇博客，可能认得出其中一些名字：WebGoat、JuiceShop、OWASP Benchmark 等。但问题在于：现在的 LLM 很可能已经把这些仓库的代码以及互联网上大量公开的分析文章都吸收进去了，这让它们具备了先验知识，也会让结果失真。
它们的代码往往不够真实，充斥着大量注释、标注和变量名，直接暗示或明示漏洞在代码中的位置以及如何利用。有时工具的结果甚至就明明白白写在仓库里。

- XBOW 为自动化渗透测试工具提供了基准，但没有针对静态分析做适配：这些代码往往过于人为和简单，无法代表真实应用。ZeroPath 在清洗它们时做得不错，但只清洗了其中一小部分。而且这些测试用例个个都是微型应用，专为触发某个特定攻击场景而设计。如果只看 Python 基准，XBOW 有 45 个；45 个不同的微型应用，平均每个不到 98 行代码、3 个 Python 文件。这个规模太小了，无法体现横跨整个代码库或大量函数进行搜索和推理的复杂度。

- CVE 记忆偏差：由于 LLM 是在来自互联网的海量公开数据上训练的，其中就包括那些被发现并修复过 CVE 的代码库本身。这就带来了根本性的数据污染问题。AI 可能并不是通过新颖分析发现了漏洞，而只是认出了训练时记住的某个模式。

近来学界设计了一些基准测试，如 CyberGym、Eyeballvul 或 SecVulEval。这些基准有明显改进，也更贴近真实案例，但它们缺少对现代 Web 应用的聚焦，或把漏洞从更大的应用上下文中剥离了出来。

- EyeballVul：Timothée Chauvin 推出的较新基准，从开源项目中提取经过人工审定的真实漏洞，并把它们呈现为最小、可复现的测试用例。虽然基于真实代码，但它仍然把漏洞从更大的应用上下文中剥离出来，让搜索问题变得更容易。

- SecVulEval 与 CyberGym：这两套基准用于评测 C 或 C++ 中的漏洞。在各自领域内它们很有价值，但聚焦 C 和 C++ 意味着这些数据并不适用于现代云原生开发中占主导地位的 Python/JavaScript 等面向 Web 的语言。

这些方法各有用处，该用的时候都该用，但它们未必反映现代软件开发的真实状况。真实世界的应用不是干净的孤立函数，而是由依赖、框架和业务逻辑交织成的复杂网络。

我们的做法不同。我们在 11 个大型、基于 Python、仍在积极维护的开源项目上做测试，使用的是常见 Web 框架（Django、Flask、FastAPI）。我们的方法与上述方法是互补的，我们认为它的独特之处在于：a) 目标是代表真实世界中 AI 驱动的漏洞发现（而非小型、孤立的合成样例）；b) 不受模型训练数据污染；c) 代表大多数开发者和公司实际在构建的应用类型——使用现代语言和框架的 Web 应用。

### 我们发现了什么

- Claude Code 和 Codex 今天都还挺好用：它们能找到真实的安全漏洞，但噪音非常大。整体噪音仍然很高，不过它们确实在这些流行的开源 Python Web 应用中找到了真实的安全漏洞。总体上，Claude Code 找到 46 个漏洞（TPR 14%，FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。

- 很多 IDOR 缺陷乍看之下是对的，Claude Code 还给出了可信的修复建议：LLM 不只能发现这些缺陷，还能给出可信的修复方案，比如参照代码中已有的模式添加新的权限校验。IDOR 问题往往很难分类研判，我们必须实测其中大部分才能确定，这把真阳性率拉低了很多。

- Claude Code 算得上一款不错的安全护栏工具吗？很多发现虽然在技术上是误报，但仍然是不错的“护栏”建议，或者看起来就是护栏建议。例如，模型经常建议把一条本来已经安全的 SQL 查询参数化。这虽然不是漏洞，但确实强化了代码。我们仍然把这些算作误报，只是严重程度不如其他误报。

不过，这类代码加固建议并不总是可信的。我们发现若干实例——尤其是在客户端 JavaScript 代码中——AI 试图修复它所认为的 DOM 操作问题，结果反而把代码弄坏了（在我们观察到的案例中是对 HTML 做了双重转义），而那里本来根本不存在安全问题。

- XSS 与 SQL 注入——很难把各个组件拼起来：模型很难把数据从服务端框架追踪到客户端组件（XSS 的常见模式），也很难穿过复杂的应用分层。它常常被静态定义的数据搞糊涂，或者没能识别出服务端的净化处理。

- 重复提示词有助于拿到更多结果：LLM 的概率性本质意味着，把同一个问题换个略微不同的方式问，可能得到新的发现，这凸显了分析结果的不一致性。在同一代码库上多次重复同一条提示词，我们得到的答案各不相同，但最终又会绕回到同一批发现上。

- OpenAI Codex 有时无法输出有效的 SARIF。我们预期的 66 份报告中有 9 份不是合法 SARIF。我们仍然采信了这些文件里报告的全部发现，但它们既不是合法 SARIF，也不是合法 JSON。在我们尝试的所有情况下，Claude Code 都没出现这个问题。

## 同样的代码、同样的 AI，每次都是不同的缺陷：AI 编码智能体的非确定性问题

为了探究非确定性在实践中的表现，我们从这些应用中选了三个，针对同一个安全问题——IDOR——多次重复运行同一条提示词。结果呈现出一个规律：每次运行，AI 的发现都不一样。

在漏洞检测的语境下，这是个大问题。首先，作为安全工程师，我们理想情况下希望得到更强的保证——确认我们的代码确实被按重要漏洞类别扫描过，而不是“希望这次模型搜得够仔细”。

其次，时好时坏的检测会给你的安全工具或漏洞管理系统带来不一致和噪音。例如，如果你用的是某个 SAST 平台、ASPM 或内部自建系统，这些系统往往假定某个先前检出的漏洞不再出现就意味着已被修复。但在 LLM 驱动的检测中未必如此：单次扫描可能漏掉它，于是后续扫描再次发现同一问题时就会生成一条“新”发现，导致重复的 JIRA 工单和开发者的抓狂。

以下是我们观察到的一些具体例子：

- PY-APP-007：第一次运行时，AI 识别出一个“缺少搜索授权”漏洞，而另外两次运行都没有。第二次运行标记出的问题则是那次运行独有的。第三次运行又找到了自己独特的一批漏洞。

- PY-APP-006：情况类似：第一次运行挖出用户 API 中的一个漏洞，后续几次运行则聚焦于代码库的其他部分，比如事件摘要和笔记模块。

- PY-APP-002：这里的多变性或许最为明显。检出的漏洞数从第一次运行的 3 个跳到第二次的 6 个，再跳到 11 个。每次运行给出的发现都不一样，只有部分重叠。

那么，背后是什么原因？我们认为关键因素是所谓的上下文腐化和压缩（compaction）。当一个 AI 智能体被要求分析整个代码库时，它要处理的信息量极其庞大：上下文腐化会使它无法准确地从自身上下文中检索信息。为了应对这一点，LLM 会采用某种有损压缩（有时也叫 compaction），这意味着函数名、路径等一些更精细的推理细节可能在摘要过程中丢失。

可以把它想象成在概括一部篇幅很长、情节复杂的小说。你会抓住主要情节点，但必然会漏掉一些细微之处和言外之意。同理，AI 可能跟丢某个特定的架构模式或微妙的数据流，于是在一次运行中漏掉某个漏洞，另一次运行却又抓到了。我们在 PY-APP-006 中看到了一个清晰的例子：AI 提出的某个修复方案不完整，因为它没有复用既有的用户授权基类——那是一段关键的上下文，在那次运行中似乎丢失了。

这种非确定性对我们看待 AI 原生 SAST 的方式有重要影响。一方面，AI 每次“思考”方式不同，意味着它可以探索更广泛的潜在攻击向量，很像一支视角多元的人类渗透测试团队。另一方面，它也引入了一层不确定性，可能导致混乱或异常行为。

- 覆盖不完整：单次运行可能给人虚假的安全感，因为它可能漏掉本可在后续运行中抓到的关键漏洞。

- 缺乏可重复性：无法复现结果，就很难验证 AI 的发现，也很难以一致、可重复的方式信任它的输出。

- 成本与时间增加：为得到更完整的图景而需要多次审计，这会显著增加所需的时间和计算资源。注意：对传统软件来说，代码写好之后你基本可以“免费”再跑一遍（不算硬件成本、电费等等）。但对 LLM 密集型的工具来说并非如此——在这里，读入一个代码库并对其做推理，每次扫描的 token 成本可能从几十美元到几百美元不等。今天的模型这部分成本可能随时间下降，但更新的模型也可能更贵。

## Claude Code 的新 /security-review 命令效果如何？

Anthropic 为 Claude Code 发布了一个新命令，叫 /security-review。它设计为在拉取请求上运行，用于检查改动的文件并提出问题，以识别具体的安全问题。你可以在这里找到那条提示词。

在整个代码库上运行这个命令时，我们发现它识别出的安全问题相当有限。很多时候，它找不到那些我们在提示 Claude Code 每次只搜某一类安全问题时才能找到的问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了这个命令，三个应用加起来只找到一个 XSS，与整体实验的结果相去甚远。

## 回答我们的问题

让我们结合上面的发现，重新审视最初的研究问题。

- 误报/漏报率是多少？对于跑在真实代码上的原生 AI，误报率非常高：最好情况是 Codex 在路径遍历上的 53%，或 Claude Code 在 IDOR 上的 78%；最坏情况是 Claude Code 在 SQL 注入上的 95%，以及 Codex 在 SQL 注入或 IDOR 上的 100%。表现还会随应用而差异巨大，从 PY-APP-002（Claude Code）IDOR 100%（10/10）为真实漏洞，到 PY-APP-007 的 0%（0/7）。在所有应用和所有上报的问题上，Claude Code 共找到 46 个漏洞（TPR 14%，FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。

由于我们用的是真实应用，本次实验无法准确测量漏报率。我们会在后续博客中介绍衡量漏报率的方法！

- 它为什么会失败？我们观察到的主要弱点，是对注入类问题中的代码执行缺乏深入的语义理解。模型难以处理跨过程的污点流和隐式流，而这些恰恰是传统 SAST 引擎通常要攻克的东西。部分限制也来自上下文压缩和上下文腐化。我们会继续更深入地探索这些限制，并寻找缓解办法。

- 脚手架和智能体式工作流有多重要？它们不只是重要，而是正在变得必不可少。AI 在安全评审中的未来，不是某个单一的巨型模型，而是一个由 AI 智能体组成的系统（其中就包括我们案例里用的编码智能体），它们能使用工具、对证据进行推理，并协作发现和验证漏洞。

虽然我们（目前）还没有数据能说明“使用能访问 Claude Code 的智能体”与“更典型的上下文工程（即搭建脚手架，把所有相关代码都提供给推理模型）”之间的差别，但我们观察到，系统在推进复杂流程、并就如何上报安全问题做出有依据的决策方面能力差异巨大。话虽如此，有个反例是 Sean Heelan 做了足够的上下文工程，让推理模型成功报出一个漏洞（8% 的概率）。我们真心建议你读读他的博客文章。

- 那这一切的成本呢？遗憾的是，我们没能统一地统计 Claude Code 与 Codex 之间的成本。Claude Code 的总成本是 114 美元，覆盖上述所有漏洞和所有应用（不含非确定性实验和运行 /security-review 命令的部分）。

## 结论

LLM 不是明天就能取代人类安全工程师的银弹；事实上，在端到端地查找高危注入类漏洞这件事上，它们的表现相当薄弱。不过，它们也是极其强大的工具。我们的研究显示：理解它们的长处（上下文推理）和短处（代码的深层语义），并用先进的静态分析引擎在周围构建精密的智能体式系统，我们就能打造出新一代安全工具，其能力远超以往任何方案。
