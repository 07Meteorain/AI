# 长上下文是如何失效的

### 管理好上下文，是智能体成功的关键

随着前沿模型的上下文窗口持续增长1，其中很多已经支持到 1 million token（词元），我看到许多兴奋的讨论：长上下文窗口将如何释放我们梦想中的智能体。毕竟，只要窗口足够大，你完全可以把可能需要的一切都塞进提示词里——工具、文档、指令等等——剩下的交给模型处理。

长上下文给 RAG（检索增强生成）的热情踩了刹车（反正都能塞进提示词里，不用费心找最匹配的文档了！），给了 MCP 炒作的空间（接上所有工具，模型就能干任何活！），也助长了对智能体的热情2。

但现实是，更长的上下文并不会带来更好的回答。上下文过载会让你的智能体和应用以出人意料的方式失败。上下文可能被污染、被干扰、变得混乱，或者自相矛盾。这对智能体尤其麻烦，因为它们要靠上下文来收集信息、综合结论、协调整行动。

下面我们逐一看看上下文会失控的几种方式，再回顾缓解乃至彻底避免上下文失效的方法。

## 上下文失效

- 上下文污染：幻觉混进了上下文

- 上下文干扰：上下文压过了训练所学

- 上下文混乱：多余的内容影响了回答

- 上下文冲突：上下文的不同部分彼此矛盾

### 上下文污染

上下文污染是指幻觉或其他错误混进了上下文，之后又被反复引用。

Deep Mind 团队在 Gemini 2.5 技术报告里点了上下文污染这件事，我们上周刚拆解过这份报告。玩 Pokémon 的时候，Gemini 智能体偶尔会在游戏过程中产生幻觉，污染自己的上下文：

> 这个问题尤其严重的一种形式是「上下文污染」——上下文的许多部分（目标、摘要）被关于游戏状态的错误信息「毒化」，而这些错误往往要花很长时间才能纠正。结果是，模型可能变得执迷于达成根本不可能实现或毫不相关的目标。

如果它上下文里的「目标」部分被污染了，智能体就会制定出毫无意义的策略，并反复重复某些行为，去追求一个根本无法达成的目标。

### 上下文干扰

上下文干扰是指上下文长得太长，模型过度关注上下文，反而忽略了训练时学到的东西。

在智能体式的工作流中，随着模型收集更多信息、积累历史，上下文不断增长——这些累积起来的上下文会从帮手变成干扰。玩 Pokémon 的 Gemini 智能体就清楚地展示了这个问题：

> 虽然 Gemini 2.5 Pro 支持 1M+ token 上下文，但要真正让智能体用好它，
仍是一片新的研究前沿。在这种智能体式设定下，我们观察到：当上下文明显超过 100k tokens 之后，智能体开始倾向于重复它那庞大历史里的动作，而不是综合出新的计划。这一现象虽然只是轶事，却凸显了一个重要区别：用于检索的长上下文，和用于多步生成式推理的长上下文，是两回事。

智能体没有用训练中学到的东西去制定新策略，反而执着于重复上下文历史里的旧动作。

对更小的模型来说，干扰上限要低得多。Databricks 的一项研究发现，Llama 3.1 405b 的正确率在 32k 左右开始下滑，更小的模型下滑得更早。

如果模型在上下文窗口填满之前很久就开始出问题，那超大的上下文窗口还有什么意义？一句话概括：摘要生成3 和事实检索。如果你做的不是这两件事，就该警惕你选的模型能扛到多少 token 才出现干扰。

### 上下文混乱

上下文混乱是指上下文里的多余内容被模型拿来用，生成质量很差的回答。

有那么一小段时间，看起来真的是所有人都在抢着发布 MCP。一个强大的模型、连上你所有的服务、把那些日常杂事全做完——这个梦想似乎伸手可及。只要把所有工具描述塞进提示词里，点一下开始就行。Claude 的系统提示词给我们指了路，因为那里面大部分就是工具定义，或者使用工具的说明。

但就算整合与竞争不会拖慢 MCP，上下文混乱会。结果是，「工具太多」这件事真的存在。

Berkeley Function-Calling Leaderboard 是一个工具使用基准测试，用来评测模型能否有效使用工具来回应对提示词。榜单已经到第 3 个版本，结果显示只要给模型超过一个工具，所有模型的表现都会变差4。更进一步，Berkeley 团队「设计了一些场景，其中提供的函数没有一个是相关的……我们预期模型不会输出任何函数调用」。然而，所有模型都会偶尔调用不相关的工具。

翻看这个函数调用榜单，你会发现模型越小，这个问题越严重：

上下文混乱的一个典型例子出自最近一篇论文，它评测了小模型在 GeoEngine 基准上的表现。这个测试包含 46 个不同的工具。团队把全部 46 个工具连同查询一起给了一个量化（压缩）过的 Llama 3.1 8b，模型失败了——尽管上下文还远在 16k 上下文窗口之内。但只给 19 个工具时，它就成功了。

问题在于：只要你把什么东西放进了上下文，模型就得关注它。它可能是无关信息，也可能是没必要的工具定义，但模型都会把它算进去。大模型，尤其是推理模型，正在变得更善于忽略或丢弃多余上下文，可我们仍然不断看到没价值的信息把智能体绊倒。更长的上下文让我们能塞进更多信息，但这个能力是有代价的。

### 上下文冲突

上下文冲突是指你在上下文里不断积累新的信息和工具，而这些新内容和上下文里的其他信息互相矛盾。

这是上下文混乱的一个更棘手的版本：这里的问题内容不是无关的，而是直接和提示词里的其他信息冲突。

Microsoft 和 Salesforce 的一支团队在最近一篇论文里把这件事记录得非常清楚。团队从多个基准测试里取出提示词，把它们的信息「分片」到多个提示词中。可以这样理解：有时候你坐下来，在按下回车之前把整段内容打进 ChatGPT 或 Claude，把每个必要的细节都想清楚；另一些时候，你先写一个简单的提示词，等聊天机器人给出的答案不满意时，再补充更多细节。Microsoft/Salesforce 团队改造了基准提示词，让它们看起来就像这样的多轮对话：

左侧提示词里的全部信息，都被拆进了右侧的若干条消息里，而这些消息会在多个聊天轮次中依次呈现。

分片后的提示词成绩明显更差，平均下降 39%。团队还测了一系列模型——OpenAI 备受吹捧的 o3 分数从 98.1 掉到 64.1。

这是怎么回事？为什么信息分阶段收集，模型表现反而比一次性收集更差？

答案是上下文混乱：拼装出来的上下文包含了整段对话，其中保留了模型在拿到全部信息之前、尝试回答这个问题时留下的早期答案。这些错误答案依然待在上下文里，在模型生成最终回答时影响它。团队写道：

> 我们发现，大语言模型常常在早期轮次就做出假设，并过早地尝试给出最终方案，然后过度依赖这些方案。说得直白一点，我们发现当大语言模型在对话中走错一步之后，就会迷在里面，出不来。

这对做智能体的人不是什么好兆头。智能体的上下文来自文档、工具调用，以及被委派子问题的其他模型。所有这些从不同来源拉来的上下文，都有自相矛盾的可能。更进一步，当你接入自己没写的 MCP 工具时，它们的描述和说明更可能和提示词里的其余部分冲突。

百万 token 级上下文窗口的到来，感觉像是一次范式转变。把智能体可能需要的一切都塞进提示词里的能力，让人们生出了这样的想象：超级智能助手能访问任何文档、连接每一个工具、拥有完美记忆。

但我们已经看到，上下文越大，新的失败模式就越多。上下文污染把错误埋进去，并随时间不断放大。上下文干扰让智能体过度依赖上下文，重复过去的动作而不是往前推进。上下文混乱导致它去用无关的工具或文档。上下文冲突制造内部矛盾，让推理脱轨。

这些失败对智能体打击最大，因为智能体干的恰恰是那些上下文会膨胀的活：从多个来源收集信息、连续发起工具调用、进行多轮推理、积累庞大的历史记录。

所幸，办法还是有的！接下来的一篇文章里，我们会讲缓解乃至避免这些问题的技术，从动态加载工具的方法，到给上下文建隔离区。
