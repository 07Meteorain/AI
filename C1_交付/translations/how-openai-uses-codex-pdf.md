# OpenAI 如何使用 Codex

引言 在 OpenAI，Codex 已被安全、产品工程、前端、API、基础设施、性能工程等多个技术团队日常使用。各团队用它加速各类工程任务，从理解复杂系统、重构大型代码库，到在紧迫的截止日期前交付新功能、处置故障事件。我们通过访谈 OpenAI 工程师并结合内部使用数据，整理出这些用例与最佳实践，它们展示了 Codex 如何帮助我们的团队加快速度、提升工作质量、并在规模化场景下管理复杂度。

用例 1 代码理解 在新人上手、调试或排查故障事件时，Codex 帮助我们的团队快速熟悉代码库中陌生的部分。团队经常用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的关系、追踪数据在系统中的流动。它还能揭示出架构模式或缺失的文档片段，否则这些内容需要投入大量人工才能整理出来。在故障响应过程中，Codex 通过呈现组件之间的交互、追踪故障状态如何在系统中传播，帮助工程师快速切入新领域。团队亲历 修 bug 的时候，我用 Ask 模式看看代码库里还有哪里可能出现同样的问题。性能工程师，检索系统 我值班的时候，会把堆栈跟踪贴给 Codex，问它认证流程在哪儿。它直接跳到正确的文件，我就能快速定级分流。站点可靠性工程师，API 平台 Codex 回答我那些“这个我该在哪儿做？”的仓库问题，在 Terraform 和 Python 里比 grep 快得多。DevOps 工程师，基础设施服务 试试用 Codex 做代码理解，可以参考这些示例提示词： 认证逻辑在这个仓库里是怎么实现的？ 总结一下请求在这个服务里从入口到响应是怎么流转的。 哪些模块和［插入模块名］有交互？失败是如何处理的？

用例 2 重构与迁移 Codex 常被用来完成跨多个文件或包的改动。比如，工程师在更新 API、改变某个模式的实现方式、或迁移到新的依赖时，Codex 能让这些改动被一致地应用。当同一处更新需要在几十个文件里重复落地，或者更新需要理解那些用正则表达式或查找替换不容易捕捉的结构和依赖关系时，它尤其好用。团队也用它做代码清理：拆分过大的模块、把旧模式替换成现代写法、或为更好的可测试性做准备。团队亲历 Codex 把我们所有的遗留写法都换成了新的服务模式，还把拉取请求（PR）开好了。它几分钟就干完了原本要花几小时的事。getUserById( ) 后端工程师，ChatGPT Web 为了清理上线阻塞项，我让 Codex 扫描所有旧模式的实例，用 Markdown 汇总影响范围，然后带着修复开 PR。产品工程师，ChatGPT Enterprise 试试用 Codex 做重构与迁移，可以参考这些示例提示词： 按关注点把这个文件拆成独立模块，并为每个模块生成测试。 把所有基于回调的数据库访问改写成 async / await。

用例 3 性能优化 Codex 被用来识别并处理性能瓶颈。在调优或提升可靠性的过程中，工程师会提示 Codex 分析缓慢或占用内存过多的代码路径，比如低效的循环、冗余操作或代价高昂的查询，并给出优化后的替代方案，往往能带来效率和可靠性上的实质提升。Codex 也被用来支撑代码健康度，识别仍在使用中的高风险或已废弃的模式。各团队倚重它来减少长期技术债，并主动防范回归。团队亲历 我用 Codex 扫描重复的高开销数据库调用。它很擅长标出热点路径，并起草出可供后续调优的批量查询。基础设施工程师，API 可靠性 Codex 特别适合快速发现性能问题——花 5 分钟写提示词，就能省下 30 分钟的工作。平台工程师，模型服务 试试用 Codex 做性能优化，可以参考这些示例提示词： 从内存效率的角度优化这个循环，并解释你的版本为什么更快。 在这个请求处理器里找出重复的高开销操作，并提出可以加缓存的地方。 给出一种在这个函数里批量执行数据库查询的更快写法。

用例 4 提升测试覆盖率 Codex 帮助工程师更快地写出测试——在覆盖率偏低或完全空白的地方尤其有用。在修 bug 或做重构时，工程师经常让 Codex 建议能覆盖边界情况或可能失败路径的测试。对于新代码，它能根据函数签名和周边逻辑生成单元测试或集成测试。Codex 尤其擅长找出边界条件，比如空输入、最大长度、或不常见但合法的状态，这些常常在最初的测试中被遗漏。团队亲历 我让 Codex  overnight 盯着那些覆盖率低的模块，第二天醒来就拿到了可以跑的单元测试 PR。前端工程师，ChatGPT Desktop 切换单体仓库分支很痛苦，我就让 Codex 写测试并启动 CI，同时我自己继续在当前分支上干活。后端工程师，支付与账单 试试用 Codex 提升测试覆盖率，可以参考这些示例提示词： 为这个函数写单元测试，包括边界情况和失败路径。 为这个排序工具生成一个基于属性的测试。 扩展这个测试文件，覆盖空输入和非法状态相关的缺失场景。

用例 5 提升开发速度 Codex 通过加速开发周期的开头和结尾，帮助团队走得更快。在启动一个新功能时，工程师用它来搭脚手架式模板代码——生成目录、模块和 API 桩，让可运行的代码很快跑起来，而不必手工串起每一个零件。当项目临近发布时，Codex 通过处理那些体量不大但不可或缺的任务来帮团队赶上紧迫的截止日期，比如给 bug 分流归类、填补实现上的最后一段缺口、生成发布脚本、遥测钩子或配置文件。它还用来把产品反馈变成起始代码。工程师经常贴进一条用户需求或规格说明，让 Codex 生成一份粗稿，之后再回来打磨完善。团队亲历 我整天都在开会，但仍然合了 4 个 PR，因为 Codex 一直在后台干活。产品工程师，ChatGPT Enterprise Codex 完美地交付了 3 到 4 个低优先级修复，这些要是搁在待办清单里就烂掉了，这种感觉特别让人有底气。全栈工程师，内部工具 试试用 Codex 提升开发速度，可以参考这些示例提示词： 为 POST /events 搭一个新的 API 路由，带基本的校验和日志。 用这个模板［插入你的遥测代码示例］生成一个遥测钩子，用来跟踪新引导流程的成功／失败。 基于这份规格说明生成一个桩实现：［插入规格说明或产品反馈］。

用例 6 保持心流 当日程被切碎、塞满各种打断时，Codex 帮助我们的工程师保持产出。它被用来记录未完成的工作、把笔记变成能跑的原型、或者派生出一批探索性任务留待日后重新拾起。这让人们更容易暂停并恢复工作而不丢失上下文，尤其是在值班或会议很多的时候。团队亲历 如果我看到一处顺手就能修的地方，我就丢一个 Codex 任务出去，而不是切换分支，等有空时再评审它的 PR。后端工程师，ChatGPT API 我经常把 Slack 讨论串、Datadog 追踪、issue 之类的东西转给 Codex，这样我就能专注在高优先级工作上。API 工程师，基础设施可观测性 试试用 Codex 保持心流，可以参考这些示例提示词： 生成一份重构这个服务并把它拆成更小模块的计划。 把重试逻辑做成桩，并加一个 TODO——退避逻辑我后面再补。 总结这个文件，好让我明天从上次停下的地方接着做。

用例 7 探索与构思 Codex 在开放式工作上同样有用，比如寻找替代方案或验证设计决策。你可以提示它给出解决问题的不同方式、探索陌生的模式，或者对假设做压力测试。这有助于揭示各种权衡、扩展设计选项、让实现选择更精准。它也被用来识别相关的 bug。给定一个已知问题或某个已废弃的方法，Codex 能在代码别处找出相似的模式，让捕获回归或完成清理工作变得更容易。团队亲历 Codex 帮我解决了冷启动问题——我贴进一份规格说明和文档，它就把代码脚手架搭好，或者告诉我我漏了什么。产品工程师，ChatGPT Desktop 修完一个 bug 之后，我会问 Codex 类似的 bug 可能藏在哪里，然后派生出后续任务。性能工程师，检索系统 试试用 Codex 做探索与构思，可以参考这些示例提示词 如果系统改成事件驱动而不是请求／响应模式，这段代码要怎么写？ 找出所有手工拼接 SQL 字符串、而没有用我们的查询构建器的模块。 把这段改写成更函数式的风格，避免可变状态和副作用。

最佳实践 Codex 在拿到结构、上下文和迭代空间时表现最好。下面是 OpenAI 各团队正在培养的一些习惯，以便在日常工作中稳定地从中获得价值。先从 Ask 模式入手 对于大改动，先用 Ask 模式提示 Codex 给出一份实现方案，等你切换到 Code 模式后，这份方案就成为后续提示词的输入。这个两步走的流程能让 Codex 保持聚焦，并帮助避免它输出出错。Codex 最适合处理范围界定清晰的任务——大概是你或同事花一个小时能完成，或者几百行代码能实现的量。随着模型不断进步，可以期待它能承接的任务规模逐步变大。迭代式改进 Codex 的开发环境 配好启动脚本、环境变量和网络访问，能显著降低 Codex 的出错率。在跑任务的过程中，留意那些可以在 Codex 环境配置里修正的构建错误。这可能需要几轮迭代，但从长远看能带来可观的效率提升。像写 GitHub Issue 那样组织提示词 当提示词贴近你在 PR 或 issue 里描述一项改动的方式时，Codex 回应得更好。也就是说，必要时要带上文件路径、组件名、差异和文档片段。用上“按［模块 X］里的做法来实现”这类句式能提升效果。把 Codex 任务队列当作轻量待办清单 随手派任务，把顺带冒出来的想法、半成品或偶然的修补都记下来。你不必一次就产出完整的 PR。Codex 很好地扮演了一个暂存区，等你重新进入心流时可以回来继续处理。

最佳实践 用 AGENTS.md 提供持久上下文 维护一个 AGENTS.md 文件，帮助 Codex 在多次提示词之间、在你的仓库里更有效地工作。这类文件通常包含命名约定、业务逻辑、已知的坑，或者那些光看代码无法得出的依赖关系。关于如何组织 AGENTS.md 文件，文档里有更详细的说明。用“Best of N”提升输出质量 Best-of-N 功能让你能针对单个任务同时生成多个回答，从而快速探索多个方案并挑出最好的那个。面对更复杂的任务，你可以对比几个迭代版本，把不同回答中的部分内容组合起来，得到更强的结果。展望 Codex 目前仍处于研究预览阶段，但它已经在切实改变我们的构建方式，帮助我们加快速度、写出更好的代码，并承接那些原本根本不会被排上优先级的工作。我们对前景充满期待——随着模型变得更强、Codex 与我们的工作流融合得更深，我们期待用它解锁更强大的软件开发方式。我们会继续分享一路上的收获。
