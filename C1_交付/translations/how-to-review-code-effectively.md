# 如何高效评审代码：一位 GitHub 资深工程师的哲学

GitHub 资深工程师 Sarah Vessels 讲述了她对代码评审的哲学、好的代码评审与坏的代码评审之间的差别、她寻找和评审代码的策略，以及如何让别人评审自己的代码时收获最大。

Sarah Vessels·@cheshire137

2024 年 7 月 23 日
 

 |
 
 16 分钟

- 分享：

作为 GitHub 的一名资深工程师，代码评审是我日常工作的主要重心之一。过去八年里，我评审过 7,000 多个拉取请求。为什么会这么多？因为代码评审对构建优质软件至关重要，而多一双眼睛往往能发现你本来会错过的问题。

我把代码评审视为我工作中最重要的方面之一。事实上，每当我看到某位同事有一个准备好接受代码评审的拉取请求，我都更愿意放下自己正在处理的分支，去评审他们提议的改动。毕竟，他们的拉取请求已经通过了持续集成（CI）的连环考验，也达到了他们自己判断“做完”的标准，所以它大概比我手上还在进行的工作更接近可发布状态。我宁愿让他们的代码先冲过终点线，也不想再耗上不知多久去完成我自己的代码。

我给出反馈越早——“这里可能是 nil，会导致错误”“这看起来是个 n+1 查询”“这里最好有一个方法签名”——这些反馈就能被处理得越快，bug 就能被越早压掉、功能就能被越早发布。

我想分享一下我做代码评审的方式，希望我们都能发布更好的代码。

## 什么是代码评审？

严格来说，代码评审——也就是 GitHub 上的拉取请求评审——让协作者能够对拉取请求中提出的改动发表评论，表示对这些改动的认可，或者在拉取请求被合并之前要求进一步修改。

我把拉取请求看作一段对话的开端。我读它的时候，等于作者在说“我觉得这比我们今天现有的东西更好”。代码评审是一次塑造产品实现方式的绝佳机会。作为代码评审者，我的工作就是通过提问、质疑假设，以及总体上充当第二双眼睛，与作者反复讨论，把他们的代码改得更好。

为什么要评审代码？这对你的职业生涯有好处

我从其他评审者对我自己代码的视角中学到了很多，而在反复收到“谢谢你及时做代码评审”这类正面反馈之后，我知道我的代码评审评论同样帮助队友们提升了自己。简单说，代码评审是有影响力的，而想升职就需要展示你的影响力。

代码评审之所以有影响力，是因为它促进知识共享并提升交付速度。它们是漂亮、可链接的产物，同事和主管可以拿它们来展示你有多乐于助人、多有见识。它们能凸显你良好的沟通能力，尤其是在需要处理复杂或有争议的改动时。所以，在代码评审中把自己的理由讲清楚，不仅能引导产品的未来、帮助避免故障事件，对你的职业生涯也有好处。

## 精细打磨你的代码评审流程

### 如何找到待评审的拉取请求

我待在 GitHub 通知收件箱里。它是我在浏览器里固定仅有的几个标签页之一，所以随时都能打开。每当我在等 CI、在任务之间、开始一天工作，或者总之有点空闲时，我都喜欢去翻收件箱。我评审的大部分拉取请求都是在那里找到的。GitHub 的团队通常会有一个把某个 Slack 频道当作“大本营”，那是分享待评审拉取请求的好地方——这也是我发现拉取请求的另一条主要途径。

我还很好运地用起了 GitHub 的 Slack 集成，让某个 Slack 频道订阅与我团队相关的新拉取请求。为了过滤出哪些拉取请求出现在 Slack 里，我会用一个团队专属的标签，然后在 Slack 里输入一条类似 /github subscribe your/repo pulls +label:"your-team-label" 的‘subscribe’命令。

提示

你可以在查询中重复使用 team-review-requested: 这个限定符，从而拿到归属于许多不同代码归属方的待评审拉取请求。

我喜欢用 is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team 这样的查询来搜索可能需要评审的未处理拉取请求。用这条查询，我能找到 GitHub 组织内开放的、未归档的、非草稿的拉取请求，并且它们把相关的代码归属团队列为请求的评审者。我通常会省略 review:required 这个搜索限定符，因为即使同事已经评审过某个拉取请求，我仍然想去评审它。毕竟，评审代码不仅能帮到作者，也能让我及时掌握影响到我负责代码的改动。

### 用评审者团队管理通知

你不会希望代码改动去 ping 一个这么大的团队，以至于团队里的每个人都认为评审这个改动不是自己的责任。那会导致拉取请求要么一直没人评审、搁在那里，要么在该合并之前就被合并了——因为关键评审者在铺天盖地的通知里错过了它们。这两种情况都会影响产品质量。

如果做得到，我建议把自己所在的代码归属团队数量控制好，让通知保持在你可管理的范围内。这样，落到你收件箱里的拉取请求就不只是噪音，而是你真的觉得应该去评审的东西。大而全的代码归属团队作为兜底选项也许还行，但作为自动评审请求的第一线默认选项并不好。把仓库的 CODEOWNERS 文件组织好，配上界限清晰的代码划分，以限制通知量并帮助评审者避免通知疲劳。

限制团队通知的另一种办法，是建一个第一响应者团队，然后用自动化按排期增删团队成员。这样你的团队可以专注自己日常的代码库，而排班的第一响应者会收到你团队服务范围内拉取请求的通知。比如用 PagerDuty API，你可以确定某一天由谁担任第一响应者，然后用 Octokit 库来增删团队成员。

### 用自动化让各团队的代码评审标准化

仓库级别的配置和自动化手段，比如使用 CODEOWNERS 文件和分支保护规则，有助于在各团队之间强制推行评审流程的标准。另一些标准，比如拉取请求中什么值得评论，就得由我们人类来维护。把团队内部的代码评审方式文档化下来，确保任何提供代码评审或提交拉取请求的人都知道，怎样让自己的拉取请求被评审、评审的预期周转时间是多少，以及有哪些自动化工具在辅助评审。

有些团队用项目看板来跟踪哪些拉取请求进来待评审；我见过一个管理共享 API 的团队这样做效果不错，因为这个区域经常被团队之外的人改动。另一些团队则只依赖 GitHub 通知，当代码归属划分得很紧、团队又自律地做到拉取请求一来就评审时，我也见过这种做法效果不错。

如果你遵循的是本团队特有的流程，自动化可以帮助你把预期传达给团队之外的人。例如，如果很多其他团队都依赖你团队的评审，你可以用一个机器人，在任何请求你团队评审的拉取请求上自动留一条评论，告诉作者大概什么时候能收到你的反馈。

## 什么样的代码评审算好，什么样的算差

好的代码评审能增加清晰度，并把代码推向比起点更好的状态。

作为评审者，沟通上的清晰是关键。你需要说清楚哪些评论只是个人偏好，哪些是会卡住通过的阻塞项。给出你所建议做法的示例，能提升你这次代码评审的水平，也让你的意思更清楚。如果你能举一个来自该拉取请求所在同一个仓库的例子，那就更好了——这会以一致的实现方式进一步支撑你的建议。

相比之下，糟糕的代码评审缺乏清晰度。比如，不带任何评论就一律通过或一律拒绝，会让拉取请求的作者怀疑这次评审到底彻不彻底。即使只是在附上通过的同时重述一遍你对作者意图的理解，也能暴露出你和作者的理解是否一致。

没有说清建议应该在什么时候落实的代码评审，对作者来说也可能是糟糕的体验。指出已有的、未被改动的代码应该重构、或者应该多处理一种情况，这本身没问题，但重要的是要说明这些是否属于通过的前置条件。如果这个拉取请求没有你的建议也能落地，一定要说清楚。把差异保持得很小、把那些改动拆成单独的拉取请求分别发布，可能更稳妥。

下面这条代码评审评论既具体，又清楚传达了建议的实现方式：

“我看到你新增的方法和这个文件里现有的风格一致，接收 [X] 个参数。这么多参数会损害可读性，也暗示这个函数干了太多事。你怎么看：在后续的拉取请求里把这个方法和现有的那些方法一起重构一下，让它们接受的参数更少？”

这条评论好在哪里：

- 提供了具体细节。

- 指向了具体的代码或问题。

- 提出了问题的解决方案。

- 引用了证据或给出了解释

在光谱的另一端，下面这些评审评论就差点意思：

“我不喜欢这个。”——评审者不喜欢什么？他们心里有没有一个可以明说出来的替代方案？

可以改进的地方：

- “这一行干的活儿太多了，能不能简化一下以提升可读性？”

- “我觉得这会有性能问题，因为它是个 n+1 查询。”

- “这个能不能改用 [preferred framework] 的现成方案，而不是自己写一套实现？”

“这样不行。”——为什么这些改动不行？

可以改进的地方：

- “这样不行，因为 [X]，参见这个相关 issue：[issue link]。”

- “这个在 [pull request link] 里已经试过了，因为 [X] 所以行不通。”

- “如果你在 [X] 上遇到问题，可以试试 [alternative approach]。”

“我觉得这修掉了一个 bug。”——我很喜欢这种点明，但有没有额外的上下文，比如一个 issue 链接，能让这句话更清楚？

可以改进的地方：

- “我觉得这修的是 [issue link] 里的问题。”

- “这是在修 [issue link] 里的那个 bug 吗？”

- “这看起来就是我们在 [link to failing build] 时遇到的那个问题。谢谢修复！”

## 如何给出好的代码评审

### 多提问

我把拉取请求的作者视为对这次改动最了解的人。我可以基于自己的经历——在 Ruby on Rails 单体应用、TypeScript，或者大流量数据库上工作的经验——指出我看到的问题，但我信任作者对我问题的回答。我认为他们对这些细节的理解比我的更可靠。

提示

如果你刚加入一个代码库或团队，就在代码评审中多提问，以此了解技术栈以及有哪些内部工具和库可用。你评审的每一个拉取请求，都是一次弄清作者为什么偏好这个做法而不是另一个的机会。

我还很喜欢问那些涉及代码中所做假设的问题。他们处理的数据是什么形状？是否存在与该形状不匹配的数据？代码对此应对得好吗？这段代码资源消耗大吗？性能会好吗？作为评审者，我最喜欢的回答是作者提供一个自动化测试，验证这些场景下的行为。我第二喜欢的回答是实测数据，比如从我们的数据仓库跑出来的一个查询，或者一张 Datadog 图表，说明这些场景不是问题。

作为拉取请求的作者，我很看重有人提问。当有人提问时，就给了我空间去解释我为什么对自己的改动有信心，必要时可以引用 issue、查询或图表。这也让我能把知识和经验分享给别人。作者看到的不仅是我的回答，还有其他评审者，以及日后可能需要追溯某个过往决定背景的读者。

### 给出肯定

除了提问之外，对拉取请求中你认同的部分发表评论也是个好习惯。这类评论能表明你确实读了并理解所做的改动，或者你验证了代码里的某个假设。举几个例子：

- “看起来这和这个模块里其他类用的模式一致。”

- “谢谢你为这个补了测试！”

- “这比之前可读性好多了。”

以我的经验，能收到这样的评论感觉也很好。接收一次代码评审有时会让人感到被消耗。当我同时应付好几个人提出的问题和建议时，能收到几条不要求我做任何事、而是支持并认可我已经投入的工作的评论，会很提气。

### 留意偏见和假设

你很容易让自己对评审者的偏见、或对他们所改的那块代码的偏见，影响你的评审。你会习惯某个人一直在某个领域工作、或有某种资历，于是假设他们知道自己在干什么——但每个人都会犯错。用你的眼睛去看他们的改动、用你的问题去检验他们的假设或验证你自己的假设，能在问题被部署之前抓住它。

我非常推崇写测试，因为测试能消掉一部分偏见。当你写一个测试来检查代码是否正常工作，你不必只凭作者的一面之辞，只要看测试有没有通过就行——当然，前提是这个测试本身写得对。😅

我也非常支持初级开发者在代码评审中向资深开发者提问，即使他们觉得自己的问题很傻、或答案显而易见。如果对你来说它并不明显，那这个提问就是合理的。对别人来说它也不会明显！把问题问出来，给作者留出写下答案的空间，把这份知识留给后来的人。

### 批还是不批

我把自己的评审看作一道会挡住别人的闸门——它可能阻止某个人改进我们的产品——所以我会谨慎地不予通过。我常常有自己的个人偏好，会建议一些我希望作者能做的可选改动，但不会仅凭这些就扣住不给通过。如果我对某人的拉取请求有建议，但这个拉取请求按现状不会搞坏生产、不会对用户造成负面影响、也不会引发其他问题，我就会带着这些评论给出通过。作者可以选择在合并前处理我的反馈，也可以另开一个分支后续跟进。

提示

使用功能开关（feature flags），并把拉取请求做小。你的改动越不吓人，在生产上被回滚得就越快，我也就越容易批准它！

评审代码时，要掂量你那条建议的重要程度。为了让建议被采纳而推迟发布，值得吗？值得让作者经历一整轮流程——看到你的反馈、做出建议的修改、等待 CI、再次评审、部署，最后才合并吗？如果少了这条建议不会让谁的处境变差，那就让作者自己决定要不要改、什么时候改。

“Request changes”选项会阻止拉取请求被合并，直到评审者回来给出通过。我极少用它，因为通常感觉太粗暴了。我信任我的团队知道什么时候该批准一个拉取请求，所以同事的通过就可以代替我的通过。同样地，我信任拉取请求的作者会重视并考虑我的反馈，而不是因为别人批准了我没批准就盲目合并。我几乎只有在认为存在一个紧迫的安全问题时才会选“Request changes”——因为我担心他们合并前看不到我的顾虑。

使用 AI 编码工具时，代码评审为什么依然重要

AI 编码工具通常包含各种防止代码出错或不安全的防护措施，但别被这种虚假的安全感哄睡。作为掌舵的人类评审者，你是最后一道防线，应该以同等严谨的态度评审所有代码。

## 如何让代码评审发挥最大价值

### 评审你自己的代码

GitHub 资深软件工程师 Paul Smith 教过我，在请别人评审之前先评审自己的拉取请求，我也建议你这么做。先过一遍，对那些不明显的改动——或者你在别人的拉取请求里看到会想问一句的改动——用行内评论的方式标出来。自我评审还能帮你判断一个拉取请求是不是太大了、拆开会更好。

特别推荐：如果你在意让拉取请求保持小规模，可以用 lerebear/sizeup-action 自动给拉取请求打上标签，标明其复杂度和规模。

### 欢迎合并之后的评审

如果我碰巧在别人有机会评审之前就合并了拉取请求，我依然欢迎他们的评审。如果我的拉取请求弄坏了什么、或者带来了意料之外的后果，那就在拉取请求上尽量多留评论，让这些面包屑小径帮助日后的读者追查当时发生了什么！

如果我收到针对已合并拉取请求的评审，我会像它还没落地时那样处理这些反馈。可能是一条评论解释我的思路，也可能是再开几个拉取请求来迭代我最初发布的代码，还可能是开几个新 issue 来记录待做的额外工作。

### 使用草稿拉取请求

创建新拉取请求时，你可以选择把拉取请求设为草稿。我非常依赖草稿状态来表示我要不要接受评审。比如，如果某个必需的 CI 构建挂了，或者我还没写完，我就把它保持为草稿。我对别人的拉取请求也有同样的预期：如果是草稿，我就认为作者还没准备好接受评审；如果被标记为准备接受评审，我就认为只要拿到足够多的通过，就能发布了。

草稿状态意味着拉取请求还没完成，所以我在解决合并冲突或处理评审反馈时，会把拉取请求退回草稿状态。如果我必须修改代码，我会先把自己的拉取请求标为草稿，以免把已经评审过的人淹掉。当我把它改回‘准备好’时，GitHub 会给这些评审者发通知，让他们可以再去看一遍。

### 保持善意

我总想起那句话：“用蜂蜜比用醋能招来更多苍蝇。”我希望我的拉取请求能得到评审，所以有人在我的拉取请求上评论时，我总愿意回复——尤其是在我不同意评审者意见的时候。即使我没有对某条评审评论写出回复，我也常用一个 👍 表示我同意，或者用一个 ❤ 表示感谢。

我希望评审者相信他们的建议不会被忘记，所以我用评论让他们一直知情。如果我认同他们的建议——比如建议进一步重构现有代码——我可能会表示认同，同时又提出这个改动不该放在当前这个拉取请求里。当我在后续的拉取请求里处理了他们的反馈时，我会回来附上链接，让评审者知道他们的反馈没有被忽略。

我也会在落实这些建议的后续拉取请求里 @ 上他们，并加一句说明：“这条处理了 @某某 在 <previous pull request URL> 提出的反馈。”这既为其他读者提供了上下文，也是对最初评审者的一次致意，把这个想法的功劳归给他们。

当你兑现承诺、在后续分支里处理了反馈时，这有助于建立评审者对你的信任，也能让他们更自在地批准你以后的拉取请求，因为他们知道你不会把事情留在半途。

## 收尾

代码评审对产品质量的重要性怎么强调都不为过，在 AI 生成代码的时代尤其如此。在我的职业生涯中有很多次，只是因为多了那一双眼睛，就抓住了一个 bug 或避免了一场故障事件。无论时间花在每天的评审上、花在梳理流程上，还是花在构建支撑评审的自动化上，代码评审都完全值得这份投入。让开发者现在把拉取请求彻底评审一遍，比事后去处理一个已经发布到生产的问题要更快、也没那么痛苦。

感谢你足够在意代码质量，读完了我这套代码评审的哲学。你最近查看过自己的评审队列了吗？也许现在正是把这些想法付诸实践的好时机。

如果你想更多了解如何在 GitHub 上使用拉取请求评审，可以看看 GitHub Community 上资深 DevOps 架构师 Mickey Gousset 和资深 DevOps 架构师 Joshua Johanning 讨论“评审一个拉取请求的 5 个建议”的那篇文章。
