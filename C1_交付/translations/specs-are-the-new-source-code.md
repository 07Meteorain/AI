# Ravi on Product

# 规格说明已死，规格说明万岁！

### 原型成了新规格说明，而规格说明成了新的……源码？

Ravi Mehta 和 Danny Martinez

2025 年 7 月 31 日

在我的职业生涯中，规格说明越来越短。我刚加入 Microsoft 时，一位产品经理的价值是按他写的规格说明的厚度来衡量的。多年之后，在 Tripadvisor，我们把那位把一份规格说明——潦草地写在餐巾纸上——带进产品评审会的产品经理奉为传奇。

产品团队常常把规格说明当成文书工作——在「真正的工作」开始交付之前必须走的一道必要之恶。工程师因优雅的代码而受表彰，设计师因漂亮的用户体验而受表彰，产品经理因交付了影响力而受到称赞。但规格说明呢？它们通常被草草过一遍，然后丢在一边，彻底忘掉。

感谢阅读 Ravi on Product！免费订阅即可接收新文章并支持我的工作。

这始终是个错误。在我的《产品能力工具包》中，「功能规格说明」高居十二项能力之首，这是有原因的。它是「产品执行」的基础，而产品执行又与「产品交付」「产品质量」并列。

无瑕疵的执行是产品管理的根基，而一份好的规格说明就是起跑线。

今天，我们构建产品的方式正在转变。工程师变快了——快得多。AI 能在几分钟内把粗糙的想法变成能跑的代码。瓶颈不再是构建，而是知道该构建什么，并让团队围绕这些需求达成一致。

突然之间，那份不起眼的规格说明不再是稍纵即逝的文书。它成了产品管理的根基——它正在成为源码本身。

## 为什么产品经理突然成了瓶颈

吴恩达（Andrew Ng）在近期的演讲《Building Faster with AI》中提到一个前所未有的趋势：

> 「我职业生涯中第一次看到，管理者向我提议配备的 PM 数量是工程师的两倍。我至今还不知道这个提议是不是个好主意，但我认为它预示着世界往哪个方向走。」——吴恩达（Andrew Ng）

这印证了我们在上一篇文章中的预测：随着工程师借助 AI 交付速度快上数倍，公司需要更多 PM 来支撑这些高效的工程师，而不是更少。

随着产品交付加速，产品管理的其他每个方面都承受着巨大压力——理解客户需求、打造合适的功能、验证影响力。

而所有这些压力最终都聚焦到一件产物上——规格说明。

## 规格说明——新源码

在传统软件开发中，程序员编写人类可读的「源码」，再将其编译成高度优化的机器可读「目标代码」。「目标代码」（也叫二进制文件）只是副产物，有了源码就能重新生成。源码才是字面意义上的事实来源。

OpenAI 的 Sean Grove 提出了一个颇具挑衅的论点。在他近期的演讲《The New Code》中，他认为一份写得好的提示词（也就是规格说明）就是新的源码。

从这个角度看，我们做 AI 开发的方式是反的。我们精心构思提示词，把意图传达给模型。AI 生成代码。然后我们留下代码，把提示词扔掉。

「这感觉就像你把源码绞碎了，然后极其小心地对二进制文件做版本控制，」Grove 这样评价道。

想想看。在传统编程中，源码是神圣的。源码里包含注释、结构和文档——理解并修改整个系统所需的一切。二进制文件只是下游产物。

但在 AI 时代，我们把这种关系颠倒了。我们把生成的代码视为值得保留的产物，把规格说明——也就是提示词——当成一次性的东西。

Grove 认为这完全搞反了。代码，哪怕是优雅的代码，也只是他所说的规格说明的「有损投影」。就像反编译二进制文件无法还原原始的注释和变量名一样，阅读代码也不会告诉你背后完整的意图。

然而规格说明包含了一切。一份足够完善的规格说明可以生成「好的 TypeScript、好的 Rust、服务器、客户端、文档、教程、博客文章，甚至播客。」

「一份足够完善的规格说明可以生成好的 TypeScript、好的 Rust、服务器、客户端、文档、教程、博客文章，甚至播客。」——Sean Grove，OpenAI

更重要的是，规格说明能做一些代码做不到的事：让人类和机器在共同目标上达成一致。Grove 的表述很简单：「一份写下来的规格说明能有效对齐人类，它也是你用来沟通、讨论、辩论、引用和达成同步的载体。」

他预言：「在不久的将来，最善于沟通的人就是最有价值的程序员。字面上说，如果你能有效地沟通，你就能编程。」

新的稀缺技能不是写代码，而是写出能完整承载意图和价值观的规格说明。

对产品经理来说，这话听起来应该很熟悉。这正是我们一直在做的事——只不过现在，机器也在听。

## 等等，原型不是已经把规格说明杀死了吗？

直到最近，产品生命周期都必须从规格说明（或 PRD、或概念文档、或一张餐巾纸）开始，由它推动最初的线框图、设计、原型和 MVP 开发。

传统做法感觉像一道必要之恶。工程师搭出基础 MVP，为的是让某个东西——随便什么东西——先到客户手里。「如果你不为产品的第一版感到尴尬，说明你发布得太晚了」成了信条。

我们构建产品的整套方法最近发生了重大转变，在这个新世界里，规格说明往往是产出，而不是输入。

今天，你不需要写一行代码就能把原型交到客户手里。v0、Lovable 和 Replit 之类的工具让你在几小时而不是几周内就能做出可用的原型。不需要工程能力。

这不只是更快——而是根本性不同。借助一个「vibe coding」出来的原型，你可以在写下一行功能规格说明之前就收集到真实的客户反馈。你可以验证假设、迭代流程、打磨交互。

- 旧工作流是这样的：模糊的想法 → 线框图 → 设计 → 工程师开发 MVP → 客户反馈 → 痛苦地修改规格说明 → 线框图 → 设计 → 重做 → 祈祷。

- 新工作流：模糊的想法 → 快速原型 → 客户反馈 → 清晰明确的规格说明 → AI 辅助实现。

原型并没有杀死规格说明，它们让规格说明变得更好。

## 规格驱动开发的实践

我们来看一个动手示例，看看这一切实际是怎么落地的。Danny Martinez 是 decimals 的创始人，这是一个尚在隐身状态的平台，让创作者经济领域的专家把自己人脉中的候选人安排到职位上。

- 你是一位以 AI 为先的产品经理，正在寻找新机会？留下你的信息，我们遇到有趣的机会时会通知你。

- 你是一家公司，想招聘以 AI 为先的产品经理？申请加入我们的人才网络，我们会给你一份精心筛选的候选人短名单。

Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来了两方面的影响：

- 大幅改善了较大功能与工程团队之间的沟通，以及

- 让没有任何编码经验的 Danny 也能针对小功能，从详细规格说明一路走到功能上线。

下面交给 Danny……

这是我最近处理的一个例子。交代一下背景：我们正在做一个产品，让专家型影响者把自己人脉中的候选人安排到职位上。上线了一个新的落地页之后，我们需要给专家们一个快速访问自己页面链接的方式。

> 我们需要一个头部按钮，指向 company-apply 页面。我现在在弄邮件。这个用 vibe coding 就能搞定，如果你能接手就太好了。

这条消息是我的联合创始人发的，指的是一个要上线的简单按钮。足够简单，也正是非技术人员现在可以自己上线的那类东西。

下面是配置和步骤，看它如何在几分钟内上线：

- 项目管理工具：Linear

- IDE：VS Code

- 扩展：GitHub Copilot Pro

- MCP 服务器：Linear MCP 服务器，让 Copilot 能够访问 Linear 工单

我们看看流程中的各个步骤（可以在上方的 Loom 视频中跟着做）：

- 根据我联合创始人在 Slack 上发的消息生成一张 Linear 工单（00:14）

- 在上面那张工单里明确我希望新文案写成什么（00:25）

- 打开 Copilot，提示 Claude 打开那张 Linear 工单（01:18）

- 提示 Claude 评审这张工单，并结合代码库加以分析（01:52）

- 提示 Claude 创建一个分支并实现这些改动（02:30）

- 测试这些改动，确认它们按预期工作。（02:52）

- 在 GitHub 上开一个拉取请求（PR），把这些改动发布到代码库里（03:55）

- 等一位工程师评审／批准这个 PR

把视角拉远，这套配置真正的威力就显现出来了。没错，这只是个琐碎的例子，但道理依然成立：借助 GitHub Copilot 和 Claude，一个非技术人员现在也能在 Linear 工单、代码库和工程师之间来回穿梭，全程只需要向 Claude 提几个提示词。

再说一次，这一切中最关键的部分并不是代码本身，而是规格说明。

不过，有必要说明要让上述做法运转良好需要哪些前提：

- 足够具体：规格说明含糊其辞，只会换来一个乱糟糟的代码库。让 Claude 从工单的初稿出发、评审代码库、帮忙把规格写得更具体，是这个流程中不可或缺的一环。在我们的场景里，我们还有一份写好规格说明的指南。

- 有所取舍：把上述做法用在较简单的任务上最理想。工单越复杂，就越需要一个真正懂行的人参与（「自助」在这些情况下最终完全不是自助）。

- 有人把关：这种做法之所以运转得好，正是因为有一位真正懂行的工程师在评审改动、确保简单性与功能性之间的平衡得以维持。

但要说清楚：规则已经变了。规格说明是所有构建这个产品的人的（含 LLM 的）事实来源。

在配置得当的情况下，作为非技术人员参与代码库贡献完全现实。只要有足够的时间和耐心，你就可以开始理解代码库、自己动手实现改动，而不是每次都靠 Claude 来救你。

总有一天，你甚至可能一边喝着咖啡，一边让 AI 智能体帮你把工单上线。

如果你是一位担心 AI 会抢走自己工作的产品经理，关键在于意识到：这份工作本身正在变化。但其他所有人也一样。好消息是，成为优秀产品经理所需的核心能力，在这个世界里反而更值钱了。

正如我们在上一篇文章中预测的，以这种方式开展工作的公司需要的是更多产品经理，而不是更少。而事实证明，这个预测相当灵验：

## 规格说明万岁！

科幻小说家威廉·吉布森（William Gibson）——「赛博空间」（cyberspace）一词的创造者——曾说：

> 未来已经到来——只是它来得并不均衡。

想到 AI 今天能做什么、不能做什么时，我就会想起这句话。今天，AI 带来的提升极不均衡。有些事情——生成代码、文本、图像——已经实现了量子跳跃般的突破，它们以 AI 的速度运转。另一些事情——与客户对话、发现他们的需求、说服他们购买——仍然以人的速度前进。

这种不均衡正在重塑产品团队。聚光灯正从「实现工作」转向「理解工作」。那些一直让优秀产品经理脱颖而出的核心能力——理解用户需求、清晰定义问题、设计优雅的解决方案——价值已经翻了几倍。

最优秀的产品经理把这些洞察转化成规格说明——能对齐团队、指导实现，并在日益自动化的开发世界中充当长久留存产物的规格说明。
