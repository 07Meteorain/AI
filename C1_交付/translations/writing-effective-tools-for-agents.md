# 用智能体编写高效的工具

发布于 2025 年 9 月 11 日

智能体的能力取决于我们给它们的工具。我们将分享如何编写高质量的工具和评测，以及如何用 Claude 为自己优化工具，从而提升性能。

Model Context Protocol（MCP）可以让 LLM 智能体获得上百种工具，用来解决真实世界的问题。但我们该如何让这些工具发挥最大效能？

在这篇文章中，我们介绍在各类智能体 AI 系统中提升性能最有效的技术1。

我们先介绍如何：

- 构建并测试你的工具原型

- 与智能体一起为你的工具创建并运行全面的评测

- 与 Claude Code 这样的智能体协作，自动提升工具性能

最后我们会分享一路总结出的、编写高质量工具的关键原则：

- 选对要实现（以及不要实现）的工具

- 用命名空间划定工具的功能边界

- 让工具把有意义的上下文返回给智能体

- 优化工具响应的 token 效率

- 对工具描述和规格说明做提示工程

构建评测能让你系统性地衡量工具的表现。你可以用 Claude Code 针对这套评测自动优化你的工具。

## 什么是工具？

在计算领域，确定性系统给定相同的输入，每次都会产生相同的输出；而非确定性系统——比如智能体——即使起点条件相同，生成的回应也可能不一样。

我们传统上写软件时，建立的是确定性系统之间的契约。比如 getWeather("NYC") 这样的函数调用，每次被调用时都会以完全相同的方式取回纽约的天气。

工具是一种新形态的软件，它反映的是确定性系统与非确定性智能体之间的契约。当用户问「我今天该带伞吗？」时，智能体可能去调用天气工具，也可能直接凭已有知识回答，甚至可能先问一句位置以便澄清。偶尔，智能体会产生幻觉，甚至没能理解该如何使用某个工具。

这意味着我们为智能体编写软件时需要从根本上重新思考思路：不再按给其他开发者或系统写函数与 API 的方式来写工具和 MCP 服务器，而要专门为智能体来设计它们。

我们的目标是借助工具让智能体尝试各种成功策略，从而扩大它能有效解决的任务范围。幸运的是，根据我们的经验，对智能体最「顺手」的工具，对人类来说也往往出乎意料地容易理解。

## 如何编写工具

本节介绍如何与智能体协作，既帮它编写你给它的工具，也帮它改进这些工具。先快速搭起工具原型并在本地测试。接着运行一次全面的评测，衡量之后的改动。在与智能体协作的过程中，你可以反复迭代评测与改进，直到智能体在真实任务上表现出色。

### 构建原型

不亲自动手做一遍，很难预判哪些工具对智能体顺手、哪些不顺手。先快速搭起你的工具原型。如果你在用 Claude Code 写这些工具（可能一次成型），那么把工具依赖的任何软件库、API 或 SDK 的文档提供给 Claude 会很有帮助（包括可能用到的 MCP SDK）。对 LLM 友好的文档通常能在官方文档网站上的扁平 llms.txt 文件里找到（这是我们 API 的 llms.txt）。

把工具包进一个本地 MCP 服务器或桌面扩展（DXT），你就能在 Claude Code 或 Claude 桌面应用里连接并测试它们。

要把本地 MCP 服务器连到 Claude Code，运行 claude mcp add <name> <command> [args...]。

要把本地 MCP 服务器或 DXT 连到 Claude 桌面应用，分别进入 Settings > Developer 或 Settings > Extensions。

工具也可以直接传给 Anthropic API 调用，用于程序化测试。

自己先测一遍工具，找出其中的毛刺。收集用户的反馈，建立直觉：你的工具预期要支撑哪些用例和提示词。

### 运行评测

接下来，你需要通过运行评测来衡量 Claude 使用你的工具的效果如何。先基于真实世界的用法生成大量评测任务。我们建议与智能体协作，让它帮你分析结果、判断该如何改进工具。我们的工具评测 cookbook 有这套流程的端到端示例。

生成评测任务

有了早期原型，Claude Code 可以快速探索你的工具，生成几十对提示词与回应。提示词应当从真实用法中汲取灵感，并基于真实的数据源与服务（例如内部知识库和微服务）。我们建议你避开过于简单或流于表面的「沙箱」环境，它们无法用足够的复杂度来压测你的工具。好的评测任务可能需要多次工具调用，甚至几十次。

下面是一些高质量任务的例子：

- 安排下周与 Jane 的会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会的会议记录，并预订一间会议室。

- 客户 ID 9182 反馈说，一次购买尝试被扣款了三次。找出所有相关的日志记录，并判断是否还有其他客户受到同一问题影响。

- 客户 Sarah Chen 刚刚提交了取消请求。准备一份挽留方案。判断：(1) 她为什么离开；(2) 什么样的挽留方案最有吸引力；(3) 在给出方案之前我们还应该注意哪些风险因素。

下面是一些质量较差的任务：

- 安排下周与 jane@acme.corp 的会议。

- 在支付日志中搜索 purchase_complete 和 customer_id=9182。

- 找出客户 ID 45892 的取消请求。

每条评测提示词都应配上一个可验证的回应或结果。你的验证器可以简单到只是对标准答案与采样回应做精确字符串比较，也可以高级到请 Claude 来评判回应。避免过于严格的验证器——它们会因为格式、标点或其他同样有效的表述方式这类无关差异，把正确的回应判为错误。

对于每一对提示词与回应，你还可以选择性地指定你期望智能体在解决任务时调用哪些工具，以衡量智能体在评测中是否成功理解了每个工具的用途。不过，由于正确解决任务可能有多条有效路径，尽量避免过度指定或过拟合到某一种策略。

运行评测

我们建议直接通过 LLM API 调用来程序化地运行评测。使用简单的智能体循环（用 while 循环包裹交替进行的 LLM API 调用与工具调用）：每条评测任务一个循环。每个评测智能体应当只拿到一条任务提示词和你的工具。

在评测智能体的系统提示词中，我们建议要求智能体不仅输出用于校验的结构化回应块，还输出推理块和反馈块。要求智能体在工具调用块和回应块之前先输出这些内容，可能通过触发思维链（CoT）行为提升 LLM 的有效智能水平。

如果你用 Claude 跑评测，可以直接打开交错思考（interleaved thinking）来获得类似的现成功能。这有助于你探查智能体为什么调用或不调用某些工具，并找出工具描述和规格说明中具体需要改进的地方。

除了顶层准确率，我们建议还收集其他指标，比如单次工具调用和单条任务的总耗时、工具调用总次数、token 总消耗量以及工具错误。追踪工具调用能揭示智能体常走的路径，也能提示哪些工具有整合合并的机会。

分析结果
智能体是发现问题和提供反馈的好搭档，从自相矛盾的工具描述，到低效的工具实现、让人摸不着头脑的工具 schema，它都能帮你看出来。但请记住：智能体在反馈和回应中略过的内容，往往比它说出来的更重要。大模型并不总是言其所想。

### 与智能体协作

你甚至可以让智能体帮你分析结果、改进工具。只要把评测智能体的记录拼接起来，粘贴进 Claude Code 就行。Claude 擅长分析记录，并一次性重构大量工具——比如确保新改动落地后，工具实现与工具描述仍保持自洽。

事实上，这篇文章中的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评测是在内部工作区之上构建的，映射出内部工作流的复杂度，包括真实项目、文档和消息。

我们依靠留出测试集来确保没有对「训练用」评测过拟合。这些测试集揭示出：即便相比「专家级」工具实现——无论这些工具是研究员手写的还是 Claude 自己生成的——我们仍能挖出额外的性能提升。

## 编写高效工具的原则

本节把我们的经验提炼为几条编写高效工具的指导原则。

### 为智能体选对工具

工具更多并不总能带来更好的结果。我们观察到的一个常见错误是，工具只是把已有的软件功能或 API 端点包了一层——至于这些工具是否适合智能体，则无人过问。原因在于，智能体对传统软件有着不同的「可供性」——也就是说，它们感知自己能用这些工具采取哪些行动的方式不一样。

LLM 智能体的「上下文」是有限的（也就是说，它一次能处理的信息量有上限），而计算机的内存既廉价又充足。想象一下在通讯录里查找某个联系人的任务。传统软件程序可以高效地存储并逐个处理联系人，每查完一个再继续。

但如果 LLM 智能体用的工具返回全部联系人，然后它不得不逐个 token 地读完，那它就是把有限的上下文空间浪费在无关信息上了（想象一下你逐页从头读到底在通讯录里找一个联系人——也就是暴力搜索）。更好也更自然的做法（对智能体和人都一样）是先跳到相关的那一页（比如按字母顺序找到它）。

我们建议围绕特定的高影响工作流，构建少量经过深思熟虑的工具，与你的评测任务相匹配，并从那里逐步扩展。在通讯录这个例子里，你可以选择实现 search_contacts 或 message_contact，而不是 list_contacts。

工具可以整合功能，把潜在的多个独立操作（或 API 调用）收到内部处理。例如，工具可以用相关元数据丰富工具回应，或者把经常串联的多步任务合并为一次工具调用。

举几个例子：

- 与其实现 list_users、list_events 和 create_event，不如实现一个 schedule_event 工具，由它查找空闲时间并安排日程。

- 与其实现 read_logs，不如实现 search_logs，只返回相关的日志行及其少量上下文。

- 与其实现 get_customer_by_id、list_transactions 和 list_notes，不如实现一个 get_customer_context，把某位客户近期且相关的信息一次性汇总起来。

确保你构建的每个工具都有清晰而明确的用途。工具应当让智能体在拿到同样的底层资源时，能像人一样把任务拆分开来逐个解决，同时减少那些原本会被中间输出消耗掉的上下文。

工具太多或功能重叠，也可能让智能体偏离高效策略。谨慎而有取舍地规划你要构建（或不构建）哪些工具，回报会非常可观。

### 给工具加命名空间

你的 AI 智能体可能会接入几十个 MCP 服务器和几百种不同的工具——其中也包括其他开发者提供的。当工具功能重叠或用途模糊时，智能体就会搞不清该用哪个。

命名空间（把相关工具归到共同前缀之下）有助于在大量工具之间划清边界；MCP 客户端有时默认就这么做。例如，按服务给工具加命名空间（如 asana_search、jira_search），或按资源加（如 asana_projects_search、asana_users_search），都能帮助智能体在恰当的时机选对工具。

我们发现，选择前缀式还是后缀式命名空间，对我们的工具调用评测有不可忽视的影响。影响因大模型而异，我们建议你根据自己的评测来选定命名方案。

智能体可能调用错误的工具、用错误的参数调用正确的工具、调用工具太少，或者错误地处理工具回应。只实现那些名字体现任务自然切分的工具，你就能同时减少载入智能体上下文的工具数量和工具描述，并把智能体式计算从上下文挪回到工具调用本身。这降低了智能体整体犯错的概率。

### 让工具返回有意义的上下文

同理，工具实现应当只把高信噪比的信息返回给智能体。它们应当优先保证上下文的相关性而非灵活性，并避开底层的技术标识符（例如：uuid、256px_image_url、mime_type）。而 name、image_url、file_type 这样的字段，更可能直接影响智能体后续的行动和回应。

智能体处理自然语言的名称、术语或标识符时，成功率也明显高于处理晦涩的标识符。我们发现，仅仅把任意的字母数字 UUID 换成语义上更有意义、更易理解的表述（甚至改成从 0 开始的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

在某些情况下，智能体可能需要同时应对自然语言和技术标识符两种形式的输出，哪怕只是为了触发后续的工具调用（例如 search_user(name='jane') → send_message(id=12345)）。你可以在工具中暴露一个简单的 response_format 枚举参数来同时支持两者，让智能体自己决定工具返回「简洁」还是「详细」的回应（见下图）。

### 优化工具响应的 token 效率

优化上下文的质量很重要。但优化工具回应返回给智能体的上下文数量同样重要。

对于任何可能占用大量上下文的工具回应，我们建议实现分页、范围选择、过滤和／或截断的某种组合，并给出合理的默认参数值。在 Claude Code 中，我们默认把工具回应限制在 25,000 个 token。我们预期智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求会一直存在。

如果你选择截断回应，一定要用有指导性的说明来引导智能体。你可以直接鼓励智能体采取更省 token 的策略，比如在知识检索任务中做多次小而精准的搜索，而不是一次宽泛的大范围搜索。同理，如果某次工具调用报错（例如在输入校验阶段），你可以对错误回应做提示工程，清楚传达具体且可执行的改进方向，而不是丢出一串晦涩的错误码或堆栈信息。

### 对工具描述做提示工程

现在讲到改进工具最有效的方法之一：对工具描述和规格说明做提示工程。因为它们会被载入智能体的上下文，所以整体上能把智能体引向有效的工具调用行为。

编写工具描述和规格说明时，想象一下你会如何向团队里的新人介绍这个工具。考虑那些你可能会默认带进来、却没写明的上下文——专门的查询格式、小众术语的定义、底层资源之间的关系——并把它们显式写出来。通过清晰描述（并用严格的数据模型加以约束）预期的输入和输出来避免歧义。特别地，输入参数的命名要明确无歧义：不要用名为 user 的参数，试试叫 user_id。

有了评测，你就能更有把握地衡量提示工程带来的影响。即便是对工具描述做很小的调整，也可能带来显著的提升。在我们对工具描述做出精确改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评测中达到了当前最优的表现，错误率大幅下降，任务完成度明显提升。

关于工具定义的其他最佳实践，可以查阅我们的开发者指南。如果你在为 Claude 构建工具，我们还建议读一读工具是如何被动态加载进 Claude 的系统提示词的。最后，如果你是在为某个 MCP 服务器编写工具，工具标注（tool annotations）有助于披露哪些工具需要访问开放世界资源或会做出破坏性改动。

## 展望未来

要为智能体构建高效工具，我们需要把软件开发实践从可预测的确定性模式，重新转向非确定性模式。

通过本文描述的这套迭代式、评测驱动的流程，我们识别出了一些关于什么让工具成功的稳定规律：高效的工具定义清晰而有意图，节制地使用智能体上下文，可以组合进各种不同的工作流，并让智能体能直观地解决真实世界的问题。

我们预计，未来智能体与外部世界交互的具体机制会不断演进——从 MCP 协议的更新，到底层大模型本身的升级。只要用系统化、评测驱动的方式来改进面向智能体的工具，我们就能确保：随着智能体能力不断增强，它们所依赖的工具也随之一起演进。
