## 1. 让 AI 手写 HTML 抽取器，还是用现成库？

### 原始需求

从 31 个课程 HTML 页面里抽取正文。第一直觉是用 BeautifulSoup 或 trafilatura——成熟、快、稳。

### 实际 prompt

> 从 31 个 HTML 页面抽取正文并转成语义 Segment。硬性要求：
> 1. 零第三方依赖，陌生人 clone 就能跑；
> 2. **`<pre>` 内的代码块必须原样保留**，围栏不能被破坏；
> 3. 表格要能保留行列结构；
> 4. 导航/页脚/订阅按钮这类样板文本要能过滤掉。
>
> 请先给出你的技术选型论证（用哪个库 or 自己写），再给实现。

### AI 的产出

AI 先推荐了 BeautifulSoup + trafilatura 的组合方案，理由是"成熟稳定、边界情况处理完善"。同时它也指出了我方案里的真实风险。

**然后我否掉了。** 理由写进了代码注释（`01_extract.py`）：

```python
# 之所以自己写而不是用 BeautifulSoup：
# 1) 零依赖，`git clone` + `python 01_extract.py` 就能跑，陌生人零成本复用；
# 2) 我们需要保留 <pre> 代码块原样，而这正是通用清洗库最容易破坏的地方。
```

### 人工调整

人工补了两条 AI 没提的：

1. **样板文本过滤**（`filter_boilerplate()`）——AI 只想着"怎么抽干净"，没想到"抽出来还是垃圾"。
2. **控制字符清理**（`normalize_ws` 里的 `CONTROL_CHARS`）——这是后来踩坑才补的，见第 2 节。

### 前后对比

**用现成库（预判结果）**：

```python
# 3 行搞定，但：
soup = BeautifulSoup(html, "html.parser")
main = soup.find("article") or soup.find("main")
text = main.get_text("\n", strip=True)
# ❌ <pre> 里的代码和正文被一起 get_text，缩进全毁
# ❌ 导航/页脚全进来
# ❌ 表格变成一坨纯文本
# ❌ requirements.txt 里多出 3 个依赖
```

**手写（实际产出）**：

```python
# 约 200 行，但换来：
class ArticleParser(HTMLParser):
    def handle_starttag(self, tag, attrs):
        if tag == "pre":
            self._flush()
            self._in_pre = True      # 代码块单独缓冲，不与正文混流
    ...
def is_probably_code(text):   # 代码识别
def filter_boilerplate(blocks) # 样板过滤
```

**实测效果**：
- 33 篇抽出 714 个 Block，代码块识别准确
- **过滤掉 955 块导航/页脚样板**（占原始 Block 的 14%）
  - `agentic-ai-threats`：561 → 454
  - `ai-code-review-best-practices`：227 → 143
  - `warp-vs-claude-code`：98 → 63
- 依赖：只有 `pypdf`（且仅 PDF 需要）

### 为什么这么做

**判断依据来自交付目标，不来自技术偏好。** 挑战的验收要求里有"陌生人可按说明独立使用"和"换一门课能复跑"。为省200 行代码而引入 3 个依赖，陌生人 clone 后第一步就是 `pip install` 失败——**这是把成本转嫁给了使用者**。

更重要的是 `<pre>` 破坏：这份资料里代码块占比不低，缩进被毁的技术文档是不能用的。

## 2. QC 报 267 条术语违规：改译文，还是改规则？

**这是本项目最重要的一次决策，也是我犯的最大的一个错。**

### 原始需求

跑自动质检，检查术语一致性。

### AI 的产出（第一版 QC）

```
术语违规数: 267（阈值 = 0）
  71  「不同」 -> 应为「差异」   (Diff)
  55  「模式」 -> 应为「schema」  (Schema)
  48  「码库」 -> 应为「代码库」  (Codebase)
  13  「背景」 -> 应为「上下文」  (Context)
  13  「期间」 -> 应为「跨度（span）」(Span)
```

从数据看，**译文质量很差**——到处都是术语没统一。

### 人工调整

我逐条打印了告警的上下文。第一条就露馅了：

```
[不同] …提示词的结构和风格对引导 AI 的回应影响很大。不同模型对特定格式的响应可能更好…
```

**这里的"不同"是形容词，不是把 diff 译错了。**

于是我回去查代码，找到了两层bug：

```python
# Bug 1：纯子串匹配
if bad in zh_text:          # 「码库」是「代码库」的子串，必然误报

# Bug 2（更隐蔽）：判断"原文是否含该术语"时没有词边界
if any(k in low for k in keys)   # "diff" in "different" → True！
```

Bug 2 特别值得说：逻辑上"原文确实含 diff（其实含的是 different）、译文确实含'不同'（被当成 diff 的错译）"，**每一步都'正确'，结论完全错误**。

### 前后对比

**修法 1：加词边界 + 规范译法并存降级**

```python
@staticmethod
def _has_term(haystack_lower, term_lower):
    idx = haystack_lower.find(term_lower)
    while idx != -1:
        before = haystack_lower[idx-1] if idx > 0 else " "
        after_i = idx + len(term_lower)
        after = haystack_lower[after_i] if after_i < len(haystack_lower) else " "
        if not before.isalnum() and not after.isalnum():
            return True          # 词边界通过
        idx = haystack_lower.find(term_lower, idx+1)
    return False

# 规范译法也在译文里 → 说明译者是一致的 → 降级为提示
if core and core in zh_text:
    level = "info"
```

**效果**：267 → **59**

**修法 2：识别"术语歧义"**

剩下 6 条逐条看，仍然全是误报，但换了类型：

| 告警 | 实际语境 | 真相 |
|---|---|---|
| 「背景」→「上下文」 | 「把这张照片的**背景**换成星空夜景」 | background |
| 「光标」→「Cursor」 | 「现代终端体验：**光标**移动、语法高亮」 | 就是光标 |
| 「秘密」→「密钥」 | 「帮你理清系统的**秘密**武器」 | 习语 |
| 「语境」→「上下文」 | 「在 AI **语境**中」 | 正常中文 |

**这类问题的本质**：`forbidden` 里的词本身就是**常用中文词**，脚本没有能力区分"术语误译"和"普通词义"。

**修法 3：引入 `ambiguous` 字段**

```json
{ "en": "Context", "zh": "上下文",
  "ambiguous": ["背景", "语境"] }
```

这类词**只报提示、不阻塞交付，交人工抽检**。共标记 33 条。

**效果**：硬错误 59 → **0**

### 迭代全记录

| 轮次 | 术语硬错误 | 漏译红灯 | 修了什么 |
|---|---|---|---|
| 第一版 | 267 | 30 | — |
| 第二轮 | 59 | — | 词边界匹配 + 规范译法并存降级 |
| 第三轮 | 6 | — | `ambiguous` 字段（33 条降级为提示） |
| 第四轮 | 0 | 4 | `strip_code()` 剥离 5 类必留英文 + 绝对数量下限 |
| 第五轮 | 0 | 0 | 覆盖率口径修正 |

### 为什么这么做

**如果当时选择"改译文"，会发生什么？**

我可能会让 agent 把 71 处"不同"全改成"差异"：

> ❌ 「**不同**模型对特定格式的响应可能更好」→ 「**差异**模型对特定格式的响应可能更好」

**译文会变得莫名其妙，而 QC 报告全绿。** 绿色的报告、错误的译文——**这比红色的报告更危险**，因为它会让所有人误以为质量达标。

**这四次迭代真正的产物不是"0 个违规"，而是 297 条误报样本。** 它们精确标注了"自动化判断的边界"在哪。我建议把它们固化成 `tests/qc_regression.json`（已写进 AAR 改进方案 P0）。

**核心原则：调阈值让告警消失是掩盖问题；标注不确定性才是解决问题。**

## 3. 把 171 条术语全塞进 prompt，还是只注入本段命中的？

### 原始需求

翻译 666 个 Segment。术语表 171 条，要保证全文一致。

### 第一版方案

把整个术语表拼进每个 prompt。简单、可靠、不会出现术语"没注入"的情况。

### 人工调整

我在估算时意识到一个问题：**666 段 × 171 条术语**，大部分术语在大部分段落里根本不出现。

比如翻译一个讲OAuth 令牌刷新的段落，把"上下文腐化""幂等性""故障事件"这些塞进去，**只会稀释模型对真正相关术语的注意力**。

### 实际 prompt（改后）

```python
def build_prompt(segment, glossary):
    text = segment["text"]
    low = text.lower()
    # 只注入本段实际命中的术语
    hit = [t.en for t in glossary.terms
           if any((k or "").lower() in low for k in [t.en, *t.aliases])]
    block = glossary.glossary_prompt_block(hit)
    return SYSTEM_PROMPT.replace("{glossary}", block), text
```

prompt 里的术语部分长这样（真实节选）：

```
## 术语表（英文 → 规范中文译法）
- Context Rot → 上下文腐化（勿用：上下文腐烂、上下文失效）
- Retrieval-Augmented Generation / RAG → RAG（检索增强生成）
- Token → token（词元）（勿用：令牌、标记）
- LLM → 大语言模型（LLM）（勿用：大型语言模型）
```

### 前后对比

| | 全量注入 | 按段注入 |
|---|---|---|
| 每个 prompt 术语数 | 171 条 | **20～60 条** |
| 术语相关性 | 大量无关术语占注意力 | 全部相关 |
| 漏注入风险 | 无 | 无（代码保证全覆盖） |
| prompt 长度 | ~8000 tokens | ~2000 tokens |

**11 个翻译 agent 的独立反馈印证了这个决策**——多个 agent 在报告里明确提到"按 glossary 要求在首次出现处加注：SSE（服务器推送事件）、stdio（标准输入输出）、大语言模型（LLM）"，说明它们确实在**认真读注入的术语块**，而不是被淹没。

### 为什么这么做

**prompt 预算要用在刀刃上。** 术语注入的目的是"让模型知道这几个词的规范译法"，注入 100 个不相关的词只会让这7 个变得更不重要。

**同时用代码保证不漏**——`hit` 的计算是机械的，不依赖 agent 自觉。这是"约束前置到代码"而不是"叮嘱模型"。

## 4. 「覆盖率 166%」：超额完成，还是算错了？

### 原始需求

算覆盖率，验收要求 ≥80%。

### AI 的产出

QC 全部转绿后，报告里出现：

```
词级覆盖率: 166.0%（阈值 ≥ 80%）
文档级覆盖率: 33/33 = 100.0%
Segment 翻译率: 666/666 = 100.0%
术语违规数: 0
红色问题数: 0
```

**166%。这不可能。**

### 人工调整

查代码，找到了：

```python
total_zh = sum(d["zh_words"] for d in docs.values())
word_coverage = total_zh / total_en
#             ↑ 中文字数        ↑ 英文词数
```

而 `count_words()` 里：

```python
def count_words(text):
    en = len(re.findall(r"[A-Za-z][A-Za-z'-]*", text))    # 英文：1 词 = 1
    zh = len(re.findall(r"[\u4e00-\u9fff]", text))        # 中文：1 字 = 1
    return en + zh
```

**每个汉字算一个"词"。** "context" 是 1 个词，"上下文"是 3 个"词"。所以中文字数天然是英文词数的 1.5～2 倍，比值 1.66 完全正常。

**这不是超额完成，是度量单位不一致。**

### 前后对比

**修法**：

```python
# 覆盖率 = 已译 Segment 的原文词数 ÷ 全部可译词数（统一原文侧口径）
en_done = sum(d["translated_words"] for d in docs.values() if d["coverage"] > 0)
word_coverage = en_done / en_all

# 中英长度比单独报告，并说明中文预期区间
length_ratio = total_zh / total_en   # 正常 1.0～2.1
```

顺带修了长度比阈值。原来拍脑袋定 1.9，102 段报警；改到有依据的 0.75/2.4，并给短段落豁免：

```python
# 短段落不适用：像 "## MCP 架构——一览" 这种标题只有几个词，
# 中英用词密度天然不同，比例低不代表漏译。设 25 词下限。
if res["en_words"] < 25:
    res["note"] = "短段落，长度比不作为判定依据"
```

**修后**：

```
词级覆盖率: 100.0%（阈值 ≥ 80%）      ← 诚实的口径
红色问题数: 0（阈值 = 0）              ← 唯一被修掉的真红灯
```

### 为什么这么做

**指标漂亮到不可信时，先怀疑指标。**

这个案例的价值在于：166% 比 80% 更"好看"，如果我不看就收工，会在README 里写下"覆盖率 166%，超额完成 86%"——**一个技术上错误、且会让读者怀疑整个项目的数字**。

同样的怀疑态度帮我抓住了 `splitlines()` 的 bug：**1116 行里只有 714 条记录**，这个"多出来的 402 行"是唯一的线索。

## 5. 指纹不能算错：让 AI 手算，还是写脚本？

### 原始需求

译文要缓存，键是原文的 sha1 指纹。人和 AI 都要能写入缓存。

### 问题

如果让人（或让 AI）手写文件名：

```
cache/translations/a3f5c8e91d2b4f6a...json
```

**不可能手算对。** 算错的后果很隐蔽：译文写进去了，但下次读不到，表现为"我明明翻译了怎么显示待译"——排查起来极其痛苦。

### AI 的产出

AI 提了两个方案：

1. 让人/AI 复制粘贴脚本输出里的指纹；
2. 在prompt 里给一段 Python 代码，让 AI 每次运行计算。

**两个都不好。** 方案 1 靠人复制，方案 2 靠 AI 每次记得跑——都是"把易错环节交给执行者"。

### 人工调整

我写了 `batch.py` 作为**粘合层**，让"算指纹"这件事**根本不出现在人的工作流里**：

```bash
# 1) 导出待译批次（自动带术语约束）
python batch.py export --docs claude-code-best-practices --out ../work/tr.json

# 2) 翻译，把译文填进tr.json 的 translations 字段（只需要填 seg_id → 译文）

# 3) 回填（自动算指纹、校验、包内路径）
python batch.py import --file ../work/tr.json
```

### 前后对比

**没有 batch.py（错误做法）**：

```
人/AI 写：cache/translations/<手算的sha1>.json
  ↓
✗ 算错 → 译文丢失，且不报错，只是"下次没生效"
✗ 路径写错 → 译文写到别处
✗ JSON 格式错 → 读的时候才炸
```

**有 batch.py（实际做法）**：

```python
def cmd_import(args):
    rows = {r["seg_id"]: r for r in load_segments(proj["work_dir"])}
    for seg_id, zh in tr.items():
        if seg_id not in items:      # 校验：seg_id 必须在批次里
            problems.append(f"{seg_id}: 不在批次 items 中")
            continue
        r = rows[seg_id]
        fp = r.get("fingerprint") or sha1(r["text"])   # 指纹从主干数据取，不手算
        (cache / f"{fp}.json").write_text(json.dumps({
            "seg_id": seg_id, "doc_id": r["doc_id"],
            "fingerprint": fp, "zh": zh,
            "meta": {"source": args.file},
        }, ensure_ascii=False, indent=1), encoding="utf-8")
```

**实测**：11 个批次、666 条译文，**回填失败 0 条**。

### 为什么这么做

**管线的价值不在"AI 能翻译"，而在"人能可靠地参与"。**

11 个 agent 并行翻译时，如果其中一个算错指纹，它的工作就静默丢失了。`batch.py` 让失败变成**显式的**：

```
回填 104 条译文 → cache/translations/（失败 0）
  !! xxx#0007: 不在批次 items 中（可能原文已变更，需重新 export）
```

**人只负责"把英文变成中文"，这是一件不会出错的事；其余全部交给脚本。**

这是我在整个项目里最满意的一个设计——它不提高效率，它**消除人类必然犯的错**。

## 附：这5 个决策的共同点

| # | 决策 | 表面在做什么 | 实际在做什么 |
|---|---|---|---|
| 1 | 手写抽取器 | 技术选型 | **把依赖成本从使用者身上移走** |
| 2 | 改 QC 规则而非译文 | 修 bug | **拒绝"绿色的报告 + 错误的译文"** |
| 3 | 按段注入术语 | 优化 prompt | **把prompt 预算用在刀刃上** |
| 4 | 修正覆盖率口径 | 修指标 | **不信任漂亮到不可信的数字** |
| 5 | 写 batch.py | 加个工具 | **把易错环节移出人的工作流** |

**没有一个是"用了 AI 所以效率更高"。** 全都是"**这里会出错，所以我加了一道机械的保障**"。

这也是我认为这个任务真正的难点——**不是让 AI 翻译 9 万词（那只是体力活），而是设计一套让错误无法静默通过的机制。**
