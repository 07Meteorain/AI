## 3. S2：参考方案研究阶段（4 轮）

### 轮次 2.1 —— 定位可用证据

**我的提问**：
> 「官方仓库里有33 个 records。不要复述 README 列表。我要知道：**哪个记录能证明『评估策略本身』对BPB 有独立贡献**，且它的训练配置与 baseline 完全相同？」

**AI 的检索结果**：`2026-03-19_SlidingWindowEval`

**这条检索为什么重要**：我原本想找一个「BPB 最低的记录」来抄。但真正有价值的问题是「**哪个记录能做干净的对照实验**」。找到它之后，我读它的 README，发现它明确写了 pre-quant BPB 几乎相同（1.2172 vs 1.2196）而 post-quant 差 0.0319——**这就是一个教科书级的单变量对照**。

**如果我当初只找「最好的方案」，我会直接去抄 SOTA 的 SP8192+recurrence+TTT，而完全错过「评估策略有 0.03 空间」这个最容易验证、风险最低的切入点。**

### 轮次 2.2 —— 读源码而非读结论

**我的提问**：
> 「把 SlidingWindowEval 的 `eval_val_sliding` 实现讲清楚：窗口怎么切？每个 token 会不会被重复计分？第一个窗口怎么处理？为什么这样设计是因果合法的？」

**AI 逐行解释了核心逻辑**：
```python
s = 0 if ws == 0 else max(wlen - stride, 0)
```
这一行是整段代码的**关键**：第一个窗口必须计分全部（否则开头 token 永远拿不到分），之后的窗口只计分最右边 stride 个（左边已计过）。

**我的收获**：我确认了「每个 token 恰好计分一次」这个性质。如果没有这轮源码阅读，我可能会写出一个重复计分的版本，然后得到一个虚高的 BPB——而官方明确说「BPB 无法被 hack，只能被真实优化提升」，抓到 bug 反而作废。

### 轮次 2.3 —— 交叉验证第二个证据

**我的提问**：
> 「FP16Embed 记录的收益是 -0.013 nats。它是怎么来的？」

**AI 指出**：那 -0.013 其实是**两个改动叠加**的结果：
1. fp16 嵌入直传（贡献大部分）
2. warmdown 1200→3600 + matrix_lr 0.04→0.06

**我的判断**：这个信息 README 里没写清楚，是从配置差异推断出来的。**这说明我不能只看 README 的结论数字，要看配置差异**。我把这两项在我的实验矩阵里**拆成 E2（fp16）和 E5（LR）两个独立实验**，而不是当成一个整体——这样才能知道各自贡献多少。

### 轮次 2.4 —— 识别 SOTA 里不可移植的部分

**我的提问**：
> 「当前 SOTA（1.0810）用了 7 项技术。我的条件是单卡 4GB。哪几项我**结构性地无法验证**？」

**AI 分析**（我逐项判断后接受）：

| 技术 | 我的判断 |
|------|---------|
| SP8192 | **无法验证** —— 需重导数据，我无法确认 BPB 计算与官方一致 |
| 3-layer recurrence | **无法验证** —— 依赖 11 层物理层，我只有 6 层显存预算 |
| legal TTT | **无法验证合规性** —— 判违规则提交作废 |
| GPTQ/SDClip | 边际收益低，int8 已够用 |
| 并行残差 | 可验证（虽然收益可能依赖规模）|
| QK-gain | 可验证（但需扫描，不能照抄 5.25） |
| LR 调优 | 可验证 |

**我的决策**：这个分析直接变成了 `方案设计.md` 里的「**否决清单**」。我认为**写清楚为什么不做什么，比罗列做了什么更有说服力**。

## 4. S3：方案设计阶段（5 轮）

### 轮次 3.1 —— 假设生成

**我的提问**：
> 「我只有一个单卡 4GB 环境。给我 10 个**能在这种条件下被证伪**的假设，不要给我需要 8卡才能验证的空想。」

**价值判断**：这一轮我明确加了「**能被证伪**」这个约束。如果不加，AI 会给我「用 MoE」「用 RLHF」这类完全无法验证的建议。**加约束条件是让 AI 输出可用的关键技巧。**

### 轮次 3.2 —— 主线选择

**我的提问**：
> 「评估策略 vs 优化器 vs 架构，作为第一主线，各利弊？如果只能选一个，选哪个？」

**AI 的分析**：评估策略是唯一「零训练成本、零模型改动、纯确定性收益」的一项。

**我的独立判断**：我补充了 AI 没考虑到的一点——**评估策略是我唯一能在本地完整验证的**。其他项即使方向对，我也只能验证「没崩」，无法验证「有效」。

**这一轮的关键学习**：AI 能给分析，但**最终决策的依据是我自己的约束条件**。我不应该让 AI 替我决定主线。

### 轮次 3.3 —— 预判失败模式

**我的提问**：
> 「假设 fp16 嵌入导致 artifact 超 16MB。给出完整的应对决策树，不要只说『缩小模型』。」

**AI 输出**：baseline 用掉 15,863,489 字节，距16,000,000 只剩约 136KB；fp16 嵌入需约 512KB；**不够**。应对是缩 MLP hidden（上游用过 1024→992）。

**我的补充**：我加了一条 AI 没提的——
> 「如果所有腾挪都压不下来，**放弃 fp16 嵌入，把空间给模型容量**。0.007 BPB 不值得让模型整体变小。」

**这一轮的价值**：预判失败模式的价值不在于「避免失败」，而在于**失败时不必临场慌乱**。而且我提前想清楚了「什么情况下该放弃」，这避免了沉没成本陷阱。

### 轮次 3.4 —— 否决清单

**我的提问**：
> 「列出所有被上游验证为**负收益**的技术，我不要重复踩坑。」

**AI 找到**（来自 `FP16Embed_WD3600` 的「things I tried that didn't work」）：
- SwiGLU：per-step 更好但慢 45%，net negative
- depth recurrence：10 分钟步数不够
- QAT：每步开销不值得
- lzma：比 zlib 压得更差
- 更高 embed LR（0.08）：损害收敛

**我的判断**：这一轮是**性价比最高的一轮**。我几乎没有成本就避免 了 5 个坑。而且这解释了为什么上游 SOTA 用 zlib 而不是 lzma。

### 轮次 3.5 —— 实验矩阵设计

**我的提问**：
> 「设计一个消融矩阵，要求：单变量对照、算力严格相等、每个实验能归因到一个明确的问题。」

**AI 的初稿有问题**：它建议每个配置跑 3 个 seed。我指出了一个矛盾——
> 「7 个实验 × 3 seed = 21 次跑。我单卡每次 20分钟，要 7 小时。我已经跑过 E0~E6 后能估出噪声量级，没必要每个都烧 3 倍。」

**修正后的设计**：E0~E6 各跑 1 seed（7 次），只对最终组合 E6 跑 3 seed（3 次），共 10 次。

**这一轮的学习**：**AI 的建议需要基于我的实际约束来审查**，不能直接采纳。

## 5. S4：环境搭建阶段（6 轮，含 3 个真实 bug）

这一阶段是**人-AI 协作价值最明显的地方**：AI 帮我诊断了 3 个我完全看不懂的错误。

### 轮次 4.1 —— 网络封锁

**问题**：`huggingface.co` 返回 502，官方数据下载不了。

**AI 的排查**：逐个测试候选源，发现——
- PyPI：✅ 可用
- `hf-mirror.com`：✅ **可用**
- `raw.githubusercontent.com`：❌
- `cdn-lfs.huggingface.co`：❌（fused kernel 走这个，必然失败）

**关键判断**：`cdn-lfs` 被封意味着即使 API 通了，大文件下载也会失败。这避免了「下载 20分钟后失败」的浪费。

### 轮次 4.2 —— torch CPU轮子

**问题**：`pip install torch` 装成了 `2.14.1+cpu`，`torch.cuda.is_available()` 返回 False。

**AI 的诊断**：PyPI 的 Windows 默认轮子是 CPU-only，必须指定 CUDA index。

**解决**：`pip install torch --index-url https://download.pytorch.org/whl/cu124` → `2.6.0+cu124`。

**踩坑记录**：我第一次试`cu121` index 时报 `No matching distribution`（因为 Python 3.13 + cu121 无匹配轮子）。AI 建议换 `cu124` 才成功。**这类环境问题不试错无法解决。**

### 轮次 4.3 —— bug #1：GQA 内核不可用

**报错**：`TorchRuntimeError: Failed running call_function <built-in function scaled_dot_product_attention>... No available kernel. Aborting execution.`

**我自己的第一反应（错的）**：以为是显存不够或 batch 太小。

**AI 的诊断**：让我实际探测各 SDPA 后端。探测结果：
```
FLASH FAIL No available kernel
MEM_EFF FAIL No available kernel
MATH OK
CUDNN OK
```
并指出警告信息：`For dense input, both fused kernels require query, key and value to have the same num_heads. Query[2,8,512,32], Key[2,4,512,32]`。

**根因**：fused GQA 内核在当前构建下**不支持 kv head 广播**（官方 8×H100 上可用，因为有flash-attn 3）。

**我的解决**：实现 `GQA_IMPL` 自动探测——启动时试一次 fused，不可用就降级为 `repeat_interleave` 手动展开（数学等价）。

**这一轮的价值**：如果只是反复调 batch size，我会浪费大量时间且永远修不好。**AI 的价值在于「设计一个探针把猜测变成事实」。**

### 轮次 4.4 —— bug #2：Triton 缺失

**报错**：`RuntimeError: Cannot find a working triton installation.`

**AI 的诊断**：Windows 不带Triton，`torch.compile` 的 inductor 后端不可用。官方 Linux + H100 环境自带。

**我的解决**：加 `USE_COMPILE` 开关，本地走 eager。

**我的推理（重要）**：我判断这**不影响结论有效性**，理由是——我的实验用**固定步数**做等算力对照，而不是固定 wallclock。eager 慢只意味着每个实验耗时更长，但 1000 步 × 相同模型 = 相同计算量，BPB 可比。

**这个判断不是 AI 告诉我的，是我自己想清楚的。** 如果我当初选了「固定 wallclock」作为对照变量，那么 eager 模式下每个实验只跑 200 步 vs 编译模式跑 1000 步，**结论就彻底失效了**。这是我整个实验设计里最重要的一次预判。

### 轮次 4.5 —— bug #3：评估超时

**问题**：冒烟测试 15 分钟超时（900s 被 SIGTERM）。

**AI 的分析**：训练只花 32 秒，慢的是**评估**——官方验证集 62,021,632 tokens，滑窗 stride=128 需 15 万个窗口。

**我的解决**：加 `MAX_VAL_TOKENS` 参数，取验证集**前缀**。

**为什么取前缀是合法的**：官方验证集本身就是**冻结的前 50k 文档**，取前缀不引入任何选择偏差。而且我**只用它做 sliding vs chunked 的同 checkpoint 对照**，不做超参选择。

**诚实要求**：我在 submission.json 里加了 `val_set_is_full_official` 字段，任何人拿到我的结果都能一眼看出这是全集还是子集。**可追溯性比好看重要。**

### 轮次 4.6 —— 步数标定

**我的提问**：
> 「实测单步耗时和显存，不要估算。」

**实测结果**：0.053s/step（batch 8×512），峰值 405MB（评估时 948MB）。

**用途**：确认 4GB 显存放得下 → 6 层 256 维的配置可行 → 1000 步实验约 90 秒训练 + 评估。

**这一轮的价值**：把「我觉得能跑」变成「我确认真能跑」。**在受限环境下，实测标定比推理可靠。**

## 6. S5：代码实现阶段（4 轮）

### 轮次 5.1 —— 骨架搭建

**我的提问**：
> 「我要在官方 `train_gpt.py` 上加 5 个可开关的改动，但一行基座代码都不改。帮我规划最小侵入的改造点。」

**AI 的方案**：把 `eval_val` 拆成两个独立函数（chunked / sliding），其余改动用环境变量开关。

**我的采纳与调整**：我额外要求 submission.json 里必须包含**每个改动的开关状态**。理由——别人复现我的结果时，必须知道确切配置，否则就无法验证。

### 轮次 5.2 —— 逐行解释官方量化逻辑

**我的提问**：
> 「逐行解释 `quantize_state_dict_int8`，特别是：为什么小张量不量化？为什么用 per-row 而不是 per-tensor scale？`INT8_KEEP_FLOAT_MAX_NUMEL = 65536` 这个数字的依据是什么？」

**AI 的解释要点**：
- 小张量量化误差 > 存储收益，所以直接 fp16 保留
- 2D 矩阵不同输出通道的动态范围差异大，per-row scale 能用满码字
- 65536 是「量化开销 vs 收益」的工程经验阈值

**我的判断**：`INT8_KEEP_FLOAT_MAX_NUMEL` 这类阈值是**经验值不是推导值**。我不打算改它——改它需要大量实验验证，而我验证不起。**保持原样是最诚实的选择。**

### 轮次 5.3 —— 滑窗实现审查

**我的提问**：
> 「审查我写的 `eval_val_sliding`，重点：会不会重复计分？字节数统计和 chunked 路径是否一致？如果不一致我的对照实验就失效。」

**AI 指出的一致性风险**：我的 sliding 版本用 `float64` 直接累加，而 chunked 版本走 LUT。两边必须用**同一套逻辑**，否则 BPB 不可比。

**我的修正**：统一走同一套LUT 计算。

**这一轮的价值**：这是我**最关键的一次 review**。如果两边字节数算法不一致，`sliding_gain` 这个数字就是纯噪声，而它是我整个方案的主线证据。

### 轮次 5.4 —— 边界情况自查

**我的提问**：
> 「列出 eval_val_sliding 所有可能出错的边界情况。」

**AI 列出的清单**：
| 边界 | 处理 |
|------|------|
| 最后一个窗口不足 seq_len | `wlen = end - ws` 正确截断 |
| 第一个窗口 | `s = 0` 计分全部 |
| 窗口步进越过末尾 | `range(0, total_tokens, stride)` 天然处理 |
| 全局 token 数不被 seq_len 整除 | `load_validation_tokens` 里已对齐 |
| 多 rank 分片 | 按窗口数均分，边界 rank 拿到空列表也不报错 |

**我的处理**：全部确认已有正确处理。这个清单帮我发现「空窗口列表」这个情况虽然不会崩，但会打印 `0/0` 的进度——不影响正确性，容忍。

## 7. S6：实验与复盘阶段（3 轮）

### 轮次 6.1 —— 消融结果解读

**我的提问**：
> 「这是消融结果。请**只指出与我预期不符的地方**，不要重复确认我猜对的部分。」

**这个提问技巧的价值**：默认的「请分析这些数据」会让 AI 大量输出「你的结果符合预期」这类无用内容。**要求它只找异常**，直接把注意力集中在真正需要解释的地方。

### 轮次 6.2 —— 归因谨慎性检查

**我的提问**：
> 「E3（并行残差）单独跑有收益，但组合后收益消失。这说明什么？给我至少三种解释，并指出哪种需要额外实验验证。」

**AI 给出三种解释**：
1. 并行残差的收益依赖模型深度（6 层太浅，收益本就小）
2. 与其他改动有交互作用（梯度尺度变化）
3. 训练噪声（单 seed 无法排除）

**我的判断**：需要**单seed vs 3 seed 对比**才能区分。所以 E6 必须跑 3 seed。

**这一轮的价值**：AI 帮我避免了「把噪声当信号」的陷阱。**提出多种解释并指出哪个需要验证，而不是选一个最顺耳的。**

### 轮次 6.3 —— 结论边界审查

**我的提问**：
> 「审查我所有结论里，哪些是『本地实测支持的』，哪些是『从上游外推的』。任何混在一起的表述都指出来。」

**AI 的审查发现**：我在初版报告里有一处把「上游 SOTA 的 SP8192 收益」和「我的实测」放在同一段里，读者会误以为我也验证了 SP8192。

**我的修正**：所有结论**严格分两层**呈现——「本地实测」与「上游已验证」，且用不同表格样式区分。

**这一轮是整份AI 日志里最重要的一轮。** 因为这个 challenge 的评审标准里，「无成绩记录/无法复现」是明确的红旗，**结论的可追溯性直接决定成败**。AI 在这里帮我做了一次「诚实性审计」，这比任何技术建议都重要。

3. **要求自我审计**：「审查我的结论里哪些是实测、哪些是外推」——这直接防止了最致命的诚信问题

## 9. 诚实声明

1. 本日志记录的是**真实发生的排查与设计过程**，包括 3 个我一开始判断错误的 bug（GQA 内核、Triton 缺失、评估超时）。

4. 本项目**没有使用任何外部模型 API 训练**，也没有把数据或代码发送给第三方服务。AI 仅用于代码辅助、文档分析和方案讨论。
5. 时间戳为本次开发过程的**顺序记录**，非精确到秒——因为部分操作是并行的。**我不会为了「看起来更真实」而伪造精确时间戳。**
