## 0. 一句话概括我的方案

**不碰模型规模，只碰「每一比特怎么用」和「每个 token 用多少上下文打分」。**

官方 baseline 的 1.2244 BPB 里，有很大一块并不是模型能力不足，而是**评估方式本身在浪费信息**：它把验证集切成互不重叠的 1024-token 块，每块第一个 token 完全没有上下文，平均每个 token 只拿到约 512 个上文。我要做的第一件事不是改模型，而是改评估——用滑窗让每个 token 都拿到接近满额的上下文。这是零训练成本、零模型改动的纯工程收益，也是唯一一个我能用单卡就完整验证的改动。

在此之上，我再叠加三项**已被上游多次验证**的模型侧改动（fp16 嵌入直传、并行残差、QK-gain + LR 调度调优），每一项都做成可单独关闭的开关，构成消融矩阵。

## 1. 我打算把 1.2244 往哪个方向压？选一个主线

**主线选择：评估策略（Sliding Window Evaluation）。**

我不选「优化器升级」也不选「架构大改」作为第一主线，理由如下：

| 候选方向 | 为什么不作为主线 |
|---------|----------------|
| 升级 tokenizer 到 SP8192 | 历史收益最大（-0.03~-0.05），但它需要重新导出整个训练/验证集，且官方明确说「改tokenizer 的提交会被更严格审查」。我第一轮不想把风险全押在最容易被质疑的一环上。 |
| Muon 优化器升级 | **baseline 已经在用 Muon 了**。官方 `train_gpt.py` 的默认配置就是 Muon + Newton-Schulz。我要做的只是调 LR 和 momentum 区间，收益量级 -0.01~-0.02，且高度依赖具体超参，不是「换一个东西」的改善。 |
| 架构大改（depth recurrence 等） | 上游记录 `2026-03-18_FP16Embed_WD3600` 明确写了失败教训：depth recurrence「想法有潜力，但10 分钟给不了它足够的步数」。在没有 8×H100 的验证能力前押注它，是赌博。 |
| **评估策略（滑窗）** | **零训练成本、零模型改动、纯确定性收益，且能在本地小卡上完整复现验证。** |

所以我的判断是：**先拿确定收益，再谈架构冒险。**

## 2. 我怎么知道这个方向有效？—— 引用的证据

我读的是官方仓库里 `records/` 目录下的**实测记录**，不是二手博客：

### 证据 1（最直接）：`records/track_10min_16mb/2026-03-19_SlidingWindowEval/README.md`

该记录的作者用**与baseline 完全相同的架构和训练配置**，只改了评估方式：

| 指标 | Naive Baseline | Sliding Window |
|------|---------------|----------------|
| Pre-quant val_bpb | 1.2172 | 1.2196 |
| **Post-quant val_bpb** | **1.2244** | **1.1925** |
| 改善 | — | **-0.0319** |
| 训练步数 | 13,780 | 13,450 |

关键点在这个对照的**干净程度**：训练配置没动，pre-quant BPB 几乎一样（1.2172 vs 1.2196，差异来自训练步数差330 步），但 post-quant 差了 0.0319。这说明 **0.0319 全部来自评估方式**，不是来自训练。这是一次教科书级的单变量对照实验，正是 CHALLENGE.md 要求的「先写假设 → 跑对照 → 看差值」。

它用的机制是：`EVAL_STRIDE=64`，窗口长度仍是 1024，每步前进 64，只对最右边 64 个 token 计分。我读过了 `train_gpt.py` 的 `eval_val_sliding` 实现，确认了因果性——每个 token 恰好被计分一次，且只用前缀信息，没有未来泄漏。

### 证据 2：`records/track_10min_16mb/2026-03-18_FP16Embed_WD3600/README.md`

同一作者的相邻记录，讲了另一件事：

> 把 `tok_emb.weight` 从 int8 量化改成 fp16 直传，post-quant BPB 退化从 ~0.007 压到 ~0.0005。代价约 500KB artifact，于是把 MLP hidden 从 1024 降到 992 来腾空间。

这条证据的价值在于它揭示了**量化误差的来源分布**：tied embedding 同时承担 embedding 和 output head 两个角色，量化误差会直接放大到 logits 上，所以它是最敏感的张量。这是一个「用空间换精度」的正确权衡——而且我们本来就有空间权衡问题要解。

### 证据 3：`records/track_10min_16mb/2026-04-09_SP8192_3LayerRecur_ParResid_QK525_LegalTTT/README.md`（当前 SOTA 1.0810）

这份记录列出了冲进 SOTA 的 7 项技术。我从中筛出**能在我的验证条件下证伪或证实**的两项：

- **Parallel Residuals**（PR #1204/#1412）：attention 和 MLP 读同一份输入，GPT-J 风格。上游把它列为 -0.01 级别的贡献。
- **QK-Gain 5.25**：可学习的 per-head query 缩放，记录明确说「从 4.0 到 5.25 单调改进」。

我**没有**采用它的SP8192、3-layer recurrence 和 legal TTT——理由见第 4 节。

### 我的独立判断

以上三条都是别人的结果，我要做的不是复述，而是**在自己的条件下验证它们是否成立**。特别是证据 1 的 0.0319，我要在本地重跑一遍——因为上游是在 8×H100 上跑的，本地单卡训练出的模型不同，滑窗带来的上下文增益是否同样成立，需要我自己确认。**别人的数字只能当假设，不能当结论。**

## 3. 我打算跑多少次实验？每次看什么指标？

### 3.1 算力约束的现实

| 资源 | 状态 |
|------|------|
| 8× H100 SXM | ❌ 无。本机只有单张 RTX 3050（4GB 显存） |
| 云GPU |❌ 无预算（需先申请 Elite20 算力券，而申请前提就是这份草案） |
| FineWeb 验证集 | ✅ 已通过 hf-mirror 拿到官方 `fineweb_val_000000.bin`（124MB，官方 50k 文档全集） |
| 训练分片 | ✅ 已下载官方 `fineweb_train_*.bin` |

**这决定了我的实验策略：不能复现 10 分钟 8 卡的口径，但可以复现「单变量对照」的方法论。**

### 3.2 实验矩阵

我设计**等算力对照**——每个配置跑**完全相同的步数和 token 数**，唯一变量是要测的那一项。这样差值才能归因到那一个改动上。

|实验 | 配置 | 检验的假设 | 看的指标 |
|------|------|-----------|---------|
| E0 | baseline 原样（chunked 评估 + int8 嵌入） | 建立本地基线 | val_bpb、artifact bytes、量化前后差值 |
| E1 | baseline + 滑窗评估 | 上下文增益在本地是否复现 | val_bpb（sliding vs chunked 差值） |
| E2 | baseline + fp16 嵌入直传 | 量化退化能否压到 ~0.0005 | post-quant − pre-quant 差值、artifact bytes |
| E3 | baseline + 并行残差 | 架构改动的独立贡献 | val_bpb |
| E4 | baseline + QK-gain 调优 | per-head 缩放是否单调有效 | val_bpb |
| E5 | baseline + LR/warmdown 调优 | 10min 预算下 schedule 是否是瓶颈 | val_bpb、最终 train_loss |
| E6 | **全部组合** | 各组件是否协同 | val_bpb、artifact bytes |
| E7 | E6 的 3 个 seed | 结论是否稳定（非噪声） | val_bpb 均值 ± stderr |

**每个实验必看三个指标**，缺一不可：
1. `val_bpb`（越低越好，tokenizer 无关）
2. `artifact_bytes`（必须 ≤ 16,000,000，超了直接判负）
3. **量化前后差值** —— 这是我的方法论护城河。榜单分数用的是量化后的模型，如果只看 pre-quant 数字，我会把「模型变强」和「压缩变松」搞混。

### 3.3 算力预算怎么花

本地跑不满 10 分钟×多次，所以我把预算集中在**最需要验证的假设**上：

- E0/E1 必须跑：它们验证我方案的主线，也是所有其他实验的参照系。
- E2 必须跑：它决定我要不要为 fp16 嵌入腾artifact 空间，是**架构级的决策依据**。
- E3/E4/E5 各跑一次：确认方向，如果某个改动在本地无收益甚至有害，我就把它从组合里剔除，并如实记录。
- E7 只对最终组合跑 3 个 seed：因为 E0~E6 已经有 7 个数据点，噪声量级可以估出来，没必要每个都烧 3 倍算力。

## 4. 失败怎么办？

这一条我认真想了，因为它是这份草案里最能暴露真实水平的地方。

### 4.1 如果滑窗评估在本地没复现出收益

**可能原因**：滑窗的收益来自「每个 token 拿到更多上文」。如果本地模型训练得更少，上下文带来的增益可能被模型本身的欠拟合淹没。

**应对**：
1. 先分离两个因素——用**同一个 checkpoint** 分别跑 chunked 和 sliding，如果差值存在，说明是评估方式的功劳，与训练无关。这是最干净的验证，能排除「模型不同」这个混淆变量。
2. 如果差值显著小于上游的 0.0319，我会在报告里**如实写明差距**，并给出解释（训练步数差异导致的上下文利用能力差异）。**不会**去调参把它凑到 0.03。
3. 如果差值接近 0，我会检查 stride 是否过大（stride 越大，每个 token 的上文越少，收益越小），做 stride 扫描找最优点。

### 4.2 如果 fp16 嵌入直传导致超 16MB

这是**最可能发生的失败**，因为 fp16 比 int8 大一倍，而 tied embedding 有 1024×512 = 524,288 个参数，差值约 512KB。

**应对（按优先级）**：
1. 先量化 artifact 的实际余量——baseline 用掉15,863,489 字节，距 16,000,000 还有约 136KB，但 fp16 嵌入需要约 512KB，**不够**。
2. 按上游 `FP16Embed_WD3600` 的办法：把 MLP hidden 从 1024 降到 992，用省下的空间换嵌入的精度。这是个精确的容量置换。
3. 如果还不够，我按优先级继续砍：MLP hidden 992 → 960 → 896。每次改动后重新测artifact 和 BPB，因为缩 MLP 会损失模型能力，必须实测而非估算。
4. **如果所有腾挪都压不下来**，我的决策是：**放弃 fp16 嵌入，保留 int8 量化，把这约 500KB 用来加大模型或 MLP**。理由是：0.007 BPB 的量化退化不值得让模型整体变小。这是权衡后的取舍，不是死磕。

### 4.3 如果某个架构改动（并行残差 / QK-gain）让BPB 变差

**应对**：
1. **不掩盖，直接从组合里剔除**，并在消融报告里写明「实测有害，故未采用」。
2. 排查顺序：先看是不是和其他改动互相干扰（单独跑一次隔离），再看是不是学习率没跟着调（架构变了，梯度尺度会变，LR 可能要重调）。
3. 反思为什么我猜错了——上游是在 11 层 + SP8192 上验证的，我在 9 层 + SP1024 上，很多收益的前提条件不成立。**这本身就是一条有价值的结论**，说明「榜单技术不能无条件移植」。

### 4.4 如果本地结论和上游差异很大

**这是最可能的情况，也是我最需要提前想清楚的情况。**

我的应对原则：**不外推**。我不会写「本地 1.19，因此 8×H100 上能到 1.18」这种话。本地单卡 4GB 显存的训练配置和官方 8 卡口径差距太大，任何外推都是编数字。

具体做法：
- 报告里把**结论分成两层**：「在本地条件下实测得到的」和「在上游 8×H100 记录中已验证的」，两者不混写。
- 提交到榜单的分数，我只会填**我真实测到的数字**，并注明测量的硬件和配置与榜单口径不同。
- 8×H100 的完整跑法和预期区间，我写成**可复现的运行方案**（命令 + 配置 + 上游对照），而不是伪造一个我没跑过的分数。

### 4.5 如果 artifact 超限

**应对**：训练循环末尾我已经内置了自检（`ARTIFACT_SIZE_OK` / `ARTIFACT_SIZE_VIOLATION`）。超限就直接判负，绝不提交。CHALLENGE.md 里「超 16MB 却没发现」被列为明确的陷阱。

## 5. 我拿什么、为什么这么拿

遵守 CHALLENGE.md 的**拿来主义原则**：严禁从零写 Transformer。

| 来源 | 我拿了什么 | 我改了什么 | 为什么改 |
|------|-----------|-----------|---------|
| `openai/parameter-golf` `train_gpt.py` | 整个训练/评估/量化骨架、数据加载、BPB 计算、Muon 实现 | 重构 `eval_val`，拆成 chunked 与 sliding 两个独立函数 | 原来只有一个评估路径，我要能对照开关，才能测出滑窗的独立贡献 |
| `records/.../2026-03-19_SlidingWindowEval` | `eval_val_sliding` 的实现思路 | 重写并补充边界处理、字节数统计一致性 | 确认了窗口计分不重不漏的逻辑 |
| `records/.../2026-03-18_FP16Embed_WD3600` | fp16 嵌入直传的思路 + 「缩 MLP 腾空间」的手法 | 加了 `FP16_PASSTHROUGH_PATTERNS` 开关 | 让它可开关、可消融 |
| `records/.../2026-04-09_..._LegalTTT` | 并行残差、QK-gain 的做法 | 加了 `PARALLEL_RESIDUAL_START` 可配置起始层 | 上游从第 7 层开始，我要能验证「浅层并行是否有害」 |
| KellerJordan `modded-nanogpt` | Muon + Newton-Schulz 优化器 | 沿用未改 | 这是官方 baseline 已在用的，换掉它属于自找麻烦 |

**我明确没有拿的**：SP8192 tokenizer、3-layer depth recurrence、legal score-first TTT、GPTQ。

理由不是它们不好，而是：
- SP8192 需要重新导出数据，而我无法验证重导出的 BPB 计算是否与官方一致——官方明确警告「改 tokenizer 的提交会被更严格审查」，在没有官方环境交叉验证前提交，风险大于收益。
- depth recurrence 上游已有明确失败记录（10 分钟步数不够）。
- legal TTT 的合规性判定我无法在本地完整验证，一旦被判违规，代价是整个提交作废。

**这三句话（拿了什么、改了什么、为什么改）就是我的工程能力证明。**
