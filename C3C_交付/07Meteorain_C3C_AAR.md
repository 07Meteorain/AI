# C3C · AAR 复盘

> AAR（After Action Review）四问：本来要发生什么 → 实际发生了什么 → 为什么有差异 → 下次怎么改。
>
> 本文不写"我们学到了团队合作很重要"这种话。凡是没能在下次行动里落地的结论，都不写进来。

---

## 0. 一句话结论

**我们把"两个人互相教"做成了可复算的东西，但真正教会我们的不是对方，是对方审出来的 bug。**

原计划是"分工 → 各自实现 → 集成"。实际发生的是"分工 → 各自实现 → 集成（以为成了）→
互检发现 13 条 → 改 → 再发现 2 条语义错误"。**"以为成了"的那一段，占了整个项目 60% 的时间，
而它本该是最短的一段。**

## 1. AAR 四问

### 1.1 本来要发生什么

| 计划 | 预期 |
| --- | --- |
| 契约冻结后并行开发 | 集成一次通过，靠契约保证接口零摩擦 |
| 两位协作者各写各的 | 第二轮换房间，各写 1~2 个迁移功能 |
| 单向互检 | 每人提 2~3 条意见，主要是风格与健壮性 |
| 总计 | 3 轮、约 2 小时、100 项左右的测试 |

### 1.2 实际发生了什么

| 实际 | 数据 |
| --- | --- |
| 接口摩擦 | **0 次**。契约签名一次对上，首轮集成 56 项测试全绿 |
| 语义错误 | **2 次**（v1.3 类型标签、v1.5 R4 位置），都发生在"测试全绿之后" |
| 互检意见 | **13 条**，8 条修掉，5 条书面裁定不修（其中 2 条是设计取舍） |
| 换房间结果 | A 在 B 的文件里写出了 286 行 `explain.py`，被原作者审出 **6 条**，4 条是真 bug |
| 轮次 | 4 轮（不是 3 轮），最后一轮几乎全是修复 |
| 最终测试 | **108 项** |

### 1.3 为什么有差异

**差异一：契约保证了"接口对得上"，但它保证不了"语义对得上"。**

契约写的是"`tags` 取并集"。这句话在语法上完整、在类型上正确、在测试里通过——
但它在语义上是错的：技能可以叠加（并集对），类型互斥（并集错）。
**签名是两个人能对齐的部分，语义是两个人最容易各自想当然的部分。**

这就是为什么首轮 0 接口摩擦、却有 2 次语义返工。

**差异二："测试全绿"制造了虚假的完成感。**

56 项测试全绿时，我认为第一阶段结束了。实际上那时工具会输出
"一个事件同时是决策和实现"这种明显错误的合并日志——**因为没人写过这条断言**。
测试覆盖的是"我们想到要问的问题"，而不是"正确性"。

**差异三：评审的质量取决于提问的方式，不取决于评审者的水平。**

第一轮我给的是"评审一下 `render.py`/`cli.py`"，得到的是"认可两处 + 不同意两处"。
第三轮我给的是"至少找出 2 个我没提到的问题，给文件:行号 + 复现命令 + 期望输出 + 严重度"，
得到的是 6 条，其中一条是**真正的死循环**。同一个评审者，两次的输出质量差了一个数量级。

### 1.4 下次怎么改（可执行，不是口号）

| 改法 | 具体动作 | 本次对应证据 |
| --- | --- | --- |
| **契约里加"语义断言"一节** | 每个字段除了类型，还要写一句"它**不**表示什么"（如：`类型` 互斥，不可以并列） | v1.3 本可以提前避免 |
| **测试里加"荒谬输出"检查** | 至少一条测试断言"合并日志里不出现两个 `类型:` 标签"这类**语义不变量** | F4 |
| **任何规则必须构造"只有它可能命中"的用例** | 验证 R4 时必须让 R2 不可能命中（时钟相等） | F8 我自己的误判 |
| **评审 prompt 强制三件套** | 文件:行号 + 复现命令 + 期望值；禁止"建议优化" | 第三轮 vs 第一轮的质量差 |
| **生成证据文件时显式指定编码** | 不用 `>` 重定向，用 `WriteAllText` + 无 BOM UTF-8 | F7 |
| **核心函数要有"极端参数"测试** | `_wrap(s, 1)` 这种永远不该由用户触发的调用也要测 | F6 |

## 2. 六条具体失败与根因

| # | 失败 | 根因（不是"粗心"这种糊弄话） | 谁抓到 |
| --- | --- | --- | --- |
| 1 | 迁移边用并集标签，制造伪证据 | 把"合并后的条目"当成了"每个人写下的条目"；逻辑主体错位 | Aster 主动提问 |
| 2 | 画像与迁移边两套口径 | 修补局部时没有回头检查**同一个数字在别处是怎么算的** | Aster 主动提问 |
| 3 | 一个事件同时带 `类型:决策` 和 `类型:实现` | "并集"对技能对、对类型错；一条规则被无差别套用到两种语义 | Bramble 互检 → 主持人实测 |
| 4 | "等 4 类"报了总类别数 | 计数类代码最常见的错：分母/基准选错，且不报错、不崩溃 | 主持人肉眼 |
| 5 | `_wrap` 死循环 | 修排版时引入；`limit` 极小时"移动位置"永远无法推进 | Bramble 评审 → 主持人 timeout 实测 |
| 6 | JSON 变成 UTF-16 / 带 BOM | 依赖工具的默认编码；跨语言管道没有显式契约 | 主持人两次报错 |

**共同点**：6 条里有 4 条是"**逻辑对、语义错**"，1 条是"**边界条件**"，1 条是"**隐式默认值**"。
没有一条是"写错语法"或"接口对不上"。这基本就是 AI 生成代码的失败画像。

## 3. 三个反直觉的发现

### 3.1 冻结一份错误的契约，比不冻结更危险

不冻结，两人会打架，打架会被立刻发现。
冻结了，两人都"正确"地实现了错误的设计，错误被**规范化**了，所有人都会照着它写测试。

`model.py` 是我写的，我宣布它冻结不许改。它的错误（标签一律并集）传播到了
`merge.py`、`analyze.py`、`render.py` 三个模块，最后靠 Bramble 的评审才被挖出来。

**结论**：冻结时要配一条"任何人都可以质疑冻结层，但必须由主持人改"的通道。
本次契约 §10 第 4 条写了这条，是它救了场。

### 3.2 R4-补充合并，实际从不作为主路径生效

我们花了一整轮实现 R4"一方正文包含另一方 → 取更完整者"。上线实测：

- 只要两版时钟不等 → **R2 先命中**，R4 轮不到；
- 只有两版时钟相等时，R4 才有机会。

也就是说，我们写的是一条**只在时钟并列时才有用的补位规则**，而契约原文的语气暗示它是主路径。
这不是实现错误，是**规则顺序与规则意图不匹配**。

我们最终选择不改顺序（改了会让"时钟更新但内容更短"的版本输给更长的旧版本），
而是在契约里写清它只是 tie-breaker。**"发现设计意图与实现效果不符，然后承认它"，
比"改到符合预期"更重要**——因为改的代价是另一个更严重的问题。

### 3.3 未达成共识的那一条，是整份记录里最有价值的部分

E-021 是唯一一条 R3「待复核」：

- Aster：explain 应该给每个版本标注证据强度（强/弱）；
- Bramble：不需要，规则代号已经说明了工具凭什么这么裁，再叠一层就是在替读者下结论。

两人时钟相同、无决策标记、无包含关系——工具拒绝裁决，原样并排保留。

我们没有强行统一。理由：**一个只有共识的协作记录是不可信的**。
真实协作里一定有计划外的分歧，把它藏起来的记录，价值不如把它留着的记录。

## 4. 如果重来，会改的三件事

### 4.1 先跑真实数据，再写测试

本次的顺序是"实现 → 写测试 → 跑测试 → 全绿 → 集成 → 跑真实数据 → 发现语义错误"。
应该改成"实现 → 跑真实数据 → **人眼看**输出 → 再写测试"。

理由：F4（两个类型标签）、F5（等 4 类）都是**肉眼一秒钟能看出来的**，
但 56 项测试一条都没断言过。**测试只能固化你已有的判断，不能产生判断。**

### 4.2 换房间应该在第一轮就做

我们第二轮才换房间。但第一轮两人都只是"照契约实现"，没有真正进入对方的思维。
如果第一轮就让 B 去改 A 的 `merge.py`，B 会更早发现"规则顺序"的问题，
A 会更早发现"渲染层需要复用宽度表"的问题。

**换房间不是验收手段，是开发手段。**

### 4.3 给每个"统计数字"配一条反向断言

"占比 57.7%"这种数字，写一行断言："两组占比相加必须等于 100%±0.1"
"`类型` 标签每条至多一个"。这类**不变量断言**比"结果等于某个期望值"更能抓住口径错误。

## 5. 度量

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 契约变更 | 5 次 | 2 次是语义错误（v1.3、v1.5），2 次是口径统一（v1.1、v1.2），1 次是范围扩展（v1.4） |
| 互检意见 | 13 条 | 8 修 / 5 书面裁定不修 |
| 真 bug（会导致错误输出） | 3 条 | v1.1 伪证据、v1.3 类型标签、`_wrap` 死循环 |
| 测试 | 108 项，1,342 行 | 首轮 56 → 第二轮 99 → 最终 108 |
| 代码 | 1,977 行 | 8 个模块，零第三方依赖 |
| AI 协作轮次 | 4 轮 | 3 轮开发 + 1 轮收尾修复 |
| 需要返工的语义错误 | 2 次 | 都发生在"测试全绿"之后 |

**最该被记住的一个数**：**3**。
13 条互检意见里，只有 3 条会导致用户看到错误结果，其余 10 条是健壮性、一致性、排版。
如果我们只做"能跑就行"，工具现在会输出一份看起来完美、实际上把技能迁移算错的报告。

## 6. 对 C3C 四个目标的复盘

| 目标 | 是否达成 | 证据 | 不足 |
| --- | --- | --- | --- |
| 完成一次分工清晰的双人协作 | 是 | 契约先冻结文件所有权；两轮；`协作记录.md` §1–2 | 主持人掌握的裁定权过大，两人之间没有直接对话（只能通过契约与主持人转述） |
| 产出联合成果并互检 | 是 | 1,977 行工具 + 108 项测试；13 条互检意见 | 互检靠"隔空评审文件"，没有实时的结对编程 |
| 迁移复用对方的至少一个技能 | 是 | 双向两条边、5 条证据（E-011~E-015）；换房间写作 | 证据来自协作者自我打标签，有自我报告偏差，缺独立第三方测量 |
| 复盘协作与迁移的有效性 | 是 | 本文 | "迁移有效性"目前只靠"被原作者审出 6 条 bug"这种间接指标，没有前后测 |

**最大的不足，说清楚**：两位协作者都是 AI，"技能迁移"缺少**人类学习曲线**作为对照。
一个 AI 读完对方的代码就能模仿对方的约定，这件事说明不了"迁移机制有效"，
只能说明"上下文足够时模型能对齐风格"。真正的人类迁移会更慢、更不整齐、需要更多次失败。

这个缺口没法用现有材料补上。它也是下次最该补的实验设计：
**让一个真人只读契约、不看代码，独立实现同一模块，然后对比。**
