# C3C · AI 使用日志

> 记录时间：2026-11-06 ~ 2026-11-07 ｜ 工具：DeepSeek Harness（多 agent 编排）
> 本文只记**真实发生过的事**，包括 8 次失败。凡是我当时判断错了的，都保留原样，不美化。

---

## 1. 工作流设计：为什么不是"一句话让 AI 写一个工具"

C3C 要的是"互相教会对方原本不会的东西"，单 agent 做不到"互相"——它没有第二个人格，
也就没有"我不知道但对方知道"这件事。

所以这次用的是一个**三方结构**，不是"我 + 一个 AI"：

```
主持人（学生）
  ├── 起草契约 v1.0（数据模型 / 函数签名 / 文件所有权 / 退出码）
  ├── 协作者 A · Aster（独立上下文，只看契约）→ merge.py + analyze.py
  ├── 协作者 B · Bramble（独立上下文，只看契约）→ render.py + cli.py + tests
  ├── 集成：跑测试、跑 CLI、构造反例
  ├── 裁定：5 次契约变更
  └── 第三轮：两人换房间，进入对方代码库改东西
```

**为什么这个结构能产生"迁移"而不是"各做一半"**：

| 设计 | 不这样会怎样 |
| --- | --- |
| 契约先冻结，两人**并发**开工、互相看不见代码 | 一个 agent 从头写到尾，不存在"分工"，只有"一个人干活" |
| 每个文件有唯一所有者，别人不许碰 | 两人同时改同一文件，冲突解决不了，最后退化成一个人干 |
| 第二轮**强制换房间**：A 改 B 的文件，B 改 A 的文件 | 迁移只能停留在"我读过你的代码"，无法验证是否真学会 |
| 换完房间由**原作者**评审 | 谁都能说"我学会了"，只有原作者能判断"你是不是真懂我为什么这么写" |
| 所有意见必须有 `文件:行号` + 复现命令 | 评审退化成"我觉得可以优化一下"的客套话 |

**代价**：三个 agent 的上下文互不可见，所有协作必须**落成文件**（契约、日志、笔记、评审）。
这也是为什么本交付里 `notes/` 有 8 份文件——它们不是"额外材料"，它们是**协作本身**。

## 2. Prompt 迭代：三次明显的改法

### 2.1 第一轮：把"要求"写成"边界"

**v1 的思路**："你是协作者 A，实现 merge 模块，要求零依赖、有测试、中文注释。"

问题：这种 prompt 会得到一个"尽力而为"的实现，但**不会得到一个符合接口契约的实现**。
两个 agent 各自"尽力而为"的结果，是集成时字段名对不上。

**v2（实际使用）改成"边界清单"**：

```
- 你只写这两个文件：duolog/merge.py、duolog/analyze.py
- 不要创建或修改 render.py / cli.py / tests/（归 Bramble）
- 不要修改 model.py 和任务契约.md
- 契约 §3/§5/§6/§7 逐条对照后再交付
- 公共函数必须有中文 docstring，说清"为什么这样设计"，不是"做了什么"
- 交付时回报：你最不确定的 3 个地方
```

最后一条是关键：**"回报你最不确定的 3 个地方"** 直接把 agent 的自我怀疑变成了我的测试清单。
Aster 回的三处（R3 拼接分隔符、`authors` 该不该含零条目 owner、`skill_tags` 口径）
里，第三处直接催生了契约 v1.2。

### 2.2 第二轮：把"你去改他的代码"改成"这是你该修的具体 bug"

第一轮结束时我给的是方向（"学 SEL-2，动 Bramble 的文件"），但我很快发现这不够：
agent 会倾向于**只加东西、不动别人的代码**（保守），或者**大改重写**（冒进）。

**改成给"实测证据"**：

```
复现：
python -m duolog merge --a examples/sample_a.md --b examples/sample_b.md \
       --author-a Aster --author-b Bramble --no-color

画像表 Aster 那行的「类型标签」列输出是：
互检×2、实现×2、决策×1、等 4 类

实际 Aster 有 4 类，列里已显示 3 类，还剩 1 类。
"等 4 类"报的是总类别数（render.py:238），应该是剩余数。
```

**"给复现命令 + 实际输出 + 期望输出 + 文件行号"** 比任何形容词都有效：
Aster 一次就改对了，连"为什么这里会错"都写进了迁移笔记。

### 2.3 第三轮：把"评审一下"改成"至少找出 2 个我没提到的问题"

"评审一下"会得到 5 条"代码很清晰，建议加注释"。所以我改成：

```
请你独立找出至少 2 个她没注意到的问题。我给几个方向做线索（你可以推翻）：
- winner 对 single/confirmed 都返回 None，下游分得清吗？
- _load_entries 重构后，错误信息和退出码有没有走样？
- 固定 72 列，终端窄于 72 列会怎样？
- --json 与 --no-color 同时给、--json 与 eid 不存在同时发生时，stdout/stderr 分工干净吗？

每条请给出：文件:行号、复现命令、实际输出、期望输出、严重度。
没有证据的问题不要写——不确定就写"疑似，需主持人实测验证"，我会去跑。
```

结果 Bramble 报了 6 条，其中 1 条是**真正的死循环**（`_wrap('中',1)` 挂死），
连提出者自己都标了"当前 CLI 不触发，但函数级必挂"。这是本次质量最高的一次评审。

**这条 prompt 的可复用结论**：给 AI 评审任务时，要说清"允许你推翻我的线索"，
否则它会顺着我的猜测去凑证据。

## 3. 失败清单（8 条，全部真实发生）

### F1 · 沙箱里的 PowerShell 根本起不来（浪费 3 次调用）

前三次 `pwsh` 调用全部返回 `exit code: 3221225794`（`0xC0000142`，DLL 初始化失败），没有任何输出。
我当时的错误判断是"可能是工作目录含中文导致的"，试了 ASCII 工作目录仍然失败。
真实原因：DSH 的 Windows 沙箱在这个环境下无法为子进程初始化。
绕过方式是用 `danger-full-access` 逐条执行——**但这意味着整个项目从头到尾都没有真正跑在沙箱约束下**。

**代价**：后面每一次跑测试、跑 CLI 都要单独申请一次完全权限，来回十几轮。

### F2 · 冻结的契约也是错的（v1.0 → v1.1）

`model.py` 是我自己写的、宣布"冻结不许改"的契约层。它规定的"迁移边 = 条目带技能标签"
看着天衣无缝，实际上合并后的标签是两人并集——于是"两人一起记了分工"被算成"Aster 用了 SEL-2"。

**我当时的判断是错的**：我以为冻结 = 正确。冻结只保证不变。

### F3 · 两套口径同时存在（v1.2）

修完 F2 后，迁移边按"原始条目"算，但画像的 `skill_tags` 还按"合并条目"算。
结果工具会输出"Bramble 有 1 条 SEL-1 计数，但没有 SEL-1 迁移边"——自己打自己脸。

**是 Aster 主动提问才发现的**。她原话："这会出现'有计数、无迁移边'。若要与迁移边同口径，请回一句，我改成遍历 versions（约 10 行）。"
一个 10 行的改动，如果她不说，所有人都会以为报告是对的。

### F4 · 类型标签取并集，一个事件同时是两件事（v1.3）

Bramble 在互检里提了，我跑出来确认：

```
## E-003 | 2 | 技能:SEL-1,类型:决策,类型:实现
```

E-003 是"A 写'这是决策'、B 写'这是实现'"的冲突，R1 裁决给 A 之后，**标签还是两人的并集**。
技能可加、类型互斥——"并集"对了一半标签是对的、对另一半是错的，这是最难发现的那类错。

### F5 · "等 N 类"报的是总类别数

```
│ Aster │ 6 │ 54.5% │ SEL-1×2 │ 互检×2、实现×2、决策×1、等 4 类 │
```

实际只剩 1 类没显示，却写"等 4 类"。代码是 `"等 {0} 类".format(len(ordered))`，报的是总数。
**这是我自己集成时肉眼发现的**——不是任何测试抓到的，因为测试只断言"没有崩溃"。

### F6 · `_wrap` 死循环：为了修一个排版问题，引入一个挂死

Aster 修"顿号出现在行首"时改了折行逻辑，当 `limit` 小于首字符宽度时会原地打转：

```
python -c "from duolog.explain import _wrap; print(_wrap('中',1))"   → 挂死
```

**这个 bug 是评审提出、我实测坐实的**（5 秒超时）。它完全不经过 CLI，所以端到端测试永远不会碰到它。
如果只跑"用户会跑的命令"，这个 bug 会一直躺在那儿。

### F7 · PowerShell 重定向把 JSON 写成了 UTF-16 / 带 BOM

生成 `demo/merged.json` 时，`>` 重定向默认写 UTF-16，`Out-File -Encoding utf8` 又带 BOM，
Python 用 `encoding='utf-8'` 读直接抛 `UnicodeDecodeError` / `JSONDecodeError`。
连续失败两次，最后改用 `[System.IO.File]::WriteAllText(..., New-Object UTF8Encoding($false))`。

**教训**：跨语言管道的编码是"看不见的耦合"。生成证据文件时要显式指定编码，不能依赖默认值。

### F8 · 我自己的测试用例构造错了，误判 R4 不工作

第一次验 R4 时，我构造"时钟 1 vs 时钟 2，后者是前者超集"，期望命中 R4，结果命中 R2。
我第一反应是"Bramble 的 R4 没生效"。

读了规则顺序才发现：**R2 在 R4 之前，时钟不等时 R2 恒先命中**。我改构造时钟相等的用例，R4 立刻命中。
这次误判反而产出了本次最有价值的一条设计洞察（R4 只是 tie-breaker → 契约 v1.5）。

**教训**：验证一个分支时，必须先构造"只有它可能命中"的输入。

## 4. AI 生成的代码哪里最不可靠

按实际修掉的 bug 归类，排名如下：

| 类型 | 次数 | 例子 |
| --- | --- | --- |
| **语义/口径不一致**（单个模块对，跨模块矛盾） | 3 | F2/F3/F4，全是"每个模块单看都对，合起来自相矛盾" |
| **边界条件**（`limit` 极小、空输入、单字符） | 1 | F6 死循环 |
| **计数/统计口径**（总数 vs 剩余数、分母是谁） | 1 | F5 |
| **语法/接口不匹配** | **0** | 108 项测试首轮就有 56 项全绿，契约签名一次对上 |
| **绝对路径 / 环境依赖** | 0 | 全部用相对路径，零第三方依赖 |

**结论**：契约 + 强约束 prompt 基本消灭了"接口对不上"这类低级错误，
AI 的失败主要集中在**它没有机会自问的问题**上——"这两个数字是不是同一个分母"、
"如果第二个人从另一个角度看，这条规则还成立吗"。
这类问题只能靠**换一个人来审**，或者靠**人跑一遍真实数据**。
