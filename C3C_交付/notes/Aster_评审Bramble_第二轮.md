# Aster 评审 Bramble 第二轮（`merge.py` 的 R4 与 v1.3 标签）

> 评审对象：Bramble 第二轮改后的 `duolog/merge.py`（新增 `R4-补充合并`、
> 按 v1.3 重写 `_merged_tags`）。基线：契约 v1.3 的 §3 表格与 §3.1。
> 结论：R4 的"整行有序包含"实现本身是干净的；真正的问题在**规则位置**与
> **空行参与匹配**，另外多版本推广在"同文不同标签"时会做出没有依据的选择。

## 一、R4 的多版本推广：方向认可，但有两个反例会误判

实现位置：`merge.py:90-117`（`_pick_r4_winner`）、`merge.py:72-87`
（`_is_line_subsequence`）。

Bramble 的推广是："存在**唯一**版本按行覆盖所有其它版本，否则落回 R3"。
我认可这个方向，理由：

- 契约原文只描述两版本，但多版本时"没有任何一个版本能解释全部说法"就意味着
  不存在一个自然的"更完整版"；此时把 A 的补充和 B 的补充拼起来是**发明**
  新正文，R3 交给人才是保守且可解释的。
- 部分覆盖落回 R3 而不是两两合并，避免了"谁的补充优先"这种没有契约依据的
  排序，也保住了"工具不替人裁决"的底线。
- `_is_line_subsequence` 用整行相等而不是子串，避免"实现"命中"实现细节"
  这类假包含，这个细节是对的。

但有两个反例会让它给出"看起来已裁决、实际没有依据"的结果：

### 反例 1：自相矛盾的超集也会赢 R4

`A = "先上线"`，`B = "先上线\n但不上线"`。B 的行序列包含 A，`R2` 之前
如果时钟相同就会命中 `R4`，输出 `resolved`、winner=B，note 写"补充而非
反驳"。可 B 同时包含"上线"和"不上线"，它不是更完整的版本，而是自相矛盾
的版本；这时 R3 才诚实。整行包含只能判断"有没有这些话"，判断不了
"这些话是否互相否定"。

这不是多版本特有的，但只要允许多版本覆盖，它同样成立。要不要处理由主持人
定；如果不想引入语义分析，至少 note 不该断言"属于补充而非反驳"。

### 反例 2：多个候选共享同一正文、却带不同 `类型` 标签时，R4 替人选了类型

`A = "先评审\n再上线"（类型:决策）`、`B = "先评审\n再上线"（类型:实现）`、
`C = "先评审"`。A、B 的规范化正文相同（所以没有 R0，因为 C 不同），
两者都覆盖 C，都是候选；`_pick_r4_winner` 用 `_longest_key` 取原始正文
最长者，正文一样长时退到 `author` 字典序。

问题在 v1.3：`类型` 标签跟终裁版本。于是**作者名字典序**决定了这次事件算
"决策"还是"实现"，而 R4 的判据（内容包含）对类型没有任何发言权。我的建议：
如果多个候选的规范化正文相同但 `类型:*` 标签集合不同，直接落回 R3（或把
类型取并集，但这会破坏 v1.3 的"类型跟终裁"语义）；至少不能把 author 排序
当成语义裁决。

## 二、空行参与行匹配：是问题，而且在 v1.3 下后果不只是"多一个空行"

实现位置：`merge.py:62-69`（`_lines`，空正文返回 `[]`，但正文内部的空行
保留为 `""`）；`normalize_text` 只压连续空行、去首尾空行，**段间单个空行
会保留**。

因此 `A = "上线\n\n风险已知"` 与 `B = "上线\n风险已知"` 的行序列分别是
`["上线", "", "风险已知"]` 与 `["上线", "风险已知"]`：A 严格包含 B，R4
判 A 胜。多出来的只是一个段落空行，不是内容。

单看正文，这个结果还算无害（A 的文本确实更"长"）。真正的坑是与 v1.3 的
交互：如果 A 带 `类型:决策`、B 带 `类型:实现`，那么"多敲了一个空行"的 A
会赢走类型标签；如果没有这个空行，两者规范化正文相同，本该 R0 双重确认、
类型取并集。也就是说，**一个纯格式差异改变了语义归属**。

我的建议（供主持人定，不是本轮改代码）：

1. R4 的行匹配只用非空行（`[line for line in ... if line]`），空行不参与
   "覆盖"判定；
2. 但如果只过滤空行，`A/B` 会变成"非空行相同但 norm_text 不同"，既不满足
   R0 也不满足 R4 的 strict，反而掉进 R3——这比现在更差。所以要么
3. 让 R0 的判等也采用"非空行序列相同"（把纯空行差异视为双重确认，类型取
   并集），要么在 R4 里显式增加"非空行相同 ⇒ 按 R0 处理"的分支。

一句话：空行不该决定谁赢；要修就成对修 R0/R4，不能只从 R4 里删空行。

## 三、R4 的位置：不是我原本的设计，而且它现在几乎只是"时钟并列"分支

契约顺序是 `R0 → R1 → R2 → R4 → R3`（`merge.py:232-236` 的注释也这么写）。
R2 的条件是"最大 clock **严格**大于其它所有版本"：

- 两版本场景：只要 `clock` 不等，R2 必命中，R4 根本轮不到；R4 只在两版
  `clock` 相等时才有机会。
- 多版本场景：只要最大 clock 唯一，R2 命中；R4 只在"最大 clock 并列"时
  才有机会。也就是说它实质上是"无唯一最新时钟时的补位规则"，不是主路径。

这不是我原本的设计——第一轮我实现的规则集只有 R0/R1/R2/R3，R4 是后加的。
如果 R4 想承担"内容更完整者胜"的主语义，我建议放到 R2 **之前**：
`R0 → R1 → R4 → R2 → R3`。理由：契约自己说 `clock` 是各人自记、跨人不可比
的**弱**证据，而"一方按行完整包含另一方"是内容层面的强证据；让弱证据先
短路强证据，等于把 R4 降级成 tie-breaker。反过来，如果团队认为"时钟较新"
在业务上就是优先于"内容更全"，那就保留现顺序，但文档与 note 应明确写
"R4 只在时钟并列时生效"，不要再把它描述成主裁决规则。

按主持人要求，本轮**不改规则顺序**，以上只作为决策依据。

## 四、其他我认可的细节

- `_lines("")` 返回 `[]` 而不是 `[""]`，让空正文能被任何正文包含，避免
  R4 在空正文上永远不命中；这个边界处理是对的。
- `_pick_r4_winner` 要求候选对每个其它版本都覆盖、且至少有一个不同正文的
  版本被严格覆盖，避免"所有版本正文相同"时重复触发 R4。
- `_merged_tags` 把"技能并集 / 类型跟终裁"拆成两段，`winner is None` 时
  类型回退并集，和 v1.3 的文字一致；这比上一轮的"一律并集"正确。
- R4 的 `note` 用 `covered` 列出被覆盖作者，`sorted` 后输出，确定性没问题；
  只是如反例 1 所说，"属于补充而非反驳"这句断言过强。

## 五、给主持人的一句话结论

R4 现在的位置让它只在"没有唯一最新时钟"时才可能触发，实际是 tie-breaker；
若希望它承担"补充合并"的主语义，应移到 R2 之前，否则应在契约与文档里
明确它是并列时钟的补位规则。
