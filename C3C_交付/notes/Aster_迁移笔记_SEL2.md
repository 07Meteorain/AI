# Aster 迁移笔记：SEL-2（CLI 工程化与终端渲染）

> 第一轮我写 SEL-1（merge/analyze），第二轮临时学 SEL-2 并落地 `explain`。
> 这份笔记记"我原来不会什么、怎么靠 Bramble 的约定补上、哪里还心虚"。

## ① 我原本不会的到底是什么

一句话：**我会算，但不会把中文结果稳定地放进终端。**

具体是三件事：

1. **终端显示宽度不是 `len()`。** 我以前会直接 `print` 或按字符数补空格；
   不知道一个汉字占两列、组合符占零列，也不知道 `East Asian Width` 的
   W/F 与 Ambiguous 要分开处理。中文表格"看起来只是没对齐"的 bug，我大概率
   会归因到字体或终端，而不是宽度算法。
2. **框线表的几何是算出来的，不是画出来的。** 列宽要取"表头与所有单元格的
   最大显示宽度"，要截断、要补白，还要保证同一张表每行严格等宽；这些步骤
   有先后顺序（先 flatten、再量宽、最后上色）。
3. **CLI 的退出码是接口，不是提示。** 我以前只会 `sys.exit(1)`；不知道
   argparse 的用法错误要翻译成 2、解析 error 要固定成 1、`--json` 的 stdout
   不能混入任何人类可读文本，也不知道要让 `main()` 返回 int 以便测试直接调用。

## ② Bramble 的约定里，我一开始最不适应的一条

**"所有单元格先 `_flatten` 成单行，换行用 ` / ` 压平。"**（`render.py:82-86`）

我第一反应是"证据就该原样多行展示，压平是丢信息"。写 `explain` 时我一度想
让每个 version 的正文在框里自然换行——那其实正是框线表最怕的东西：只要一个
单元格带 `\n`，终端会自动换行，框线立刻断成两截，整张表报废。

后来接受它，是因为想清楚了三件事：

- **终端是扫读界面，不是存档界面。** 需要完整原文的人可以看 `--json` 或
  `--report`；终端表格的职责是让人一眼定位，而不是承载全文。
- **换行不是"更多信息"，是"更多几何"。** 多行单元格会让列宽计算从"一维"
  变成"二维"，渲染复杂度上一个量级，而收益只是省一次跳转。
- **压平必须和截断配套。** `_flatten` + `_truncate(max_col)` 保证"无论日志
  多长，表格宽度有上界"，这正是 80 列终端能用的前提。

所以我在 `explain` 里反过来用了它的思路：**先决定可用宽度，再按宽度折行**，
折行只发生在"整段纯文本"里（框内没有第二个表格），而不是塞进表格单元格。

## ③ 我写的 `explain` 里，哪几行是直接抄他的思维

不是抄代码，是抄"先量宽、再排版"的顺序：

1. **`explain.py:63-106` `_wrap`**：逐字符累加 `display_width`，超限才换行。
   这就是 `render.py:89-104` `_truncate` 的循环反过来用——它按宽度截断，
   我按同一套宽度判断在哪里断行。第三轮又在这基础上补了行首禁则。
2. **`explain.py:124-153` `_pad` / `_box`**：内容行先算好，最后统一补白到
   `_INNER_WIDTH` 再加边框。这是 `_render_table` 的做法：宽度先定死，内容再往里填，
   而不是让内容决定边框。
3. **`explain.py:43-60` `_clean_text`**：把 ESC 等控制字符换成空格。这是
   `render.py:71-79` `_scrub` 的同一动机——契约要求无 ANSI，就不能只保证
   "渲染器不加"，还要挡住日志正文里自带的。
4. **`cli.py:170-199` `_load_entries`**：读文件 → 解析 → 收集 `ParseIssue` →
   有 error 就中止，返回值区分"读不了(2)"与"解析错(1)"。结构直接来自
   `cli.py` 原来的 `_run_merge`，我只是把它抽出来给两个子命令共用。
5. **`cli.py:253-283` `_run_explain`**：错误走 stderr、前缀统一 `duolog:`、
   `--json` 分支不经过任何渲染函数、最后 `return 0`。这是照 `_run_merge` 的
   控制流抄的，连 `_write_stdout` 的用法都没换。

## ④ 哪一处我照做了但心里没底

1. **固定 72 列：主持人已裁定保留，我接受。** 理由不是"72 好看"，而是
   `explain` 的输出要可复现：宽度一旦随终端变化，同一份证据在不同机器上
   的字节就不同，没法做 golden 对比。窄终端靠软换行可读，这是有意的代价；
   框线字符按 `display_width=1`（Ambiguous）也沿用项目约定，测试只保证
   在该约定下逐行等宽。
2. **`winner` 对 `single` / `confirmed` / `needs_review` 都取 `None`：
   主持人已认可，我接受。** `winner` 的语义是"有没有人赢"，不是"这条
   事件属于谁"；`status` 才是判据（single / confirmed / needs_review）。
   如果未来要让 `single` 返回作者名，应同时改契约与测试，而不是只改
   `_winner_author`。
3. **行首禁则已做，但不是完整的避头尾。** 第三轮补了"标点不能落行首"：
   折行点若会以 `，。、；：！？）】」”’…` 等开头，就把上一行末字一起下移，
   保证不超宽；`limit` 小于首字符宽度时会无条件吐出该字符并前进，避免
   死循环。但只处理了**行首**禁则，没有行末禁则（如开括号/前置标点），
   长 URL/长英文词仍会从中间切开；更完整的做法需要一张禁则表与断词规则。
4. **CLI 的 parse error 文案和 merge 不完全一致**：merge 是"未写任何输出文件"，
   explain 是"未输出溯源结果"。两者都以 `duolog: 解析出现 error` 开头，
   退出码也一致；但如果测试断言整句，会差几个字。
5. **`_load_entries` 读文件失败的顺序**：现在先 flush 已累积的 ParseIssue，
   再报读文件错误；这是主持人实测后要求的顺序，已加回归测试锁住。
