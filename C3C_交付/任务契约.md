> 这份文件是**契约层**：两位协作者各自实现自己的模块，只允许依赖这里写死的类型与签名，
> 不允许 import 对方模块的内部实现。目的是让两人能并行开发、最后由主持人机械集成。
>
> 契约由主持人（Meteorain）起草并冻结（clock=0）。协作者可以提修改意见，
> 但改动必须写进 `协作记录.md` 的"契约变更"一节。

## 2. 协作者 A 必须提供的 API（`duolog/merge.py`）

```python
@dataclass(frozen=True)
class Conflict:
    eid: str
    versions: tuple[Entry, ...]      # 参与冲突的原始条目，按 (author, clock) 排序
    winner: Entry | None             # None 表示无法裁决
    rule: str                        # 规则代号，见 §3
    resolution: str                  # "resolved" | "needs_review"
    note: str                        # 一句话人读理由，中文

@dataclass
class MergedItem:
    eid: str
    authors: tuple[str, ...]         # 已排序、去重
    tags: tuple[str, ...]            # 见 §3.1：技能取并集，类型跟终裁版本
    text: str                        # 合并后的最终正文
    status: str                      # "single" | "confirmed" | "resolved" | "needs_review"
    versions: tuple[Entry, ...]      # 参与合并的原始条目，按 (author, clock) 排序
    rule: str                        # 触发规则代号；无冲突时用 ""
    def to_dict(self) -> dict        # 见 §5 的 JSON 形状

@dataclass
class MergeResult:
    items: list[MergedItem]
    conflicts: list[Conflict]
    fingerprint: str                 # 见 §4
    stats: dict                      # 见 §6
    def to_dict(self) -> dict

def merge(entries: Sequence[Entry]) -> MergeResult
```

`merge` 必须是**纯函数**：同样的条目集合（与输入顺序无关）得到完全相同的输出，
包括 `items` 顺序、`fingerprint`、`stats`。

## 3. 冲突裁决规则（顺序执行，先命中先返回）

| 代号 | 条件 | 结果 |
| --- | --- | --- |
| `R0` | 所有版本规范化正文相同 | `status="confirmed"`，`text` 取**最长**原始正文（保留更多人写下的细节），`rule="R0"` |
| `R1` | 恰好一个版本带标签 `类型:决策` | 该版本胜，`status="resolved"`，`rule="R1-决策优先"` |
| `R2` | 最大 `clock` 严格大于其它所有版本的 `clock` | 时钟最大的版本胜，`status="resolved"`，`rule="R2-时钟较新"` |
| `R4` | 一方规范化正文**严格包含**另一方（另一方正文的每一行按顺序整体出现在前者中） | 取更完整者，`status="resolved"`，`rule="R4-补充合并"` |
| `R3` | 其余情况 | `status="needs_review"`，`winner=None`，`text` 为各版本按作者名排序后以 `【作者】` 标注拼接，`rule="R3-无法裁决"` |

执行顺序固定为 `R0 → R1 → R2 → R4 → R3`。

> **位置说明（变更 v1.5）**：R4 排在 R2 之后，因此在**两版 `clock` 相等**时才有机会命中——
> 它是"并列时钟"的补位规则，不是"补充合并"的主路径。集成实测（`clock=1/2` 且后者是前者超集时，
> 结果仍是 `R2-时钟较新`）确认了这一点。如果把 R4 提到 R2 之前，会让"时钟更新但内容更短"的版本
> 输给更长的旧版本，风险大于收益，所以**保持原位，改为在文档里说清**。
> 这不是我们最初写 R4 时的意图，是写完才发现的事。

- 只有一个版本 → `status="single"`，`rule=""`，不进 `conflicts`。
- 两个以上版本但都命中 `R0` → 也**不进** `conflicts`（不算冲突，算双重确认）。
- 命中 `R1`/`R2`/`R4`/`R3` 的才算冲突，全部进入 `MergeResult.conflicts`。

### 3.1 合并后的标签语义（变更 v1.3）

- **技能标签** `技能:*`：始终取**并集**。技能是"参与"，可以叠加——A 和 B 都在这件事上用到了
  SEL-1，两边的标签都该保留。
- **类型标签** `类型:*`：**只看终裁版本**。有 winner（R1/R2/R4）时取 winner 自己的类型标签；
  无 winner（R3）或 `single`/`confirmed` 时取并集。

> **变更 v1.3 的理由（集成阶段发现）**：v1.0 的 `tags` 一律取并集，于是 E-003 这种
> 「A 写决策、B 写是实现」的冲突在裁决给 A 之后，合并日志里仍然是
> `类型:决策,类型:实现` —— 一个事件同时是"决策"和"实现"，下游的类型分布统计直接作废。
> 技能可加、类型互斥，这是两种标签的本质区别。**并集规则对了一半，才是最坑的那种错。**

> **设计理由（A 需要能解释）**：`clock` 是各作者自己的逻辑时钟，两人之间不共享同一时钟，
> 所以"时钟大"只是**弱**证据；"决策"是**强**语义标记，优先级更高。都拿不准时，
> 工具宁可说"我不知道"，也不替人做裁决。

## 4. 可复现指纹

`MergeResult.fingerprint = fingerprint_of(payload)`，其中

```python
payload = {"version": 1, "items": [item.to_dict() for item in items]}
```

`items` 必须按 `(eid_key(eid), authors)` 排序后再算——`eid_key` 从 `duolog.model` 导入。

## 5. JSON 输出形状（`to_dict`，B 的 `--json` 直接 `json.dumps` 这个）

```json
{
  "eid": "E-003",
  "authors": ["Aster", "Bramble"],
  "tags": ["技能:SEL-1", "类型:决策"],
  "status": "resolved",
  "rule": "R1-决策优先",
  "text": "..."
}
```

`versions` **不要**放进 JSON（体积大且属于内部证据）。
`MergeResult.to_dict()` 返回：

```json
{"version": 1, "fingerprint": "<hex>", "stats": {...}, "items": [ <item.to_dict()>, ... ]}
```

## 6. `stats` 的键（固定，值为 int）

`total_items`、`single`、`confirmed`、`resolved`、`needs_review`、
`conflicts`、`authors`（作者数量）、`entries`（原始条目总数）。

## 7. 协作者 A 必须提供的 API（`duolog/analyze.py`）

```python
@dataclass(frozen=True)
class TransferEdge:
    src: str                 # 技能原拥有者
    dst: str                 # 使用该技能的人
    skill: str               # 形如 "SEL-1"
    evidence: tuple[str, ...]  # 支撑该迁移的 eid，已排序

@dataclass(frozen=True)
class Profile:
    authors: tuple[str, ...]                 # 已排序
    skill_tags: dict[str, dict[str, int]]    # author -> skill -> 条目数
    type_tags: dict[str, dict[str, int]]     # author -> 类型 -> 条目数
    transfers: tuple[TransferEdge, ...]      # 按 (skill, src, dst) 排序
    share: dict[str, float]                  # author -> 条目占比，保留 4 位小数
    def to_dict(self) -> dict

def profile(items: Sequence[MergedItem], skill_owner: Mapping[str, str]) -> Profile
```

- `skill_owner` 形如 `{"SEL-1": "Aster", "SEL-2": "Bramble"}`。
- `authors`：所有**原始条目作者**与 `skill_owner` 中非空作者名的并集，按名字排序。
  把技能拥有者也并进来，是为了让"队里有人一条都没写"这件事在画像里可见，
  而不是悄悄消失。
- `skill_tags[author][skill]` 与 `type_tags[author][type]`：**逐版本统计**。
  只统计 `v.author == author` 的原始条目自己带的标签，**不用**合并后的并集。
  > **变更 v1.2（主持人裁定，回应 Aster 的提问）**：并集口径会把 E-003 这种
  > "A 写决策、B 写实现"的冲突条目，记成"B 也用了 SEL-1、也做了决策"，
  > 和 v1.1 之后迁移边的逐版本口径自相矛盾——同一个人可能"有计数、无迁移边"。
  > 一个画像里两套口径，读的人会先怀疑工具再怀疑数据，所以统一成逐版本。
- `share[author] = 该作者的原始条目数 / 原始条目总数`，保留 4 位小数，分母 0 时全 `0.0`。
  同样按原始条目算，不按合并后的条目算——否则"两人共同确认"这件事会同时抬高两个人的占比。
- 迁移边**按单条原始条目判定，不看合并后的标签并集**：遍历 `item.versions` 中每条 `v`，
  若 `v.author != owner` 且 `v.has_tag("技能:<S>")`，记一条 `src=owner, dst=v.author`，证据为 `v.eid`。
  同一 `(src,dst,skill)` 合并成一条，`evidence` 收该组合下所有 eid（排序去重）。
  > **变更 v1.1（主持人）**：原文写的是「该条目带 `技能:<S>` 标签」，指的是合并后的并集标签。
  > 但两人共同确认的条目标签是并集，A 的日志里没打 `技能:SEL-2`，合并后却会带上，
  > 于是"两人一起记了分工"被算成"Aster 使用了 SEL-2"——纯属伪证据。
  > 迁移必须是**某个人自己写下的条目**，所以改成看 `versions`。见 `协作记录.md`「契约变更」。
- `share` 以"条目数"为分母，分母为 0 时全部取 `0.0`。
- `to_dict()` 要给出可直接 `json.dumps` 的结构，键名与上面字段同名。

返回纯文本；不含 ANSI，行宽对齐必须用 render.display_width（复用，不许另写一套）。"""

def explain_dict(result, eid: str) -> dict | None

 "winner": str | None,          # winner 作者名，无则 None

## 9. 协作者 B 必须提供的 CLI（`duolog/cli.py`）

```
python -m duolog merge --a A.md --b B.md [--author-a NAME] [--author-b NAME]
                       [--out PATH] [--report PATH] [--json] [--no-color] [--strict]
python -m duolog explain --a A.md --b B.md --eid E-003 [--author-a NAME] [--author-b NAME] [--json]
python -m duolog selfcheck
```

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功，且（若给了 `--strict`）没有 `needs_review` |
| 1 | 成功但存在 `needs_review` 且给了 `--strict`；或解析出现 error；或 `explain` 的 eid 不存在 |
| 2 | 用法错误 / 输入文件读不了 |

- `--json` 输出到 stdout，且**不能**混入 ANSI。
- `--out` 写合并后的 Markdown 日志（可再次被 `parse_log` 读回，形成闭环），
  `--report` 写 `render_markdown` 的结果。
- `selfcheck` 是零参数自检：内置两段样例日志，跑通解析→合并→渲染，
  打印 `selfcheck: ok <fingerprint>`，退出码 0。它不依赖任何外部文件。

## 10. 硬约束

1. **零第三方依赖**，只用标准库。
2. Python 3.9 语法（`from __future__ import annotations` 可用）。
3. 公共函数与类必须有中文 docstring，说明"为什么这样设计"，不只是"做了什么"。
4. 不得修改 `duolog/model.py`；发现契约有问题就在协作记录里提，由主持人改。
5. 不得写死任何绝对路径。
