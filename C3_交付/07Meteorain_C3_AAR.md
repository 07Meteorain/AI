# C3 AAR · 事后回顾

> AAR = After Action Review。不是"总结"，是**对照预期找差距，并对差距给出可验证的改进**。
> 本文按 预期 → 实际 → 差距 → 根因 → 改进 组织，失败项不美化。

---

## 0. 速览

| 项 | 结论 |
| --- | --- |
| 计划做什么 | 40 分钟内产出一套"能发出去"的群内参与材料 + 一个可运行的自查工具 |
| 实际做成什么 | 工具完成并 12 项测试通过；真实案例证据链完成；模板 4 份；**群聊参与本身未发生** |
| 最大成功 | 用三篇真实范文把评分器校准到与人直觉一致（0 / 33 / 100） |
| 最大失败 | 结论一度强于证据（把"进程创建被干预"写成"安全软件注入"） |
| 最该改的 | **先校准、再扩展**：任何自造指标，先拿真实样本打分，再谈规模 |

## 4. 失败经验（6 条，含 2 条未解决）

### F1 失败后重试，而不是换变量

- **现象**：同一条 `pwsh` 命令连续执行 3 次，3 次同样的 3221225794。
- **代价**：约 2 分钟 + 2 次无效调用。
- **5 Why**：为什么会重试？→ 因为没有假设。→ 为什么没有假设？→ 因为把"失败"当成"偶发"而不是"有原因的确定行为"。
- **改进**：**同一条命令失败一次即禁止原样重试**，第二次必须改变一个变量（命令 / 宿主 / 通道）。
- **验证**：本材料后续所有排障，第一次失败后立刻改用探针矩阵，未再重复。

### F2 交付物的起点选错（花了整整一轮返工）

- **现象**：第一版方案是"提问模板 / 讨论话术 / 复盘模板"三件套。
- **代价**：一轮方案返工。
- **根因**：把"产出文档"当成了"完成挑战"，而挑战评分表里的关键词是**推动力、新信息、可执行结论**——
  模板只是容器，容器本身不产生这些。
- **改进**：**先写"评委凭什么给分"，再写"我交付什么"**。若某个交付物无法通过一条可执行的检验，就删掉它。
- **验证**：本次工具通过 `--min 70` 与 12 项测试被检验；模板则明确标注为"辅助件"。

### F3 自造指标没校准就先跑（最典型的一类错）

- **现象**：评分器 v1 对一篇六要素齐全的好帖只给 80 分。
- **代价**：若不修，交付的将是一个"对好帖子偏严、对差帖子偏松"的评分器——**看起来能用，实际误导**。
- **根因**：先写实现，再找样本；正确顺序是**先定样本的期望分，再写实现**。
- **改进**：任何自造指标，**先准备 3 个"人工已判定"的样本**（差/中/好），把期望分写进测试，再写代码。
- **验证**：`tests/test_question_lint.py::TestScoreLadder` 已把 0 < 33 < 100 固化成测试。

### F4 过拟合到句式（"怎么回事"被当成好问题）

- **现象**：只要句末带问号且含"怎么"就给满分 15。
- **根因**：用"词表"近似"语义"，边界情况必然出错。
- **改进**：对**低信息问句白名单**做显式排除（怎么办 / 怎么回事 / 如何是好），并加最短长度约束。
- **遗留**：仍然是词表法，遇到"请问这个该怎么处理比较好呢"这种长句仍会误判。**未彻底解决**。

### F5 结论强于证据（本次最严重的一条）

- **现象**：排障到一半，AI 倾向写"根因是安全软件/DLP 注入"。
- **为什么危险**：提权后一切正常，但提权**同时**改变了"权限"和"是否被注入"两个变量。
  用一次观察归因两个变量，逻辑上不成立。
- **代价**：如果照抄，整份案例会变成"术语正确、推理错误"的专业幻觉。
- **改进**：**归因必须能排除竞争假设**；排不掉就写成"机制层"而非"具体软件"。本次最终写成"进程创建层被干预"。
- **验证**：`case_0xC0000142/案例复盘.md` §3 假设表里，H4/H5 明确标注"无法区分"。

### F6 文档/代码比例失衡（未完全解决）

- **现象**：约 300 行代码 vs 约 3000 行文档。
- **风险**：文档可以靠"写得好看"拿分，但读者真正需要的是"能用的东西"。
- **本材料的应对**：把文档全部绑定到可执行对象——每个模板都指向一个**真实跑过的**文件/输出，
  没有"纯理念"章节。
- **遗留**：比例仍然偏高。**如果重来一次**，我会把"回帖模板"压成一页，把省下的时间用来找 2 个真实用户试跑工具。**未做**。

## 7. 可复用的检查清单（沉淀成习惯）

```text
开工前：
  □ 写下"评委凭什么给分"，再决定交付物
  □ 任何自造指标，先准备 3 个人工判定样本
排障时：
  □ 同一命令失败一次 → 禁止原样重试，改一个变量
  □ 先做最小探针（谁坏了 / 全坏了）
  □ 归因必须能排除竞争假设，否则降级为"机制层"
交付前：
  □ 每条结论标注：已确认 / 候选 / 未验证
  □ 每个模板指向一个真实跑过的文件
  □ 未做的部分写进"未解决"，不留白也不编
```

---

> 这次最大的收获不是那 9 个文件，而是发现：**AI 能把"写"的成本降到 1/10，
> 但会把"判断写得对不对"的责任 100% 还给你。** AAR 就是接住这份责任的地方。
