## 2. 第 2 步：一次真实的环境排障（AI 先错了两轮）

### 2.1 我发出的第一个指令

> 「帮我列出 C3 目录下的文件」

AI 的回应是调用 `pwsh -Command "Get-ChildItem"`，返回：

```text
exitCode = 3221225794，stdout 空，stderr 空
```

**AI 的反应是「再试一次」。** 第二次、第三次，结果一模一样。

到第三次时我介入，改成一个不同的问题：

> 「不要重试同一条命令。换**最小探针**：依次试 `cmd.exe /c echo hi`、`git --version`、`where git`，
> 各自记录退出码和 stderr，看是"某个命令坏"还是"所有子进程都坏"。」

这一句把问题从"这个工具有 bug"改写成"进程创建是否可用"，**排查方向从此不同**。

### 2.2 探针结果（真实输出）

| 探针 | 宿主 | 结果 |
| --- | --- | --- |
| `pwsh -Command "echo hi"` | 直接调用 | 3221225794 |
| `cmd.exe /c echo hi` | Node spawnSync | 3221225794 |
| `git --version` | Node spawnSync | 3221225794 |
| `git --version` | Node spawnSync, `stdio: pipe` | EPERM |
| `cmd.exe /c echo hi` | 提权后 | **0** |

`3221225794` = `0xC0000142` = `STATUS_DLL_INIT_FAILED`。

### 2.3 事后看，这里有三层浪费

| 浪费 | 代价 | 本可以怎么省 |
| --- | --- | --- |
| AI 重复同一条命令 3 次 | 约 2 分钟 + 2 次调用 | 第二次失败就该换参数，而不是重试 |
| 没有第一时间看**退出码语义** | 多走了"换命令"这一步 | 3221225794 是十六进制错误码，先转 0x 再看含义 |
| 我直到第 3 轮才给"最小探针"指令 | 整条排障链晚了 3 分钟 | 第一句指令就该写"先探针后修" |

> 这段排障后来被我整成了 [`case_0xC0000142/`](case_0xC0000142/) 的案例——
> **失败的经验也是可交付物**，前提是把它写下来。

## 3. 方案取舍：我否决了 AI 的第一版交付物

### 3.1 AI 的第一版（被否决）

> 「C3 是社区参与类挑战，建议交付：① 高质量提问模板 ② 讨论引导话术 ③ 复盘模板」

看起来合理，但按这个做出来会是**三份一模一样的 Markdown 空壳**：

| 问题 | 为什么致命 |
| --- | --- |
| 不可验证 | 没有人能判断"这个模板好不好用"，包括我自己 |
| 不可复现 | 交完就结束，没有任何东西可以跑 |
| 撞红旗 | 挑战明确写着「一句话指令直接提交、无迭代」扣分，模板堆砌本质上是同一类东西 |

### 3.2 我的改写指令（第二次迭代的关键）

> 「模板不算产物。给我一个**能跑的东西**：把"高质量提问"变成可机械检查的规则，
> 输入一段草稿，输出缺哪几项、扣几分、怎么补。然后**用一篇真人写的差帖和一篇好帖验证它**。」

这一改，交付物从"文档"变成了"工具 + 数据 + 结论"，也才有了后面的全部内容。

### 3.3 三次 prompt 迭代对照

| 轮次 | 我的 prompt（节选） | AI 的产出 | 问题 | 我的修正 |
| --- | --- | --- | --- | --- |
| v1 | 「帮我完成 C3 挑战」 | 一份 1500 字的"参与指南" | 全是正确但无用的话（"要积极发言"） | 要求可验证 |
| v2 | 「做一个提问质量检查器」 | 6 个关键词正则，命中即加分 | 好帖子和差帖子分数接近，无区分度 | 要求"用真实范文校准" |
| v3 | 「用 `cases/` 里的三篇跑一遍，把分数给我看」 | 跑出 0 / 42 / 80 | **好帖子只有 80**，暴露检测漏洞 | 定位到"只认动词不认列表" |

> 注意 v2→v3 这一步：**我没有靠读代码发现 bug，是靠"分数不符合直觉"发现的。**
> 这也是我给工具加 `cases/` 目录的原因——没有校准样本的评分器只是玄学。

## 4. 第 6 步：AI 写的代码被真实数据打脸（最值得记的一段）

### 4.1 第一次跑分

```text
bad_01.md    0.0 / 100    E
mid_01.md   42.0 / 100    D
good_01.md  80.0 / 100    B     ← 问题在这
```

`good_01.md` 是我逐条写满六要素的真实提问稿，AI 判它 80 分，扣在"已尝试方案"：

```text
[×] 已尝试方案（≥2 条，含结果）  0.0/20  已尝试条目：0 条
```

但那篇稿子里明明有 5 条尝试。原因：

| 稿子里的写法 | v1 的正则 |
| --- | --- |
| `1. stdio: "inherit" → 仍然 3221225794` | 只找「试过 / 查过 / 试了」等动词 → **一个都没匹配** |

**AI 按"人怎么写句子"建模，而真实投稿是按"编号列表 + 箭头"写的。**
这是典型的"在训练分布里正确，在真实文本里失效"。

### 4.2 修复

```python
def _attempt_items(text):
    """列表项只要"动作 + 结果"齐了，也算一次尝试。"""
    n = 0
    for line in text.splitlines():
        s = line.strip()
        if not re.match(r"^(\d+[.)]\s+|[-*+]\s+)", s):
            continue
        if re.search(RESULT_WORDS, s, re.I) or "→" in s or "->" in s or "status=" in s:
            n += 1
    return n
```

改成取两者最大值后，`good_01.md` → **100 / 100**。

### 4.3 同一轮里的第二个 bug（我自己发现的）

`mid_01.md` 因为句末有「怎么回事？」被判为"有具体提问"，拿满 15 分。
但"怎么回事"恰恰是最典型的**低信息问句**——它把"该问什么"的活留给了回答者。

修法：给"具体提问"加两个约束——**问句长度 ≥ 8 字**，且**排除"怎么办/怎么回事/如何是好"这类纯感叹式问法**。
改完 `mid_01.md` 从 42 降到 33（评级从 D 掉到 E），与人工直觉一致。

### 4.4 最终的分数阶梯

| 样本 | 修复前 | 修复后 | 评级 | 人工直觉是否同意 |
| --- | --- | --- | --- | --- |
| `bad_01.md`（救命！报错了怎么办？？） | 0 | 0 | E | 同意 |
| `mid_01.md`（有现象，无环境/无期望） | 42 | 33 | E | 同意（AI 原判偏松） |
| `good_01.md`（六要素齐全 + 可跑复现） | 80 | 100 | A | 同意（AI 原判偏严） |

**两个 bug 的方向相反**：一个对好帖子太严，一个对差帖子太松。
如果没有 `cases/` 里这三篇真实文本，两个 bug 都会一路带到交付里，而且**看不出来**。

## 5. 测试：我让 AI 给工具写"会失败的测试"

12 项测试里，我认为最有价值的不是"功能对不对"，而是这几条**契约测试**：

| 测试 | 它防的是什么 |
| --- | --- |
| `test_each_element_adds_points` | 补要素却掉分——评分逻辑不自洽 |
| `test_case_ordering` | 好帖分值低于差帖——工具失效却"跑得通" |
| `test_min_threshold_exit_code` | 阈值不生效——守门员形同虚设 |
| `test_attempts_from_list_items` | 就是我刚修的那个 bug，**防止回归** |

```text
Ran 12 tests in 0.792s
OK
```

## 6. AI 说错/说不准的地方（不是"边界"，是具体错处）

| # | AI 的说法 | 实际 | 谁发现的 |
| --- | --- | --- | --- |
| 1 | 「再试一次 pwsh」 | 同一条命令必然同样失败 | 我 |
| 2 | 把"已尝试"理解成"有动词才算" | 编号列表是更常见的写法 | 分数异常 |
| 3 | 「怎么回事？」算具体提问 | 恰恰是低信息问句 | 我 |
| 4 | 第一版交付物是"模板三件套" | 不可验证、撞红旗 | 我 |
| 5 | 排障时倾向写「根因是安全软件注入」 | 提权同时改变了"权限"和"注入"两个变量，**不能归因** | 我（见案例 §3 的 H4/H5） |

第 5 条是这次最危险的一条：**AI 给出的结论比证据支持的更强**。
如果照抄，就会变成一篇"看起来专业、实际站不住"的复盘——而这正好是 C3 评分里"内容实质"要扣的分。

## 7. 我坚持要人工做的四件事

| 事项 | 为什么不能外包给 AI |
| --- | --- |
| 判定"这份交付物值不值钱" | AI 会夸自己写的东西；价值排序需要外部标准 |
| 判定"这个结论证据够不够" | AI 倾向于把候选写成定论（见 §6 第 5 条） |
| 决定"群聊参与部分怎么处理" | 涉及诚实：我不能代你发言，也不该编造截图 |
| 校准评分器 | 只有人知道"好帖子该拿几分"，工具做不到自我校准 |

---

## 8. 诚实边界（必须写清楚的三件事）

1. **群聊部分没有伪造。** 这份材料提供的是"发出去就能用"的稿件 + 记录模板，
   真实的群内往返（日期、链接、对方回复）必须由本人在 `participation/参与记录表.md` 里填。
2. **`case_0xC0000142` 的时间线和退出码是本次实测**，但"根因是安全软件/DLP 注入"仍是**候选**，
   我没有 Procmon 现场证据。
3. **工具的分数只反映"信息完整度"，不反映"问题是否值得问"。** 一个六要素齐全的蠢问题仍能拿 100 分——
   这是工具的已知盲区，写在 README 的「局限」一节里。

## 9. AI 段位自评

**🟡 中级（高效执行者，非决策者）**

| 维度 | 评价 |
| --- | --- |
| 强项 | 结构化写作、代码骨架、把模糊需求变成可运行脚本、跨文档命名一致性 |
| 弱项 | 排障时倾向"重试"而非"换变量"；结论比证据强；对"文本的真实写法"建模不足 |
| 这次的证据 | 12 项测试一次通过、40 分钟产出 9 个文件；但**两处关键 bug 和一处越界结论全部由人兜住** |

> 对比来看：AI 把"从 0 到 1 写出工具"的成本压到了 20 分钟，
> 但**把"这个工具是否可信"的成本压不下来**——后者靠的是三篇真实范文和一次分数异常。
