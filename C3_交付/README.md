## 这是什么

一套由三部分组成的材料：

| 部分 | 内容 | 形态 |
| --- | --- | --- |
| **① 工具** | `question_lint.py`：一段提问草稿进去，六要素缺什么、扣多少分、怎么补，出来 | 可运行，12 项测试 |
| **② 案例** | `case_0xC0000142/`：一次真实故障的完整证据链（现象→证据→假设→排除→结论） | 可复现，附探针脚本 |
| **③ 方法** | `participation/`：提问 / 回帖 / 结论卡 / 参与记录，四份模板 | 可直接复制使用 |

加三份必需交付物：**AI 日志**、**AAR**、**反思**。

## 快速开始

```bash
cd C3_交付/linter

python question_lint.py cases/good_01.md        # 看一篇 100 分的提问长什么样
python question_lint.py cases/bad_01.md         # 看一篇 0 分的提问长什么样
python question_lint.py --batch cases           # 三篇一起跑（demo_output.txt 就是它的输出）
python question_lint.py --selftest              # 内置自检
python -m unittest discover -s tests -v         # 12 项测试
```

**零依赖**：Python 3.9+ 直接跑，不需要 `pip install` 任何东西。

### 当你自己要发帖时

```bash
python question_lint.py 我的草稿.md --rewrite --min 70
```

- `--rewrite`：逐条告诉你缺什么、补哪句话；
- `--min 70`：低于 70 分退出码为 2，可以挂进 pre-commit 或发帖脚本，**让"发不出去"变成机器的事**。

## 核心设计：为什么是"工具"而不是"模板"

模板回答不了"我这份稿子到底行不行"。评审也回答不了——**没人能证明一份模板被用过**。

所以这套材料把判断标准写成了代码：

| 六要素 | 权重 | 机械判据 |
| --- | --- | --- |
| 上下文（环境 / 版本 / 目标） | 20 | 是否有系统/版本 + 目标句 |
| 已尝试方案（≥2 条含结果） | 20 | 动词行 或 编号列表项含结果标记 |
| 具体卡点（错误码 / 定位） | 15 | 错误码/异常类型 + 文件:行 |
| 证据（日志 / 复现 / 截图） | 20 | 代码块 + 复现步骤 + 截图，三取二 |
| 期望 vs 实际 | 10 | 两侧标记是否同时出现 |
| 可回答的具体提问 | 15 | 问句 ≥ 8 字且非"怎么办"式 |
| 负向信号 | -5 ~ -10 | 情绪词 / "报错了"无下文 / 过短 / 连续感叹号 |

评分阶梯（`cases/` 里就是这三篇，测试锁死了顺序）：

| 样本 | 分数 | 评级 | 特征 |
| --- | --- | --- | --- |
| `bad_01.md` | 0 | E | "救命！报错了，怎么办？？？" |
| `mid_01.md` | 33 | E | 有现象、有一句尝试，没有环境/期望/复现 |
| `good_01.md` | 100 | A | 六要素齐全 + 20 行可跑复现 + 两个可回答的问题 |

## 局限（写在显眼处）

1. **这个工具只衡量"信息完整度"，不衡量"问题值不值得问"。**
   一个六要素齐全的蠢问题照样能拿 100 分——信息完整和问题有价值是两件事。
2. **它是词表法，不是语义理解。** 长句子里的软性问法仍会误判（见 AAR 的 F4，未彻底解决）。
3. **校准样本只有 3 篇，且全由作者一人判定。** 换成别人的直觉，分档可能移动。
4. **群内参与本身没有被伪造。** 真实的发帖、回复、结论回馈必须由本人完成，
   记录填在 `participation/参与记录表.md` 的空格里。这份材料给的是"能立刻发出去的稿件"和"记录框架"。
