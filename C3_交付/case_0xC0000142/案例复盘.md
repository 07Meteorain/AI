# 真实案例：从「报错了」到一条可执行的结论

> 这份文件是 C3 的**示范样本**：一个真实故障的完整证据链，
> 按「现象 → 证据 → 假设 → 排除 → 结论 → 回帖」组织。
> 你可以把它当作模板，把 0xC0000142 换成你自己的问题。

---

## 0. 一句话结论

> **当"所有"子进程都以 `0xC0000142`（STATUS_DLL_INIT_FAILED）秒退，且错误不随命令、路径变化时，
> 不要去改代码——问题在进程创建层（沙箱 / 终端安全软件注入），改代码一定白改。**

判据只有一条：`cmd.exe /c echo hi` 也挂。

---

## 1. 现场

| 项 | 值 |
| --- | --- |
| 时间 | 2026-11-06 00:12（Asia/Shanghai） |
| 触发动作 | 在 `E:\我的挑战\C3` 目录下调 `pwsh -Command "echo hi"` |
| 返回 | `exitCode = 3221225794`，stdout 为空，stderr 为空 |
| 换个命令 | `git --version` 同样 3221225794 |
| 换个宿主 | Node `spawnSync` 同样 3221225794（`stdio: "pipe"` 时变成 EPERM） |

`3221225794` 的十六进制是 `0xC0000142`，即 `STATUS_DLL_INIT_FAILED`：
**进程已经创建，但在 DLL 初始化阶段就死了**，所以拿不到任何输出。

这个细节很关键——它把问题从"命令执行失败"缩小到了"进程启动失败"。

---

## 2. 证据链（可复跑）

### E1 最小复现（Node，本次实际使用的探针）

```js
const { spawnSync } = require('child_process');
for (const c of ['cmd.exe', 'git', 'where']) {
  const r = spawnSync(c, ['--version'], { stdio: 'inherit' });
  console.log(c, 'status=', r.status, 'err=', r.error && r.error.code);
}
```

实测输出：

```text
cmd.exe status= 3221225794
git     status= 3221225794
where   status= 3221225794
```

**第一条就足够下结论了**：`cmd.exe` 是系统自带、绝对路径可解析、不依赖任何项目环境的程序。
它都挂，说明问题不在"我的命令"。

### E2 换 stdio 模式（意外发现）

| stdio | 结果 |
| --- | --- |
| `inherit` | 3221225794 |
| `ignore` | 3221225794 |
| 重定向到文件句柄 | 3221225794 |
| `pipe` | **null / EPERM** |

同一个命令，只因为输出通道不同，错误类型就变了。
说明失败点在**进程创建**这一步，而且创建过程中的不同代码路径受不同限制。

### E3 排除"PATH / 路径 / 权限位"

- 用绝对路径调 `cmd.exe`：仍然 3221225794 → 不是 PATH
- 同一用户、同一目录：换成别的可执行文件全挂 → 不是单个文件权限位
- 在"提升权限"的终端里跑同一条命令：`status = 0`，`git version 2.55.0.windows.5` 正常打印 → **不是机器坏了**

### E4 对照表

见 [`control_run.txt`](control_run.txt)：同一台机器、同一条命令，
受限环境三个探针全红，完整权限下三个探针全绿。

## 3. 假设与排除（这一步是"高质量"和"瞎试"的分水岭）

| # | 假设 | 如果成立，应该观察到 | 实际观察 | 判定 |
| --- | --- | --- | --- | --- |
| H1 | 命令写错 / 参数错 | 换成 `echo hi` 应成功 | 也挂 | ✗ 排除 |
| H2 | PATH 找不到可执行文件 | 用绝对路径应成功 | 仍挂 | ✗ 排除 |
| H3 | 缺 VC 运行库 | 换个程序可能能跑；事件日志有 SideBySide 错误 | 与程序无关，全挂 | ✗ 基本排除（未查事件日志，置信度 0.7） |
| H4 | 安全软件 / 沙箱注入 DLL | 提权或退出该软件后恢复 | 提权后 `status = 0` | **✓ 保留** |
| H5 | 我的用户权限不够 | 换管理员应成功 | 提权后成功 | ✓ 与 H4 同向，不能区分 |
| H6 | pipe 通道被额外拦截 | pipe 应给出不同错误 | EPERM 而非 0xC0000142 | **✓ 保留** |

**H4 与 H5 无法用现有证据区分**——这是本次最诚实的一处：
提权同时改变了"权限"和"是否被注入"两个变量，我在这一步停手，
没有把结论写成"因为权限不足"，而是写成"进程创建层被干预"。

## 4. 结论（可以直接贴到群里的话）

```markdown
结论：0xC0000142 不是你的代码问题，是进程创建层被干预。

三步自查（30 秒）：
1. 跑 `cmd.exe /c echo hi`，看退出码是否为 3221225794 / 0xC0000142；
2. 若是，把 stdio 换成 pipe 再看一次——错误变成 EPERM 就基本确认是环境拦截；
3. 在提权终端里重跑一次探针；由红转绿 = 环境层问题，收工，别改代码。

根因候选：终端安全/DLP 客户端注入、容器/沙箱的作业对象限制。
定位工具：Procmon（过滤 CreateProcess + 结果列 STATUS_DLL_INIT_FAILED）。
```
