# Meteorain_C4A_拿来说明

> C4A 明确要求："必须从 `wechat-doc-mapper.skill` 出发。
> 不奖励从零开始——奖励'拿来 → 理解 → 改造 → 超越'。说明你拿了什么、改了什么、为什么改。"

本文分三部分：**一、拿了什么**（继承）、**二、改了什么**（改造）、
**三、为什么这么改**（取舍分析）。

---

## 一、拿了什么：从wechat-doc-mapper 继承的资产

### 1.1 先读代码，再动手

拿到 `wechat-doc-mapper.skill` 后，我完整读了三个文件：

| 文件 | 行数 | 我从里面得到什么 |
|---|---|---|
| `SKILL.md` | 322 | 设计思路：作者识别链、信号映射、缺口分析的编排方式 |
| `scripts/wechat_doc_mapper.py` | 557 | 可直接复用的代码骨架与工具函数 |
| `references/challenges.yaml` | — | 「判据外置到 YAML」的架构模式 |

### 1.2 直接继承的代码资产

原脚本里这些函数**几乎原样搬过来**（只改了少量参数）：

| 原函数 | 继承方式 | 说明 |
|---|---|---|
| `inventory_folder()` | → `collect_submissions()` | 递归扫描、元数据采集、跳过隐藏文件、遍历异常保护 |
| `NAMING_PATTERN` 正则 | → `NAMING_RX` | 作者识别的命名规范基础 |
| `extract_title()` 全套 | → `extract_text()` | `.pdf`/`.docx`/`.pptx`/`.xlsx`/`.tex`/`.bib` 的格式分发读取 |
| `generate_excel()` | → `render_xlsx()` | openpyxl 样式：表头填充、冻结首行、列宽自适应、边框 |
| `_title_from_text()` | → `_read_text_safe()` | UTF-8 + `errors="replace"` 的容错读取 |
| `challenges.yaml` 外置模式 | → `c4_rubric.yaml` | 判据与代码分离的架构原则 |

**粗略统计**：评审器 `c4a_evaluator.py` 约 900 行，其中约 **250 行**直接继承或小改自原脚本
（格式读取、Excel 样式、扫描骨架、正则容错）。这部分**不是我的设计**，是拿来主义。

### 1.3 继承的三个设计思想

比代码更重要的是三个**设计判断**，我把它们完整保留了下来：

**① 作者优先原则**
> 原技能注释里写：「这是 FIRST analytical step. Before classifying content,
> determine WHO submitted each file. Think of it as sorting mail — you look at
> the return address before opening the envelope.」

我在 C4A 里延续了这个顺序：`collect_submissions()` 必须先跑完、确定作者归属，
`check_completeness()` 与 `evaluate_quality()` 只在已分组的 bundle 上工作。
**不分组就没有"某个人的完整性"这个概念**——C4A 评的是人，不是文件。

**② 命名规范 + 回退链**
原技能没有强推命名规范，而是设计了「文件名 → 元数据 → 目录 → 文档头 → 标记待确认」
的降级链。我完整继承并**加长了这条链**（四级 + 目录传播 + 别名归并）。

**③ 判据外置到 YAML**
原技能把挑战定义放`challenges.yaml`，代码读它。我在 C4A 里把评审标准放
`c4_rubric.yaml`，代码读它——**这个模式让"改标准不用改代码"成为可能**，
是我后续能做20 个 check_item 的前提。

### 1.4 继承的边界情况处理

原脚本 `main()` 里对异常的处理方式（`try/except` 包住、失败返回降级值而非崩溃）
被完整沿用，并扩展到每个格式解析函数：

```python
def _title_from_pdf(path):        # 原版
    from pypdf import PdfReader
    r = PdfReader(path)            # ← 损坏文件会直接抛异常

def _text_from_pdf(path):          # C4A 版
    try:
        from pypdf import PdfReader
        return "\n".join(...)
    except Exception:
        return ""                  # ← 任何失败都降级为空串
```

**为什么必须这样改**：C4A 要处理的是「一个装着几十个人杂乱文件的群文件夹」。
原脚本处理的是「一个作者自己整理好的文件夹」，可以假设文件是好的。
**输入环境的宽容度要求完全不同**——一个人的坏文件不能中断全批评审。

## 二、改了什么：从分类器到阅卷器

### 2.1 本质转变

| | wechat-doc-mapper | c4a-skill-evaluator |
|---|---|---|
| **回答的问题** | 这些文件属于哪个挑战？ | 这份提交够不够格？ |
| **输出** | 清单表格 | 评级 + 证据 + 排名 + 改进建议 |
| **判定依据** | 文件名关键词 + 扩展名 | 20 个加权 check_item + 结构性解析 |
| **失败模式** | 分类错了（文件归错挑战） | **误判**（把差的判成好的） |
| **设计取向** | 召回率优先（别漏文件） | **精确率优先**（别给假高分） |

**失败模式的变化，是所有改造的根源。**
分类错了，用户自己一眼能看出来（"这明显不是 C1 啊"）；
评审判错了，会直接误导老师和同学——**这是有实际伤害的**。

所以改造的方向不是"覆盖更多"，而是"**结论更可信**"。

### 2.2 七个具体改造

#### 改造① 关键词打分 → 加权 check_item + veto

**原方案**（`map_to_challenges()`）：
```python
scores[cid] = 0
for kw in cdata["signal_keywords"]:
    if kw.lower() in combined: score += 2      # 命中一个词 +2
for ext in cdata["signal_extensions"]:
    if item["ext"] == ext: score += 3          # 扩展名匹配 +3
for seg in cdata["signal_paths"]:
    if seg in item["path"]: score += 4         # 路径片段 +4
```

所有信号**等权累加**，靠总分高低选主挑战。这个模型用于分类是合理的
（分类错了不致命），但用于**评级**有两个致命问题：

1. **无法表达"致命伤"**——硬编码路径和"写了安装说明"都是 +2，可以互相抵消
2. **不产出证据**——只知道"得分 7分"，不知道"哪句话给了哪一分"

**改造后**：每个信号是一个带权重、可独立判定的 check_item；
致命项标记 `type: veto`，命中即把该维度**封顶 ❌**。

**为什么 veto 是必需的**（这是实测逼出来的）：
LiMing 的提交硬编码了 `/Users/lm/Desktop/meeting_summary/summary.py`，
但同时有安装说明（+1.0）、相对路径写法（+0.8）、无凭据（+1.5）——
等权累加得 `3.3/5.8 = 57%`，评级 ⚠️「部分满足」。

**但 C4 对可复用的检验原话是"让一个陌生人按你的说明操作，能成功吗？"**
答案已经是否定的。加权平均把致命伤稀释成了小瑕疵。
所以：veto 命中 → 该维度直接 ❌，不管其他项拿多少分。

#### 改造② 纯文本匹配 → 结构性硬校验

原脚本所有判定都基于**字符串包含**。我增加了三类真实解析：

| 检查 | 实现 | 拦住了什么 |
|---|---|---|
| 代码可解析 | `ast.parse(src)` | 语法错误的 .py混进提交 |
| frontmatter 合法 | `re.search(r"\A---\s*\n...name:", s)` | 没写清 name/description 的 SKILL.md |
| 归档可打开 | `tarfile.is_tarfile(p)` | 损坏的 .skill 包 |
| 媒体真实存在 | 扩展名 + 文件大小 | 用"截图描述"冒充 demo |

**为什么这比关键词更可信**：语法错误这件事**没有解释空间**——
`ast.parse` 说失败就是失败，不存在"可能是我关键词选得不好"。
这类证据的置信度直接标 `high`。

顺带一个副作用：结构性证据成为**置信度的锚点**。
当某维度有关键项由硬校验支撑时，整体置信度就是 `high`，而非`low`。

#### 改造③ 单层作者识别 → 四级链 + 目录传播 + 别名归并

原技能已有四级链（文件名 → 元数据 → 目录 → 文档头），我完整继承并补了三个补丁：

**补丁 a：目录传播**
```python
# 原版：只处理"同目录"
if str(Path(rec.rel_path).parent) in c4_dirs:
    rec.is_c4 = True

# C4A 版：沿目录树向上找最近的、已归属某作者的祖先目录
parts = Path(rec.rel_path).parts[:-1]
for k in range(len(parts), 0, -1):
    d = str(Path(*parts[:k]))
    if d in author_dirs:
        owners = author_dirs[d]
        break
```

**为什么必须加**：真实群文件夹里 `ZhangWei/scripts/pr_desc.py` 没有 `_C4_` 标记，
但它**恰恰是判断「可执行」最关键的证据**。
最初的"同目录"版本把它漏掉了，导致 ZhangWei 的 E4 判❌——
**测试直接抓到了这个 bug**（详见方案设计 §6 第4 条）。

**补丁 b：别名归并**
`ZhangWei` / `zhangwei` / `Zhangwei` 应视为同一人。
原技能注释里明确写了「The skill does NOT auto-merge variants — flag potential
duplicates for manual review」——**我选择自动归并**，理由是 C4A 要出排名，
让人工去猜"这两个名字是不是一个人"不可接受。首字母大写做规范化。

**补丁 c：中文名vs 目录名的冲突**
`王晓_C4_技能说明.md` 放在 `WangXiao/` 目录下，原逻辑会解析出两个作者。
规则：**同目录下，目录名的可信度高于文件名**（目录是人主动建的，文件名可能来自模板）。

#### 改造④ 只比"文件在不在" → 加权完整性 + 依据可追溯

原 `gap analysis` 输出的是「C2 缺少 references.bib」这种**存在性缺口**。

C4A 的完整性检查做了三件事升级：
1. **加权**：五个必交文件各 0.20，但 `demo` 因为常有"用文字描述代替"的情况，
   判定上更严格
2. **三级判定**：✅ / ⚠️ / ❌，而不是简单的有/无
3. **依据可追溯**：每个判定附带 `文件名命中强信号：ZhangWei_C4_skill说明`
   或 `正文仅命中 2 个信号（需 3）`

**为什么优先级是"真实文件 > 文件名 > 正文"**：
人主动命名的文件名，比程序猜测的正文命中更能反映意图。
一个人把文件命名成 `教学说明.md`，比他在正文里恰好写了"步骤"两个字更可信。

#### 改造⑤ 挑战映射 → 四条件质量评审

这是最大的新增，原技能完全没有对应能力。20 个 check_item 的设计已在
方案设计中详述，这里只说**取舍**：

| 维度 | 我加了什么 | 为什么加 |
|---|---|---|
| 可复用 | R2 veto、R4 路径可移植 | 硬编码路径是C4「可复用」的头号杀手 |
| 可执行 | E3 CLI 入口、E4 结构解析 | 区分"能跑"和"别人能跑起来" |
| 可验证 | V1 测试、V2 预期输出、V4 边界 | C4 原文："给定输入 X，能得到预期输出 Y 吗？" |
| IO 明确 | I1 句式正则（权重 1.5） | C4 原文："一句话能说清输入____，输出____" |

每个维度的 item 都**直接对应 C4.md 的检验方法原文**，不是我自己发明的标准。
这很重要——评审标准必须可追溯到challenge 原文，否则就是"我说了算"。

#### 改造⑥ 双格式输出 → 四格式 + 置信度标注

原技能输出 Markdown + Excel 两样。C4A 输出四样，且**每一份都加了置信度**：

| 格式 | 原技能 | C4A 增加 |
|---|---|---|
| Markdown | 清单表格 | 逐项证据表（含文件行号），置信度标记 |
| Excel | 3 sheet（清单/覆盖/参考） | 5 sheet，新增「逐项评审明细」可筛选 |
| JSON | 无 | 全部原始判定，供二次分析 |
| HTML | 无 | 仪表板，四条件达成度可视化 |

Excel 的「逐项评审明细」是最有用的新增——它把 20 个判定摊平成可筛选表格，
老师筛 `R2 = ❌` 就得到"哪些人写了硬编码路径"的可执行名单。

#### 改造⑦ 从"输出结论"到"暴露不确定性"

原脚本输出结论，没有不确定性的概念。C4A 增加了三处：

1. **置信度分级**：每条判定标 `high`/`medium`/`low`
2. **低置信度惩罚**：综合分 × 0.90 + 标记"需人工复核"
3. **矛盾检测**：完整性 80%+ 但质量 <25%（或反之）→ 报警"可能是空壳提交"

**这是我认为最重要的一项改造**。
一个自动评审工具最大的风险不是"判错"——任何工具都会偶尔判错——
而是**"判错了还说得很有把握"**。

明确标记"这条结论我不确定"，让人类去判断哪几条需要细看，
比给一个假装很确定的错结论有价值得多。

## 三、为什么这么改：取舍分析

### 3.1 三个关键取舍

#### 取舍① 精确率 vs 召回率

| | 分类任务（wechat-doc-mapper） | 评审任务（C4A） |
|---|---|---|
| 目标 | 别漏掉任何可能相关的文件 | 别把不达标的东西判成达标 |
| 漏判代价 | 用户自己会发现 | **老师可能据此评分** |
| 误判代价 | 用户自己会发现 | **伤害同学，且难以申诉** |

所以我**主动放弃了一部分覆盖率**换取精确率：
- `R1 有安装说明` 只用 11 个关键词，宁可漏判也不乱判
- 单关键词命中一律标`low` 置信度
- 作者 `Unknown` 时**不参与排名**，而不是猜一个

**代价是明确的**：会漏掉一些写得规范但用词 peculiar的提交。
**这是有意的取舍**，并且通过置信度标注让用户知道"这里可能没看准"。

#### 取舍② 规则 vs LLM

已在方案设计 §2 详述。核心判断：
**C4 四条件是客观可判定信号，不需要理解，只需要检测。**

用LLM 做本可以做的事，代价是结论不可复现（同一份文件两次结论可能不同）、
成本高、且**无法产出可追溯的证据**（"模型觉得可复用"在争议时毫无用处）。

我把 LLM 放在规则不确定时的补充位置，且本版未接入——
**接口用 `confidence` 字段预留了，这是有意的范围控制**。
理由：如果规则层连自己的误判率都测不出来，加 LLM 只会让问题更难定位。

#### 取舍③ 通用性 vs 深度

`c4_rubric.yaml` 的schema 设计成通用结构（检查项 = 类型 + 信号 + 权重）。
所以换个挑战标准就能复用。

**代价**：无法为 C4 四条件做深度优化。比如"可执行"这一项，
通用schema 只能检查"有没有代码块""能不能解析"，
但没法判断"这段代码是否解决了一个真问题"。

**我接受这个代价**：C4A 的评分标准里有 30% 给"评审准确性"，
说明评审质量比通用性重要。

### 3.2 一个我**没有**做的改造

原脚本的 `map_to_challenges()` 支持"一个文档映射到多个挑战"
（primary + secondaries）。C4A **没有沿用**这个设计。

**原因**：C4 提交是**一个技能一个包**，一个 bundle 天然对应一个挑战/作者。
多挑战映射是为"一份讨论记录同时涉及 C2 和 C3"设计的——
那是分类问题，不是评审问题。

**强行沿用会怎样**：会让"这个提交到底算几份"变得模糊，
而 C4A 的排名必须基于明确的"一个人一份提交"。

### 3.3 保留的、但弱化的部分

| 原技能机制 | C4A 处理 | 为什么弱化 |
|---|---|---|
| `infer_purpose()` 推断用途 | **移除** | 评审不需要知道文件"是什么用途"，只需要知道"够不够格" |
| `extract_title()` 提标题 | 保留但并入 `extract_text()` | 评审只需要正文，标题是正文子集 |
| 二级挑战映射 | 移除 | 见上|
| Excel "Challenge Reference" sheet | 移除，改为 "文件清单" sheet | C4A 的读者不需要挑战定义参考 |

**移除 `infer_purpose()` 是个判断**。它挺有意思，但评审场景里
"这份文件是会议纪要还是教程"对判定"够不够格"没有帮助——
删掉它让代码少了约 40 行，也让报告更聚焦。

## 四、总结：拿 → 理解 → 改造 → 超越

| 阶段 | 具体做了什么 |
|---|---|
| **拿** | 复用约 250 行代码（格式读取、Excel 样式、扫描骨架、正则容错）+ 3 个设计思想（作者优先、判据外置、优雅降级） |
| **理解** | 完整读懂三份文件后才动手；发现原脚本的`try/except` 缺失是**因为它假设输入干净**，而 C4A 的输入是几十人的杂乱群文件夹 |
| **改造** | 7 项改造：加权+veto、结构化硬校验、目录传播、三级完整性、四条件评审、四格式输出、置信度体系 |
| **超越** | 原技能是"分类盘点"，C4A 是"自动阅卷"；核心增量不是功能而是**可信度机制**（证据、置信度、矛盾检测、误判率测量） |

**一句话总结**：

> 从 wechat-doc-mapper 拿来的不是代码风格，而是"**把判据外置、把作者优先、
> 把失败处理干净**"这三个工程习惯。
> 而我加的最重要的东西，不是任何一项功能，是**让评审器承认自己会不确定**——
> 证据、置信度、矛盾检测、误判率测量，都是为了让这个工具的结论可被信任。
> 一个会主动说"这条我不确定"的评审器，比一个永远给分的评审器有用得多。
