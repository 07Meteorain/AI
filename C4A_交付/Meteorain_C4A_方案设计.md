# Meteorain_C4A_方案设计

> 挑战：C4A 技能提交自动评审 ｜ 平台 ID：`ch-20260717031432-5jvqje`
> 基座：`wechat-doc-mapper.skill`（C4 示例技能 1）
> 完成级别：**Level 4 完整评审系统**

---

## 一、要解决的问题

C4 挑战里，每人提交一个技能包（五个必须文件 + 四条件达标）。老师/助教收到群文件后要做三件事：

1. **谁交了？** —— 30 份文件散在微信群里，命名各异
2. **齐不齐？** —— 五个必须文件是否都在
3. **合不合格？** —— 可复用 / 可执行 / 可验证 / IO明确，四条主观标准

现有工具 `wechat-doc-mapper` 只能做第1、2 件事（分类 + 缺口），**没有第 3 件事的能力**。
C4A 要做的就是在它之上长出"阅卷"能力。

**关键约束（来自挑战说明）**：无论文件怎么从微信弄到本地，技能必须只接受
**一个本地文件夹路径**作为输入。这决定了整个架构的形态。

---

## 二、架构选型：为什么是"规则为主、LLM 为辅"

C4A 原文给了三种方案选择，这是本设计的第一个关键决策：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯规则（关键词/正则） | 确定性强、快、零成本 | 覆盖率低、易误判 |
| 纯 LLM | 理解力强、灵活 | 不确定、慢、贵、不可复现 |
| 规则 + LLM 混合 | 规则快筛 + LLM 深审 | 架构复杂 |

### 我的选择：**规则为默认主路径，LLM 仅在规则不确定时介入**

理由不是"规则更先进"，而是对**评审这件事的性质**做了判断：

C4 的四条件是**客观可判定的信号**——"有没有硬编码绝对路径""代码能不能解析"
"有没有写明输入输出"。这些不需要"理解"，只需要**检测**。用 LLM 去检测它们，
是用不确定的工具做确定的事，代价是：

- 同一份提交跑两次，结论可能不同 → 报告无法作为争议裁决依据
- 30 份提交 × 4 维度 = 120 次调用，慢且贵
- 结论无法追��到具体证据（"模型觉得可复用"不算依据）

所以我把设计目标定为：**不是"更聪明的判断"，而是"更可信的判断"**。

### 为此设计了四个机制

| 机制 | 解决什么问题 |
|---|---|
| **证据化** | 每条 ✅/⚠️/❌ 都带 `文件:行号 + 原文片段`，可逐条复核 |
| **置信度分级** | 结构性硬校验=high；单关键词命中=low，并强制标记人工复核 |
| **一票否决（veto）** | 硬编码路径 / 凭据泄露这类致命项，命中即把该维度封顶 ❌ |
| **矛盾检测** | 完整性高但质量极低（或反之）时报警，提示可能是空壳提交 |

### LLM 保留在哪里

规则层判为 `low` 置信度、或作者 `Unknown` 时，才用 LLM 做一次**定向深审**，
产出**补充说明**而非**替代结论**。这样 LLM 的成本只花在真正困难的少数 case 上，
且规则结论始终保留、可被单独审计。（本版未接入 LLM 调用，接口位置已用
`confidence` 字段预留——这是有意的范围控制，不是遗漏。）

## 三、系统架构

```
                  ┌──────────────────────────────────┐
    微信群文件夹  │      c4a_evaluator.py            │
        │        │                                  │
        ▼        │  ① collect_submissions()          │
  ┌───────────┐  │     递归扫描 → C4 识别 →          │
  │ 文件采集   │  │     四级作者识别链 → 目录传播│
  └─────┬─────┘  │                                  │
        │        │  ② check_completeness()          │
        ▼        │     五必须文件加权检查             │
  ┌───────────┐  │                                  │
  │ 完整性检查 │  │  ③ evaluate_quality()            │
  └─────┬─────┘  │     四条件 × 20 个 check_item    │
        │        │     加权 + veto + 置信度          │
        ▼        │                                  │
  ┌───────────┐  │  ④ 三种渲染器                     │
  │ 质量评审   │  │     Markdown / JSON / Excel      │
  └─────┬─────┘  │     + HTML 仪表板                │
        │        └──────────────────────────────────┘
        ▼
   评审报告 + 证据链
```

### 判据全部外置

`references/c4_rubric.yaml` 是**唯一**的判据来源，包含：
- 5 个必须文件的检测信号与权重
- 4 个维度 × 20 个 check_item（类型、信号、权重、veto 标记）
- 全部评分阈值

**改标准不用改代码**——加一个检查项只需在 YAML 里追加一段。

## 四、核心设计详解

### 4.1 作者识别：四级链 + 目录传播

`wechat-doc-mapper` 的作者识别链是它的精髓，我完整保留并加强了：

| 优先级 | 方式 | 置信度 |
|---|---|---|
| 1 | 文件名规范 `姓名_C4_xxx` | high |
| 2 | 父目录名（作者文件夹） | high |
| 3 | PDF/DOCX 元数据 | medium |
| 4 | 文档头 `作者：XXX` | medium |
| 5 | 标记 `Unknown`，不参与排名 | — |

**新增：目录传播（directory propagation）**

真实群文件夹里，一个人往往把整个技能包放进自己的目录：

```
ZhangWei/
├── ZhangWei_C4_skill说明.md      ← 有 C4 标记
├── ZhangWei_C4_教学说明.md       ← 有 C4 标记
└── scripts/
    └── pr_desc.py                ← 没有 C4 标记，但在作者目录下
```

若只按"同目录"传播，`pr_desc.py` 会被漏掉——而它恰恰是**判断可执行性最关键的证据**。
所以规则是：**沿目录树向上找最近的"已归属某作者"的祖先目录**，把该作者目录子树内
其余文件一并纳入。

这条规则是实测踩出来的：最初版本用"同目录"传播，测试直接报错
`python_ast_parseable: False`——因为 ZhangWei 的 `pr_desc.py` 没被收进来，
"代码可解析"这项自然判不出来。

### 4.2 完整性检查：优先级即可信度

判定优先级刻意设计为 **真实文件 > 文件名 > 正文关键词**：

```
1. 文件名含强信号（skill说明 / 教学 / AI日志…）→ ✅
2. 真实媒体文件存在（.mp4/.png/.gif…）        → ✅   ← demo 用这个
3. 正文命中 ≥N 个结构信号                      → ✅
4. 正文命中 1~N-1 个                           → ⚠️
5. 都没有                                     → ❌
```

理由：**人主动命名的文件名，可信度高于程序猜测的正文命中**。
一个人把文件命名成 `教学说明.md`，比他在正文里恰好写了"步骤"两个字更能说明意图。

### 4.3 质量评审：加权 check_item + veto

这是核心创新。每个维度拆成若干 check_item，每个 item 有独立权重：

| 维度 | 检查项（权重） |
|---|---|
| **可复用** | R1 有安装说明(1.0)｜**R2 无硬编码绝对路径(1.5, veto)**｜R3 声明环境依赖(1.0)｜R4 路径可移植(0.8)｜**R5 无凭据泄露(1.5, veto)** |
| **可执行** | E1 有代码块(1.0)｜E2 有工作流步骤(1.0)｜E3 有 CLI 入口(1.0)｜**E4 代码/YAML 可解析(1.5, 结构)**｜E5 声明依赖安装(0.8) |
| **可验证** | V1 有测试用例(1.0)｜V2 定义预期输出(1.2)｜**V3 有真实运行佐证(1.0, 结构)**｜V4 边界情况处理(0.8) |
| **IO 明确** | **I1 「输入X输出Y」句式(1.5)**｜I2 输入有类型(1.0)｜I3 输出有类型(1.0)｜I4 one-liner(1.2) |

打分：

```
ratio = Σ(满足项 weight) / Σ(全部项 weight)
✅ ratio ≥ 0.70 ｜ ⚠️ 0.35~0.70 ｜ ❌ < 0.35
质量总分 = 四维度 ratio 平均
综合分 = 完整性 × 0.40 + 质量 × 0.60
```

**权重不是随手填的**，依据是"该项对C4 四条件的本质重要性"：
E4（代码能不能跑）权重 1.5，因为「可执行」的定义就是"能跑的东西"；
I1（一句话 IO）权重 1.5，因为它是「IO 明确」最直接的检验；
E5（依赖声明）只给 0.8，因为它锦上添花而非必需。

#### 为什么需要 veto（一票否决）

朴素的加权评分有个致命漏洞：

> LiMing 的提交里硬编码了 `/Users/lm/Desktop/meeting_summary/summary.py`，
> 但他同时有"安装"说明（+1.0）、有相对路径写法（+0.8）、无凭据泄露（+1.5）。
> 加权算下来 `ratio = 3.3/5.8 = 57%` → 评级 ⚠️「部分满足」。

**这在C4 的语境下是错的。** C4 对「可复用」的检验原话是：

> 让一个陌生人按你的说明操作，能成功吗？

答案已经是否定的——陌生人拿到这份文件就跑不起来，因为路径指向他的电脑。
加权平均把"致命伤"稀释成了"小瑕疵"，这是自动评审最容易犯、也最有害的错误。

所以引入 **veto**：R2 或 R5 任一命中红线，该维度评级**直接封顶 ❌**，
不管其他项拿到多少分。

实测效果：LiMing 的「可复用」从 ⚠️(57%) 变为 ❌(封顶)，
且置信度自动降为 `low` 触发人工复核标记——**这正是评审员最需要被提醒的地方**。

#### 结构性硬校验：置信度的锚点

E4 与 V3 不用关键词，而是做**真实解析**：

```python
ast.parse(源码)                      # 代码能不能被 Python 解析
re.search(r"\A---\s*\n...name:", s) # SKILL.md 有没有合法 frontmatter
tarfile.is_tarfile(p)                # .skill 包能不能打开
```

这类判定**不会看错**，因此置信度标 `high`。
当一个维度的关键项由硬校验支撑时，整体置信度就是 `high`。

反过来，只靠单词��命中（关键词型 item）的结论标 `low`——
比如 LiMing 的 R1 命中"安装"二字，但这可能只是句子里恰好有这个词。

### 4.4 报告：三种格式各司其职

| 格式 | 面向 | 独有价值 |
|---|---|---|
| **Markdown** | 评审者逐条核对 | `<details>` 折叠的逐项证据表，含行号 |
| **Excel** | 筛选与二次统计 | "逐项评审明细"表可按 `项ID=R2` 筛选，一键找出所有硬编码路径问题 |
| **HTML 仪表板** | 全班一眼看分布 | 四条件达成度条形图 + 完整性矩阵 + 排名 |

Excel 的"逐项评审明细"是最实用的一张——它把 4 维度 × 5 项摊平成 20 行/人，
老师筛 `R2 = ❌` 就得到"哪些人写了硬编码路径"的可执行名单。

## 五、误判率怎么证明

C4A 评审标准把"误判率低"放在 25 分权重（最高的一项）。所以我不会只声称它低，
而是给出测量方法：

### 5.1 黄金测试集

`tests/golden_dataset/` 下三份**我手工标注了 ground truth** 的模拟提交，
覆盖三种典型质量档位：

| 样本 | 档位 | 人工标注要点 |
|---|---|---|
| `ZhangWei/` | 优秀 | 五文件齐全、四条件达标、代码可解析 |
| `LiMing/` | 中等 | 缺 demo、**硬编码 `/Users/` 与 `C:\`** |
| `WangXiao/` | 较差 | 命名不规范（中文名+目录名混用）、内容单薄、无 demo |

三份都是**按真实群文件的脏乱程度写的**——包括 LiMing 那种"路径写死在自己电脑上"
的典型问题。评审器要能认出这些问题，才算真的可用。

### 5.2 测试分层

| 层 | 数量 | 作用 |
|---|---|---|
| 采集 | 5 | 作者识别、中文名、目录传播 |
| 完整性 | 3 | 满分检出、缺失检出 |
| 质量 | 6 | **含 2 个反向用例**（故意写坏代码验证能检出） |
| ground truth 一致性 | 1 | 与人工标注逐维度比对 |
| 边界 | 5 | 空目录、损坏包、非 C4 文件、未知作者 |
| 报告 | 2 | 章节完整、JSON 可序列化 |
| 判据自检 | 4 | **防死配置**（见下） |

**防死配置**是容易被忽略但很关键的一类测试：
若我在 YAML 里加了一个 structural 检查项却忘了在代码里实现，
`evaluate_quality` 会**抛 KeyError** 而不是静默判成 ❌——
因为"静默判 ❌"会制造一个看起来很确定的假结论，比报错有害得多。

### 5.3 实测结果

```
Ran 26 tests in 1.4s
OK

判定总数 : 15      一致数 : 15
人机一致率 : 100.0%    误判率 : 0.0%
```

**对 100% 这个数字必须说清楚三件事**（否则就是自欺欺人）：

1. **样本只有 3 份**，统计意义有限，不能声称"在任何班级都 100%"
2. **ground truth 是我自己标的**，存在我与评审器"共同犯错"的可能——
   虽然两者实现路径完全不同（人工是通读全文，评审器是逐信号检测）
3. **它证明的是"在已标注样本上结论可信"**，不是"规则完美"

**剩余风险集中在哪里**：置信度为 `low` 的结论。这些来自单词��命中，
本质上无法完全自动化。评审器的做法不是假装能判，而是**明确标记出来交给人**——
报告中所有 `low` 结论都带"需人工复核"提示。这比追求一个漂亮的准确率数字诚实得多。

## 六、开发过程中发现并修复的真实缺陷

这些不是事后补的故事，是测试真的失败、然后定位修复的：

| # | 缺陷 | 发现方式 | 修复 |
|---|---|---|---|
| 1 | YAML `0.70#` 注释粘连 → 阈值变成字符串 `'0.70# >= 0.70'` | 评分时 `ValueError` | 补空格；并加测试 `test_scoring_thresholds_parseable` 防复发 |
| 2 | 判据字段名与代码不一致（YAML 写描述文字，代码当阈值读） | 同上 | 拆成 `full_threshold`/`partial_threshold` 两个数值字段 |
| 3 | `王晓_C4_说明.md` 放进 `WangXiao/` → 同一人被拆成两个作者 | 作者数断言失败 | 同目录下优先采信目录名 |
| 4 | **`scripts/pr_desc.py` 未被收集** → 代码可解析检查失效 | E4 断言失败 | 目录传播改为"沿目录树向上找最近祖先" |
| 5 | veto 项逻辑错误：`positive` 为空导致干净文件也被判不满足 | R5 断言失败 | veto 语义改为"不踩红线即通过" |
| 6 | LiMing 硬编码路径被判 ⚠️ 而非 ❌ | ground truth 比对失败 | 引入评级封顶机制（veto → ❌） |
| 7 | 张伟置信度被误判 `low`（明明有硬校验支撑） | 人工复核发现 | 置信度改为"取最强证据类别" |

第 4 条尤其值得记录：**如果我不写那个"代码可解析"的测试，
这个缺陷会一直藏着**——评审器会安静地把所有人的可执行维度判低，
而报告看起来一切正常。**这就是为什么要给"看起来能跑"的功能配断言。**

## 七、Level 达成情况

| Level | 要求 | 状态 |
|---|---|---|
| **L1** 文件采集器 | 识别 C4 文件、按作者分组 | ✅ 四级作者识别链 + 目录传播 + 别名归并 |
| **L2** 完整性检查器 | 五必须文件检查 + 缺什么 | ✅ 加权完整性 + 判定依据可追溯 |
| **L3** 质量评审器 | 四条件自动评审 | ✅ 20 个 check_item + 加权 + veto + 置信度 |
| **L4** 完整评审系统 | 仪表板/排名/建议/版本追踪 | ✅ 排名 + Markdown/Excel/HTML 三格式 + 个性化建议 |

Level 4 中"版本追踪（`_v2`/`_v3` 迭代）"未做——因为三个测试样本都没有版本文件，
**做了无法验证**，属于"无法证伪的交付"。等有真实多版本数据再补。

## 八、可复用性：这个技能换个场景还能用

判据在 YAML 里，与C4A 解耦。把 `c4_rubric.yaml` 换成别的挑战标准，
它就变成任何"提交型作业"的自动阅卷器：

| 场景 | 需要改什么 |
|---|---|
| C1 课程资料翻译 | 换必交文件定义 + 质量维度（术语一致性、覆盖率…） |
| C2 论文评审 | 换质量维度（引用可核验性、实验可复现性…） |
| 通用代码作业批改 | 换质量维度（复杂度、测试覆盖、风格…） |

架构层面已经支持：`required_deliverables` 与 `quality_criteria` 是两个独立配置块，
新增检查项不用碰代码。

## 九、已知局限（诚实清单）

| 局限 | 影响 | 缓解 |
|---|---|---|
| 样本仅 3 份，一致率 100% 统计意义有限 | 不能外推到任意班级 | 已明确标注；扩充数据集是下一步 |
| ground truth 由本人标注 | 可能存在共同偏差 | 人工通读 vs 信号检测，两条独立路径 |
| 单词��命中无法完全自动化 | 部分结论必然不准 | 标 `low` 置信度 + 提示人工复核，不假装能判 |
| 未接 LLM | 纯规则覆盖不到"语义质量" | 接口以 `confidence` 字段预留 |
| PDF/DOCX 正文解析依赖可选库 | 缺库时仅按文件名判定 | `--strict` 可显式开启完整解析 |
| 无版本追踪 | 无法展示 `_v2` 迭代轨迹 | 需真实多版本数据才能验证 |

## 十、结论

C4A 的核心不是"写一个评分脚本"，而是回答了一个方法论问题：

> **自动评审的价值不在于替人做判断，而在于让人把判断做在更有依据的地方。**

所以本设计把 25 分权重的"误判率低"理解成"**结论可追溯、风险主动暴露**"，
而不是"追求一个更高的准确率数字"。为此付出了一个真实代价：
大量代码花在证据收集、置信度标注、矛盾检测上——这些对"让报告好看"毫无帮助。

如果重新做一次，我会在两个地方更进一步：
1. **把黄金数据集扩到 8~10 份**，覆盖更多边界情况，让一致率数字有统计意义
2. **引入双人独立标注**算 kappa 一致度，避免 ground truth 单一来源的问题
