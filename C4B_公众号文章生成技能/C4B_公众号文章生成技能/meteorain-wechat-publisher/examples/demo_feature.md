# 公众号排版避坑实录

先说结论：公众号排版这件事，难点从来不在 Markdown 转 HTML，而在于微信编辑器有一整套**不成文规则**。

> [!NOTE] 这篇文章的写作方式
> 全文用 Markdown 写，用一条命令转成公众号 HTML，中间零手工调整。这既是文章内容，也是这篇文章的演示。
> [!WARNING] 一个残酷的现实
> 「排版好看」是玄学，「粘贴不丢样式」是工程问题。这篇文章只解决后者——因为前者可以靠审美，后者只能靠踩坑。

## 坑一：代码块的换行会消失

这是我最先撞上的坑。把 Markdown 转成 HTML 之后，代码块里的换行全没了。

原因不玄学：转换脚本把代码写进 `<p>` 标签，而 HTML 规范规定 `<p>` 里的换行**会被折叠成空格**。于是四行 Python 变成了一行：

def hello(): print("a") print("b") return True

缩进没了，代码也就没法看了。

解法是把换行替换成 `<br>`——这个标签在公众号里是被保留的。

> 这件事的教训是：转换器最容易出错的不是「少了功能」，而是「看起来能跑，其实悄悄改了语义」。

## 坑二：引用块里的加粗会消失

第二个坑更隐蔽。Markdown 里这样写：

> 这里的 **加粗** 和 `代码` 都会保留。

转换之后，`加粗` 变成了普通的 `加粗`，红色高亮也没了。

原因在于脚本用了「取纯文本再重新包一层」的做法——它把引用块里所有内联格式都扔掉了，只留下文字。

## 坑三：h1 标签不允许存在

微信编辑器把 `h1` 留给文章标题。正文里如果出现 `<h1>`，要么不渲染，要么跟标题打架。所以必须降级成 `<h2>`。

## 坑四：div 标签会被吃掉

`<div>` 在公众号里不可靠。最保险的做法是换成 `<p>` 或 `<span>`。

> [!TIP] 判断标准很简单
> 如果一个标签的作用纯粹是「分组」，那它在公众号里大概率没用——因为公众号不允许你控制分组。

## 坑五：样式必须全部内联

公众号不接受 `<style>` 标签，也不认 `class`。每一个元素都得自带`style="..."`属性。

这就是为什么转换脚本必须把所有样式**展开**成内联形式，一层层套上去。

## 坑六：图片只能用 PNG

SVG 在保存时会直接消失。唯一的出路是转成 PNG，然后以 base64 内嵌。

> [!CAUTION] 这是最容易白干两小时的地方
> 你精心画了一张矢量图，粘贴进编辑器，预览正常，保存之后图没了。

## 坑七：中英文之间没有空格

这个不算「报错」，但直接影响观感。中文和英文数字混排时自动补一个空格，专业度立刻上一个台阶。

## 我最后怎么解决的

前面七个坑，每个单独修都不难，难的是**七个一起修并且不互相破坏**。所以我把它们收敛成了一个脚本：

| 坑 | 解法 |
|---|---|
| 代码块换行 | 拆行后用 `<br>` 拼接 |
| 引用内联格式 | 搬运子节点而非取纯文本 |
| 表格 | 逐个单元格套样式 |
| 中文间距 | 中英文边界自动补空格 |

一条命令，输入 Markdown，输出能直接粘贴的 HTML。

> [!SUCCESS] 最终形态
> 从「一个脚本」到「一个技能」，中间还差三步：主题系统、目录生成、批量转换。这三步才是从工具变成生产力的关键。

## 写在最后

工具的价值不在于它多复杂，而在于它**让多少件麻烦事消失了**。当一件事从「半小时的体力活」变成「一条命令」，你就腾出了做更重要事情的时间。

这也是我理解的 AI-First：不追求让AI替你干活，而是让 AI 把重复劳动整个吞掉。
