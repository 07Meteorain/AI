## 三、做得不好的四件事

### 3.1 没给「发布」预留时间（最重要）

**问题**：整个C4B 的时间几乎全花在脚本上。文章链接到现在是空的。

**根因分析**：

我在写代码时进入了一种很舒服的状态——每修一个 bug 都有即时反馈，
跑eval 数字会变绿。而「注册公众号」这件事：
- 反馈延迟长（要填资料、等审核）
- 有不确定性（可能被驳回）
- 不在我熟悉的舒适区

于是我下意识地**一直做有即时反馈的事，把有延迟的事推到最后**。
最后没时间了。

> **这是个通用的失败模式，不只是这次。** 技术工作里，
> 「让数字变绿」的诱惑远大于「去搞一个有摩擦的外部流程」。
> 越是有即时反馈的事，越容易被过度投入。

**改进方案**：把「能否发布」当作**项目的可行性判据**，而不是最后一步。

具体做法：接到「要发布」的任务时，第一件事是确认发布渠道是否可用。
如果发布需要账号，**第一步就该去申请账号**，因为审核周期不可控。
技术做得再好，链接是空的，Level 3 就不算完成。

### 3.2 第一版 callout 的处理顺序就写错了

**问题**：`sanitize()` 里我先做了 blockquote 转换，再做 callout 检测。
结果 callout 一个都渲染不出来。

**根因**：我没有想清楚这两个操作对同一个 DOM 节点的操作顺序。
blockquote 转换会把 `<blockquote>` 变成 `<p>`，callout 的 `[!KIND]` 标记
是靠 `<blockquote>` 识别的——标记一被抹掉，就再也认不出来了。

**为什么没提前发现**：我在写代码时是「凭直觉排顺序」，没有把
「这两个步骤有依赖」这件事写下来。

**改进方案**：**代码顺序有依赖时，必须在注释里写明 why。**

我后来在 `SKILL.md` 里加了：

> 5. convert `[!KIND]` callouts — **must precede step 6**

但这个注释是**修完 bug 之后**才加的。正确做法是第一次写就写。

### 3.3 第一次跑 eval 前，我以为修得差不多了

**问题**：写完 7 项能力后，我心里的状态是「差不多了」。
第一次跑 eval：**30 通过 / 6 失败**。

**其中 3 个失败是我「明明修过了」的**：

| 失败项 | 我以为的状态 | 实际状态 |
|--------|-------------|---------|
| 页脚不显示 | 明明调了 `build_footer()` | 追加到 soup 根节点，**落在 `<body>` 外**，render 时被丢弃 |
| 嵌套 `<p>` | 已经改用 `<section>` 了 | 只改了 callout，TOC/元数据/页脚**还是 `<p>`** |
| 片段模式 | 明明加了 `--fragment` | 同一个根因 |

**根因**：「我写了这个函数」和「这个函数生效了」之间，
隔着一个「函数有没有被正确调用」的距离。

我修了三处写法相同的地方，只改了一处。
这说明我是**按代码改没改**来判断完成度，而不是**按输出对不对**来判断。

**改进方案**：把 eval 当成**完成的定义**，而不是事后检查。

具体做法：每写完一个功能就立刻加对应断言，
而不是写完全部功能再统一测。前者能在 30 秒内发现问题，
后者会在 6 个失败里让你分不清哪个是哪个。

### 3.4 没有做「人工复核」，目录编号错了但测试全绿

5 套主题写完了，eval 检查了「输出互不相同」——通过了。
37 条断言也全绿。

但我最后用肉眼读了一遍产出，发现**目录编号是错的**：

```
1. 我用 AI 造了一个公众号排版技能…    ← 这是标题，不该进目录
2. 五分钟跑通，十分钟发现问题
6. 坑二：引用块的加粗…                ← 跳号了
8. 一个没料到的陷阱…← 又跳号
```

两个原因：编号时把 `h2` 和 `h3` 一起计数；
front matter 的标题渲染成元数据块后，正文里的 `# 一级标题`
又被降级成 `h2` 当成第 1 节。

**根因**：我的 37 条断言检查的是「目录存在吗」，**不是「目录编号对吗」**。

**这个失败最值得记**，因为它的形态和其他失败都不同：
不是「测试挂了」，而是「**测试全绿但东西是错的**」。

**改进方案**：
技术指标交给 eval，审美和语义指标交给眼睛。
凡是「机器只能验证存在性、无法验证好坏」的东西，必须人工看一眼。

我把这条写进了复盘，因为它比那6 个 eval 失败更危险——
**失败的测试会告诉你，绿色的测试不会。**

## 四、三个最有价值的技术发现

### 4.1 有一次我选择改测试，而不是改代码

eval 报「缩进丢失」。

正常反应是：改代码，让 `print` 前面出现 4 个普通空格，测试就绿了。

但我先做了验证：**输出里到底有没有缩进？**

```bash
grep -o 'def demo.\{0,160\}' output.html
```
```
def demo():<br/>    print("one")<br/>    return 2
```

有缩进，是 U+00A0。

**代码是对的，断言是错的**——断言在找 4 个普通空格，
而正确方案必须用 NBSP（因为普通空格在 HTML 里必然被折叠）。

这时候如果改代码让测试变绿，就是**把技术债换个地方藏**，
而且下次谁再改这个功能，还会踩同一个坑。

我的选择：改断言，并在旁边写明为什么。

> **教训**：测试失败时，先判断谁错了。
> 「让测试变绿」不是目标，「让代码正确」才是。
> 这和当初盲目相信「跑通了」是同一种错误的两个方向。

### 4.2 `get_text()` 和 `string =` 是两种「看起来一样」的危险写法

starter kit 里有两行：

```python
p.string = code_text      # 取文本 → 塞进新容器
p.string = bq.get_text()  # 拍平子树 → 塞进新容器
```

两行都写得很干净，都很像「正确做法」。

但它们都在做同一件危险的事：**丢弃结构信息**。

- 代码块的「结构」是换行
- 引用块的「结构」是内联标签

**通用的判断规则**：
当你发现自己在写 `xxx.string = something.get_text()` 时，
先问一句：**我丢掉的结构，读者看得见吗？**
看得见，就说明不该丢。

### 4.3 最贵的 bug 是「看起来能跑」的那类

两个 starter bug 有一个共同点：**生成的文件完全正常**。

用编辑器打开 HTML，换行符好好地在那儿，缩进也在。
用 `grep` 检查，能搜到「代码」「加粗」这些字样。

只有真正**在浏览器里渲染**，才会发现它是错的。

> 这类 bug 的特征是：**所有静态检查都通过，只有真实使用才暴露。**
> 所以真正的防线不是「检查得更细」，而是**「真的用一次」**。

## 五、如果重来，我会怎么做

### 时间线上的调整

| 阶段 | 我的做法 | 应该的做法 |
|------|---------|-----------|
| 开始 | 读挑战书 → 读代码 | 读挑战书 → **先确认发布渠道** |
| 开发 | 全部时间给脚本 | 脚本 60%，预留 40% 给文章和发布 |
| 验收 | 写完 7 项才跑 eval | 每写完一项就跑对应断言 |
| 收尾 | 才想起做文章 | 文章和脚本同步进行 |
| 发布 | 没做 | **提前申请账号** |

### 方法上的调整

1. **探针文件要更早、更狠。** 我在跑通基线后才写探针。
   如果在读 starter kit 的时候就构造这个文件，能更早建立「它有什么问题」的假设。

2. **eval 要随着功能写。** 37 条断言如果是最后一次性写的，
   我会很难定位「6 个失败分别对应哪次改动」。

3. **加一个「渲染验证」环节。** eval 检查的是字符串，
   我应该至少有一次真正用浏览器打开看。
   本次我的审美验证是缺失的（见 3.4）。

## 六、给自己的一条规则

如果这次只能带走一条，我选这条：

> **完成的标准不是我做了什么，而是「别人拿到能用的东西是什么」。**

具体到这次：

- 我修了 7 项能力 → 但没有链接，Level 3 就不算完成
- 我写了 37 条断言 → 但如果文章发不出去，读者拿不到任何东西

**技术完成度 ≠ 交付完成度。**

前者是自己的舒适区，后者才是别人能看到的东西。
