## 一、原本想做什么

一句话：**做一个能自动查出AI 编造引用的工具。**

动机很朴素——我自己用 AI 写论文时，遇到过"参考文献看起来完美但查不到"
的情况。当时是靠手动 Google 一条条查，20 条引用花了近一小时。
更糟的是：**这个过程太枯燥，导致很多人（包括我）干脆不查。**

所以我判断：这里有一个真实的痛点 + 一个可以自动化的高频动作 = 一个值得封装成
技能的"可复制能力"。这正是 CHALLENGE.md 第九节 Step 1 要求的选题标准。

## 三、失败与不足（本次复盘的核心）

### 3.1 失败 1：我第一次写代码时，留下了一个自己都没检查的死代码

**现象**：脚本写完后直接运行，报`SyntaxError`。

**根因**：在 `build_fixed_bib()` 里我写了这样一行：

```python
fixed = re.sub(r"(?im)^(\s*(?:title|year|...)\s*=\s*)[{"].*?([}\"],?\s*)$",
               lambda m: m.group(0), raw)
fixed = raw          # ← 紧接着又被覆盖了
```

两处问题：
1. 字符类 `[{"]` 里的 `"` 提前终止了 raw string；
2. 就算语法正确，这行也是**死代码**——下一行 `fixed = raw` 立刻覆盖它。

**为什么会发生**：我在实现 `--fix` 功能时反复调整逻辑，写废了中间版本却忘了删。
写完没有语法检查就交付测试。

**我的判断**：这是最不该犯的错误。**它不是"遇到了难题"，是"没做最基本的质量动作"。**
如果我第一轮就 `python -m py_compile` 检查一下，30 秒就能发现。

**改进**：
- 以后写完脚本先跑语法检查再运行；
- 死代码要在提交前清掉——它会让下一个读代码的人（或AI）困惑。

---

### 3.2 失败 2：致命 Bug 潜伏了整整一个测试轮次

**现象**：第一次实测，8 条引用的作者、年份、DOI 全变成了同一条（最后一条）的内容。

**根因**：

```python
open_ch = text[m.end() - 1]    # ← 以为拿到 '{'，实际拿到 ','
```

正则 `r"@(\w+)\s*[{(]\s*([^,\s]+)\s*,"` **以逗号结尾**，所以 `m.end()-1`
是逗号。括号深度计数因此失控，扫描位置漂移到文件末尾，每条 bib 都把后面
所有条目一起吞了。

**为什么会发生**：我写完解析器后，没有用"已知答案"去校验它——
我是先写代码，再喂给我自己造的样本。我**认识**那些论文，所以我一眼就能看出
输出错了。但我没有在写完后立刻打印解析结果做逐字段比对。

**更深一层的原因**：`m.end()-1` 这个写法本身就是个**危险信号**——它依赖"正则
最后一个字符是什么"的隐含假设。这类代码读起来很像对的，实际上极脆。

**改进**：
- 写解析器后，先用**已知内容**逐字段断言，而不是靠眼看；
- 凡是出现"索引魔法数"（`x-1`、`x+20`）的地方，要么用捕获组，要么写测试保护；
- 这条已经落进代码：现在用 `m.group(2)` 拿括号字符，并加了 `hard_limit`
  防止单条未闭合条目吞掉整个文件。

### 3.3 失败 3（最重要）：我差点用一个"看起来全绿"的结论掩盖事实

**现象**：第 4 轮修完 bug 后，`vaswani2017` 仍提示"年份不符（2017 vs 2025）"。

**我当时最省事的做法**：把年份容差从 `±1`放宽到 `±N`，或者干脆对年份
不一致直接放行。改完之后报告会变成**全部 VERIFIED，全绿**。

**但我先去查了**：

1. `curl` 那个 DOI → **HTTP 404**
2. 查 Crossref → 命中 2017 的正确记录
3. 查 OpenAlex → 命中 `publication_year: 2025` 的记录
4. 换作者名再查 OpenAlex → 确认这是"Attention Is All You Need"
   **被合并/重新索引的另一版本**

**结论**：这不是我的 bug，是**数据源的真实行为**——ACM 的 `10.5555` 前缀
在出版社有效但未注册到 Crossref，DOI 直查必然 404，回退标题检索就命中了
年份不同的合并版本。

**我最终的选择**：
- 不判VERIFIED（确实有不一致，不能装作没看见）
- 也不判"你写错了"（你的年份可能反而是对的）
- 原因码写明"疑似版本漂移，建议人工确认"
- **在 `--fix` 里拒绝自动改写 `year` 字段**，只加注释提示人工确认

**为什么这是本次复盘最重要的一条**：

一个核查工具，最危险的失败模式**不是漏报，而是给出一个看起来确定的错误结论**。
如果我放宽阈值让它全绿，这个工具就从"帮你避免错误"变成了"帮你确认错误"——
它变得更好看了，但更没用了。

而且这个陷阱很隐蔽：C4 评的是"技能质量"和"被使用次数"，
一份"所有引用都通过"的漂亮报告，作为交付品是**加分的**。
**正是评价机制在鼓励我做那个错误的决定。**

> 我把它记下来，是因为它不只是一个技术决策，而是一条原则：
> **证据不足时要说"不知道"，不要造一个让人安心的答案。**
> 这条原则对做核查工具尤其重要——核查工具的整个价值，
> 就是它不会在你需要确定的地方撒谎。

## 四、做得还可以的地方

| 环节 | 为什么有效 |
|---|---|
| **先探测 API 再写码** | 提前发现 arXiv 403（需 UA）、SS 429（限流）。否则我会把这两个问题误判成"网络不通"，交付一个坏掉的技能 |
| **零依赖的取舍** | 直觉上"用 bibtexparser 更专业"，但装了依赖别人第一步就卡住。C4 评使用次数——**用不起来等于零分** |
| **拒绝删除编造条目** | `--fix` 把编造条目**注释**而非删除。因为审计可能错，删除是破坏性操作，不可逆 |
| **干净目录复现测试** | 在自己目录跑通证明不了"可复用"。去 `/tmp` 重新解压跑一遍，才真的验证了 |
| **逐条查"最接近的是谁"** | 不只说"没找到"，而是给出最接近的真实论文。用户能立刻判断是真引用还是标题记错 |

### 5.3 一个我暂时不做的

**语义级核查**——判断"这篇论文是否真的支持你这句论述"。

我知道这个能力最有价值，但当前做不到可信：需要读懂论文全文并做蕴含判断，
远超一个脚本的能力范围。**我不打算用一个半成品功能去假装能做到**。

我的处理是：在 SKILL.md 里**明确划出这个边界**，并在教学文档里反复强调
"VERIFIED ≠ 引用正确"。把做不到的事说清楚，比做个看起来能用的功能更有用。

## 六、这个项目让我记住的三件事

1. **先验证环境，再写代码。**
   三个 curl 请求省掉了后面所有的"为什么跑不通"。
   看起来慢，实际上最快。

2. **测试必须脱离开发环境。**
   在自己的目录里跑通，不等于别人能用。
   C4 说"让陌生人按你的说明操作能成功吗"——那就必须真的让陌生人（干净目录）
   试一次。

3. **工具的价值在于它敢说"不知道"。**
   这一条我是被迫学会的：我本可以让报告全绿，
   但那样这个工具就从"帮你避免错误"变成了"帮你确认错误"。
   **报告好看 ≠ 结论正确**，这两件事必须分开。

## 七、给自己的一句提醒

这个项目让我有点成就感的地方，不在于脚本有多少行，而在于——

**我做了三次"本可以糊过去"的选择，并且每次都选了慢的那条路**：
写完代码先检查、报错就去查根因、输出不好看就去查数据源。

这三次加起来花了不少时间，但它们是这个技能唯一有价值的东西。
**一个核查工具如果自己经不起核查，那它报告的一切都不值得相信。**
