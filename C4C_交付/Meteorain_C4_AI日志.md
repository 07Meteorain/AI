## 第 0 轮：读题与需求拆解

**我的指令**：「帮我完成C4 这个挑战，严格按照挑战文件里的内容完成」

**我的分析过程**：

我先读了 `CHALLENGE.md`、`rubric.json`、`challenge.yaml`，又解开了两个参考
`.skill` 包看标准结构（发现参考包实际是 **ZIP** 格式而非文档里说的 tar.gz——
这点很重要，否则打包格式会错）。

然后我把评审标准反推成需求：

| 评审维度 | 权重 | 我的应对 |
|---|---|---|
| 技能质量 | 25 | 必须有确定性脚本，不能只是 prompt |
| 可教性 | 20 | 教学文档要能"教别人用起来" |
| 产物完整性 | 15 | 目录自包含，clone 后可运行 |
| AI 使用质量 | 20 | 真实多轮迭代 + 如实记录失败 |
| 复盘质量 | 20 | AAR 含具体问题与改进方案 |

**选题决策**：我选择做「引用真伪审计」。理由有三：

1. **它是我真实重复做的事**——C2挑战本身就要求"可靠引用核查"，
   不是我为了交差硬造的选题，符合 CHALLENGE.md 第九节 Step 1 的要求。
2. **痛点真实且普遍**——AI 编造引用是整个学术写作领域的共性问题。
3. **可验证性极强**——一条引用要么存在要么不存在，判定天然可测。

> 💡 **这一步的关键判断**：C4 的评判标准第一条是「**被使用次数**」，
> 不是"技能多厉害"。所以选题必须满足「**很多人经常需要**」。
> 相比"审计我的挑战作业"这种高度定制化的技能，
> 查引用真伪的受众是所有写论文的人——量级完全不同。

## 第 1 轮：先验证环境，再定方案

**我做的事**：写代码之前，先用 curl 探测每个候选API 的真实可用性。

这一步的价值远超预期——如果我没先探测，就会埋下三个坑：

| 探测结果 | 影响 |
|---|---|
| Crossref `HTTP 200` | ✅ 可用，且**按 DOI 精确查询** |
| OpenAlex `HTTP 200` | ✅ 可用，覆盖面最广 |
| arXiv **HTTP 403** | ⚠️必须带 `User-Agent`，否则直接被拒 |
| Semantic Scholar **HTTP 429** | ⚠️ 限流严重，**不能作为主依赖** |

**探测中发现的关键事实**：

- arXiv 的 403 是因为 curl 默认 UA 被拒。加上
  `-A "C4Auditor/1.0 (mailto:...)"` 后正常返回 200。
  → 这个坑如果没提前发现，会被误判成"网络不通"。
- Semantic Scholar 匿名调用直接 429，必须申请 key。
  → **决策：把Semantic Scholar 降级为可选**，主链路只用三个免密钥源。
- OpenAlex 返回 `publication_year: 2025`——但 "Attention Is All You Need"
  明明是 2017 年的论文。这个异常我当时记下了，第 5 轮回来处理。

**架构决策**（受这些探测结果影响）：

```
1. bib 有 DOI   → Crossref /works/{doi}      （置信度最高）
2. bib 有 arXiv → arXiv /query?id_list=      （命中率最高）
3. 都不行       → 标题检索 Crossref + OpenAlex（最模糊）
```

外加两条：**零第三方依赖**（只import 标准库）、**三级降级**（任一源失败不阻塞其余）。

## 第 2 轮：编写脚本

**产出**：`citation_auditor.py`（约 33 KB）

我一次性写出完整实现，包含：

- 手写 BibTeX 解析器（括号深度跟踪，容忍嵌套花括号与引号）
- `.tex` 的 `\cite/\citep/\citet` 键提取
- 标题相似度：`difflib` 字符ratio + 词集 Jaccard 按标题长度加权
- 7 类幻觉指纹（泛义词堆砌、模板会议名、未来年份、DOI 损坏、页码倒置等）
- 指数退避重试 + 限流处理
- 四档判定 + Markdown/JSON 报告 + 修正版 bib 生成

**为什么坚持手写 bib 解析器**：为了零依赖。引入 `bibtexparser` 就要
`pip install`，而**别人机器上第一步就装不上依赖的技能，根本不会被用**——
C4 评的是使用次数，不是代码炫技。

## 第 3 轮：第一次实测——发现致命 Bug

我把 8 条样本喂给脚本，结果**输出明显错误**：

```
[FABRICATED] doe2021innovative
    题名: An Innovative Deep Learning Framework for Scalable Intelligence   ← 标题对
    作者: He, Kaiming, Zhang, Xiangyu, Ren, Shaoqing                     ← 作者全错？
    年份: 2015  期刊: ICLR  DOI: 10.1234/jair.2023.45112                 ← 全是最后一条的
```

**所有 8 条引用的作者、年份、DOI 都变成了同一条（`lecun2015deep`）的内容**，
只有标题是对的。

### Bug #1（致命）：解析器取错了括号字符

**根因**：

```python
for m in re.finditer(r"@(\w+)\s*[{(]\s*([^,\s]+)\s*,", text):
    open_ch = text[m.end() - 1]        # ← 错在这里
```

这个正则**以逗号结尾**，所以 `m.end()-1` 取到的是 `,`（逗号），而不是
`{`或 `(`。

后果：`open_ch` 变成逗号后，括号深度计数完全失控——遇到逗号`depth+1`、
遇到 `}` 才 `depth-1`，扫描位置一路漂移到文件末尾。于是**每一条 bib 的字段
都把后面所有条目的内容一起吞了进去**，作者和年份全被最后一条覆盖。

**修复**：用正则捕获组取真正的括号字符。

```python
for m in re.finditer(r"@(\w+)\s*([{(])\s*([^,\s]+)\s*,", text):
    open_ch = m.group(2)      # ← 现在是真正的 '{' 或 '('
    citekey = m.group(3)
```

**同时加了一个安全上限**：`hard_limit = min(len(text), i + 20000)`。
理由是——一条未闭合的条目不该吞掉整个文件。这是**防御性编程**：
我无法保证用户（或 LLM）生成的 `.bib` 总是格式正确。

### 修复后验证

8 条条目全部独立解析，作者、年份、DOI 各不相同。Bug #1 确认修复。

## 第 4 轮：第二次实测——两个算法 Bug

修完解析器，条目独立了，但**所有作者匹配度都是 0.00**，
包括明显正确的 `vaswani2017attention`（Vaswani 等，arXiv 1706.03762）。

### Bug #2（严重）：作者姓氏提取错误

**根因**：

```python
parts = [p for p in x.split() if len(p) > 1]
out.add(parts[0][:1] if False else parts[0])   # ← 只取第一段
```

我的意图是提取姓氏，但两种数据源的姓名格式是**相反**的：

| 来源 | 格式 | 提取结果 |
|---|---|---|
| BibTeX | `Vaswani, Ashish` | `vaswani`（逗号前，正确） |
| arXiv API | `Ashish Vaswani` | `ashish`（名字，**错**） |

`Vaswani` vs `Ashish` → 永远匹配不上 → 重合度恒为 0。

**修复**：显式处理两种格式——有逗号取逗号前，无逗号取**最后一段**
（并排除 `Jr./PhD` 等后缀）。

### Bug #3（中等）：候选排序只看标题相似度

修完 Bug #2，排序又暴露出问题：`vaswani2017` 被判"年份不符
（bib=2017 vs 真实=2025）"。

我怀疑是 OpenAlex 返回的 2025 记录挤掉了正确的 2017 记录。验证后确认：
排序键是 `(title_sim, cited_by)`，而那条 2025 记录**标题相似度同样很高**
（都是 "Attention Is All You Need"），引用量还更大，于是胜出。

**修复**：让排序综合四个信号，并把 bib 里的年份当作**先验**。

```python
def rank(c):
    ao   = 作者匹配度          # 排除同名不同作者的论文
    yr   = 1/(1+|bib年份-候选年份|)   # 排除重印/重新索引版本
    return (ao, yr, 标题相似度, 引用量)
```

### 第三次实测结果

```
[VERIFIED]   4 条
[PARTIAL]    2 条
[FABRICATED] 2 条
```

**判定分布终于与样本设计完全吻合。** 特别注意 `goodfellow2014generative`
被正确判为 PARTIAL并指出"bib=2019 vs 数据源=2014"——这是样本里我故意埋的
年份错误，说明脚本真的在比对元数据，而不只是查存在性。

## 第 5 轮：调查"版本漂移"这一真实陷阱

还剩一条 `vaswani2017` 提示年份不一致。我没有直接忽略，而是**顺着查下去**：

1. 直接 curl 该 DOI `10.5555/3295222.3295349` → **HTTP 404**
2. 换标题搜 Crossref → 命中 2017 的正确记录
3. 换 OpenAlex → 命中 `publication_year: 2025` 的记录

**结论**：这不是 bug，是**数据源的真实行为**。

- `10.5555` 是 ACM 的前缀，**在出版社侧有效，但未注册到 Crossref**，
  所以 DOI 直查必然 404；
- 回退到标题检索后，OpenAlex 命中的是被合并/重新索引的版本，
  其 `publication_year` 是 2025。

**我的处理决策**（这里我改了设计，而不是改代码凑结果）：

1. **不把它判成 VERIFIED** —— 确实存在不一致，不该装作没看见；
2. **也不判成"用户写错了"** —— 用户的年份可能是对的，数据的未必；
3. 原因码写明"常见于同一论文存在重印/修订版本，建议人工确认"；
4. **拒绝自动改写 `year` 字段**——为此在 `--fix` 里加了保护：
   ```python
   drift = "重印/修订版本" in (r.get("reason") or "")
   if drift:  # 保留原值，只加注释说明需人工确认
   ```
5. 写进 SKILL.md 的「已知误报」章节。

> 💡 这一轮是整个项目最重要的判断。
> 当时最省事的做法是：调高年份容差，让它显示 VERIFIED，报告立刻"全绿"好看得多。
> 但那是在**用结论掩盖事实**。工具的价值恰恰在于：证据不足时说"我不知道"，
> 而不是造一个让人安心的答案。
> 对应到 C2 挑战要求的"可靠引用核查"——**核查工具本身若会给出误导性结论，
> 它就是不可靠的**。

## 第 7 轮：用真实语料交叉验证（发现 3 个新 bug）

推送前clone 仓库时，我发现自己的 C2 交付里有一份**已经过人工+双API 核验**的
`references.bib`（17 条，验收规则比我的技能更严：token-set F1 ≥ 0.90）。

这是一个理想的对照实验：**一份已知正确的文献库，我的工具会不会误报？**

### 第一次交叉验证结果

```
共审计 17 条引用
  [VERIFIED]     14 条  ( 82%)
  [PARTIAL]       1 条  (  5%)
  [FABRICATED]    2 条  ( 11%)   ← 三条被误杀
```

**14 条正确，但3 条被误判。** 我逐条查了原因——这三条都是**我的工具的缺陷**，
不是C2 的问题。

### Bug #4（严重）：`10.48550/arxiv.*` 前缀不路由到 arXiv

`dsp2022` 的 DOI 是 `10.48550/arxiv.2210.12283`。这个前缀是 **DataCite** 给 arXiv
签发的，**不在 Crossref 注册**，所以我的 DOI 直查必然404，
掉进标题检索的模糊匹配里，相似度只有 0.57 → 判成编造。

**修复**：识别 `10.48550/arxiv.` 前缀，直接改走 arXiv 精确查询。
这和第 5 轮的 `10.5555` 是同一类问题的另一个分支——**DOI 前缀决定了该走哪个源**。

### Bug #5（中等）：机构作者与分号分隔的作者列表

`coqmanual` 的作者是 `{The Coq Development Team}`——**花括号包裹的机构作者**。
我的姓氏提取逻辑按"逗号前/最后一段"处理，遇到花括号整体包裹就切错了。

同时 `alphaproof2025` 用**分号**分隔作者（Nature 导出格式），
而我只支持 BibTeX 标准的 `and`。

**修复**：
- `split_authors()` 同时支持 `and` / `;` / `others` 三种分隔符；
- `_surname()` 对 `{...}` 包裹的整体机构名特殊处理。

### Bug #6（中等）：版本号后缀拉低相似度

`coqmanual` 的真实标题是 `The Coq Proof Assistant Reference Manual - version 8.19.0`，
而 bib 里写的是不带版本号的短标题。逐字 ratio 因此只有 0.80，低于阈值 0.82。

**修复**：加"包含关系"规则——若一个标题是另一个的子串，
且差异 token 不超过较长标题的一半，判为同一文献（相似度提到 0.95）。

### 修复后的交叉验证

```
共审计 17 条引用，用时 7.4s
  [VERIFIED]     16 条  ( 94%)
  [PARTIAL]       0 条  (  5%)
  [FABRICATED]    0 条  (  0%)      ← 误报清零
  [UNCHECKED]     1 条  (  5%)      ← coqmanual
退出码 0（干净）
```

剩下唯一一条 `coqmanual` 判为 `UNCHECKED` 而非 VERIFIED/FABRICATED，原因是：
**Crossref / arXiv / OpenAlex 三个库都不收录软件参考手册**。
这类条目查不到是**预期的**，判成"编造"是误伤。

我为此专门加了文档类条目的识别（`reference manual` / `user guide` /
`technical report` / `手册` 等关键词），命中时判 `UNCHECKED` 并说明原因。

### 同时做回归测试

修改完必须确认**原 demo 没被改坏**：

```
demo/sample_refs.bib  →  4 VERIFIED / 2 PARTIAL / 2 FABRICATED   ← 与修改前一致✅
C2 references.bib     →  16 VERIFIED / 0 FABRICATED              ← 误报清零  ✅
```

> 💡 **这一轮是整个项目价值最高的一轮。**
> 用自建样本只能证明"能抓到假引用"——因为样本是我自己造的，我知道答案。
> 用**别人已核验过的真实文献库**才能证明"不会冤枉好引用"。
> 一个误伤真实引用的核查工具，危害比漏检更大：
> 它会让用户删掉自己真正引用过的论文。

## AI 使用方式小结

### 我采用的协作模式

| 环节 | 我让AI 做的 | 我自己做的 |
|---|---|---|
| 需求分析 | 拆解评审维度、对比选题 | **决定选题**（引用真伪） |
| 方案设计 | 提出降级架构、字段 schema | **要求先探测 API 再写码** |
| 代码实现 | 写完整脚本 | — |
| 调试 | 定位根因（解析器/排序） | **判断该不该改** |
| 验证设计 | 设计复现测试 | **决定在干净目录验证** |

### 三条我自己坚持的原则

1. **先探测再写码。** 如果没提前curl 那三个 API，我会把 arXiv 403
   误判成"网络不通"，把 Semantic Scholar 429 当成可用——
   技能交付出去就是坏的。

2. **测试必须独立于开发环境。** 在自己的目录里跑通≠ 可复用。
   必须在干净目录重新验证，这才是 CHALLENGE.md 说的"让陌生人能成功"。

3. **诚实报告，不粉饰。** 这一轮开发里有 3 个真 bug、一个 API 限制、
   一个数据源陷阱。如果日志只写"一次成功"，它就失去了作为
   "AI 使用记录"的价值。`rubric.json` 的 `aiUsage` 维度明确写着
   `一句话指令直接提交` 是负向信号——多轮迭代和失败经验才是我要展示的。
