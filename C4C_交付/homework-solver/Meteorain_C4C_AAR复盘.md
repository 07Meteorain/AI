## 二、最有价值的三件事

### 2.1 验证模块抓到了两个「求解率 100% 但答案全错」的 bug

**当时的场景**：单元测试 27/27 通过，基准测试 44/44 = 100%，一切看起来很完美。

**我逐题核对标准答案时发现**：
| 题 | 系统答案 | 正确答案 |
|----|---------|---------|
| AP1(a) | -11520 | -20 |
| AP2 | $\infty\operatorname{sign}(\langle-1,1\rangle\cdots)$ | $\pi$ |
| AP3 | $0$ | $\pi$ |

**根因**：
1. `_find_matching_brace` 起点算错一格 → `\frac{a}{b}` 被解析成 `a*b`
2. `Symbol('n', integer=True)` 让 SymPy 的 Gruntz 算法返回 0（正确是 π），**且不报错**

**为什么这件事重要**：
> 如果只看「求解率」这个指标，这两个 bug 会一路写进 PDF 交付出去。
> **「正确率」如果不可核验，就只是自欺欺人的数字。**

**我学到的**：
指标会骗人，尤其当指标只统计「有没有产出」而不检查「产出对不对」。
rubric 里「输出可核验」这五个字，权重给到 25 分，是有道理的。

### 2.2 回归测试暴露了「重写 = 丢失能力」

**场景**：我重写 `solve.py` 加了三个新学科，新学科测试 100% 通过。
我以为任务完成了。

**跑Berkeley 回归测试**：7/8 + 3/10 = 55%，比 starter kit 的 100% 差得多。

**逐题对比 `3_solutions.json`**，定位丢失的 8 题：
- 关键词优先级搞反了（「prove」把计算题抢去给 LLM）
- 抽象函数检测误伤了有具体函数定义的题
- 路由只看题干，不看子题（AP1 全部内容都在子题里）

**我学到的**：
> **AI 不会自动告诉你「你弄丢了什么」。**
>
> 我重写求解器时，新学科跑得好会给人强烈的完成感。
> 是**跑回归测试 + 与原实现逐题对比**才发现丢了 8 题。
>
> **AI 开发的安全性来自「有基线可对比」，而不是「AI 写得多好」。**

**采取的措施**：把「先跑通原测试再动手」写进了工作原则。

### 2.3 「宁可说不会」这条规则，救了一次学生

早期版本里，物理求解器未识别题型时会 fall through 到通用求解器。
通用求解器从「两个点电荷求库仑力」的题面里抓到第一个数字 `3.0`，
化简后作为答案输出。

**结果**：一个看起来完全正常、实际完全错误的答案。

**修正**：
> 领域求解器一旦命中，要么给答案，要么明确报未解，
> 绝不退回通用求解器。

**我学到的**：
这条规则反直觉——「多试几种方法总比直接放弃好」。
但对**教育工具**来说，**「静默的错误答案」比「明确的不知道」危害大得多**：
前者会直接骗过学生，后者只是能力不足。

写代码时我一度觉得这条约束太严格，
直到看到那个 `3.0`——它证明了我的直觉是错的。

## 三、做得不好的地方

### 3.1 顺序错了：先重写，后测试

**正确顺序应该是**：
```
1. 跑通 starter kit，记录基线 ← 我做了
2. 写新代码
3. 跑回归                 ← 我漏了，直到很晚才做
```

我在步骤 1 之后就直接开始重写，
结果新学科写完才发现**把老学科的能力弄丢了**，
又花了 6 轮迭代补回来。

**代价**：约 30% 的开发时间花在修复自己造成的回归上。

**下次的做法**：任何"重写/重构"任务，
**第一步就把现有测试跑一遍并保存结果**，作为后续对比基线。

### 3.2 环境适配不足

三处低级但耗时的问题：
1. **相对路径 + 子进程 cwd**：`tectonic` 报 `output directory does not exist`，
   因为相对路径被二次解析。修法：强制 `resolve()` 成绝对路径
2. **CJK 字体硬编码**：只装了微软雅黑的机器上编译直接失败。修法：动态探测
3. **正则字符类写错**：`[dt]?` 想匹配「可选的 d 或 t」，
   但方括号是正则的**字符类**，永远匹配不到 `\frac`

**共同点**：这三个问题在 Linux 上一个都不会出现。

**我学到的**：
> 跨平台工程的坑不在算法，在**路径、编码、依赖探测**。
> 本地开发只在 Windows 上做，导致这些坑全部集中爆发。
> 更好的做法是：写完就在目标平台验证，或者至少用绝对路径 + 防御式依赖探测。

### 3.3 正则在 shell 里被转义破坏

调试过程中多次遇到：想测`\\frac`，经过 bash 后变成 `\frac`，
再经过 Python 字符串又变一层，测的根本不是我写的那个东西。

**浪费时间的操作**：反复调整转义层数。

**后来的做法**：把测试代码写进 `.py` 文件，用 `python file.py` 跑，
不用 `-c` 内联。这一条就省下了一个多小时。

**我学到的**：
> 调试复杂字符串时，**尽快落到文件里**。
> 内联命令行是 debug 的陷阱——转义层数是隐式的，出错时很难定位。

### 3.4 没有一开始就写单元测试

我是在功能基本完成后才补的 `test_domain_solvers.py`。

**如果一开始就写**，它会立刻抓出：
- `Matrix.orthogonalize` 的 classmethod 用法错误（静默返回空列表）
- `M.svd()` 在 SymPy 1.13 不存在
- 各种意图路由的正则不匹配

**代价**：这三个 bug 各自花了一轮调试。

**下次的做法**：写完第一个求解器就配测试，
哪怕只有 3 个用例，也比 30 个用例 + 3 轮返工划算。

## 四、几个技术判断的复盘

### 4.1 判断：优先确定性，而非优先 LLM 能力 ✅

**决策**：把路由设计成「SymPy 优先，LLM 兜底」，
而不是直觉上的「LLM 为主」。

**依据**：实测 44/44 的题目 SymPy 全都能确定性求解。

**复盘**：这个判断是对的，而且比"用更强的模型"更有价值——
结果可复现、零幻觉、成本为零、离线可用。
**但它有前期成本**：每个域都要写求解器，不能靠模型能力"兜"过去。

**适用边界**：题目能被形式化时，符号计算永远优于 LLM。
题目需要真正的理解/推理时，反过来。

### 4.2 判断：验证只打标签，不改答案 ✅

**决策**：验证失败时**标记警告**，而不是"自动修正答案"。

**复盘**：对的。而且这个决定在 5.4 救了场——
验证器自己有 bug（数值逼近溢出导致 NaN），
如果它"自动修正"，正确答案 π 会被改成一个假值。

**关键区分**：**"我发现可能错了" ≠ "我知道正确答案是什么"**。
前者可以自动化，后者不行。

### 4.3 判断：内置 tectonic 而非要求装 TeX ✅

**决策**：把 50MB 的 tectonic.exe 放进 `tools/`。

**复盘**：对的。对评审场景，这是"能跑"和"跑不起来"的区别。
有人会问"仓库怎么这么大"——但一个 50MB 的 exe
换来的是 `git clone` 后立即可验证，这笔交易很划算。

**风险**：tectonic 首次运行要下载约 200MB 宏包，需要联网。
**缓解**：文档里给了 MiKTeX/TeX Live 作为备选。

### 4.4 判断：不用 LLM SDK，用 urllib ❌ 有争议

**决策**：手写 HTTP 调用，不用 openai/anthropic SDK。

**复盘**：**这一点我可能错了**。
当时的理由是"少一个依赖，读者能看清请求结构"，
但实际上手写 HTTP 带来的是：
- 错误处理要自己写（重试、超时、限流）
- 流式输出、token 计数这些边界情况处理不全
- API 变更时需要自己跟进

如果重做，我会用 SDK，把省下的时间花在**验证的严密性**上——
那才是这个项目真正的差异化价值。

## 六、如果重做，会怎么改？

按优先级排序：

### 6.1 立刻做：先跑通再重写

```
git clone starter kit
python scripts/pipeline.py <test> baseline/   ← 保存基线输出
# 然后才动手改
```

**成本**：5 分钟。**收益**：省下 6 轮回归修复。

### 6.2 立刻做：写完第一个求解器就配测试

哪怕只有 3 个用例。`Matrix.orthogonalize` 的坑，
一个 `assert len(q) > 0` 就能抓出来。

### 6.3 早点做：把踩坑写进代码注释

我确实做到了（`domain_skills/linear_algebra.yaml` 的 `oracle_insight`
字段、代码里的 ⚠️ 注释）。**这个习惯值得保持**——
三个月后我会忘记为什么 `\frac` 的正则要写成 `(?:d|t)?`，
但注释会告诉我。

### 6.4 早点做：验证模块和求解器同步写

不要等求解器"写完"再补验证。
**每写一个求解器就配一个验证**，
这样"求解率 100% 但答案全错"的问题不会有机会发生。

### 6.5 会考虑：用 LLM SDK 而非手写 HTTP

见4.4 的复盘。

### 7.1 做到了什么

- 核心域 100%，**超过** Claude 基线 94.4%
- 三个新学科域从 0 到 100%（starter kit 是 40%）

### 7.2 没做到什么

- **模型对比报告**（无 API Key，选择不编数据）
- **真正的量纲代数**（用的是启发式检查）
- 概率统计、数值方法等域
- LLM 路径未经真实调用验证

### 7.3 一句话总结

> 这次开发最大的收获不是"做出了 100% 求解率"，
> 而是学会了一件事：
> **在 AI 参与的工程里，可验证性比能力更重要。**
>
> 两个 bug 在求解率上是 100%，但答案是全错的。
> 如果没有逐题核对、没有交叉检验、没有回归测试，
> 我会交出一个"看起来完美、实际错误"的作品。
>
> 这也正是我把验证模块做进流水线的理由——
> **它不是给评审看的，是给自己和未来的使用者看的。**
