## 二、核心决策：SymPy 还是国产 LLM？

这是 CHALLENGE.md Level 3 明确要求回答的问题：
> 「你需要决定哪些题用 SymPy（确定性计算），哪些题用国产 LLM（推理/证明/文字），
> 如何结合两者。」

### 2.1 路由策略

路由决策实现在 `scripts/solve.py::decide_route()`，优先级从高到低：

```
① 结构性信号（最可靠）
   ├─ 含 \begin{pmatrix}→ 矩阵求解器
   ├─ 含 y' / dy/dx      → ODE 求解器
   └─ 含物理量关键词     → 物理求解器

② 概念模板库命中        → 模板求解器（确定性，零幻觉）

③ ε-δ 计算题           → ε-δ 构造器

④ 才考虑 LLM
   ├─ 抽象函数 f(x)/g(x) → LLM
   ├─ 证明/论证题         → LLM
   └─ 纯文字概念题        → LLM

⑤兜底：SymPy 失败 → LLM 二次机会
```

### 2.2 为什么这个顺序？（三个真实的坑）

**坑1：关键词会抢走结构性题目。**
最初把「prove / verify / explain」当作"需要 LLM"的信号，
结果 Berkeley WS3 的 P4「验证 y=C₁e^{2x}+C₂e^{3x} 是 y''-5y'+6y=0 的解」
被判成证明题送去 LLM——但它其实是**纯代入计算**，SymPy 三行就能验完。
**修正：结构性信号（矩阵/ODE/物理）永远优先于动词关键词。**

**坑 2：抽象函数检测会误伤有解的题。**
`has_abstract_functions()`看到 `f(x)` 就判"需推理"，
但 P4 的题干明确给了 `f(x) = x²`——这是**可算的具体函数**。
**修正：先检查是否给出了函数定义，有定义就按计算题处理。**

**坑 3：题干的信息量可能远小于子题。**
AP1 的题干是「下面列出三个极限，配对方法并求值」——**一个公式都没有**，
全部内容在 (a)(b)(c) 里。只看题干会误判成"纯文字题"。
**修正：路由判断时把子题文本一并纳入。**

### 2.3 融合策略：三层降级

```
SymPy（确定性）
    ↓ 失败
概念模板 / 专用构造器
    ↓ 失败
国产 LLM（Qwen3.6 / Kimi2.5 / DeepSeek）
    ↓ 无 Key / 无网
RuleBasedFallback（明确报告"未求解"，绝不编答案）
```

**关键原则：领域求解器一旦命中，要么给出答案，要么明确报未解，
绝不退回通用求解器。**

> 这条是我在测试中踩出来的。早期版本里，
> 「两个点电荷求库仑力」因为物理求解器没识别出题型，
> 落到了通用求解器；通用求解器从题面抓到第一个数字 `3.0`，
> 化简后当答案输出——**一个看起来完全正常、实际完全错误的答案**。
>
> 「静默地给出错误答案」比「明确说不会」危害大得多：
> 前者会直接骗过学生，后者只是能力不足。

## 三、国产模型选型

### 3.1 选 Qwen 3.6 为主，Kimi 2.5 / DeepSeek 为备

| 模型 | 优势 | 本项目中的定位 |
|------|------|----------------|
| **Qwen 3.6**（通义千问） | 数学推理强、中文理解好 | **默认**，覆盖绝大多数 LLM 兜底场景 |
| Kimi 2.5（Moonshot） | 长上下文、多步推理 | 长作业/复杂证明的备选 |
| DeepSeek | 代码 + 数学 | 对照组 |
| Claude | starter kit 原始基线 | **仅用于 Level 4 对照实验** |

三家都是 OpenAI 兼容协议，`llm_engine.py` 用一个 client 全部覆盖，
切换只需改 `--provider` 参数。

### 3.2 迁移对照表

| 能力 | starter kit（Claude 版） | 本项目（国产模型版） |
|------|------------------------|-------------------|
| 推理/证明/文字题 | Claude Code 主循环人工组织 | `llm_engine.py` 统一调度，JSON Schema 强约束 |
| 结构化输出 | 人工在对话里整理 | `json_object` + 三层 JSON 抽取降级 |
| 失败可观测 | 靠翻对话记录 | `llm_trace.jsonl`，含时间戳/prompt哈希/响应摘要 |
| 成本控制 | 不可观测 | token 统计 + prompt SHA256 缓存 |
| 无网/无 Key 兜底 | 不可用 | `RuleBasedFallback`，明确报未解 |
| 多模型对比 | 无 | `compare_prookies()`→ `compare_providers()` |

## 四、答案验证设计

rubric 里「输出可核验」是 solverQuality（25分）的关键信号。
starter kit 算完就输出，从不回头检查。我加了一套四层验证：

| 层 | 方法 | 抓什么错 |
|----|------|---------|
| L1 | 形式检查 | 空答案、NaN、zoo、未解占位符混入 |
| L2 | 数值代入 | 答案代回原方程对不上 |
| L3 | 交叉检验 | 符号算法 vs 数值逼近结论不一致 |
| L4 | 量纲/形状 | 物理量量纲不匹配、矩阵形状错 |

### 4.1 验证抓到的真实 bug

**最有价值的一个**——SymPy 的**静默误算**：

```python
from sympy import *
n = Symbol('n', positive=True, integer=True)
limit(n*sin(2*pi/n)/2, n, oo)   # → 0❌  正确答案是 π
limit(n*sin(2*pi/n)/2, n, oo)   # 去掉 integer=True → π ✓
```

带 `integer=True` 假设时，Gruntz 算法返回 **0**，而且**完全不报错**。
圆内接正 n 边形面积的极限因此被算成 0。

**这暴露了验证模块的必要性**：如果只靠 SymPy 自己，
这个错误会一路写进 PDF，没人发现。

**修正（双保险）**：
1. 求解器侧：不用 `integer=True`，并加解析值交叉核对
2. 验证侧：`cross_check_limit` 用高精度数值逼近独立复核，
   符号路径与数值路径不一致时报「⚠ 验证存疑」

### 4.2 另一个被验证抓到的 bug

分数解析的 `_find_matching_brace` 起点算错一格，
导致 `\frac{x^2 + 2x - 24}{x - 4}` 被解析成 **乘法** `(x-4)(x²+2x-24)`。
AP1(a) 因此给出 -11520（正确是 -20）。

这个 bug 用例随机测试很难碰到——**是逐题核对标准答案时发现的**。

## 六、关键技术选型

### 6.1 为什么内置 tectonic 而不是要求装 TeX Live？

starter kit 的 PDF 编译是「脚手架」，需要用户自备 LaTeX 环境。
评审时如果对方没装 TeX，产物就是一堆 `.tex` 而已。

tectonic 是**单文件、零依赖**的 LaTeX 引擎（一个 50MB 的 exe），
首次运行自动下载宏包。我把它放进 `tools/` 目录，
`detect_engines()` 会优先发现它——**克隆下来就能跑通全流程**。

### 6.2 CJK 字体动态探测

硬编码 `\setCJKmainfont{Noto Serif CJK SC}` 在只装了微软雅黑的
Windows 上会直接编译失败（`fontspec Error: The font cannot be found`）。

改成 `detect_cjk_fonts()` 扫描系统字体目录，
按「开源优先 → 系统字体兜底」排序，生成
`\IfFontExistsTF{...}{...}{}` 逐个探测的 LaTeX 代码块。

### 6.3 依赖分级

`requirements.txt` 把依赖分成「必需/推荐/可选」三档，
缺推荐依赖会降级但不致命（如没装 matplotlib 就不生成图，
没装 pdfplumber 就只支持 Markdown）。
