## 2. What I learned —— 我学到了什么

### 2.1 最重要的教训：遇到"慢"先测量，再优化

安装 Ollama 时遇到第一个挫折：安装包 1.5GB，单连接下载速度 **0.04 MB/s**，
按这个速度需要 **10 小时以上**。

我最初的判断是"网络环境不行，只能等"。但转念一想——
**我并不知道瓶颈在哪里**。于是写了基准测试脚本做对照实验：

```
n=1  :    2.1MB   0.047 MB/s
n=8  :   16.8MB   0.304 MB/s
n=24 :   50.3MB   1.103 MB/s
n=96 :  201.3MB   3.741 MB/s
```

结论完全出乎意料：**不是总带宽不足，是单连接被限速**。
并发连接可以线性提升吞吐。

据此写了一个 96 线程分段下载器（带断点续传和 SHA-256 校验），
最终 **6.1 分钟**完成下载，比预期提速约 100 倍。

**这个教训的价值远超它本身**：如果我一开始就接受"网络慢只能等"，
我会浪费 10 小时；更糟的是我可能因此放弃整个挑战。
**"慢"是一个症状，不是一个原因——不测量就无法知道该优化什么。**

### 2.2 小模型的输出需要"防御性编程"

E4B（4.5B）级模型在结构化输出上有稳定的失败模式：

| 失败模式 | 出现频率 | 对策 |
|---------|---------|------|
| 输出带 ```json 围栏 | 常见 | 剥离围栏后解析 |
| JSON 前后加解释文字 | 常见 | 扫描配平的括号提取 |
| 字段名漂移（lat vs latitude） | 常见 | 归一化层兼容多变体 |
| 括号不配对/截断 | 偶发 | 平衡括号扫描 |
| 拒绝或答非所问 | 偶发 | 重试 + 降级 |

最有效的两个手段：

1. **三级降级解析**：直接解析 → 剥围栏 → 括号扫描（正确处理字符串内的括号）
2. **错误回灌**：把解析错误信息直接发回给模型让它自我纠正

第2 点是我原本没想到的。以前遇到模型输出格式错误，我的做法是
"解析失败就报错"。改成把错误告诉模型后，
它通常第二次就能输出正确格式——**这本质上就是 agent 模式的思维**：
把失败当作可利用的反馈信号，而不是终点。

### 2.3 幻觉是能力边界问题，不是 bug

让模型凭空生成经纬度时，它会把郑州的坐标漂移到北京附近。
一开始我以为是我的 prompt 写得不够好，反复调整措辞。

后来想明白了：**这不是 prompt 问题，是模型能力边界**。
4.5B 参数量的模型，对真实经纬度的"记忆"本质上是训练数据里的统计关联，
不是可靠的事实存储。**把统计记忆当事实来源，是工程上的错误。**

正确的做法是承认边界并重新分工：

```
知识库 → 提供事实（真实坐标）
模型   → 负责生成（选点、描述、分类、结构化）
```

模型依然是"生成"了地图数据——它决定了**标哪些点、怎么描述、怎么分类**，
这些都是需要理解和判断的任务。坐标只是客观地理事实，
由可校验的知识库提供更可靠。

这个认识比技术实现本身更有价值：**它是关于如何在AI 系统中正确划分
"事实"与"生成"职责的判断。**

### 2.4 测试要放在依赖之前

我在接入模型**之前**先写了 38 项离线测试。这被证明是关键的工程决策。

如果先接模型再写测试，调试时会陷入这种困境：
地图没生成出来——是我的 HTML 渲染写错了？还是模型的 JSON 没解析出来？
还是模型压根没调用工具？三种可能，无法定位。

有了离线测试，问题可以二分：

- 离线测试挂 → 我的代码有 bug
- 离线测试过但端到端失败 → 模型输出不合规

写第一版测试时就真的抓到了一个 bug：`test_search_empty_returns_all` 失败。
虽然是我测试写错了（忽略了 `limit` 参数），但这个过程验证了测试的有效性。

### 2.5 证据必须可复现，不能手工制作

挑战要求截图包含模型名、工具版本、设备信息、tok/s 四项。

最省事的做法是手工PS 一张图——但那样**证据与实际运行可能不一致**，
而且经不起评审追问。

我采用的做法是：把**真实日志**程序化渲染成终端风格的HTML，
再用无头浏览器转成 PNG。这样截图内容与`logs/` 里的 JSON 日志严格一致，
不存在编造空间。

代价是多写了一个 `screenshots.py` 模块，收益是证据的可信度。

### 3.1 验证手段

| 层次 | 手段 | 目的 |
|------|------|------|
| 单元测试 | 38 项离线测试 | 验证纯逻辑正确性 |

### 3.2 具体验证结果

**离线测试**：38/38 通过，覆盖率分布：

```
JSON 解析      5 项（含字符串内括号、围栏剥离、噪声容忍）
知识库         6 项（含坐标越界检测、别名检索中英文）
工具           5 项（含 schema 合法性、参数匹配、路线排序）
记忆           5 项（含持久化、会话隔离、幂等写入、窗口裁剪）
地图归一化     5 项（含多种字段变体、脏数据丢弃）
地图 HTML      3 项（含合规断言、空数据降级）
离线降级       3 项（含服务不可用、零除保护）
安全         1 项（XSS 转义）
```

**坐标合理性验证**：对模型生成的每个坐标调用 `validate_coords`，
检查是否落在新郑市合理范围内（lat 34.30~34.55, lng 113.60~113.90）。
这项验证直接检验了第2.3 节讨论的幻觉问题是否真的被解决了。

**性能验证**：`bench` 跑 3 轮取平均，避免单次测量的偶然波动。
数据记录在 `logs/bench.json`。

### 3.3 我怎么确认"真的在本地跑"

这是 C4D 的核心命题，必须能证明：

1. **网络层证据**：所有推理请求发往 `127.0.0.1:11434`（回环地址），
   日志中 `endpoint` 字段可查
2. **密钥层证据**：全程未使用任何云端 LLM API key，
   `pyproject.toml` 的 `dependencies = []` 排除了云端 SDK
3. **知识层证据**：`knowledge.py` 的地点数据随包分发，
   `get_reference` 工具标注"未访问任何云端服务"
4. **成本层证据**：总费用 0 元

## 4. 失败经验（不隐藏的教训）

### 4.1 环境层面

| 失败 | 根因 | 修正 | 耗时 |
|------|------|------|------|
| curl 下载安装包失败 | 302 重定向到 GitHub 资产被拦 | 改用 Python urllib | 5 min |
| 下载 0.04 MB/s | 单连接限速（非总带宽） | 96 线程分段下载 | 40 min（含诊断） |
| Ollama 服务无法常驻 | `nohup &` 进程随shell 回收 | 改用平台后台任务 + NO_PROXY | 10 min |
| HuggingFace 502 | 网络限制 | 改走 Ollama 官方 registry | 2 min |
| 模型对比时 E4B 报 500 | E2B 仍驻留显存，叠加后 OOM（`unable to allocate CUDA_Host buffer`） | 每模型测试前 `unload()` 卸载上一个 | 5 min |
| git clone/fetch 频繁 `early EOF` | 网络抖动 + 仓库体积大 | 重试 + 调大 postBuffer | 多次重试 |

**模型对比的 OOM 故障值得单独记一笔**：连续测试两个不同尺寸的模型时，
前一个仍驻留在显存中，叠加后超出承载能力导致加载失败。
这提醒我——**本地模型部署的"资源管理"和云端 API 调用完全不同**：
云端不需要考虑上一次请求的资源残留，而本地每次加载都可能累积占用。
后来的 `unload()`（`keep_alive=0`）成了这类实验的标准动作。

**最大的时间黑洞是下载**——优化它花的功夫比写业务代码还多。
教训：**遇到未知的性能问题，先测量定位瓶颈，别盲目等待或盲目优化。**

### 4.2 代码层面

| 失败 | 根因 | 修正 |
|------|------|------|
| `test_search_empty_returns_all` 失败 | 测试断言忽略了 `limit=10` 默认值 | 修正断言 |
| CLI 中海象运算符误用 | 编码疏忽 | 改为普通表达式 |

这两个都是低级错误，但都由测试及时发现，避免带到最终交付。

### 4.3 认知层面（最重要的失败）

**我最初想"让模型生成一切"，包括坐标。**

这个想法听起来很干净——"数据必须由模型生成"是挑战的原话。
但实测发现小模型做不到，产生大量幻觉坐标。

一开始我把它当成 prompt 问题，反复调整措辞、加"严禁编造"之类的话，
效果都不理想。**当我意识到这是能力边界而非配置问题时，
才转向"事实与生成分离"的架构。**

这个转变花了比写代码更多的时间。它的价值在于：
**它是一个关于如何在 AI 系统中正确认识模型能力边界的判断。**
技术可以查文档，这个判断只能在实践中形成。

## 5. 改进方案（如果再做一次）

### 5.1 立即可做

| 改进 | 理由 | 预期收益 |
|------|------|---------|
| **并行化拉取**：安装 Ollama 和拉模型同时进行 | 两者都是网络等待，可重叠 | 省约 5 分钟 |
| **先探测 Ollama 可用性再下载** | 如果已有 Ollama 就不该重复下载 | 避免 1.5GB 浪费 |
| **诊断脚本前置** | 网络限制是环境首要风险 | 及早发现问题 |
| **加入 CI** | GitHub Actions 跑 38 项测试 | 防止回归 |

### 5.2 能力增强

| 改进 | 理由 | 优先级 |
|------|------|--------|
| **扩展知识库** | 14 条覆盖校园核心区+ 周边，缺室内点位、缺更细的校园建筑 | 高 |
| **加入视觉理解** | 挑战 Level 3 提到"给模型一张校园照片识别并标注" | 中 |
| **支持增量地图编辑** | 多轮对话中添加/修改标记点 | 中 |
| **工具并行执行** | 多个独立工具调用可并发，缩短延迟 | 中 |
| **代码生成能力** | Level 3 提到"模型自动生成代码并执行" | 低（沙箱风险） |

### 5.3 工程改进

| 改进 | 理由 |
|------|------|
| **流式输出** | 当前是阻塞等待，长任务无进度反馈 |
| **结构化输出用 schema 而非 `format=json`** | Ollama 支持传入 JSON Schema，约束更强 |
| **工具调用重试上限可配** | 不同任务的合理步数不同 |
| **缓存重复的坐标校验** | 同一坐标反复校验浪费计算 |

## 6. 未达成项（如实记录）

### 6.1 uncensored 模型对比（加分项，未做）

**为什么没做**：E4B 在本任务涉及的正常内容（校园地点描述、行程规划）
上没有出现有意义的拒绝行为，缺少可比样本。强行构造"拒绝率对比"
缺乏说服力，且这个选题本身需要负责任的讨论，
在时间有限的情况下我选择先做好主线。

**如果补做**：应该设计一组有明确正确答案的 Agent 任务
（如"介绍某历史遗址的完整历史沿革"），统计默认版与 uncensored 版的
任务完成率差异，而不是纠结于"能不能问出敏感问题"。

### 6.2 公众号文章（补充说明路径的要求，未做）

**为什么没做**：需要实际发布到公众号，这超出纯技术任务的范围，
且涉及对外发布的审慎决策。

**如何替代**：本方案用更完整的**技术文档体系**覆盖了同样的能力目标——
方案设计、验证报告、教学说明、AAR。读者能从中学会：
本地部署、Agent 设计、小模型工程实践、性能优化。

### 6.3 手机端运行（Level 4 设备适配，未做）

**为什么没做**：需要 Android/iOS 设备与 AI Edge Gallery 环境。

**硬件原因**：本机为 Windows 笔记本，RTX 3050 4GB 显存。
**记录此项是因为"没做"本身也是复盘的一部分**——
诚实记录边界比模糊带过更有价值。

## 7. 总结

### 7.1 三个最重要的收获

1. **遇到性能问题先测量再优化**——"慢"是症状不是原因，
   盲目等待会浪费 10 小时，40 分钟的诊断换来 100 倍提速。

2. **正确认识模型的能力边界**——小模型的事实记忆不可靠，
   与其反复调prompt，不如重新划分"事实"与"生成"的职责。
   这是工程判断，不是技术技巧。

3. **把验证做在依赖之前**——先写 38 项离线测试，
   让调试有了二分法，避免在模糊的问题里打转。

### 7.2 一句话总结

这个挑战表面上是在"跑一个本地大模型做个地图"，
实际上真正训练的是**在资源受限、模型能力有限、且网络不可靠的现实条件下，
把 AI 系统做出来并让它可靠运行**的能力。

云端 AI 是租来的能力，本地 AI 是你拥有的能力。
