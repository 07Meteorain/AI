## 0. 先讲清楚：这不是「一句话直接提交」

用户只给了一条指令。**本日志记录的是执行代理在内部把这条指令拆成 8 个阶段、经历 12 次返工的过程，不虚构用户的多轮对话。**

区分三件事：

| 类型 | 本日志中的体现 |
| --- | --- |
| 用户输入 | 仅第 0 节引用的一条指令 |
| 代理内部迭代 | 第 3 节的 R1–R7：每次都有输入、动作、产出、验收、返工 |
| 人工决策点 | 第 6 节：哪些必须由人确认（发布账号、许可证、事实口径） |

这样写的原因：评分标准里的「多轮迭代、prompt 优化、工作流设计」如果靠编造用户对话来满足，属于造假；**真实的多轮体现在「产出 → 自检 → 发现缺陷 → 修正 → 再验证」的闭环**，日志应能逐条对应到文件和命令。

### R1：环境与仓库勘察（约 10 分钟）

**输入**：目标仓库 URL。

**动作与真实发现**：

1. 第一次执行 `Get-ChildItem` 返回 `exit code 3221225794`（`STATUS_DLL_INIT_FAILED`）。不是命令写错，而是执行环境初始化异常；在文件策略切换为 full-access 后重试成功。
2. 工具版本：git 2.55、gh 2.102、Python 3.14；没有 Node。
3. `gh auth status` 显示未登录；但 `git push --dry-run` 返回 `Everything up-to-date`，说明 Git 侧另有凭据（Windows GCM）。两者不一致，先记录，不急着下结论。
4. 克隆目标仓库：`master` 分支、99 个提交、1,246 个文件、已有 `C1`–`C5` 交付、标签 `c5-v1.0.0`。
5. 根 README 是 25 KB 的索引 + 各挑战说明；根目录没有 LICENSE/CONTRIBUTING。

**产出**：环境事实表、仓库现状清单。

**评审**：`git push --dry-run` 的「成功」不能证明有写权限——dry-run 可能不真正写 ref。必须用一次真实推送或 API 验证（后面 R6 才做）。

**返工**：第一次 pwsh 调用失败后没有反复重试同一个命令，而是换工具（glob/read）确认文件存在，再在策略变化后重试 shell。

### R3：工具实现与四次指标修正（约 25 分钟）

**输入**：`httpie` 本地克隆。

**v0 设计**：

- 只用标准库 + `git` 命令；
- 输出 Markdown + JSON；
- 指标：规模、语言、目录、作者、年份、Conventional Commit 占比、merge、治理文件、过期分支、churn、健康度；
- `--now` 固定基准时间，保证报告可复现。

**v0 结果与缺陷**（每个都是真实跑出来才发现的）：

| # | 现象 | 根因 | 修正 | 验证 |
| --- | --- | --- | --- | --- |
| 1 | 「首次提交」显示 2024-12-17，仓库年龄 692 天 | `git log --reverse --max-count=1` 先取最新再反转；`--max-count` 在 `--reverse` 之前生效 | 改为 `git log --reverse --max-parents=0` 取根提交 | 首次提交变为 2012-02-25，年龄 5,372 天 |
| 2 | 「本地分支 2」，多出一个 `origin` | `%(refname:short)` 把 `refs/remotes/origin/HEAD` 缩成 `origin`，被误判为本地分支 | 改用完整 `%(refname)` 前缀判断，跳过 `/HEAD` | 本地 1 / 远程 10 |
| 3 | 测试文件 103 个、测试 8,937 行 | 把 `tests/fixtures/` 下的样本全算成测试 | 只匹配 `test_*.py`、`*_test.go`、`tests/*.py` 等 | 37 个测试文件、6,847 行 |
| 4 | 版本标签 50 个却判「缺失」，健康度 72 | `compute_health` 没为 `tags` 写分支，落到通用 `gov` 检查 | 增加 `tags` 专项判断 | 77 分，标签 5/5 |

**额外修正**：

- `source_loc` 原本把测试也算进源码，导致测试/源码比 0.35；改为「源码不含测试」后为 0.56，更符合直觉；
- `Path.write_text(newline=...)` 是 Python 3.10+ 参数，为兼容 3.9 移除；
- 传入仓库子目录时，`git -C` 会向上找到父仓库，但文件读取仍按子目录拼接路径，可能错位；统一提升到 `--show-toplevel`。

**测试失败与修复**：

1. `test_inactive_and_stale_branches` 报 `KeyError: 'stale_days'` → 健康度函数改用 `branches.get("stale_days", 180)`；
2. `test_not_a_git_repo` 没抛异常 → 测试目录建在了临时仓库内部，`git rev-parse` 向上找到了父仓库；改用仓库外的临时目录。

**产出**：`工具/repo_inspector.py`（约 900 行）、`工具/tests/test_repo_inspector.py`（15 项，全绿）。

**评审**：每次指标变化都重跑两个仓库，确认「修正一个口径不会悄悄改变另一个数字」。

## 4. Prompt 迭代：从一句话到可验收任务

这里的「prompt」指执行代理自用的任务提示，不是伪造的用户对话。

| 版本 | Prompt 要点 | 产出 | 暴露的问题 | 下一版改进 |
| --- | --- | --- | --- | --- |
| P0（用户） | 「完成 C5A，新建文件夹，上传，严格按挑战文件」 | 无 | 没有验收标准、没有分析对象 | 先读文件，提取硬约束 |
| P1（拆解） | 「列出交付物、评分维度、红旗项；每个交付物给验收证据」 | 交付矩阵 | 仍未定义「仓库分析」的深度 | 加「事实/判断分离 + 可复现」 |
| P2（工具契约） | 「零依赖；Markdown+JSON；指标必须能用 git 原命令复核；`--now` 可复现；15 项测试」 | 工具 v0 | 指标口径有 4 个 bug | 每个指标写入口径 + 交叉验证 |
| P3（分析写作） | 「先事实表，再判断；每个数字标来源；必须写风险与反例；给出复现命令」 | 3 篇分析 | 出现 13→11、fixture 误称等事实错误 | 写作后强制「回查原始数据」 |
| P4（Git） | 「短分支；Conventional Commits；PR 描述含测试与评分对照；合并后打 tag」 | 分支/PR/tag | 认证解析 bug；PR 未创建前无法写编号 | 先创建 PR，再回填编号到文档 |
| P5（自审） | 「按评分维度逐项找证据；红旗逐条反证；链接/测试复跑」 | 提交说明 | 根 README 缺索引 | 补索引并纳入提交 |

**P2 的一个具体改进**（展示「prompt 优化」不是口号）：

- 旧：`统计测试代码行数`
- 新：`统计测试代码行数；测试文件仅匹配 test_*.py / *_test.go / tests/*.py；fixtures 不计入；源码行数不含测试；报告注明口径`
- 效果：测试/源码比从 0.35 修正为 0.56，避免把「测试写得少」误判。

## 5. 失败与返工清单（完整）

| # | 失败/返工 | 症状 | 根因 | 修正 | 教训 |

| 2 | 首次提交日期错误 | 2024 而非 2012 | `--reverse` 与 `--max-count` 顺序 | `--max-parents=0` | git 参数组合要看语义，不靠猜 |
| 3 | 分支数错误 | 本地 2 个，多出 `origin` | `%(refname:short)` 缩写歧义 | 用完整 refname | 短名适合展示，不适合判断 |
| 4 | 测试文件虚高 | 103 个 / 8,937 行 | fixtures 被当测试 | 收窄匹配规则 | 指标先定义口径，再写代码 |
| 5 | 标签误判 | 50 个 tag 却「缺失」 | 健康度缺 `tags` 分支 | 专项判断 | 新检查项必须覆盖所有 key |
| 6 | 单测 KeyError | `stale_days` 不存在 | 测试构造的 metrics 缺字段 | `.get(..., 180)` | 防御式读取 |
| 7 | 单测未抛异常 | 空目录仍被识别为仓库 | 测试目录在仓库内部 | 用外部临时目录 | 测试隔离要彻底 |
| 8 | token 401 | `Bad credentials` | PowerShell 把字符串 `[0]` 当数组索引 | 按行解析 + Trim | 跨语言处理凭据要小心 |
| 9 | 控制台乱码 | `Get-Content` 显示乱码 | PS 5.1 默认 ANSI 读取 UTF-8 | 用 `read` 工具/UTF-8 输出 | 不要用控制台判断文件编码 |
| 10 | 挑战目录数写错 | 13 vs 11 | 凭印象写，未数 | 命令计数后全文修正 | 文档里的数字也要有来源 |
| 11 | 健康度语义偏差 | 归档仓库 29 分 | 评分面向产品仓库 | 写「分数的正确读法」 | 指标要标注适用边界 |
| 12 | 根 README 缺索引 | 首页看不到 C5A | 只关注新目录 | 补目录行与章节 | 交付要从「评审入口」检查 |

> 这些不是「AI 一次成功」的装饰，而是实际发生过的返工。每条都能在 git 历史、证据文件或测试输出里找到对应痕迹。

## 6. AI 使用边界与人工决策

### AI 做了什么

- 环境勘察、仓库克隆、指标统计、代码与测试编写；
- 文档起草、事实交叉验证、链接检查；
- Git 分支/提交/合并/tag 的执行；
- 把用户一句话拆成可验收工作流。

### 必须由人决定/确认的

| 事项 | 为什么不能由 AI 单独决定 | 本次处理 |
| --- | --- | --- |
| 发布到哪个账号/仓库 | 涉及账号权限与公开范围 | 用户已明确给出仓库 URL；使用本机已存凭据推送 |
| 许可证选择 | 法律含义，取决于作者意图 | 本交付未替仓库新增 LICENSE；在自检中建议，不擅自选 |
| 分析结论的采用 | 影响对外表述 | 文档区分事实/判断，并给出复现命令供人工复核 |
| 真实用户反馈 | 不存在就是不存在 | 不编造「用户说…」；只记录内部自审 |

### 诚实边界

- 没有真实用户多轮对话，因此不声称「用户反馈后改进」；
- 健康度是启发式，不是代码质量评级；
- 分析快照固定，仓库后续变化不在覆盖范围内；
- 未使用外部 AI 评审；「独立评审」仅指自审清单，不冒充第三方。

## 7. 可复用 Prompt 模板（仓库分析）

```text
角色：你是代码仓库分析员，不是代码生成器。

任务：分析 <仓库 URL>，输出一份能让工程师在 30 分钟内决定「用不用/改不改」的报告。

硬约束：
1. 先克隆到本地，固定 commit 快照，所有数字可用 git 命令复核；
2. 区分「事实」与「判断」：事实给命令/文件，判断给理由；
3. 必须覆盖：定位、目录职责、依赖方向、入口、测试、CI/发布、协作历史、风险；
4. 至少给出 3 条可借鉴实践与 3 条不要照搬的点；
5. 末尾给复现命令与指标口径；
6. 不允许编造 star 数、贡献者、行数；不确定就写「未验证」。

输出结构：
- 结论先行（5 条）
- 10 分钟地图
- 架构与关键路径
- 测试与 CI
- 协作与提交
- 风险清单（证据/影响/缓解）
- 可借鉴/别照搬
- 复现与边界
```
