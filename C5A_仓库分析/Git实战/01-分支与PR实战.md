# 分支与 PR 实战：把 12 个文件变成一次可评审的合并

> 本文记录本次 C5A 交付在 [`07Meteorain/AI`](https://github.com/07Meteorain/AI) 上的真实 Git 操作：
> 从 `master` 开短分支、分阶段提交、推送、开 PR、合并、打 tag。
> 命令与哈希均来自实际执行；拓扑全文见 [`../证据/git-log-graph.txt`](../证据/git-log-graph.txt)。

---

## 1. 为什么不用「直接 push master」

| 做法 | 优点 | 问题 |
| --- | --- | --- |
| 直接 push master | 快 | 无法 review；出问题只能 revert；历史里看不出「为什么改」 |
| 长分支开发一周 | 一次合并 | 冲突大、review 难、CI 反馈晚 |
| **短分支 + 小提交 + PR** | 可 review、可回滚、CI 提前跑 | 多几次命令 |

本次选第三种。目标不是「显得规范」，而是：

1. 让每个提交**只做一件事**，评审可以逐条看；
2. 让 PR 成为**交付说明的载体**（测试命令、风险、评分对照）；
3. 合并后保留分支拓扑，方便回溯「这批文件是怎么进来的」。

### 提交粒度是怎么定的

- **能独立回滚**：工具、测试、文档、CI、索引分开；某篇文档写错，revert 不会带走代码。
- **能独立 review**：每个提交的 diff 主题单一；`docs(c5a): ...` 的提交只改文档。
- **不提交生成物**：`__pycache__` 被 `.gitignore` 排除；证据是「有意保存的报告」，不是缓存。
- **提交信息带正文**：说明「做了什么、为什么、验证方式」，而不是只写「update」。

## 4. 执行命令（可复制）

```bash
# 0) 克隆并确认基线
git clone https://github.com/07Meteorain/AI.git
cd AI
git log -1 --format='%H %s'        # 451f4b6 ...

# 1) 开短分支
git switch -c feat/c5a-repo-analysis

# 2) 分阶段提交（本次用 -F 指定 UTF-8 消息文件，避免中文乱码）
git add -- C5A_仓库分析/.gitignore C5A_仓库分析/证据/httpie-report.md ...
git commit -F .git/c5a-01.txt

# 3) 推送分支（首次带 -u）
git push -u origin feat/c5a-repo-analysis

# 4) 开 PR（body 见第 5 节）
gh pr create \
  --base master \
  --head feat/c5a-repo-analysis \
  --title "C5A: GitHub 入门与仓库理解交付" \
  --body-file .git/c5a-pr-body.md

# 5) 等 CI（若触发），合并为 merge commit
gh pr checks --watch
gh pr merge <PR_NUMBER> --merge

# 6) 同步 master 并打 tag
git switch master
git pull --ff-only origin master
git tag -a c5a-v1.0.0 -m "C5A: 仓库分析交付（repo_inspector + 双仓库分析 + Git 实战）"
git push origin c5a-v1.0.0

# 7) 保存拓扑证据
git log --graph --oneline --decorate -25 > C5A_仓库分析/证据/git-log-graph.txt
```

> 说明：本次提交信息用 `git commit -F` 从 UTF-8 文件读入，避免 Windows 控制台代码页把中文变成乱码。日常也可以直接 `git commit -m`，但跨平台团队建议统一 UTF-8。

## 6. 合并方式：为什么用 merge commit

| 方式 | 结果 | 适用 |
| --- | --- | --- |
| Squash merge | 12 个提交压成 1 个 | 分支提交很碎、只想保留结果 |
| Rebase merge | 提交线性接到 master，无 merge commit | 追求线性历史 |
| **Merge commit** | 保留分支拓扑 + 一个合并提交 | 想保留「这批改动是一个 PR」的证据 |

本次选 merge commit，原因：

1. 挑战本身要展示 branch/PR/merge，保留拓扑比「压成一个提交」更有说服力；
2. 12 个提交已经按逻辑分组，不需要再压；
3. 合并提交信息自带 PR 编号，方便回溯。

**合并后检查**：

```bash
git log --graph --oneline --decorate -15
git show --stat HEAD
git tag --contains HEAD
```

## 7. 回滚预案

如果合并后发现严重问题：

```bash
# 1) 找到 merge commit
git log --merges --oneline -3

# 2) 撤销合并（保留主分支历史）
git revert -m 1 <merge-sha>
git push origin master

# 3) 修复后重新合并（注意：Git 可能认为分支已合并）
git switch feat/c5a-repo-analysis
git rebase master
git switch master
git merge --no-ff feat/c5a-repo-analysis
```

如果只是某个文件写错：`git revert <该提交的sha>`，不要回滚整个 PR。

## 9. 这次学到的四件事

1. **提交信息要先想清楚再 commit**：`type(scope): subject` + 正文「为什么/验证」，写的时候会逼自己检查改动是否单一。
2. **PR 描述是交付的一部分**：评审先看描述与测试命令，再看 diff；描述里写清边界，能减少一半提问。
3. **中文提交信息要管编码**：Windows 控制台 + PowerShell + git 的组合容易乱码；用 UTF-8 消息文件最稳。
4. **合并后立刻打 tag**：否则「交付的是哪个提交」只能靠记忆；tag 是给未来的自己留的路标。

## 10. 附：分支/PR 命令速查

```bash
git switch -c feat/xxx                 # 开分支
git status -sb                         # 看分支与改动
git add -p                             # 分块暂存，避免混入无关改动
git commit -F msg.txt                  # UTF-8 提交信息
git push -u origin feat/xxx            # 首次推送
gh pr create --fill                    # 用提交信息生成 PR
gh pr checks --watch                   # 等 CI
gh pr merge <n> --merge                # 合并（保留 merge commit）
gh pr view <n> --web                   # 浏览器查看
git tag -a v1.0.0 -m "..."             # 附注标签
git push origin v1.0.0                 # 推标签
```
