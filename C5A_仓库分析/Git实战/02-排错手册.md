# Git 常见故障排查手册

> 14 个真实高频场景。每个场景按「症状 → 诊断 → 根因 → 修复 → 预防」写，命令可直接复制。
> 约定：`<...>` 是占位符；带 ⚠️ 的操作会改写历史，执行前先 `git branch backup/<date>` 或 `git tag backup/<date>`。

---

## 0. 先记住三条保命命令

```bash
git status                 # 我现在在哪、改了什么、有没有冲突
git log --oneline --graph --decorate -20   # 最近发生了什么
git reflog -20             # 我（或别人）到底动过哪些 HEAD
```

**90% 的「代码丢了」都能被 `git reflog` 救回来**，前提是别急着 `git gc`、别删 `.git`。

---

## 1. 处于 detached HEAD（分离头指针）

**症状**

```
$ git status
HEAD detached at 3.2.4
nothing to commit, working tree clean
```

**诊断**

```bash
git branch --show-current      # 输出为空
git status -sb                 # 第一行 HEAD (no branch)
```

**根因**：`git checkout <tag>` / `git checkout <commit>` / `git checkout origin/main` 会进入分离状态，新提交不属于任何分支。

**修复**

```bash
# 只是看看：直接切回分支
git switch main

# 已经在分离状态提交了代码：把当前提交接到新分支上
git switch -c rescue/my-work
```

**预防**：查看历史用 `git switch --detach <tag>` 并明确知道自己在「只读模式」；要改代码就先开分支。

---

## 2. 提交到了错误的分支

**症状**：在 `main` 上写了本该属于 `feature/x` 的提交，且还没 push。

**诊断**

```bash
git log --oneline -3
git branch --contains HEAD
```

**修复**

```bash
# 1) 在正确分支上接住这个提交
git switch -c feature/x          # 如果分支还不存在
# 或 git switch feature/x        # 已存在

# 2) 把 main 退回提交前（保留工作区）
git switch main
git reset --soft HEAD~1          # 提交回到暂存区

# 3) 回到 feature/x 正常提交
git switch feature/x
git commit -m "feat: ..."
```

如果错提交已经 push 到共享分支：不要 `reset`，用 `git revert <sha>` 生成反向提交。

**预防**：开工前 `git switch -c feat/...`；`git status -sb` 确认分支名；push 前看一眼 `git log origin/main..HEAD`。

---

## 3. 撤销最近一次提交（本地）

**症状**：刚 `commit` 完发现漏文件/信息写错/根本不该提交。

**三种模式**

```bash
git reset --soft HEAD~1    # 撤销 commit，改动留在暂存区（最安全，推荐）
git reset --mixed HEAD~1   # 撤销 commit 和 add，改动留在工作区（默认）
git reset --hard HEAD~1    # 连改动一起删（危险，先确认没有未保存内容）
```

**已经 push 了怎么办**

```bash
git revert <sha>           # 生成一个反向提交，历史不改写
```

**诊断是否已 push**

```bash
git branch -r --contains <sha>
```

**预防**：提交前 `git diff --cached`；重要分支开启保护，禁止 force push。

---

## 4. 修改已推送的提交信息 / 补文件（amend）

**症状**：`git commit --amend` 后 push 被拒；或想改上一条提交信息。

**修复（仅限自己的分支）**

```bash
git commit --amend -m "feat: correct message"
git push --force-with-lease origin feature/x
```

`--force-with-lease` 比 `--force` 安全：如果远端在你 fetch 后又被别人更新，它会拒绝覆盖。

**共享分支**：不要 amend/force；用 `git revert` 或追加一个 `docs: fix typo` 提交。

**预防**：PR 分支合并前整理提交（interactive rebase）；主分支保护 + 禁止 force push。

## 5. 合并冲突

**症状**

```
CONFLICT (content): Merge conflict in config.txt
Automatic merge failed; fix conflicts and then commit the result.
```

完整实录见 [`../证据/conflict-drill.txt`](../证据/conflict-drill.txt)。

**诊断**

```bash
git status --short          # UU = both modified
git diff --name-only --diff-filter=U
```

**修复**

```bash
# 1) 打开冲突文件，处理 <<<<<<< ======= >>>>>>>
# 2) 只保留想要的内容，删除标记
# 3) 标记已解决
git add config.txt

# 4) 完成合并
git commit                  # 使用默认 merge message，或 -m 自定义

# 想放弃这次合并：
git merge --abort
```

**理解冲突标记**

```
<<<<<<< HEAD
port=8081          # 当前分支（ours）
=======
port=9090          # 被合并分支（theirs）
>>>>>>> feature/port
```

**预防**：小步合并、频繁 rebase 功能分支；避免多人同时改同一段配置；格式化提交单独放，减少噪音。

## 6. push 被拒：non-fast-forward

**症状**

```
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs
```

**根因**：远端有你本地没有的提交（别人推了，或你在网页上改过）。

**修复**

```bash
git fetch origin
git log --oneline HEAD..origin/main    # 看远端多了什么
git rebase origin/main                 # 或 git merge origin/main
# 解决冲突、跑测试
git push origin main
```

**不要**直接 `git push --force`——会覆盖别人的提交。

**预防**：push 前先 `git pull --rebase`；主分支开启保护。

## 7. 误提交大文件 / 密钥

**症状**：`git push` 报 `GH001: Large files detected`，或提交里出现 `.env`、`id_rsa`、token。

**处理顺序（很重要）**

1. **先轮换密钥**：只要 push 过，就当作已泄露；撤销/重置 token、改密码。
2. **从当前提交移除**：

   ```bash
   git rm --cached .env
   echo ".env" >> .gitignore
   git commit -m "chore: stop tracking .env"
   ```

3. **如果已经 push，且必须从历史抹掉**：

   ```bash
   # 备份
   git branch backup/before-filter
   # 用 git-filter-repo（推荐，需单独安装）
   git filter-repo --path .env --invert-paths
   git push --force --all
   git push --force --tags
   ```

   `filter-repo` 会重写所有提交哈希，协作者必须重新 clone。

**预防**：`.gitignore` 先于第一次提交；pre-commit 钩子跑 `gitleaks`/`detect-secrets`；大文件用 LFS 或 Release。

## 8. `.gitignore` 不生效

**症状**：把文件加进 `.gitignore`，`git status` 还是显示它。

**根因**：文件已经被跟踪；`.gitignore` 只影响**未跟踪**文件。

**修复**

```bash
git rm --cached path/to/file        # 保留本地文件，停止跟踪
git commit -m "chore: untrack generated file"
```

**诊断为什么被忽略/没被忽略**

```bash
git check-ignore -v path/to/file
git status --ignored --short
```

**预防**：项目初始化时就写 `.gitignore`；生成物目录（`dist/`、`.venv/`、`__pycache__/`）先忽略再创建。

## 9. 换行符导致整文件 diff（CRLF/LF）

**症状**：只改了一行，`git diff` 显示整个文件都变了；Windows 与 macOS 协作时常见。

**诊断**

```bash
git config --get core.autocrlf
file path/to/file
git diff --ignore-space-at-eol --stat
```

**修复**

```bash
# 统一由 .gitattributes 管理（推荐）
printf '* text=auto eol=lf\n*.png binary\n' > .gitattributes
git add --renormalize .
git commit -m "chore: normalize line endings"
```

**预防**：仓库根放 `.gitattributes`；Windows 上 `core.autocrlf=false`，让 `.gitattributes` 说话；编辑器统一 LF。

## 10. 误删分支 / 提交「丢了」

**症状**：`git branch -D feature/x` 后发现有价值提交；或 rebase 后历史不对。

**诊断**

```bash
git reflog -30
git fsck --lost-found
```

**修复**

```bash
# reflog 里找到提交哈希后
git switch -c rescue/feature-x <sha>
# 或把分支指针直接移回去
git branch feature/x <sha>
```

**注意**：reflog 默认保留 90 天；`git gc --prune=now` 会清掉不可达对象。

**预防**：删分支前 `git log --oneline main..feature/x` 确认没有独有提交；用 `git branch -d`（安全删除）而不是 `-D`。

## 11. clone 太慢 / 仓库太大

**症状**：`git clone` 几十分钟，或磁盘不够。

**修复**

```bash
# 只要最新代码
git clone --depth 1 <url>

# 只要部分目录（Git 2.25+）
git clone --filter=blob:none --sparse <url>
cd repo
git sparse-checkout set path/to/dir

# 只要某个 tag
git clone --depth 1 --branch v3.2.4 <url>
```

**代价**：浅克隆没有完整历史，`git log`、`git blame`、`git bisect` 会受限；需要时 `git fetch --unshallow`。

**预防**：仓库不要把构建产物/大素材提交进去；用 Release Assets 或 LFS。

## 12. 认证失败：401 / 403 / Permission denied

**症状**

```
remote: Permission to user/repo.git denied to other-user.
fatal: unable to access '...': The requested URL returned error: 403
```

或 `gh: Bad credentials (HTTP 401)`。

**诊断**

```bash
git remote -v
gh auth status
git config --get credential.helper
```

**根因**

- HTTPS 用了错误账号的缓存凭据；
- PAT 过期 / 没有 `repo` 权限；
- SSH key 没加到 GitHub，或用了另一个 key；
- 公司代理拦截。

**修复**

```bash
# 清理错误凭据（标准 git credential 协议；GCM 会同步删除存储项）
printf "protocol=https\nhost=github.com\n\n" | git credential reject

# 或者用 Git Credential Manager 查看/登出账号
git credential-manager github list
git credential-manager github logout <account>

# 管理 Windows 凭据：控制面板 → 凭据管理器 → Windows 凭据

# 改用 SSH
git remote set-url origin git@github.com:user/repo.git
ssh -T git@github.com

# 检查 token 权限（classic PAT 需要 repo；fine-grained 需要 Contents: Read/Write）
```

**预防**：一台机器只用一个 GitHub 账号；PAT 设置过期提醒；优先 SSH + `~/.ssh/config`。

## 13. Windows 上只改大小写，Git 不识别

**症状**：把 `Readme.md` 改成 `README.md`，`git status` 没变化。

**根因**：Windows 文件系统大小写不敏感，Git 默认也不区分。

**修复**

```bash
git mv Readme.md temp.md
git mv temp.md README.md
git commit -m "docs: rename Readme.md to README.md"
```

或

```bash
git config core.ignorecase false
```

（改配置后注意：可能突然出现大量「重命名」状态，先确认再提交。）

**预防**：文件名从第一天就用目标大小写；跨平台项目在 CI 里加 Linux 构建，能暴露大小写问题。

## 14. 合并后想撤销（已 push）

**症状**：merge commit 已进主分支，发现合并错了。

**修复**

```bash
# 找到 merge commit
git log --merges --oneline -5

# 撤销合并，保留主分支历史（-m 1 表示保留第一父提交，即主分支）
git revert -m 1 <merge-sha>
git push origin main
```

**注意**：revert 之后再想「重新合并」同一个分支，Git 可能认为已合并过；需要 `git revert <revert-sha>` 或重新开分支。

**预防**：合并前跑全量测试；用 PR + 保护分支，让合并动作可审计。

## 附：故障速查表

| 症状 | 最可能的命令 |
| --- | --- |
| 不知道自己在哪 | `git status -sb` |
| 提交丢了 | `git reflog` |
| 改错分支 | `git switch -c` + `git reset --soft` |
| push 被拒 | `git fetch` + `git rebase origin/main` |
| 冲突 | `git status` → 编辑 → `git add` → `git commit` |
| 想撤销已推送提交 | `git revert <sha>` |
| 大文件进历史 | `git filter-repo`（先备份、先轮换密钥） |
| 忽略不生效 | `git rm --cached` |
| 换行符噪音 | `.gitattributes` + `git add --renormalize .` |
| 认证失败 | `gh auth status` / `git credential reject` |

> 最后一条经验：**先诊断，再动手**。`git status`、`git log`、`git reflog` 三句话能解释绝大多数「灵异事件」；在没弄清状态前执行 `reset --hard` 或 `push --force`，才是真正的故障来源。
