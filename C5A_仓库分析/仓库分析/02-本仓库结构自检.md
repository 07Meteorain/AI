## 0. 一句话结论

这是一个**课程作业归档仓库**，不是单一产品仓库：99 个提交、1,246 个文件、204,846 行文本、7 个各自独立的测试目录，11 个挑战目录平铺在根目录。它的主要问题不是「代码写得差」，而是**归档型仓库缺少产品型仓库的治理设施**：没有根级 LICENSE / CONTRIBUTING / CHANGELOG，二进制资产偏重（单文件 47.8 MiB），提交信息偏长且不规范，且几乎没有分支/合并痕迹。

健康度 **29/100** 要用对语境：这套评分是为「产品仓库」设计的，对「作业归档」会低估（例如根目录没有 `tests/`，但各交付目录其实有 7 个测试目录）。**分数本身不是结论，缺口清单才是。**

## 2. 五个具体发现

### 发现 1：二进制资产是最大的工程负担

| 文件 | 大小 | 问题 |
| --- | ---: | --- |
| `C4C_交付/homework-solver/tools/tectonic.exe` | 47.8 MiB | 可执行文件直接进 Git 历史 |
| `C4C_交付/Meteorain_C4C_homework-solver.skill` | 18.6 MiB | 打包产物 |
| `C1_交付/source_materials/CS146S_offline/pdfs/how-openai-uses-codex.pdf` | 7.7 MiB | 原始素材 |
| `C1_交付/source_materials/Vibe_Coding_Playbook.pdf` | 7.6 MiB | 原始素材 |
| `C1_交付/source_materials/CS146S_offline/pdfs/how-anthropic-uses-claude-code.pdf` | 5.9 MiB | 原始素材 |

事实：

- 工作区总大小 **112.1 MB**，`.git` 打包后 **65.01 MiB**；
- `.gitattributes` 把 `.pdf`、`.skill`、`.png` 标为 binary，但**没有为 `*.exe` 写规则**（Git 仍会按内容识别为二进制，但缺少显式声明）；
- 仓库没有使用 Git LFS（`git lfs` 未配置），也没有把大文件放到 Release Assets。

影响：

- 新协作者 `git clone` 成本高（65 MB 包 + 112 MB 工作区）；
- 每次改一个 47.8 MB 的 exe，Git 都会存一份新对象，历史只增不减；
- GitHub 对单文件 >50 MB 会警告、>100 MB 会拒绝；当前 47.8 MB 已接近警告线。

**判断**：如果这些二进制是「运行必需」，应迁移到 Git LFS 或 Release；如果是「构建产物」，应加入 `.gitignore` 并给出构建脚本。**不要用「删掉再提交」解决——历史里的对象还在**，需要用 `git filter-repo` 重写历史（不可逆，需先备份）。

### 发现 2：根级治理文件缺失，但这是「归档仓库」的通病

| 检查项 | 状态 | 说明 |
| --- | --- | --- |
| README | ✅ | 25 KB，索引了 10 个挑战；`C2G_ParameterGolf` 未进索引（见发现 4） |
| LICENSE | ❌ | 未声明许可证；他人无法合法复用 |
| CONTRIBUTING | ❌ | 没有贡献/复跑约定 |
| CHANGELOG | ❌ | 只有 `C5_交付/CHANGELOG.md`，非仓库级 |
| CODE_OF_CONDUCT | ❌ | 个人仓库可省，但公开展示时建议有 |
| SECURITY | ❌ | 无漏洞披露渠道 |
| Issue 模板 | ❌ | 无 |
| Dependabot | ❌ | 无依赖自动更新 |
| CI | ✅ | 仅 `.github/workflows/c5-promptlint.yml`，只覆盖 C5 |
| 根级测试 | ❌ | 7 个测试目录分散在各交付内 |

健康度扣分主要来自这里。但要区分：

- **对产品仓库**：LICENSE、CONTRIBUTING、CHANGELOG 是「可被外部使用」的前提，缺一不可；
- **对个人作业归档**：LICENSE 仍然重要（否则默认保留所有权利），CONTRIBUTING/COC 可以简化，但不能没有「如何复跑」的说明。

### 发现 3：提交信息偏长，且缺少机器可读的类型

| 指标 | 数值 | 评价 |
| --- | ---: | --- |
| 平均主题长度 | 63.8 字符 | 偏长（建议 ≤ 50，硬上限 72） |
| 超过 72 字符 | 34.3% | 在 GitHub 列表/`git log --oneline` 中会被截断 |
| 带正文 | 17.2% | 复杂改动缺少「为什么」 |
| Conventional Commits | 10 条（10.1%） | 仅 `docs/feat/ci/fix`，未形成规范 |
| merge commit | 0 | 没有分支/PR 合并痕迹，全部直接推 master |

例子（真实历史）：

```
C5：promptlint 的静态检查器（12 条规则 + 81 项测试 + SARIF/基线）
C4C：引用真伪审计器（citation-truth-auditor）
C2G 最终版：E7 3-seed 验证完成 (1.73955, t=-11.05): THIRD_PARTY_NOTICES.md
```

这些信息本身有价值，但把「挑战编号 + 主题 + 细节 + 文件名」全塞进一行，会让历史难以扫描。更好的写法是：

```
feat(c5): add promptlint static checker

- 12 rules (PL001–PL012), 81 tests
- SARIF 2.1.0 output for GitHub Code Scanning
```

### 发现 4：仓库是「内容归档」，不是「可构建项目」

- 67.4% 的文件在 `C1_交付`（课程翻译 + 原始素材）；
- 763 个 JSON、183 个 Markdown，真正的 Python 只有 103 个文件；
- 7 个测试目录各自为政：

```
C2A_C9_交付/tests
C3C_交付/tests
C3_交付/linter/tests
C4A_交付/tests
C4C_交付/homework-solver/tests
C4D_交付/姓名_C4D_agent-skill/tests
C5_交付/tests
```

这意味着：

- 根目录 `python -m unittest discover` 不会自动覆盖所有测试；
- 新人要读 11 个目录里的 README 才知道每个挑战怎么跑；根 README 的索引还漏了 `C2G_ParameterGolf`（仓库里存在，但目录表没有它）；
- 仓库级「一键验证」不存在。

**判断**：归档仓库不必强行合并成一个包，但应该有一个**根级验收入口**（Makefile / `scripts/verify_all.py`），按目录依次调用各挑战的测试。这比把所有代码塞进一个 `src/` 更符合当前用途。

### 发现 5：没有分支模型，所有改动直接进 master

- 99 个提交、0 个 merge commit、1 个本地分支；
- 没有 PR 记录，也没有「功能分支 → 合并」的痕迹；
- 只有一个标签 `c5-v1.0.0`。

对个人仓库，这不算错误——trunk-based 也可以工作。但 C5A 的目标之一就是「规范使用 commit/branch/PR」，所以本次交付特意补上了这一段（见 [`../Git实战/01-分支与PR实战.md`](../Git实战/01-分支与PR实战.md)）。

## 4. 改进清单（按优先级）

### P0：本周可做，收益最大

1. **处理大二进制**
   - 短期：把 `tectonic.exe`、`.skill` 移到 GitHub Release Assets，仓库里只留下载脚本与 SHA256；
   - 中期：启用 Git LFS（`.gitattributes` 加 `*.exe filter=lfs ...`）；
   - 长期：如确需瘦身，用 `git filter-repo --path ... --invert-paths` 重写历史（先备份、通知协作者重新克隆）。
2. **补根级许可证与贡献说明**
   - `LICENSE`（如 MIT/Apache-2.0/CC-BY-4.0，按内容性质选择；课程原文版权不归你，需在 README 标明）；
   - `CONTRIBUTING.md`：如何复跑、如何提 PR、提交信息格式；
   - `SECURITY.md`：漏洞/敏感信息如何私下报告。
3. **提交信息规范**
   - 采用 `type(scope): subject`，主题 ≤ 72 字符；
   - 复杂改动写正文：动机、方案、验证；
   - 可用 `commitlint` 或一个 20 行的 `commit-msg` hook 兜底。

### P1：一个月内

4. **根级验收入口**
   - `Makefile` 或 `scripts/verify_all.py`：按目录跑 7 套测试，输出汇总表；
   - CI 增加一条 `verify-all` 工作流，只在根目录/工具目录变更时触发。
5. **发布节奏**
   - 每个挑战交付打一个 tag（`c1-v1.0.0`、`c2-v1.0.0`…），配 Release Notes；
   - 现有 `c5-v1.0.0` 可作为模板。
6. **Issue/PR 模板**
   - 作业仓库可以用很轻的模板：背景、改动、验证命令、截图/输出。

### P2：有空再做

## 附：健康度 29 分的正确读法

这套评分（见 `工具/repo_inspector.py` 的 `compute_health`）是**产品仓库视角**：

- 「根目录有 tests/」得 8 分——本仓库没有，但子目录有 7 套测试，所以这 8 分丢得冤；
- 「LICENSE / CONTRIBUTING / CHANGELOG」各占 4–5 分——对公开仓库确实必要；
- 「近期活跃」得 8 分——本仓库最近 1 天有提交，拿到满分；
- 「分支卫生」得 7 分——只有 1 个远程分支，满分。

所以 29 分不等于「这个仓库很烂」，而是「它离一个可被外部复用的产品仓库还差哪些件」。**评分是缺口探测器，不是道德判决。** 我在 [`../复盘/AAR复盘.md`](../复盘/AAR复盘.md) 里也把「启发式评分误伤归档仓库」列为本次的一次失败经验。
