# 读仓库方法论：从「能跑」到「敢改」

> 这份文档回答一个问题：**拿到一个陌生 GitHub 仓库，怎样在 30 分钟内建立可行动的理解，而不是从第一个源文件开始读。**
> 它来自本次对 [`httpie/cli`](https://github.com/httpie/cli) 与 [`07Meteorain/AI`](https://github.com/07Meteorain/AI) 的两次实战，命令与判断都可以复现。

---

## 0. 先分清三个问题

读仓库前，先明确你要回答哪一个：

| 问题 | 时间盒 | 产出 |
| --- | --- | --- |
| 它是什么？能不能用？ | 3 分钟 | 一句话定位 + 许可证 + 最近是否活跃 |
| 它怎么工作？我能不能改？ | 30 分钟 | 目录地图 + 入口 + 测试方式 + CI |
| 它为什么长这样？值不值得长期投入？ | 3 小时 | 历史脉络 + 关键决策 + 风险清单 |

**最常见的错误**：用「读代码」的方式回答第一个问题。第一个问题的答案在 README、LICENSE、Release 和目录结构里，不在 `src/core.py`。

---

## 1. 三层阅读法

### L1：3 分钟，判断「要不要继续读」

按顺序看五样东西：

1. **README 第一屏**：一句话定位、安装命令、示例；
2. **LICENSE**：没有许可证 = 默认保留所有权利，不能合法复用；
3. **最近 Release / 最近提交**：是否活跃、版本节奏；
4. **根目录**：`src/`、`tests/`、`docs/`、`.github/` 是否存在；
5. **CONTRIBUTING**：是否欢迎外部贡献、有什么硬性要求。

**通过标准**：能用一句话说出「它解决什么问题、给谁用、还能不能维护」。说不出来，先别 clone。

### L2：30 分钟，建立「可操作的地图」

1. **包管理清单**：`pyproject.toml` / `setup.cfg` / `package.json` / `Cargo.toml` / `go.mod`；
2. **入口**：`console_scripts`、`bin/`、`main`、`__main__.py`、路由表；
3. **目录职责**：每个顶层目录用一句话概括，写下来；
4. **测试**：测试框架、测试目录、如何跑单个测试；
5. **CI**：跑什么、在哪些平台、哪些检查是必须的；
6. **依赖方向**：谁 import 谁，有没有循环。

**通过标准**：能画出「用户输入 → 入口 → 核心逻辑 → 输出」的 5 步链路，并指出改一个功能要动哪几个目录。

### L3：3 小时，理解「为什么」和「风险」

1. **历史**：`git log --graph --oneline --decorate` 看分支/合并；按年份看提交量；
2. **关键决策**：`git log -S"关键词"` 找某段代码何时引入；读相关 Issue/PR；
3. **热点**：哪些文件被改得最多（churn），通常也是 bug/复杂度集中地；
4. **人**：`git shortlog -sn`，看总线因子；
5. **治理**：Issue 模板、PR 模板、CODEOWNERS、发布流程、安全政策；
6. **风险**：依赖是否 EOL、CI 是否长期红、分支是否堆积。

**通过标准**：能说出「这个项目最脆弱的三个点」和「如果我提 PR，最可能被卡在哪」。

## 2. 六步检查清单（带命令）

### 第 1 步：定位与许可证

```bash
head -40 README.md
ls LICENSE* COPYING* 2>/dev/null
```

| 看到 | 判断 |
| --- | --- |
| 一句话 + 安装 + 示例 | 正常 |
| 只有徽章和截图 | 文档偏营销，去 docs/ 找细节 |
| 没有 LICENSE | 不能直接复用代码；只能读 |
| README 与代码明显不符 | 维护停滞或分支错位 |

### 第 2 步：构建清单与入口

```bash
ls pyproject.toml setup.py setup.cfg package.json Cargo.toml go.mod 2>/dev/null
grep -n "entry_points\|console_scripts\|\[project.scripts\]" setup.cfg pyproject.toml 2>/dev/null
```

`httpie` 的例子：

```ini
[options.entry_points]
console_scripts =
    http = httpie.__main__:main
    https = httpie.__main__:main
    httpie = httpie.manager.__main__:main
```

一行配置就告诉你：`http` 和 `https` 是同一个入口，`httpie` 是另一个管理器入口。**先读入口，再读实现**，比从目录树猜快得多。

### 第 3 步：目录职责

```bash
# 只看两层，避免被几千个文件淹没
find . -maxdepth 2 -type d -not -path './.git*' | sort
```

给每个目录写一句「它负责什么」。写不出来，说明你还没读懂；不要假装读懂。

### 第 4 步：测试怎么跑

```bash
grep -n "testpaths\|pytest\|unittest\|jest\|vitest" setup.cfg pyproject.toml package.json Makefile 2>/dev/null
ls tests test 2>/dev/null | head
```

| 信号 | 含义 |
| --- | --- |
| 有 `tests/` 且有 CI 跑测试 | 基本可信 |
| 测试很多但 CI 不跑 | 测试可能已腐烂 |
| 只有 `test_*.py` 没有断言 | 假测试 |
| `xfail_strict = True` | 对「已知失败」有治理，加分 |

### 第 5 步：CI 与发布

```bash
ls .github/workflows/
grep -n "on:\|branches:\|paths:\|matrix:" .github/workflows/*.yml
```

**能推断的**：支持哪些 OS/Python、哪些检查是门禁、发布是否自动化。
**不能推断的**：覆盖率阈值（除非看到 `--cov-fail-under`）、代码质量（CI 绿不等于代码好）、真实使用量。

### 第 6 步：历史与协作

```bash
git log --graph --oneline --decorate -30
git shortlog -sn --all | head -10
git log --merges --oneline | wc -l
git log --format=%s | grep -cE '\(#[0-9]+\)$'
```

| 图形 | 解读 |
| --- | --- |
| 大量 `Merge pull request` | 使用 GitHub PR + merge commit |
| 大量 `(#123)` 结尾、无 merge | squash/rebase 合并 |
| 一条直线 | 直接推 master，或单人项目 |
| 分支线长期不合并 | 分支堆积/实验未收尾 |

## 3. 目录结构的四种常见形态

| 形态 | 识别特征 | 读法 |
| --- | --- | --- |
| **src layout** | `src/pkg/`、`tests/` 与源码分离 | 先看 `pyproject.toml` 的 packages 配置 |
| **flat package** | 根目录直接 `pkg/`（httpie 就是） | 入口 + `__main__.py` 优先 |
| **monorepo** | 多个 `packages/`、`apps/`、按挑战/产品分区 | 先读根 README 的索引，再读每个子项目的 README |
| **framework convention** | `app/`、`pages/`、`routes/`、`migrations/` | 直接套框架的约定，不要逐文件读 |

**判别技巧**：看 `git ls-files | awk -F/ '{print $1}' | sort | uniq -c | sort -rn`，文件最多的顶层目录通常就是主战场；但**文件多不等于重要**（本仓库的 `C1_交付` 占 67.4%，核心却是各挑战的 Python 工具）。

## 4. 读提交历史的四个动作

### 4.1 看形状

```bash
git log --graph --oneline --decorate --all -40
```

判断：主干是否稳定、分支是否短命、合并是否规范。

### 4.2 看节奏

```bash
git log --format=%ad --date=format:%Y | sort | uniq -c
```

提交量骤降的年份，往往对应维护者换人、项目转向或进入维护期。httpie 的曲线（2012 年 309 → 2023 年 36 → 2024 年 23）就很说明问题。

### 4.3 看单文件演化

```bash
git log --follow --oneline -- path/to/file
git log -S"specific_symbol" --oneline -- path/
git blame -L 40,60 path/to/file
```

`-S`（pickaxe）找「某段字符串何时被引入/删除」，是理解设计决策最快的工具之一。

### 4.4 看谁在维护

```bash
git shortlog -sn --all
```

如果一个人占 >60%，就要把「总线因子」写进风险清单。注意同名不同写法（httpie 的 Jakub 有三种拼写），统计时要合并。

## 5. 五个危险信号

1. **没有 LICENSE**：默认不可复用；公司使用尤其要小心。
2. **测试目录存在但 CI 不跑**：测试可能早已失效。
3. **超过一年无提交且未归档**：依赖会过期，安全问题无人修。
4. **单个文件 >10 MB 或大量二进制**：clone 慢、历史膨胀、diff 不可读。
5. **分支长期不合并 + 无 PR 模板**：协作流程不清晰，贡献者容易做无用功。

> 危险信号不是「一票否决」，而是「继续投入前必须先解释清楚」的问题。

## 6. 从读到改：第一个 PR 的最短路径

1. **找入口**：Issue 里的 `good first issue`、文档 typo、测试补充；
2. **先复现**：在本地跑失败用例，确认不是环境问题；
3. **读 CONTRIBUTING**：分支命名、提交格式、是否要求 CHANGELOG；
4. **小步提交**：一个提交只做一件事；先测试后实现；
5. **本地全量验证**：跑测试 + 风格检查；
6. **PR 描述**：背景、改动、验证命令、风险；截图/日志比形容词有用；
7. **响应 review**：把讨论结论写回代码/文档，不要只留在评论区。

## 7. 命令速查表

| 目的 | 命令 |
| --- | --- |
| 看仓库概览 | `git log --graph --oneline --decorate -30` |
| 看文件树（两层） | `find . -maxdepth 2 -type d -not -path './.git*' \| sort` |
| 看文件类型分布 | `git ls-files \| sed 's/.*\.//' \| sort \| uniq -c \| sort -rn` |
| 看作者 | `git shortlog -sn --all` |
| 看某文件历史 | `git log --follow --oneline -- <file>` |
| 找字符串引入 | `git log -S"<text>" --oneline` |
| 看某行归属 | `git blame -L <start>,<end> <file>` |
| 看 merge 数 | `git log --merges --oneline \| wc -l` |
| 看 PR 合并痕迹 | `git log --format=%s \| grep -cE '\(#[0-9]+\)$'` |
| 看 tag | `git tag --sort=-creatordate \| head` |
| 看仓库大小 | `git count-objects -vH` |
| 看大文件 | `git ls-files -z \| xargs -0 ls -lS \| head` |
| 看未跟踪/忽略 | `git status --porcelain --ignored` |
| 浅克隆 | `git clone --depth 1 <url>` |
| 只取部分目录 | `git clone --filter=blob:none --sparse <url>` + `git sparse-checkout set <dir>` |

> Windows PowerShell 下把 `sed/awk/grep` 换成 `Select-String`/`ForEach-Object`，或直接用 Git Bash。本交付的分析器已经把这些统计封装成跨平台 Python。

## 8. 30 分钟练习（用 httpie 做样本）

按顺序完成，每步写一句话结论：

1. 读 README 第一屏，写出「它是什么、给谁用」；
2. 打开 `setup.cfg`，写出三个命令入口和 Python 版本要求；
3. 画出 `cli → core/client → output → plugins` 的依赖图；
4. 找到测试怎么跑，跑一个测试文件；
5. 读 `.github/workflows/tests.yml`，写出矩阵维度；
6. 用 `git shortlog -sn` 判断总线因子；
7. 用 `git tag` 看最近三个版本的时间间隔；
8. 写出「如果我提 PR，最可能被要求补什么」。

**参考答案**在 [`01-httpie-cli-深度分析.md`](01-httpie-cli-深度分析.md)，但建议先自己做一遍，再对照。

## 9. 工具能替你做什么，不能做什么

本交付的 `工具/repo_inspector.py` 自动完成：

- 规模、语言、目录、最大文件；
- 提交数、作者、年份、Conventional Commits 占比、merge 数；
- 治理文件清单、过期分支、健康度评分；
- 变更热点、测试联动比例。

它**不能**替你判断：

- 代码是否正确、设计是否合理；
- 测试是否真的有效（只统计行数/文件数）；
- 社区是否友好、维护者是否响应；
- 许可证是否适合你的使用场景（只能告诉你「有没有」）。

**正确用法**：用工具拿到可复核的「体检数据」，再用人工阅读解释「为什么」。两者缺一不可。

## 10. 一页纸总结

```
先问目的 → 再读 README/LICENSE/Release
→ 找入口（entry points / main）
→ 画目录职责与依赖方向
→ 跑测试、看 CI
→ 看历史形状、节奏、作者
→ 列风险与可改点
→ 最后才读核心实现
```

读仓库的目标不是「读完」，而是**在可接受的时间内做出可行动的判断**：能不能用、要不要改、从哪下手、风险在哪。
