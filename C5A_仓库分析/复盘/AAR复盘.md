# AAR 复盘：C5A 仓库分析交付

> **AAR** = After Action Review（事后回顾）。本文回答四个问题：**预期是什么、实际发生了什么、为什么、下次怎么做。**
> 写作时间：2026-11-10；交付快照与 PR 状态见 [`../Git实战/01-分支与PR实战.md`](../Git实战/01-分支与PR实战.md)。

---

## 1. 预期：什么算「完成」

开工时我把「完成」定义成五条可验收标准，而不是「文件写完」：

| # | 预期 | 验收方式 |
| --- | --- | --- |
| 1 | 三件必需交付物齐全：仓库分析、README、AI 日志 | 逐项对照 `挑战说明.md` |
| 2 | 分析有真实对象、真实数字，能复现 | 固定 commit + 原生命令复核 |
| 3 | 工具可运行、有测试、零依赖 | `python -m unittest` 全绿 |
| 4 | 展示 Git 工作流：分支、提交、PR、合并、tag | `git log --graph` + PR 链接 |
| 5 | 不触发三个红旗项 | 提交说明逐条反证 |

**目标分数**：不设「必须 100」——评分是评审的事；我设的是「每个维度都有证据，且不装懂」。

## 2. 实际：产出了什么

### 2.1 交付物

| 类别 | 文件 | 规模 |
| --- | --- | --- |
| 总览 | `README.md`、`提交说明.md` | 2 篇 |
| 仓库分析 | `01-httpie-cli-深度分析.md`、`02-本仓库结构自检.md`、`03-读仓库方法论.md` | 3 篇 |
| 工具 | `repo_inspector.py` + 15 项 unittest | 约 600 行 + 约 300 行测试 |
| Git 实战 | 分支/PR 记录、14 个排错场景 | 2 篇 |
| AI 记录 | `AI使用日志.md` | 1 篇（8 轮） |
| 复盘 | `AAR复盘.md` | 本文件 |
| 证据 | 2 份量化报告 + JSON、测试输出、冲突演练、提交拓扑 | 7 个文件 |

### 2.2 数字结果

| 对象 | 提交 | 文件 | 文本行 | 测试/源码 | 健康度 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `httpie/cli` | 1,797 | 265 | 28,276 | 0.56 | 77/100 |
| `07Meteorain/AI` | 99 | 1,246 | 204,846 | 0.15 | 29/100 |

### 2.3 时间与返工

- 从读题到交付约 1 小时（不含推送等待）；
- 12 次明确返工（见 AI 日志第 5 节），其中 4 次是**指标口径错误**，3 次是**文档事实错误**，2 次是**测试/环境问题**，3 次是**认证/流程问题**；
- 工具从 v0 到 v1 改了 4 个指标 bug，健康度从 72 修正到 77。

### 2.4 超出预期的地方

1. **没有只做「一次分析」**：额外做了本仓库自检与方法论，形成「他人仓库 / 自己仓库 / 通用方法」三角。
2. **工具不是玩具**：15 项测试覆盖解析、评分边界、临时仓库、过期分支、错误路径。
3. **真实冲突演练**：不是抄教程，而是在临时仓库制造冲突、解决、保存实录。
4. **诚实边界**：明确写出「没有真实用户多轮反馈」「健康度是启发式」，没有为了评分编造。

### 2.5 没达到预期的地方

1. **分析深度受时间限制**：httpie 只精读了入口、架构、测试、CI 与治理，没有逐个模块读实现；`output/` 与 `client.py` 只到「职责级」。
2. **没有真实 Issue/PR 交互**：PR 是自建自合，没有经历维护者 review，无法验证「社区沟通」能力。
3. **健康度模型对归档仓库不公平**：29 分低估了测试分布，虽在文档中解释，但模型本身没修。
4. **AAR 写于外部评审之前**：复盘质量最终要由评审判断，自评只能覆盖「过程」。

## 3. 为什么：做对了什么，做错了什么

### 3.1 做对的五件事

| # | 做法 | 为什么有效 | 证据 |
| --- | --- | --- | --- |
| 1 | 先读题、做交付矩阵 | 避免「写了很多但漏了必需物」 | `提交说明.md` 对照表 |
| 2 | 指标先定义口径，再写代码 | 发现 4 个 bug 时能快速判断是「实现错」还是「定义错」 | AI 日志 R3 |
| 3 | 用原生命令交叉验证工具 | 防止「工具算错但报告很漂亮」 | `git rev-list/tag/log` 复核 |
| 4 | 把事实与判断分开 | 评审能独立复核，不被迫接受结论 | 每篇分析的「复现/边界」 |
| 5 | 失败也写进日志 | 体现真实迭代，而不是「一次成功」的幻觉 | AI 日志 12 条返工 |

### 3.2 做错的六件事

| # | 错误 | 影响 | 根因（表层） |
| --- | --- | --- | --- |
| 1 | `--reverse --max-count=1` 取首提交 | 仓库年龄错 12 年 | 凭直觉组合参数，没读语义 |
| 2 | `%(refname:short)` 判断分支类型 | 本地分支多 1 个 | 短名有歧义，展示用字段被拿来判断 |
| 3 | 测试文件匹配过宽 | 测试数 103 vs 37 | 没先定义「什么算测试」 |
| 4 | 健康度漏 `tags` 分支 | 50 个 tag 判缺失 | 新检查项没有覆盖所有 key |
| 5 | 文档写「13 个挑战目录」 | 事实错误 | 凭印象写数字，没数 |
| 6 | 根 README 最后才补索引 | 评审入口缺失 | 只关注新目录，没从「首页」看交付 |

### 3.3 两个「五个为什么」

#### 为什么会出现 4 个指标 bug？

1. 为什么首提交日期错？——用了 `--reverse --max-count=1`。
2. 为什么这么用？——想「反转后取一条」，但没意识到 `--max-count` 先于 `--reverse` 生效。
3. 为什么没发现？——本地测试仓库只有 2 个提交，且没有断言「首提交日期」。
4. 为什么测试没覆盖？——测试目标是「工具能跑」，不是「口径正确」。
5. 为什么目标定低了？——把「有测试」当成质量，而不是「测试能证明口径」。

**改进**：为每个关键指标加一个「已知答案」断言（fixture 仓库固定日期、固定分支、固定 tag），并做一次真实仓库的 golden test。

#### 为什么健康度对归档仓库只有 29 分？

1. 为什么低？——根目录没有 `tests/`、LICENSE、CONTRIBUTING，且提交信息超长。
2. 为什么按根目录判断？——模型假设「一个仓库 = 一个产品」，测试在根 `tests/`。
3. 为什么假设产品仓库？——参考的是 httpie 这类项目，没考虑「作业归档/多项目 monorepo」。
4. 为什么没提前发现？——先写模型，后跑第二个仓库；跑完才发现语义偏差。
5. 为什么没改模型？——时间有限，且改模型会改变已有报告；选择「保留分数 + 写清边界」。

**改进**：增加 `--profile product|archive|monorepo`，或至少把「根 tests」改成「任意层级 tests 目录存在即得分」；报告顶部标注适用类型。

## 4. 下次怎么做：可执行改进

| # | 改进 | 触发条件 | 验收标准 | 截止 |
| --- | --- | --- | --- | --- |
| 1 | 为 `repo_inspector` 加 golden-metric 测试 | 修改任何统计逻辑前 | 固定 fixture 的首提交日期/分支数/tag 数/测试文件数全部断言 | 下次迭代 |
| 2 | 增加 `--profile` 或「根 tests 递归检测」 | 分析非产品型仓库时 | 归档仓库的测试项不再误判为 0 | 下次迭代 |
| 3 | 文档数字必须带来源 | 写任何数字时 | 每个数字旁有命令或证据链接；完稿后随机抽 5 个复核 | 立即 |
| 4 | PR 从第一天开 draft | 开始改代码时 | 分支存在即 push，PR 描述随进度更新 | 下次 |
| 5 | 认证先验证再依赖 | 需要 push 前 | `gh api user` + 仓库 permissions 均成功 | 立即 |
| 6 | 用链接检查脚本 | 交付前 | 相对链接 0 失效（脚本输出为准） | 每次交付 |
| 7 | 写作为「数据 → 提纲 → 正文」 | 写分析前 | 先出事实表，再写判断；避免边写边猜 | 下次 |
| 8 | 保留一份「未做清单」 | 交付时 | README 有「已知限制」；AAR 有「没达到」 | 立即 |

## 5. 如果重做，只改三件事

1. **先工具、后写作，且先跑两个仓库再定指标**
   这次是「工具 → 报告 → 写作」，但指标口径在写作中还在改。重做会先把 httpie 与 AI 仓库都跑通、把差异解释清楚，再动笔。

2. **PR 从第一天开始，而不是最后**
   Draft PR 能提前暴露「根 README 索引」「CI 触发路径」这类集成问题；这次是最后才发现索引缺失。

3. **给「分析深度」设时间盒**
   例如：架构 60 分钟、测试/CI 30 分钟、历史/治理 30 分钟，到点就停，把剩余问题写进「未读清单」。这次在 httpie 的 `output/` 上花了过多时间，收益递减。

## 6. 可迁移的五条经验

1. **指标的口径比代码重要**：同一个「测试行数」，含不含 fixture 会差 30%。
2. **交叉验证是最便宜的质检**：工具算 + 原命令算，不一致就查。
3. **交付从评审入口倒推**：评审先看根 README，再看目录，再看证据；不是先看你的代码。
4. **失败要留痕**：返工记录比「一次成功」更能证明能力，也更能指导下一次。
5. **诚实是策略，不是道德**：写清「没做什么/不知道什么」，评审反而更信任你做的部分。

## 7. 评分维度自评

> 自评不是要分，而是检查「每个维度是否有证据」。最终以评审为准。

| 维度 | 分值 | 自评 | 依据 | 主要缺口 |
| --- | ---: | ---: | --- | --- |
| 基础掌握 | 25 | 22 | 分支/提交/PR/合并/tag 全流程；14 个排错场景；真实冲突演练 | 没有经历真实维护者 review；未演示 bisect/submodule |
| 产物完整性 | 20 | 19 | 三件套 + AAR；工具可运行；一键复现；证据齐全 | 分析只覆盖 2 个仓库 |
| 技术实现 | 15 | 14 | 零依赖、单文件、15 测试、固定快照、口径清晰 | 健康度模型未做 profile 区分 |
| AI 使用质量 | 20 | 18 | 8 轮、12 返工、prompt 迭代、工作流门禁、证据链 | 无真实用户多轮反馈 |
| 复盘质量 | 20 | 15 | 具体失败、五个为什么、8 条改进、重做方案 | 写于外部评审前，缺少「评审后」验证 |
| **合计** | **100** | **88** | — | — |

**为什么不是更高**：

- 基础掌握扣 3 分：PR 是自建自合，没有真实 review 往返；`git bisect`、submodule 只写在手册里，没有实操证据。
- 复盘扣 5 分：AAR 的改进项还没有经过下一轮验证，属于「计划」而非「已验证」。
- AI 使用扣 2 分：用户只给了一条指令，多轮是代理内部迭代；这在日志里已说明，不冒充人机协作。

**为什么不是更低**：

- 每个扣分点都有对应证据与改进项，不是「感觉」；
- 红旗项逐条有反证（见 `提交说明.md`）；
- 工具与报告可独立复跑，不依赖本次会话环境。

## 9. 一句话总结

这次交付最大的收获不是「写完了 C5A」，而是**建立了一条可复用的链路**：读题 → 定口径 → 写工具 → 交叉验证 → 写作 → 走 Git 流程 → 自审 → 复盘。链路里的每个环节都留下了一个下次可以复用的检查点；而这次踩过的 12 个坑，就是这条链路的「测试用例」。
