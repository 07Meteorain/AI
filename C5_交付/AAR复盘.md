# AAR 复盘 · C5 promptlint

> AAR = After Action Review。回答四个问题：**预期是什么、实际发生了什么、
> 为什么有差距、下次怎么改**。失败的部分不美化。

## 0 摘要

- 交付了一个可运行的零依赖 linter：12 条规则、81 项测试、text/JSON/SARIF 三种
  报告、基线机制、完整社区文件与 CI。
- 最大的教训不在代码，而在**环境**：本次会话的受限 shell 全部以
  `0xC0000142` 秒退，只能用完全权限绕过。**绕过不是修复**，根因至今未定位。
- 仍有 **2 个问题未解决**：F1（沙箱进程创建层故障的根因）与 F5（独立评审介入
  过晚，且第一次评审因范围过大超时）。

## 3 做对了什么

### 3.1 先定义「什么不做」

规则不是越多越好。用「可机械判定 / 可给位置 / 可写反例」三条筛掉 6 条语义规则，
是这次最正确的取舍。它让每条 finding 都能被用户复核，也让测试可以穷举。

### 3.2 示例即契约

`examples/` 不是装饰：`good/` 必须 0 问题，`bad/` 必须 12 问题，CI 用 grep 数
断言这两个数字。任何规则行为变化都会在这里或测试里暴露。

### 3.3 测试反馈足够快

81 项测试 0.2 秒跑完。这个速度让「改一行跑一次」成为可能，也是 3 轮返工能
快速收敛的原因。

### 3.4 把失败写进交付

第 0 轮的环境故障与 C3 交付里的 `case_0xC0000142` 是同一现象。我没有把它包装成
「已解决」，而是写进 AI日志与本节，并标注「绕过」。**读者能看到的失败，比看不到
的失败有价值。**

## 4 失败经验

### F1 · 受限 shell 全部 `0xC0000142`，根因未定位【未解决】

**现象**：所有 `pwsh -Command` 调用无输出、退出码 `3221225794`（`0xC0000142`，
`STATUS_DLL_INIT_FAILED`）；换命令、换工作目录、后台 job、子 agent 全部相同。

**证据**：
- 普通模式：`(no output) [exit code: 3221225794]`
- ACL 诊断脚本：`VERDICT=NOT_THIS_CLASS`（`writeDac=true`、`writeOwner=true`，
  0 个 package ACE）
- 提权单命令：`escalated-ok` + `Get-Location` 正常

**影响**：所有命令都要走 full-access 审批；如果审批不可用，整个交付无法完成。
**处理**：用 full-access 执行；在文档中不声称已修复。
**根因**：未定位。候选仍是「进程创建层被沙箱/安全软件干预」，但没有 Procmon、
没有事件日志，不能写成结论。

### F2 · 掩码里的 `U+2026` 在控制台显示为 `??`

**现象**：demo 输出 `sk-l??2b9d`、`1380??8000`。
**原因**：`mask_secret()` 与 `snippet()` 使用 `…`（U+2026），在 GBK 代码页的
控制台不可打印。
**修复**：全部替换为 ASCII `...`；重新生成 demo。
**教训**：linter 的默认输出必须能在**最窄的终端**里显示，不能假设 UTF-8。

### F3 · 用了 Python 3.10 才有的 `Path.write_text(newline=...)`

**现象**：`pyproject.toml` 声明 `>=3.9`，但 3 处写文件用了 3.10 新增参数。
**发现**：自查 `ast.parse(feature_version=(3,9))` 只能查语法，查不出 API 差异；
靠逐行检查 `write_text` 才发现。
**修复**：改为 `path.open("w", encoding="utf-8", newline="\n")`。
**教训**：**「本机 3.12 跑通」不等于「支持 3.9」**；只有 CI 矩阵是证据。

### F4 · 文档里的指标漂移（75 → 81，12 轮 → 10 轮）

**现象**：加完 CRLF 测试后，README/提交说明仍写 75 项；评审修复后测试到 81 项，
文档又落后一轮；AI日志原计划 12 轮，实际 10 轮。
**原因**：指标手写在多处文档，没有单一来源。
**修复**：交付前用脚本统计行数/测试数，逐处修正。
**教训**：能被自动计算的数字，不应该手写。

### F5 · 独立评审介入太晚，第一次评审还超时【部分未解决】

**现象**：代码与文档基本完成后才发起评审；第一个评审 agent 运行 40+ 分钟未返回，
被中断；第二个聚焦评审（只读 5 个文件）约 10 分钟返回 5 个缺陷。
**原因**：评审任务范围给得太大（整个包 + 测试 + 示例），且没有时间预算。
**处理**：改为「只读 5 个文件、最多 6 条问题」的聚焦评审。
**结果**：5 条全部属实并修复，其中「基线指纹缺少 occurrence 序数」正是第 2 轮
设计咨询提醒过、我当时没有做的那一条——说明评审不是形式，它抓到了我漏掉的代价。
**未解决**：无法量化「如果第 2 轮就评审」能少多少返工，本次没有对照实验；评审是
AI 对 AI，不能替代真实使用者。

## 5 根因分析

| 问题 | 直接原因 | 更深一层 | 系统性原因 |
| --- | --- | --- | --- |
| F1 | 沙箱进程创建失败 | 环境层干预（未证实） | 交付流程假设 shell 可用，没有备用执行路径 |
| F2 | 字符选择不当 | 默认输出假设 UTF-8 | 没有「最小终端」验收项 |
| F3 | 使用了 3.10 API | 本机 3.12 | 缺少 3.9 运行时，只做了语法检查 |
| F4 | 指标手写 | 无单一来源 | 文档与代码没有生成关系 |
| F5 | 评审范围过大 | 没有评审时间预算 | 评审被当成「最后一道工序」而不是并行活动 |

## 6 改进方案

| 优先级 | 改进 | 验收标准 |
| --- | --- | --- |
| P0 | 推送后确认 GitHub Actions 变绿；失败则修到绿，不把「本地通过」当完成 | Actions run 结论为 success（5 个 Python 版本 + SARIF） |
| P0 | 把环境故障写进提交说明的「诚实边界」，避免评审者误以为本次全程正常运行 | 文档可检索到 `0xC0000142` |
| P1 | 增加 `scripts/metrics.py`，从代码/测试生成 README 中的计数，或加测试断言文档数字 | 文档数字与脚本输出一致 |
| P1 | 建立 `tests/false_positives/` 语料库，收集 3 条真实误报并加回归测试 | 至少 3 条样本 + 对应测试 |
| P2 | 找 3 位外部使用者，只给 README，记录他们卡在哪一步 | 3 份试用记录；至少 1 条文档改进 |
| P2 | 评审提前到第 2 轮，限定「只读 N 个文件、M 分钟」 | 下一项目评审在第 2 轮发生，且不超过 10 分钟 |

## 7 重来会改的 3 件事

1. **先让 CI 空跑一次，再写代码。** 中文目录名、SARIF 上传路径、`working-directory`
   都是高风险点，本次直到最后才验证；早跑一次能把「能不能跑」和「写得对不对」
   分开。
2. **先写 `docs/rules.md` 的「误报边界」，再写规则。** PL009 的边界（只认 XML 标签）
   是后补的；如果先写边界，会早一点决定是否支持 Markdown 分隔符。
3. **第 2 轮就拉独立评审，并明确范围与时间预算。** 第一次评审因范围过大超时，
   等于浪费了一轮；聚焦评审 5 个文件的版本才有效。

## 8 诚实边界

1. **没有真实用户采用数据**：没有外部 issue、PR、下载量，所有指标来自本仓库。
2. **评审是 AI 对 AI**：独立评审由另一个 agent 完成，不是人类代码评审；它能发现
   逻辑问题，但不能替代真实使用者的反馈。
3. **CI 角色**：monorepo 只运行根目录 workflow；`C5_交付/.github/workflows/ci.yml`
   是为「抽出为独立仓库」准备的，本次的真实 CI 是根目录的
   `c5-promptlint.yml`，这一点在 README 与注释里写明。
4. **覆盖有限**：12 条规则只覆盖机器可判定的模板缺陷；prompt 的语义质量、
   事实性、安全性不在范围内。
5. **token 估算误差**：±30%，只能用于数量级判断。
