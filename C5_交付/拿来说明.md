# 拿来说明 · 5 个关键决策是怎么用 AI 做出来的

> 挑战要求「拿来说明」。这里给 5 个，选取标准是**真正改变过交付结果的决策**，
> 不是「我也用了 AI」的流水账。
>
> 每个决策都按同一结构写：**原始需求 → 实际 prompt → AI 产出 → 人工调整 →
> 前后对比 → 为什么**。
>
> 说明：本文引用的 AI 产出都来自本次会话里真实发出的两个设计咨询 prompt
> （原文见各节），不是事后编的。5 个决策里，**1 个是 AI 说服了我，2 个是我改写
> 或否掉了 AI 的建议，1 个是我先忽略了 AI 的提醒、后来被独立评审抓回来**。

---

## 1. 零依赖，还是 click + rich + PyYAML？——AI 说服了我

### 原始需求

做一个 prompt 模板检查器，要求「陌生人 clone 下来就能验证」。我的第一直觉是
`click` + `rich` + `PyYAML`：开发快、终端输出好看、YAML 不用自己写。

### 实际 prompt

> Stack: the tool must run after `git clone` with **NO pip install**, be
> CI-friendly, and possibly become an editor plugin later. Would you recommend
> click + rich + PyYAML, or the standard library only? Give your honest
> recommendation and the main tradeoff.

### AI 的产出

> Recommend **standard library only** (argparse, json, tomllib, pathlib,
> dataclasses), not click+rich+PyYAML. … each third-party dep adds pinning,
> supply-chain risk, and plugin-embedding friction, and rich's escape codes hurt
> CI logs. Main tradeoff: lose easy YAML configs and polished terminal UX (dev
> velocity now) vs. zero-friction install, reproducible CI, embeddability. If YAML
> is mandatory, make it an optional extra … never a hard dependency.

### 人工调整

我原本准备反驳，但它的论证和我自己的交付目标一致：这不是一个「尽快做出来」的
产品，而是一个「别人要能验证」的作业。我接受了标准库方案，并补了两条它没有
展开、但本项目真实存在的理由：

1. **front matter 只支持 `vars` 列表**，这个限制必须写进文档；如果引入 PyYAML，
   就等于承诺完整 YAML 语义，边界反而模糊。
2. **窄终端的输出风险**。AI 提到 `rich` 的转义码会伤害 CI 日志；本项目后来真的
   踩到了同类问题——掩码里的 `U+2026` 在 GBK 控制台显示成 `??`（见 AI日志第 3 轮）。
   这反过来证明「少一层输出库」是对的。

### 前后对比

| | click + rich + PyYAML | 零依赖（实际） |
| --- | --- | --- |
| 安装步骤 | `pip install`（3 个包 + 传递依赖） | 0 |
| 供应链/锁版本 | 3 个直接依赖 | 0 |
| YAML 能力 | 完整 | 只支持 `vars` 列表（已文档化） |
| 彩色/表格输出 | 有 | 无（text/JSON/SARIF 都可用） |
| 编辑器插件复用 | 需打包依赖 | 直接 import |
| 陌生人验证成本 | 先解决环境 | `python -m promptlint ...` |

### 为什么这么做

**这次是 AI 改变了我的第一版方案，而不是我否掉 AI。** 它给出的不是"标准库更好"
这种口号，而是**把每个依赖的成本拆到"锁版本、供应链、插件嵌入、CI 日志"四个
具体场景**，正好对应本项目的验收条件。接受一个有论证的反对意见，比坚持"我本来
就想这么写"更有价值。

## 2. 29 条规则，为什么最后只留 12 条？

### 原始需求

先让 AI 列出一份「prompt linter 应该检查什么」的完整清单，再决定做哪些。

### 实际 prompt

> Rules: list every check you would put in such a linter, as many as you can
> justify. For each: one line, and mark whether it can be judged from text alone
> (yes/no).

### AI 的产出

AI 给了 29 条，并明确分成两类：

- **可只凭文本判定（24 条）**：分隔符不匹配、孤立花括号、空占位符、非法变量名、
  同形字、混合模板方言（Jinja/f-string/`${}`）、占位符内空白不一致、使用未声明、
  声明未使用、重复声明冲突、控制块不平衡、未知过滤器、废弃语法、嵌套复杂度、
  引号/围栏不平衡、硬编码密钥（启发式）、PII（启发式）、行尾空白/BOM/CRLF 混用、
  超长行/预算、必需段落为空、重复模板、include 环、围栏内占位符、可选变量无默认值。
- **不可只凭文本判定（5 条）**：调用点缺参、调用点类型不匹配、真实 token 数与
  上下文窗口、插值未转义导致的注入风险、角色顺序/消息语义。

### 人工调整

我用三条标准筛：

1. **能不能只凭文本判定**（不需要调用模型、调用点或分词器）；
2. **能不能给出确定位置**（行/列，可点击）；
3. **能不能写出一条可复现的反例**（否则无法测试）。

结果不是"24 条全做"，而是**合并 + 删除到 12 条**：

- 同形字、混合方言、未知过滤器、include 环、控制块不平衡——**不做**：本项目的
  front matter 是最小子集，这些检查会暗示支持并不存在的模板语言。
- 行尾空白、BOM、CRLF 混用——合并为 PL011（不可见字符），CRLF 只在解析层归一化。
- 必需段落为空——不做：需要"角色/段落"概念，超出模板文本。
- token 预算保留为 PL010；密钥与 PII 保留为启发式，但把"误报边界"写进文档。

### 前后对比

| | AI 清单（29 条） | 实际（12 条） |
| --- | --- | --- |
| 可只凭文本判定 | 24 | 12（全部） |
| 有确定位置 | 24 | 12（全部） |
| 有反例 + 测试 | 0（清单阶段） | 12（每条至少 2 个用例） |
| 会暗示不支持的语言特性 | 6 条会 | 0 |
| 误报来源 | 分散 | 集中在 PL007/PL008/PL009，边界可写 |

### 为什么这么做

**一条不可判定的规则，等于把「AI 的意见」伪装成 lint 结果。** 用户看到
`语气不一致` 时无法反驳，也无法修复——这比没有规则更伤害信任。AI 的清单是很好的
**候选池**，但"能列出来"和"能负责地报出来"是两件事。

## 3. 基线指纹要不要包含行号？——AI 提醒了，我先没听，后来补上

### 原始需求

让存量仓库能接入：接受历史问题，只让新增问题失败。

### 实际 prompt

> Baseline for suppressing accepted findings: fingerprint should be sha1 of what
> fields? Compare including the line number vs excluding it. Which do you
> recommend and what is the cost?

### AI 的产出

> Including the line number invalidates the baseline on any insertion above, so
> accepted findings reappear after unrelated edits. Excluding line/column
> survives moves and reformatting. **Recommendation: exclude line/column.**
> Cost: identical snippets in the same file collapse into one entry, so a new
> duplicate instance is silently suppressed — mitigate with a per-file occurrence
> counter (#2, #3) rather than line numbers.

### 人工调整

我采纳了「不含行号」，但**第一版没有做 occurrence counter**，理由是"同一片段
重复出现本来就该一起接受"。这个判断是错的：独立评审指出，两行完全相同的代码
共享指纹，**新增的重复问题会被静默压制**，与基线"只藏旧的、不藏新的"目标矛盾。

于是补了 occurrence 序数：同一文件内，相同 `(规则, 消息, 源码行)` 的第 1、2、3 次
出现分别进入指纹。新增测试 `test_only_the_accepted_occurrence_is_suppressed`
证明"基线只接受第 1 处时，第 2 处仍会报出来"。

### 前后对比

| 场景 | 含行号 | 不含行号、无序号（第一版） | 不含行号 + 序号（最终） |
| --- | --- | --- | --- |
| 文件头加 3 行注释 | 全部失效 | 0 条失效 | 0 条失效 |
| 新增一处重复问题 | 能发现 | **被静默压制** | 能发现（序号不同） |
| 修复其中一处 | 旧基线部分失效 | 另一处仍被压制 | 另一处仍被压制（可接受） |
| 实现复杂度 | 低 | 低 | 中（需要按文件计数） |

### 为什么这么做

**AI 的提醒是对的，我一开始只听了前半句。** 这件事的价值不在"AI 答对了"，而在
**评审把"我漏掉的代价"变成了一个可复现的测试**。如果我只是把 AI 的回答抄进文档，
这个 bug 会一直留着。

## 4. 只做 text + JSON，还是加 SARIF？——AI 说"不是第一优先"，我仍然做了

### 原始需求

报告要能"进 CI"。

### 实际 prompt

> Report formats: text + JSON is the minimum. Is SARIF 2.1.0 worth the
> implementation cost for a small open-source linter used in GitHub Actions? Why
> or why not?

### AI 的产出

> **Worth it, but not first.** For a GitHub Actions linter it's the
> highest-leverage format: `upload-sarif` yields inline PR annotations plus the
> Security tab for ~100–150 lines of mechanical JSON serialization against a
> static schema. Ship text + JSON first, add SARIF on demand; in the interim
> `::error file=…,line=…` workflow commands give basic annotations at near-zero
> cost.

### 人工调整

我接受了它的技术判断，但没有接受它的**排序**：本项目的首要使用场景就是 GitHub
Actions（挑战要求"可验证"），所以 SARIF 不是"以后再说"，而是第一版就要有的证据。

实现上按它说的控制成本：只做静态 schema 需要的字段，约 80 行 + 5 项测试；
没有引入 SARIF SDK，也没有实现 `fixes`/`codeFlows` 等高级字段。

### 前后对比

| | text + JSON | + SARIF（实际） |
| --- | --- | --- |
| 人看 | 可以 | 可以 |
| 程序读 | 可以 | 可以 |
| PR 行内标注 | 不行 | 可以（Code Scanning） |
| 结果去重 | 自己实现 | `partialFingerprints` 交给平台 |
| 实现成本 | 低 | ~80 行 + 5 项测试 |
| 错误定位 | 日志第 N 行 | 文件:行:列 |

### 为什么这么做

**"可验证"不是"有一个报告文件"，而是"问题出现在开发者已经在看的地方"。** AI 的
"先 text+JSON"是对一般项目的合理建议；对本项目，SARIF 恰好是验收场景的一部分，
所以我把"以后"提前到了 1.0.0。

## 5. 密钥命中后：显示原值、全隐藏，还是掩码？

### 原始需求

PL005 命中后，消息里要不要带上命中的值？

### 实际 prompt

> When a secret is detected, should the finding message show the full value, hide
> it entirely, or mask it? Give the recommendation and the main risk of each
> alternative.

### AI 的产出

> **Mask.** Full value: leaks the secret into CI logs, PR comments, and SARIF
> uploads — permanent, world-readable exposure; never acceptable. Hide entirely:
> users cannot tell which credential matched, making triage and false-positive
> disputes expensive. Masking (e.g. `AKIA…4F2Q`, ≤4 chars each side) preserves
> locatability with minimal exposure; residual risk is short tokens, where a mask
> reveals most of the value — **so show only a length/type hint below ~12
> characters.**

### 人工调整

完全采纳，并把它说的"短 token 盲点"落成规则：

```python
if len(value) < 12:
    return "<redacted:%d chars>" % len(value)
return value[:4] + "..." + value[-4:]
```

11 位手机号不再显示成 `1380...8000`（那会暴露 8/11 位），而是
`<redacted:11 chars>`；长密钥仍是 `sk-l...2b9d`。补了 11 位与 12 位边界的测试，
demo 也重新生成。

### 前后对比

| | 全显示 | 全隐藏 | 掩码（实际） |
| --- | --- | --- | --- |
| 能否定位 | 能 | 难 | 能 |
| 二次泄露 | 会（CI 日志 / SARIF / PR） | 不会 | 部分，且短值只留长度 |
| 误报申诉成本 | 低 | 高 | 低 |
| 11 位手机号 | 完整暴露 | 无法定位 | 只显示长度 |

### 为什么这么做

**安全工具的输出本身也是攻击面。** 一个把密钥打印到 CI 日志里的检查器，在修好
问题之前先制造了一个新问题。AI 补的那句"短值只给长度"是这次最具体的一个改进，
它不在我的初始设计里。

## 附：这 5 个决策的共同点

| # | 表面在做什么 | 实际在做什么 | AI 的角色 |
| --- | --- | --- | --- |
| 1 | 技术选型 | 把依赖成本从使用者身上移走 | 说服了我 |
| 2 | 砍规则 | 拒绝把"AI 意见"伪装成 lint | 提供候选池，我删掉 17 条 |
| 3 | 改指纹 | 用稳定性换采用率 | 提醒了代价，我第一次没听全 |
| 4 | 加 SARIF | 让问题出现在开发者已经在看的地方 | 判断对，排序被我推翻 |
| 5 | 改展示 | 让工具自己不成新的泄露源 | 我采纳并补了短值规则 |

**没有一个是「用了 AI 所以更快」。** 全都是「这里会出错，所以加一道机械的保障」。
AI 在这 5 个决策里的作用并不一致：有时是反对我，有时是给我候选，有时是被我
推翻，有时是提醒了一个我漏掉的代价。**取舍仍然由人做，后果也由人承担。**
