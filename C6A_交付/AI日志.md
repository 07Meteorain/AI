## 1. 工作流设计（先定流程，再动手）

我没有直接开始写页面，而是先定了一条**带验证闸门**的六段流水线，每段都有「产物」和「不通过就不进下一段」的判据：

```
① 读题      → 产物：需求清单（rubric 5 维 + 4 件交付物 + 3 个红旗）
② 勘察      → 产物：仓库惯例（目录命名、README 风格、CI、Pages）
③ 设计      → 产物：数据模型 + 口径草案 + 页面信息架构
④ 实现      → 产物：管线 + 看板
⑤ 验证      → 产物：真实截图 + 数字自洽核对 + 单测
⑥ 交付      → 产物：文档 + 提交 + 推送 + 线上核对
```

关键决定：**每段都必须有可核对的外部证据**（文件、截图、命令输出），不接受「我觉得写完了」。后面有 6 次返工，全部是证据推翻了我的判断。

## 2. 逐轮记录

### 轮 1 ｜ 读题：把「严格按文件」翻译成可执行清单

**动作**：读 `挑战说明.md` 与 `challenge.json`，抽出三件事：

| 文件里的原话 | 我翻译成什么 |
| --- | --- |
| 必需交付物 `*仪表盘*,*demo*,*数据*,*AI日志*` | 四个交付物，且**文件名/目录名要含这几个词**，否则按通配符检索会漏 |
| rubric 五维（洞察 25 / 可视化 20 / 完整性 15 / AI 20 / 复盘 20） | 文档与产物的权重顺序：洞察与 AI 记录 > 代码量 |
| 三个红旗（缺交付物 / 无 AI 记录 / 一句话指令） | 「不能只有代码」；日志必须包含失败与迭代 |

**判断**：这不是一个「画几个图」的作业，而是「建一个能管理所有人作业的系统」。系统 = 数据管线 + 看板 + 口径 + 复盘。

**踩到的第一个坑（环境）**：`pwsh` 起不来，退出码 `3221225794`（0xC0000142，DLL 初始化失败）。

```
Get-ChildItem -Force           → [exit code: 3221225794]
git --version                  → [exit code: 3221225794]
```

连续重试 4 次（含后台作业）都失败，说明不是偶发。换更宽的执行权限后立刻正常——**根因是沙箱注入与本机 PowerShell 5.1 的兼容问题，不是命令本身**。同时发现一个事实：这个环境里的 `pwsh` 实际是 Windows PowerShell 5.1，后面两次编码事故都源于此。

> 教训：工具报错先分类（是命令错、还是环境错）。`0xC0000142` 是加载器错误，重试没有意义。

### 轮 2 ｜ 勘察：先看仓库惯例，再决定交付形态

**动作**：拉仓库根目录清单与 `C6_交付/` 的完整文件树。

**发现**：仓库里已有 13 个交付目录，命名统一为 `Cx_交付`；每个目录里都有 `app/`、`demo/截图/`、`tests/`、`tools/`、`AI日志.md`、`AAR复盘.md`、`README.md`、`提交说明.md`。`C6_交付` 还带 `package.json`、Service Worker、130 项 node 测试。

**决定**：沿用惯例，目录名 `C6A_交付`（含挑战编号，便于根 README 索引）。**不**引入 `package.json`（本项目零依赖，加一个反而要 `npm install`）。**不**复用 C6 的 GitHub Pages 工作流——Pages 发布的是 `C6_交付/app`，再挂一个 workflow 会互相覆盖，所以 C6A 的交付形态是「本地双击即开 + 深链」。

> 这一轮没有写一行代码，但它决定了后面 80% 的结构。

### 轮 3 ｜ 设计：数据从哪来（本轮推翻了自己的第一版）

**第一版想法**：全部用真实数据——把仓库 13 个交付目录的 commit 拉下来做看板。

**自己否掉的理由**：13 条记录撑不起「班级管理」——没有未交名单、没有班级对比、没有评审人差异，而这三点正是 rubric 里「数据洞察」的落点。

**第二版想法**：全部合成。

**又否掉的理由**：那这份作业里没有任何东西能被核对，评审只能「相信」我。

**最终方案（两层，互不冒充）**：

- **班级全景**：按平台导出的真实字段结构合成 106 人 × 6 挑战（seed 20260717），用来验证管线与看板；
- **真实锚点**：GitHub API 拉本人 13 个目录的 commit 时间/文件数，作为可核对的第二层。

这个折中的价值在最后一页体现得最明显：真实数据里 **C2G 的 50 条 commit 全挤在 1.84 小时内**——它证明「git 时间 ≠ 完成时间」，而这恰好是口径页第 3 个坑的实证。

**口径草案**（先写字典，再写代码）：应交份数、有效提交、提交率、按时率、迟交、平均分、中位数、红旗、一次通过率、评审人效应，共 10 条，每条写「公式 / 分母 / 边界情况 / 为什么这么定」。后来的实现只允许实现这 10 条，不许临时加指标。

### 轮 4 ｜ 实现：数据管线（第一次失败）

**动作**：写 `data/build_dataset.py`（标准库，单文件）：生成 → 清洗 → 聚合 → 洞察 → 落盘。

**失败原文**：

```
File "build_dataset.py", line 906, in main
    "total": r["_total"],
KeyError: '_total'
```

**根因**：撤回的提交（withdrawn）没有 `_total` 字段，字典取值直接崩。

**修复**：`r.get("_total")`，并把「撤回记录」写进清洗日志（最终 18 条）。

**同轮发现的设计问题**：初版把「缺 demo」的扣分设成 5 分，导致「缺 demo 组 vs 齐备组」的产物完整性只差 3.3 分，结论没有说服力。按 rubric 校准（缺核心交付物是红旗级）后改为 8 分，差距变成 6.0 分。

### 轮 5 ｜ 实现：真实数据抓取（连续三次失败）

**失败 1 —— 404**

```
HTTPError: HTTP Error 404: Not Found
```

根因：URL 拼错，`/git/trees/master` 少了 `/repos/{owner}/{repo}` 前缀。修复后 200。

**失败 2 —— 编码崩溃**

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'
```

根因：Windows 控制台默认 GBK，`print` 里的 ⚠ 无法编码。修复：`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，并保留 `PYTHONIOENCODING` 兜底。

**失败 3 —— 配额**

```
HTTPError: HTTP Error 403: rate limit exceeded
```

根因：匿名 GitHub API 60 次/小时，前面调试已用掉大半。处理：不重试、不绕路，改用**已成功写入的快照**（第一次成功那轮已落盘 14 个目录/97 条 commit），并给脚本加 `GITHUB_TOKEN` 支持。

> 这里刻意没有「多试几次总会过」——限额是确定性约束，绕过它反而会污染日志。

### 轮 6 ｜ 实现：前端第一版 + 第一次截图

**动作**：写 `index.html` / `styles.css` / `app.js`（手写 SVG，零依赖），用无头 Edge 截图。

**第一张截图就暴露问题**：演示模式的卡片出现在首屏正中间，挡住了两张图。

**根因**：`.tour { display:flex }` 覆盖了 HTML 的 `hidden` 属性（UA 样式的 `[hidden]{display:none}` 优先级更低）。修复：`.tour[hidden]{display:none}`。

**顺带**：为了让截图能拍「抽屉打开」「浅色主题」「演示中」这些状态，给看板加了**深链参数**（`#students?open=…&theme=light&tour=1`）。这本来是截图工具的需要，后来变成了产品特性（可分享、可复现问题）。

### 轮 7 ｜ 验证：洞察页顶部 300px 空白

**现象**：`#insights` 截图里，卡片从 y≈310 开始，上面的顶栏、筛选、tab、导语全不见了。但 `--dump-dom` 显示 DOM 完整（`topbar` 在、`overview` 已 `hidden`、`insights` 可见）。

**根因**：tab 用 hash 路由（`#insights`），而洞察容器 `id="insights"` —— **浏览器在加载时自动滚动到同名元素**，把上面 300px 顶出了视口。

**修复**：容器改名 `insightList`，并在初始化末尾 `window.scrollTo(0,0)`。

**教训**：hash 路由的锚点命名空间要和元素 id 隔离；这类 bug 只在「带 hash 加载」时出现，手点永远复现不了——所以截图脚本必须能带 hash，否则它会漏掉一整类问题。

### 轮 8 ｜ 验证：数字自洽（一次误判 + 一次真 bug）

**误判**：直方图看起来峰值在 60–69，但 KPI 中位分是 74.1，两者矛盾。我怀疑分箱写错，用 Python 独立重算：

```
n 476 median 74.1 mean 74.4
50 59 16 / 60 69 140 / 70 79 184 / 80 89 126 / 90 99 10
```

**结论**：数据没问题，是我把 x 轴刻度读错了一位（40 那格是空箱）。**没有改代码**——这一步的价值是「没有为了迁就眼睛去改数据」。

**真 bug**：洞察 I5 的「聚类峰值」显示 `100 / 120`。根因是把 bin 下标当成分数（`40 + i*10`），而 bin 的起始分就是 `i*10`。修复为区间字符串 `60–69 / 80–89`，可读性顺带变好。

---

### 轮 9 ｜ 验证：文档页渲染空列表

**现象**：口径页「踩过的坑」只剩 `1. 2. 3.`，条目文字全空。

**根因**：我把数据从 `[文案, ""]` 元组改成了纯字符串数组，但渲染仍用 `traps.map(([t]) => ...)`——对字符串解构会拿到首字符，模板里再取 `undefined`。

**修复**：`traps.map((t) => ...)`。同时把这一节的数字全部改成从 `D.alt` / `D.kpis` 动态取，避免「文档写 68 点几、实际 69.3」这类漂移。

## 4. Prompt 使用方式（可复用的部分）

这次没有把整份需求丢给模型一次生成，而是**把「生成」拆成「判定」**。有效的 prompt 模式有三个：

1. **带验收判据的指令**：不说「写个看板」，而说「产出 6 个 KPI，每个 KPI 悬停必须能看到分子/分母；分母随筛选变化」——可验收，模型不会自由发挥。
2. **先要证据，再要结论**：每条洞察必须附「证据 3–4 个数字 + 什么情况下不成立 + 该做什么」。模型被迫先算再写，编造空间被压缩。
3. **让失败进入上下文**：把报错原文贴回去（如 `KeyError: '_total'`、`404`），比描述「有个错」有效得多；三次 API 失败就是这么定位的。

反例（这次踩过）：第一版让模型「设计一套数据」，它给了一个 r=0.94 的漂亮相关——太干净反而不可信。改成「一半看基础水平、一半看轮数、再加噪声」后 r=0.686，才像真实数据。**「好看的数字」是一个需要主动怀疑的信号。**
