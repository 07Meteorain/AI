# 口径与陷阱

> 这份文档写给「想用这套看板分析另一批提交数据」的人。读完之后你应该能回答：**换个数据源，哪些指标会变、哪些不会、哪些坑一定会再踩一遍。**

---

## 一、为什么口径要写在代码前面

做看板最容易犯的错，是先写 `SELECT count(*)`，再给这个数起个名字叫「提交率」。等有人问「分母是什么」，才发现自己也不确定。

所以本项目的顺序是：**先写 `DICTIONARY`（10 条，含公式/分母/边界/理由）→ 再写 `build_metrics()` → 最后才画图**。代码里没有出现字典之外的指标，这条约束是靠 code review 守住的，不是靠自觉。

判断一个指标该不该进字典，用三个问题：

1. 它的分母是什么？换个分母结论会变吗？
2. 数据里什么样的记录会让它算错？（撤回？重复？空值？时区？）
3. 如果有人拿这个数去汇报，最坏会被怎么误读？

三个问题答不上来，就先别放进看板。

## 二、三种分母：同一批数据，三个「提交率」

| 口径 | 分子 | 分母 | 结果 | 什么时候该用 |
| --- | --- | --- | --- | --- |
| 只算已截止的挑战 | 432 | 106 × 5 = 530 | **89.6%** | 对外汇报「这门课的完成情况」 |
| 含进行中的 C6 | 511 | 106 × 6 = 636 | **80.3%** | 看板默认：反映「此刻的真实进度」 |
| 把退课/免修也算进分母 | 511 | 118 × 6 = 708 | **72.2%** | 几乎任何时候都不该用 |

三者差 17.4 个百分点，比任何「同比提升」都大。**报数不写分母，等于允许读者自己挑一个**。

看板的处理：KPI 悬停显示分子/分母；口径页把三个数并排画成条形图；`alt` 字段同时输出三个值，供外部引用。

## 三、迟交判定：三个必须写死的细节

```python
deadline = datetime.fromisoformat("2026-11-09T23:59").replace(tzinfo=TZ)   # +08:00
submitted = datetime.strptime(row["submitted_at"], "%Y-%m-%d %H:%M:%S")
if row["timezone"] == "UTC":
    submitted = submitted.replace(tzinfo=timezone.utc).astimezone(TZ).replace(tzinfo=None)
submitted = submitted.replace(tzinfo=TZ)
is_late = submitted > deadline
```

1. **时区**：两侧都必须带时区。裸字符串比较在跨时区数据上必错；本次 2 条 UTC 记录，换算后判定翻转。
2. **边界**：`23:59:59` 算按时，`00:00:00` 算迟交——用 `>` 而不是 `>=`，并写进字典。
3. **归属**：迟交是独立状态，不并入未交。并入后完成率从 80.3% 掉到 64.3%，会被读成「崩了」。

## 四、去重：为什么不能 `count(*)`

平台导出是**一行一次提交事件**：学生改了三遍就有三行。直接计数会把 611 行当成 611 份作业，提交率报到 96.1%（虚高 15.8pp）。

规则：按 `(student_id, challenge_id)` 分组，保留 `attempt_no` 最大的一条；并列时取 `submitted_at` 最晚的。`attempt_no` 不丢弃，用来算「平均提交次数 1.16」和「一次通过率 86.5%」。

副作用要写清楚：**去重后的 `submitted_at` 是「最后一次提交时间」**。如果业务想问「第一次提交是否按时」，需要另存一列——本看板没做，因为挑战关心的是最终交付。

## 五、缺失值的三种处理，差 5 分

| 处理 | 均分 | 什么时候合理 |
| --- | --- | --- |
| 只算已评审（本看板） | **74.4** | 想知道「已评的作品平均什么水平」 |
| 待评审记 0 分 | 69.3 | 几乎从不合理——它把「还没看」当成「做得差」 |
| 用班级均分填补 | ≈74.3 | 会让方差虚低，且掩盖「谁还没被评」 |

`avgZeroFilled` 这个字段保留在 `metrics.json` 里，不是为了用，是为了**让人看到差 5.1 分**。

## 六、归因：班级差还是评审人差

**观察到的**：A/B/C 班均分 76.7 / 70.7 / 75.6，极差 6.0 分。

**三个竞争解释**：

| 解释 | 需要的证据 | 本数据是否支持 |
| --- | --- | --- |
| H1 学生水平不同 | 同一评审人打分下，班级仍有 6 分差 | **不支持**：同一评审人跨班极差仅 2.5 分 |
| H2 评审人宽严不同 | 评审人均分有差，且与班级绑定 | **支持**：评审人极差 7.2 分，88% 绑定 |
| H3 交互（某班某评审人特别严） | 交叉表里出现离群单元格 | 样本太小（12% 交叉），无法判断 |

**结论写法**：不是「B 班最差」，而是「班差与评审人差不可分，需要随机交叉分派才能识别」。这句话在看板的 I3、`docs` 和 README 里各出现一次——**同一个限制要说三遍，因为读者会从三个入口进来**。

## 七、敏感性：什么条件下结论会翻转

| 结论 | 依赖的前提 | 如果前提变了 |
| --- | --- | --- |
| I4 迟交与低分几乎不相关（r = 0.02） | 课程**没有**迟交扣分规则 | 若按天扣 5%，迟交组中位会掉到 68 左右，「不相关」可能变成「弱负相关」 |
| I2 提交率 80.3% | C6 计入分母 | 只看已截止 → 89.6% |
| I6 缺 demo 组低 6.0 分 | 扣分权重按 rubric 校准（8 分/15 分维度） | 若权重减半，差距会缩到 3 分左右，结论变弱 |
| I5 C5 复盘双峰 | 该挑战的 rubric 措辞含糊 | 若评审人用了锚定样例，双峰可能合并成正态 |

## 八、拿到一批新数据，先问这 8 个问题

1. 一行代表什么？（一次事件 / 一份作业 / 一个学生）
2. 有没有撤回、作废、重复提交？规则是什么？
3. 时间戳带不带时区？截止时间在哪个时区？
4. 分母是谁？在册？在读？选课？退课的人怎么算？
5. 缺失值是「没交」「没评」还是「没记录」？三者不能混。
6. 评分是单评还是多评？评审人怎么分派？和班级/时间有没有绑定？
7. 有没有「进行中」的周期？它该不该进分母？
8. 如果有人要拿这个数去汇报，最坏会被怎么读？

这 8 个问题答完，再动手写第一行聚合代码。
