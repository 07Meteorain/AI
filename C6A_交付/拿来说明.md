# 拿来说明 · 六个关键取舍

> 这不是功能说明，是**决策记录**：每个取舍当时有哪些选项、为什么选这个、代价是什么、今天回头看会不会改。
> 格式统一为：背景 → 选项 → 选择 → 代价 → 复盘。

---

## 取舍 1：数据用「合成 + 真实」两层，而不是全真实或全合成

**背景**：挑战要「管理所有人作业」，但课程平台没有导出接口。

**选项**：

| 方案 | 优点 | 致命问题 |
| --- | --- | --- |
| A. 全真实（只有本人 13 个交付目录） | 每个数字都能核对 | 做不出班级管理：没有未交、没有班间比较、没有评审人 |
| B. 全合成 | 能撑起完整看板 | 没有任何东西可被核对，评审只能「相信」 |
| C. 分层：班级全景（合成）+ 本人提交（真实） | 既有完整场景，又有可核对锚点 | 界面上要一直解释「哪层是哪层」，有认知成本 |

**选择**：C。

**代价**：多了一个「真实数据」页，多了一套抓取脚本，多了一节「数据来源说明」；读者必须接受「两层不能混算」这个约束。

**复盘**：**会再选一次**。而且这一层真实数据后来变成了最重要的论据：C2G 的 50 条 commit 挤在 1.84 小时内，直接证明了「git 时间不能当提交时间」。如果全合成，这个洞察只能靠嘴说。

## 取舍 2：零依赖手写 SVG，而不是 ECharts / Chart.js

**背景**：8 张图，未来读者大概率是评审，不是开发者。

**选项**：

| 方案 | 视觉上限 | 交付门槛 |
| --- | --- | --- |
| A. ECharts（CDN 或本地打包） | 高，交互现成 | 需要网络或 1MB 本地文件；`file://` 下部分功能受限 |
| B. Chart.js（canvas） | 中 | 需要本地文件；canvas 导出与无障碍更麻烦 |
| C. 手写 SVG | 中上（足够看板） | 零文件、零网络、主题变量直接生效 |

**选择**：C。

**代价**：tooltip、hover、点击筛选、坐标轴都要自己写（约 300 行）；动画基本没有。

**复盘**：**会再选一次**，但有一个前提——图形类型要控制。8 张图里没有一张需要复杂交互（缩放、刷选），所以手写的成本可控。如果要做「时间范围刷选 + 联动」，我会改用 D3 或 ECharts。

## 取舍 3：数据编译进 `data.js`，而不是 `fetch('metrics.json')`

**背景**：最常见的交付事故是「本地打开一片空白」。

**选项**：

- `fetch('data/metrics.json')`：结构干净，但 `file://` 下会被 CORS 拦（Chrome/Edge 默认策略），双击打开必然空白；
- 内联到 HTML：可行，但 300KB 的 JSON 塞进 HTML 会让源码不可读；
- 编译成 `window.C6A_DATA`（`js/data.js`）：双击可开，源码仍可读，改数据只需重跑脚本。

**选择**：第三种。

**代价**：数据与代码在同一个仓库里有两份（`metrics.json` 给测试/文档，`data.js` 给看板），需要靠构建脚本保证一致。

**复盘**：**会再选一次**。README 里「30 秒验收」的第一步就是「双击打开」，如果这里失败，后面全都不用看了。

## 取舍 4：洞察写死在 `metrics.json`，而不是前端现算

**背景**：7 条洞察，有的依赖分组统计，有的依赖相关分析，有的依赖双峰判断。

**选项**：

| 方案 | 风险 |
| --- | --- |
| A. 前端过滤后现算，文案模板化 | 同一句「班级差 X 分」在不同筛选下会变成不同数，容易自相矛盾 |
| B. 后端（构建时）算好，写进 `metrics.json`，前端只展示 | 洞察不随筛选变化，需要明确说明「洞察基于全量数据」 |
| C. 文案手写死 | 数据一改就失真 |

**选择**：B。洞察数字与文案全部由 `build_insights()` 生成，前端只渲染。

**代价**：洞察不能跟着筛选变；如果只看 C6，I1 的「48.5%」仍是全量的数。

**复盘**：**会再选一次，但会补一句说明**。现在洞察页只在导语里写「数字全部由 build_dataset.py 从同一份数据算出」，没有明说「不随筛选变」——下一版应该在卡片上加一个小标记「全量口径」。

## 取舍 5：用中位数而不是均值作为主指标

**背景**：分数分布右偏（60–69 有 140 份，90+ 只有 10 份），均值会被高分尾巴稀释。

**数据**：中位 74.1，均分 74.4。这里两者只差 0.3，看起来「用哪个都行」——但换成子群体就不同了：C5 的复盘维度中位 65.5，而该维度有 41.9% 在 80 分以上（双峰），均值会落在一个「谁都不在」的位置。

**选择**：KPI 主显示中位数，均值作为副标题；维度图用中位 + IQR。

**代价**：读者对「中位数」不如「平均分」熟悉，需要一句解释（放在 KPI 的悬停里）。

**复盘**：**会再选一次**。双峰分布下，均值是最容易被误读的统计量。

---

## 取舍 6：不做后端，也不做登录

**背景**：真实场景下，这种看板一定要有权限（评审只能看自己班）、要有审计。

**选项**：

- 加一个 Flask/FastAPI 服务 + SQLite：能演示权限，但交付形态从「双击打开」变成「装 Python + 起服务」，评审成本陡增；
- 纯静态：任何人都能打开，但没有权限、没有实时、没有多人写。

**选择**：纯静态。

**代价**：明确放弃了权限、实时、协作三项能力；这些在 README 的「边界」里写清楚了。

**复盘**：**这次会再选一次，但真实项目不会**。如果这是给学院真用的系统，第一优先级就是权限与审计，其次才是可视化。把「这次是作业、不是生产系统」讲清楚，比假装它能上线更诚实。

## 附：一个没做的取舍（被否掉的方案）

**曾考虑**：给每个学生算一个「风险分」，用规则（迟交次数 × 红旗数 × 低分）排序，看板首页放「最需要关注的 10 人」。

**否掉的原因**：这个分数会把「评审人宽严」「班级绑定」全部混进去，等于用有偏的输入生成一个看似客观的排名，再让人拿它去做干预。**在没有解决 I3 的混淆之前，做风险分是危险的。** 现在只提供「按总分升序」这种透明的排序，让学生表承担「找人」的功能，而不是「判人」。

这个决定也解释了为什么学生抽屉里的「建议」只写流程动作（补 demo、改排期、看最低维度），不写「该生需要加强 XX 能力」——后者需要人来看，不该由看板下判断。
