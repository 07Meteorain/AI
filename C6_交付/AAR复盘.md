# AAR 复盘 · PromptGate（C6 Web Application）

> AAR = After Action Review：**预期什么 / 实际发生了什么 / 为什么有差距 / 下次怎么改**。
> 这份复盘的写作原则：**失败经验必须具体到能复现**，改进方案必须带可验证的指标。
> 如果某一条看起来像「以后注意」，那就是我写得不够狠。

---

## 1. 预期 vs 实际

| 维度 | 开工时的预期 | 实际 | 差距与原因 |
| --- | --- | --- | --- |
| 交付形态 | 一个能打开的 Web 页面 + 一份报告 | 一个有 5 个功能页、CLI、PWA、130 项测试的产品 | 超出预期。原因是「先纯逻辑」的顺序让后面每一步都没有返工 |
| 工期 | 主要花在规则设计 | 规则设计只占约 30%，**40% 花在验证（测试 + 截图）**，30% 在文档与部署 | 预估错了。验证比实现贵，但这笔钱必须花 |
| 规则数量 | 12 条（对齐 C5） | 15 条 | 新增的三条（PG008/PG013/PG015）来自真实使用时的缺失 |
| 误报 | 以为会很严重 | 合格样例 0 命中，7 个样本里只有 2 处需要调样本而不是调规则 | 比预期好。原因是「宁可不报也不误报」的取向（PG010 的变量隔离检查只在全文无分隔符时才报） |
| AI 出错次数 | 以为 3–5 处 | 16 处（见 [AI日志](AI日志.md) §3） | 低估了一倍以上。其中 11 处是测试抓到的 |
| 「能不能跑」 | 需要本地服务 | `file://` 双击即可，零安装 | 达成。UMD + 普通 `<script>` 的收益比预期大 |
| 移动端 | 顺手适配 | 花了 2 轮才搞清「截图被裁不是布局 bug」 | 见 §3-F2 |

**一句话**：功能完成度比预期好，**时间分配比预期糟**，AI 出错率比预期高一倍。

## 2. 做对了什么（要保留的）

### 2.1 先定裁判，再写实现

每个阶段开工前先回答「怎么判定它做完了」。这让 16 处错误里 14 处是**机器主动报告**的，
而不是我某天突然想到「这里好像不对」。成本是每个阶段多花 10 分钟，收益是几乎零返工。

### 2.2 「合格样例零命中」当第一道防线

这是 130 条测试里最重要的一条。它的作用不是防止我写错某个规则，
而是**防止我加规则时把整个产品变成一个「什么都说有问题」的噪音机**。
检查工具最容易被放弃的方式，就是它开始误报。

### 2.3 让文档从代码生成

`docs/rules.md` 由 `rules.js` 生成，CI 里 `--check`。这消除了一整类问题：
「文档说 12 条规则、代码里有 15 条」「文档里的正例其实是错的」。
代价是一个 120 行的生成脚本，收益是文档永远不会过期。

### 2.4 把「诚实边界」写进产品界面

「预算」页底部直接写着「token 是估算 ±20%」「价格是快照」。
这比写在 README 里有效得多——**用户只有在用的时候才会怀疑数字**，解释必须出现在怀疑发生的地方。

### 2.5 截图驱动 UI 回归

`?sample=bad&theme=dark&tab=budget` 这套深链一开始是为了「分享状态」，
后来变成了**截图脚本的参数**，再后来变成了**问题复现的最小单元**。
一个功能设计对了，会在三个地方同时省事。

## 3. 失败经验（F1–F7，含未解决）

### F1｜把环境故障当成产品故障，浪费了 3 轮

**现象**：`pwsh` 每次执行都返回 `0xC0000142`（进程创建失败），没有任何输出。
**错误反应**：连续三次重试同样的命令，然后开始怀疑「PowerShell 被装坏了」。
**正确做法**：第一次失败就应该做**变量隔离**——换工作目录、换权限级别、换解释器各试一次。
**真实原因**：沙箱注入导致的进程启动失败，提高权限后同一命令直接成功。
**教训**：`0xC0000142` 这类状态码要在第一次出现时就记下来（它在本仓库 C3 里已经出现过一次，我没能第一时间联想到）。
**未解决**：如果换权限后仍然失败，我当时的备用方案是「只用 `write` 工具写文件、不执行任何命令」——那会导致无法测试、无法部署，等于交付失败。这条兜底路径没有被验证过。

### F2｜把「截图被裁」误判成「布局溢出」，改了 2 版错误的 CSS

**现象**：474px 宽截图右侧内容被切掉，看起来像横向溢出。
**错误反应**：加 `min-width: 0`、`flex-wrap: wrap`、`overflow: hidden`——改了 2 轮，没有一张图变好。
**真正的排查方式**：注入 JS 读 `window.innerWidth`，发现传 `--window-size=430` 时**实际是 474**。
headless Edge 有最小窗口宽度，图按物理像素裁，所以「被裁」是截图工具的行为，不是布局。
**教训**：**先测量，再修改**。改 CSS 之前应该先问「这个宽度到底是多少」。
**未解决**：如果用真实手机测试，474px 附近的断点行为仍然没有被真正验证过（没有真机）。

### F3｜测试写错了，却以为是代码错了

**现象**：3 条测试报红，其中 2 条是**断言本身写错**：括号位置错导致 `findings.map is not a function`；
正则 `class="rule` 把 `class="rule-top"` 也数进去；`--fail-on` 用例用了 9 个字符的文本，结果命中 PG001 而不是预期的「纯 warning」。
**为什么会这样**：看到红色就假设「实现有 bug」，直接去改实现。
**教训**：红色的第一反应应该是**读 `actual` 和 `expected`**，而不是读自己的代码。断言写错的成本是双倍的（既浪费修改时间，又可能把对的实现改错）。
**改进**：测试文件里对「输入」的假设要用注释写清楚（例如「31 个字符、有任务动词、无格式约束 —— 只会命中 PG003」）。

### F4｜规则只用确定性检测，表达能力有天花板

**现象**：PG002/003/012/013/014 全是关键词匹配。像「请把这段改写得更像人写的」这种完全没有格式约束、
但意图清晰的 prompt，会被 PG003 判 warning。
**为什么接受**：调 LLM 判断会引入不可回归、不可离线、有成本三个问题。
**代价**：工具对「表达质量」无能为力，只能管「结构缺陷」。
**未解决**：没有设计「规则置信度」——现在所有 warning 看起来一样重，但它们的可靠性差别很大（PG004 几乎不会误报，PG012 经常误报）。
**下一步**：给每条规则标 `confidence: high|medium|low`，UI 上对 low 的条目标注「启发式，可能误报」，并允许默认不参与门禁。

### F5｜健康分会饱和到 0，信息量丢失

**现象**：反面教材 5 个 error → 扣 70 分 → 0 分。可是「5 个 error」和「13 个 error」都显示 0。
**为什么会这样**：线性扣分 + 下限 0 是最简单的实现，但把「很糟」和「糟透了」抹平了。
**代价**：健康分从「阅读指标」退化成了「是否及格」的二值信号，和门禁重复了。
**未解决**：没有改成非线性（例如 `100 × 0.55^errors`）。改了要重写测试、重画截图、重写文档里的数字，成本不为零，而收益只是「好看一点」。
**下一步**：改成递减权重（第 1 个 error 扣 14、第 2 个扣 10、第 3 个扣 7…），并给「0 分」加一个 `0+` 的显示。

### F6｜版本功能只有 localStorage，是个「单机玩具」

**现象**：换浏览器/换设备就没了，上限 20 条，`localStorage` 在隐私模式下直接退回内存（关页面即丢）。
**当时的选择**：不引入后端，保持「零部署成本」。
**代价**：真正需要版本管理的场景（团队协作、prompt 上线流程）恰好是最需要跨设备的地方。
**未解决**：没有「导出/导入全部版本」的功能。这是一个 30 行就能补上的缺口，但优先级排在测试与部署之后。
**下一步**：加 `导出工作区 (.json)` / `导入工作区`，让 localStorage 变成一个可以备份的缓存，而不是唯一存储。

### F7｜「没有真实用户」这件事，没有在产品里被解决

**现象**：所有关于「好用」的判断都来自我自己反复使用。
**这是最诚实的失败**：一个产品的完成度不能由作者的自评决定。
**未解决**：没有埋点、没有留存、没有任务完成率。上线后第一件事应该是拿数据推翻上面所有判断。
**下一步**：见 §5 的指标。

## 4. 五个为什么（选一个具体问题分诊）

**问题**：为什么这次交付花了大量时间在与「产品」无关的事情上（环境、截图、BOM、正则）？

1. **为什么时间花在这些地方？**
   因为每个阶段都有「看不见的失败模式」：环境跑不起来、截图看不准、文件编码不对、正则多匹配一个字符。

2. **为什么这些失败模式没有被提前消除？**
   因为我先写了实现，再想验证方式。验证方式是被「撞上」的，不是被「设计」的。

3. **为什么没有先设计验证方式？**
   因为默认假设「我知道怎么验证」——截图看一眼、跑一下命令。这个假设在跨平台、
   跨工具（headless 浏览器、PowerShell 编码、管道缓冲）的场景下是错的。

4. **为什么这个假设会错？**
   因为这些工具的默认行为是**隐式的**：headless 有最小窗口宽度、PS 5.1 按 ANSI 解析无 BOM 脚本、
   Windows 管道输出是异步的。这些都不会报错，只会「看起来不对」。

5. **根本原因？**
   **把「能跑」当成「跑对了」**。真正的验证需要至少两个独立信号（例如：测试 + 截图；退出码 + 文件存在），
   而我在早期只依赖一个。

**对应改进**：AI 日志 §4.2 的「每个阶段一个不可辩驳的裁判」表格，就是这条分诊的产物。

## 5. 改进方案（带指标）

### 5.1 立即（下一次提交内）

| 改进 | 完成标志 | 指标 |
| --- | --- | --- |
| 工作区导入/导出（补 F6） | 「版本」页有「导出 .json / 导入」按钮，且有一条测试覆盖往返一致性 | 往返后版本数、内容、指纹完全一致 |
| 规则置信度（补 F4） | 每条规则有 `confidence` 字段，low 的在 UI 上带标注 | 合格样例仍然 0 命中；标注覆盖 ≥3 条启发式规则 |
| 健康分非线性（补 F5） | 13 error 与 5 error 的分数不同 | 单调、可解释、测试覆盖边界 |

### 5.2 短期（上线后两周）

| 改进 | 完成标志 | 指标 |
| --- | --- | --- |
| 最小埋点 | 只记录「打开 / 体检 / 导出 / 存版本」四类事件，不含 prompt 内容 | 能看到漏斗：打开 → 体检 → 导出 的转化 |
| 误报反馈入口 | 每条问题上有「这是误报」按钮，本地计数并导出 | 收集 ≥20 条反馈后，误报率 < 5% |
| 首屏性能 | 用 Lighthouse 量一次 | LCP < 1s（当前无外部请求，应该轻松达标） |

### 5.3 中期（如果继续做）

| 改进 | 理由 |
| --- | --- |
| 规则可配置（自定义规则文件） | 现在规则是硬编码的，团队无法加自己的检查项 |
| Git 集成（读 PR 里的 prompt 文件） | 让门禁发生在 review 阶段，而不是本地 |
| 多 prompt 批量体检 | 一个产品通常有十几个 prompt，逐个贴太低效 |

**判断标准**：如果三个月后这个工具还在被用，那一定是因为「它进了 CI」而不是因为「它好看」。
所以中期优先级应该是 **Git 集成 > 规则可配置 > 多 prompt 批量**，UI 优化排在最后。

## 6. 如果重来

1. **第一小时不写代码**，先写「验收清单」：哪 10 个动作必须成功。这次是边做边补，导致环境问题和截图问题各吃掉一轮。
2. **给每个样本先写期望的规则 id 列表**，再跑 lint 对比。这样 E2–E4（样本本身的 bug）会在 2 分钟内暴露，而不是在测试阶段。
3. **`.js` 文件永不用 `Set-Content`**（会写 BOM）。这条已经写进 AI 日志 E14，但应该在开工时就写进「环境约定」。
4. **截图脚本第一天就写**，而不是等到功能都做完了才写。它的价值不只是出图，而是**给每个界面状态一个可复现的 URL**。
5. **健康分从第一版就做非线性**。改一个已经写进文档、截图、测试的数字，成本是改一个还没被引用的数字的 5 倍。
