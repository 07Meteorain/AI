## 0. 协作结构

| 角色 | 谁 | 做了什么 |
| --- | --- | --- |
| 需求方 / 验收方 | 人类（07Meteorain） | 给出挑战约束（「严格按 C6 文件要求」「新建文件夹」「上传到 GitHub」），在会话中途两次确认方向（一次「继续」） |

**关键事实**：人类没有逐行读代码。所以这份日志的价值在于——**AI 说的话必须能被机器验证**。
下面每一轮都写「怎么验证的」，这就是防自欺的机制。

1. > 帮我完成C6这个挑战，在C6这个挑战里新建一个文件夹，把完成的内容放到这个文件夹中，上传到 https://github.com/07Meteorain/AI 要求：严格按照C6这个挑战的文件里的内容完成C6挑战

第 1 条里有 4 个硬约束，我在开工前把它们拆成了验收项：

| 约束 | 我的执行 | 可验证证据 |
| --- | --- | --- |
| 「严格按 C6 文件」 | 只按 `challenge.json` 的 rubric 与 `*app链接*,*demo*,*repo链接*,*AI日志*` 组织交付 | [提交说明.md](提交说明.md) 第一节 |
| 「新建一个文件夹」 | 新建 `C6_交付/`（与仓库里 `C5_交付/` 的命名一致） | 目录列表 |
| 「内容放进去」 | 应用、工具、测试、文档、demo 全部自包含 | `README.md` 目录结构 |
| 「上传到仓库」 | 分阶段提交 + Pages 部署 | `git log`、线上 URL |

第 2 条「继续」发生在 core 引擎写完、UI 刚成形时 —— 它没有改变方向，只是允许我继续按自己的计划推进。
**这类「继续」是最危险的信号**：如果计划本身错了，继续只会错得更远。所以我当时的做法是先把「怎么验证」定死（测试 + 截图），再继续。

## 4. 工作流设计（这轮真正的产出）

### 4.1 顺序：先纯逻辑，再界面

```
parser → tokenizer → diff → rules → samples → 探针脚本 → UI → 截图 → 测试 → CLI → 文档 → 部署
```

为什么不是「先搭页面再填逻辑」：UI 一旦存在，任何逻辑 bug 都会先表现为「页面看起来怪」，
而「看起来怪」是主观的。**纯函数 + 探针脚本**让错误在变成视觉问题之前就被数字抓住。

### 4.2 每个阶段都要有一个「不可辩驳的裁判」

| 阶段 | 裁判 | 为什么够硬 |
| --- | --- | --- |
| 规则 | 探针脚本打印 `样本 → 命中规则 id` | 一眼能对比「我以为会命中什么」 |
| 界面 | headless 截图 | 人能看图，AI 不能自欺 |
| 逻辑 | `node --test` | 131 条断言，红就是红 |
| 交付 | 退出码 + HTTP 200 | 没有「应该可以」的空间 |

### 4.3 「合格样例零命中」是最重要的一条测试

任何新规则都可能把合格 prompt 判成不合格。这条测试把「误报」这个最伤用户的失败模式
变成一个**每次提交都会跑的断言**。加规则的人在改完代码的 3 秒内就知道自己有没有搞砸。

### 4.4 让 AI 无法自我美化

- 文档不许手写规则说明：`docs/rules.md` 由代码生成，CI 里 `--check` 失败就是失败。
- 截图不许口述：脚本生成，图里能看到什么就是什么。
- 「已修」必须有测试名或截图名对应，日志里逐条列出来。

## 5. 我（AI）在这轮里做过的判断，以及判断错了什么

| 判断 | 当时理由 | 事后看 |
| --- | --- | --- |
| 选 PromptGate 而不是「引用审计 Web 版」 | 复用 C4C 会造成「Web 套壳」的观感；PromptGate 有 forward 的实用价值，且能复用 C5 的方法论但不复用代码 | 成立。但代价是规则要重写（JS），工作量比预期大 |
| 零依赖 + UMD，不上 React/构建链 | 让 `file://` 双击可用，测试与运行时同一份代码 | 成立，且让 131 项测试跑得极快（< 1.5s） |
| 健康分与门禁分离 | 分数容易被拿来稀释致命项 | 成立。但「0/100」这种饱和值信息量偏低，见 AAR F5 |
| 规则只用确定性检测，不调 LLM | 离线、可复现、零成本；LLM 判断不可回归 | 成立，但表达能力受限（见 AAR F4） |
| 版本只存 localStorage | 不引入后端 | 勉强成立。单机可用，但「换设备就没了」是真实缺陷 |
| 先做 7 个样本再写测试 | 样本是测试的输入 | 成立，但样本本身的 bug 拖了两轮（E2–E4） |

## 6. 可复用的 Prompt / 指令模板（沉淀）

这几条在这次会话里反复用到，值得固化：

1. **先定裁判，再开工**
   > 在写任何实现之前，先说清楚：这个阶段完成时，我用哪条命令 / 哪张图 / 哪个返回码来判定它做完了。

2. **探针优先**
   > 引擎写完不要先接 UI：写一个 20 行的临时脚本，把 7 个样本的命中结果打出来，我先肉眼看一遍再往下走。

3. **每个 bug 都要有「下次不会再犯」的装置**
   > 修完这个 bug 后，加一条能复现它的测试；如果它属于某一类风险，考虑加一个结构性检查（例如文档漂移检查、资源存在性检查）。

4. **诚实边界要写在产品里，不只是写在文档里**
   > 把 token 估算的误差、价格的快照日期直接显示在「预算」页底部，而不是只写在 README。

5. **截图是 AI 时代的单元测试**
   > 每个界面状态给一个 URL 参数（`?sample=bad&theme=dark&tab=budget`），用脚本批量产图；改完 CSS 先看图，再谈「应该没问题」。
