# 拿来说明 · PromptGate

> 「拿了什么、改了什么、为什么改」。
> 这份文件存在的理由：一个人做的东西不可能凭空出现，**说清楚来源比假装原创更可信**。

---

## 1. 拿了什么

| 来源 | 拿了什么 | 怎么用的 |
| --- | --- | --- |
| 本仓库 **C5_交付（promptlint）** | 「prompt 可以像代码一样静态检查」这个判断；规则分类的思路（安全 / 稳定性 / 可维护）；零依赖的取向 | **只拿方法论，不拿代码**。C5 是 Python，本项目是浏览器 JS，规则引擎完全重写 |
| 本仓库 **C4C（引用审计器）** | 「不假装知道」的产品态度：`UNCHECKED ≠ 通过` | 转成 PromptGate 的 `已忽略 ≠ 没问题`：被基线排除的条目单独成列，不混进「通过」 |
| 本仓库 **C4A（技能评审器）** | 一票否决式判定：致命项不该被加权平均稀释 | 转成「门禁只看级别，健康分只做阅读参考」的两层设计 |
| 本仓库 **C3（提问体检器）** | 「分数 + 阈值 + 拦截」的交互范式 | 转成 PASS/FAIL 徽章 + 阈值下拉 |
| 通用前端实践 | 深链状态、localStorage 持久化、Service Worker | 常规用法，没有特殊技巧 |

**明确没有拿的**：C5 的 12 条规则的**实现**（Python 正则与 JS 的边界不同，直接照搬会带进一堆隐性 bug）。
所以本项目的 15 条规则是重新设计的：其中 12 条与 C5 主题重叠但判据重写，
另外 3 条（PG008 变量名拼写、PG013 缺 few-shot、PG015 体量预算）是 C5 里没有的。

## 2. 五个关键决策

### 决策 1：做「产品」而不是「页面」—— 加了预算和版本

**取舍**：如果只做「粘贴 → 出问题列表」，它是一个 demo，因为**用户没有理由第二次打开**。

**改了什么**：加入两个「有决策价值」的功能 ——
- 成本预算：同一个 prompt 换模型，月度成本差 24 倍。这是**写 prompt 时就该知道**的数字，不是月底看账单才知道。
- 版本 + diff：让「改好了」有证据（改了 6 行，error 从 5 降到 0）。

**代价**：多写约 600 行（预算表、价格编辑、diff 视图、版本存储），多 3 个测试文件。

**为什么值得**：一个工具被反复打开，一定是因为它**参与了决策**，而不是因为它好看。

---

### 决策 2：零依赖 + UMD，不上 React 和构建链

**取舍**：现代前端默认 React + Vite。这里反着来。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| React + Vite | 组件化、生态、开发体验 | 需要 `npm install`、需要构建、`file://` 用不了、测试要么用 DOM 环境要么另起一套 |
| **原生 + UMD（选了这个）** | `git clone` 后双击即用；测试与运行时**同一份文件**；131 项测试 1.5 秒跑完 | 手写 DOM 字符串拼接；状态管理靠一个 `state` 对象；没有组件复用 |

**最关键的理由**：`node --test` 里 `require` 的就是浏览器加载的那个文件。
如果用了构建链，测试测的是「构建产物」或「源码 + 转换器」，一旦转换配置有差异，
就会掉进「测试绿了但线上白屏」的坑。这个项目没有构建步骤，所以**不存在这种差异**。

**代价（诚实记录）**：`ui.js` 里有一堆字符串拼接，可读性不如 JSX；样式改动要重跑截图。
如果这个产品要长到 20 个页面，我会换回框架。

---

### 决策 3：门禁判定与健康分彻底分离

**取舍**：常见做法是「加权总分 → 低于 60 不通过」。这里把两件事拆开：

- **门禁**：只看级别。`fail-on error` 时，一条 error 就是 FAIL，和它有 30 条 info 无关。
- **健康分**：0–100，扣分制，只作为「读一眼」的指标，**不参与任何判定**。

**为什么**：C4A 里踩过这个坑 —— 朴素的加权评分会把致命伤稀释成小瑕疵
（一份硬编码了本机路径的提交，同时有「安装说明」加分，最后拿到 57% 的「部分满足」）。
同一个错误不能在两个项目里犯两次。

**代价**：用户会问「为什么 68 分却是 FAIL」。所以 UI 文案必须解释：
「健康分是阅读指标，不是门禁依据」（报告模板里也印着这句）。

---

### 决策 4：基线指纹不含行号

**取舍**：忽略某条问题时，用「规则 id + 消息」做指纹，**不含行号、不含文件路径**。

**为什么**：如果指纹含行号，那么「在第 1 行加一句开场白」会让所有历史忽略项复活 ——
用户会以为工具在乱报，然后开始习惯性点「忽略」，基线就废了。

**代价**：如果同一规则在同一段文本里命中两次、消息完全相同（例如两处同样的 `sk-` 泄漏），
忽略一次会把两处都忽略掉。这是刻意的取舍：**宁可漏掉一个重复项，也不要让基线失效**。

**验证**：`tests/gate.test.js` 里有一条专门的测试
「指纹不含行号：挪动位置后基线依然有效」。

---

### 决策 5：变量契约要做「渲染预览」，而不只是「列出变量」

**取舍**：大多数 lint 工具到「列出 `{{user_name}}` 出现 2 次」就结束了。
这里多做了一步：点击「渲染预览」，填上值，看到 prompt **实际长什么样**。

**为什么**：变量的问题往往不是「拼错」，而是「渲染出来读不通」。
比如 `你好{{name}}欢迎` 渲染成 `你好小明欢迎`，语法上不缺东西，读起来就是不对。
这一步把「静态检查」延伸到「可感知的后果」，也是这个产品区别于普通 linter 的地方。

**代价**：多一个 modal、一个 `renderTemplate` 函数、一条测试（把空字符串视为未填写）。

## 3. 从 C5 到 C6 的变化（如果只看差异）

| 维度 | C5 promptlint | C6 PromptGate |
| --- | --- | --- |
| 形态 | Python CLI | 浏览器应用 + CLI + PWA |
| 规则 | 12 条 | 15 条（重写，新增 3 条） |
| 输出 | text / JSON / SARIF | 同上 + Markdown 报告 + 可视化界面 |
| 成本 | 不看 | 8 个模型 × 可编辑单价 × 调用量假设 |
| 版本 | 无 | 快照 + 行级 diff |
| 依赖 | 零（Python 标准库） | 零（浏览器原生 + Node 标准库） |
| 部署 | 本地运行 | GitHub Pages 自动部署 |

## 4. 我没做的事（以及为什么）

| 没做 | 原因 | 如果要做，第一步是什么 |
| --- | --- | --- |
| 用户账号 / 云端同步 | 需要后端、需要处理 prompt 的隐私（很敏感），收益低于成本 | 先做「导出/导入工作区 .json」，让本地数据可备份 |
| 调 LLM 做语义检查 | 不可回归、不可离线、有成本；会让「同一份 prompt 两次结论不同」 | 把 LLM 检查作为可选插件，结论标 `low confidence`，不进门禁 |
| 自定义规则 DSL | 需要设计一门小语言，当前用户基数撑不起 | 先支持「规则开关 + 阈值」，再看真实需求 |
| 多语言界面 | 目标用户是中文语境 | 先把文案抽成一份 `strings.js`，翻译才有意义 |
| 真机移动端测试 | 没有设备 | 用 Playwright 的 device emulation 替代 |

---

## 5. 一句话总结

> 从 C5 拿的是「prompt 该被检查」这个判断，从 C4C 拿的是「不假装知道」这个态度，
> 从 C4A 拿的是「致命项不能被平均」这个教训。
> **代码一行没拿** —— 因为换个运行环境（Python → 浏览器）时，照搬代码是最贵的省事方式。
