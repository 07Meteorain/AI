## 三、三件失败（这一节比"做得好"重要）

### 失败 1：我用 AI 写"骂 AI 编数字"的文章，AI 在里面编了 3 个数字

**发生了什么**：初稿里有三处硬伤——

| 写的 | 真相 | 性质 |
| --- | --- | --- |
| "438 项自测" | 446 项 | 计算错误（按根 README 旧口径手算） |
| "3 条 DOI 指向虚无" | 1 个真实 arXiv ID 指向另一篇论文 + 2 个编造标题 | 把三种不同的幻觉压成一句 |
| "按钮坏了三周" | 3 分 12 秒 | **凭空构造因果**，最有欺骗性的那种 |
| "63 次提交" | **127 次** | 浅克隆只数到一截历史；`git rev-list` 不报错，安静地少算一半 |
| "446 项自测" | **464 项** | 同上（C6A 的 18 项没被算进去） |

**归因**：

1. 我一开始的验收方式是"读一遍，通顺就过"——而通顺恰恰是 AI 最擅长伪装的属性；
2. 前两个错误是"口径问题"（谁数的、按什么规则数的），第三个是"叙事问题"（为了让故事更有张力，把 3 分钟说成 3 周）。**第三类最危险，因为它读起来完全合理。**

**改法**（已经落地，不是"下次注意"）：

- 所有数字进正文前必须有脚本出处：`tools/repo_facts.py` 产出 `数据/repo_facts.csv`，正文引用它；
- 数字必须带截止点（`master@099371a`），否则下一天就变成假话；
- 因果类断言（"因为 A 所以 B"）必须能指到 commit / 文件 / 行，指不到就不写。

**残留风险**：这套机制防得住"数字"，防不住"叙述顺序"（比如用时间差制造因果感）。这类只能靠人读。

### 失败 2：标题评分器给了最高分之一条"有问题的标题"，而我差点没看出来

**发生了什么**：B1「AI 生成的东西，90% 的工夫花在证明它没骗你」拿到 77 分（全表第 2），钩子分还是全场最高（16）。评分器**没有**任何一条规则发现"90%"是编的。

**归因**：`credibility` 维度的规则是"夸张词 / 绝对化 / 无依据倍数词"——它按**词表**匹配，而"90%"不在任何词表里。词表能识别"震惊体"，识别不了"看起来严谨的伪精确"。

**改法**：

- 短期：人工评审必须回答一个问题——"标题里每个数字，我能在 30 秒内指出来源吗？"答不上就换（本次就是靠这条否掉了 B1）；
- 长期（未做，写在这里防遗忘）：给 `credibility` 加一条"数字有出处"的检查，把"标题里的数字"与 `数据/repo_facts.csv` 里的值做匹配，匹配不上就扣分。**这会误伤（有些数字是新的），所以需要人工复核队列**——和 C4C 的四档判定是同一个设计问题。

**这条失败的价值**：它让我确认了"评分器排序、人做判断"的分工是对的。反过来（人排序、机器判断）两个都会更差。

### 失败 3：数据截图改了 3 版，第一版根本不能看

**发生了什么**（任一都足以让图废掉）：

1. 5 个维度各自按满分归一后再堆叠，总宽 3,100px，分数被挤出画布；
2. `↳` 字形在微软雅黑里缺失，渲染成豆腐块；
3. 漏斗"互动 2.7 → 领取 4.6"，一个应该递减的漏斗中间变宽了；
4. 计数为 0 的桶画出一条 1px 的横线；
5. 同一张图左右两个数字不一致（3,531 vs 3,529）。

**归因**：

1. **我第一版是"按代码想象结果"**，没有"看图"。图是给人看的，不看就没有验收；
2. 参数表里 `convert_rate > engage_rate` 是逻辑错误，但它在数字上完全合法——只有画成漏斗才暴露；
3. 数字不一致是因为一处用 `ceil`、一处用硬编码的常量。**这正是文章里说的"两份实现"问题，只不过发生在同一个文件里。**

**改法**：每一步都 `read_image` 看一眼；把"漏斗必须单调递减"写成测试；所有交叉引用的数字统一从一个函数取。

## 四、做对了什么（要保留，不要下次丢掉）

1. **先勘察再动手**。第 1–2 轮没写一行正文，只读了挑战要求和仓库约定，后面所有产物都和既有风格一致（目录名、五件套、`--check`）。
2. **把判断外化成 JSON**。`title_rubric.json` 让我能"改规则 → 重算 → 看排序变化"，而不是每次重新想。
3. **人工否决保留记录**。B1 被否掉的理由写进了 `标题库.md`，一个月后还能知道当时为什么。
4. **每个数字都钉了截止点**。`master@099371a` 让"63 次提交"这句话永远可验证。
5. **复用而不是重写**。C4B 的转换器直接调用，顺手发现并绕过它目录漏条的缺陷。

## 七、这一关最想留下的结论

**内容传播里，"写"是最便宜的一步。**

真正决定结果的是三件事：
1. 有没有一个别人写不出来的观点（选题）；
2. 有没有一套能判断"哪条标题更好"的标准（评分）；
3. 有没有能力在发布后**诚实地**面对数字（口径与复盘）。

这三件事都不需要 AI 帮忙，AI 帮忙的是把它们**变成可执行的产物**：JSON 规则、生成脚本、`--check`、报告。这也是我在 C1–C6 学到的东西在这一关的用法。
