## 第 3 轮 · 环境排障（一次真实的失败）

**现象**：`pwsh` 执行任何命令都返回 `exit code: 3221225794`（`0xC0000142`，DLL 初始化失败），连 `"hello"` 都输出不出来。

**Prompt**
> 我的 shell 工具完全跑不了命令，返回 3221225794，可能是什么原因？先别改代码。

**AI 的产出**：判断是 Windows 会话/沙箱层的 DLL 初始化失败，不是命令本身的问题；建议先用只读工具（`glob`/`read`）继续勘察，改变会话策略后重试。

**结果**：策略变更后 `pwsh` 自愈。**但代价是真实的**：前 20 分钟我只能"读文件"，不能跑任何脚本——这也间接决定了后面的工作顺序（先读约定、再动手）。

**教训**：工具链坏了先别硬试，先换只读路径把信息拿全。这一段写在这里，是因为它确实影响了后面的节奏。

## 第 4 轮 · 选题（AI 的第一版被整篇否掉）

**Prompt v1**
> 帮我选一个适合"构建个人影响力"的文章题目。

**AI 的产出（v1）**：5 个方向，例如「AI 如何提升个人效率」「普通人如何用 AI 做副业」「我用 AI 一年读了 100 本书」，理由是"受众广、容易共鸣"。

**我否掉的理由**（原话记下来，因为这是本次最重要的一次人工干预）：

1. 这些题**我没有任何独有证据**。写出来就是二手的鸡汤，而评分维度第一条就是"有深度、有观点"。
2. 它们都是"正确但没人看"的类型——谁都能写，读者为什么要看我的。
3. 我的仓库里有 **3 个真实事故**：3 条被拦下的引用幻觉、审计器误伤真文献、按钮静默失效 3 分钟没人发现。这才是别人写不出来的东西。

**Prompt v2**
> 不要泛泛而谈。我的仓库里有 6 个挑战、3 个真实事故（假 arXiv ID、审计器误报、按钮 bug）。从这个材料里提炼一个**观点**，观点要能反驳"AI 提效"这种主流叙事。

**AI 的产出（v2）**：`AI 生成的东西，90% 的工夫花在证明它没骗你`，并给出"验收三层"（能跑 / 能复算 / 能截图）的骨架。

**我的判断**：骨架采纳，标题否决（见第 5 轮——那个 90% 是编的）。最终标题见第 6 轮的评分结果。

## 第 5 轮 · 事实核对（AI 编了 3 个"事实"）

**Prompt**
> 逐条核对你写进正文的每个数字和因果，标出来源；不能核验的标"待核"。

**抓到的问题**：

| AI 写的 | 实际 | 怎么发现的 |
| --- | --- | --- |
| "438 项自测" | **446 项** | 写脚本静态计数：`def test_` / `test(` 逐目录数；438 是它按根 README 的旧口径手算的，那里面 C3 记的是 32（实际 12） |
| "3 条 DOI 指向虚无" | 是 **1 个 arXiv ID** 指向另一篇真实论文 + 2 个编造标题 | 翻 `C2_交付/refs_check/VERIFICATION_LEDGER.txt` 与 C2 README 的"核验拦下的 3 次幻觉"表 |
| "一个按钮坏了三周" | **3 分 12 秒** | `git log`：`638b101` 引入、`e94f2a1` 修复，同一小时 |

**处理**：三处全部改写，并把"数字由脚本产出"升级成本关的硬规则（`tools/repo_facts.py` + `数据/指标口径.md`）。

**推送前又发现一个（同一个错误的第二个版本）**：文章写「63 次提交」，这个数是**浅克隆**里数出来的。推送前我 `git fetch --unshallow` 之后一看：真实是 **127 次**，而且远端还多了一个 C6A 目录。

浅克隆的 `git rev-list --count` 只数得到手上那截历史，它不会报错，只是安静地少算——**这正是「看起来对」的第三类**：工具没坏、命令没报错、数字就是错的。

修正后：63→127、446→464、1,320→1,355，并把正文里的 `master@099371a` 换成 `master@165f7d3`。为了让这类错误不再复发，加了三条测试：① 正文里的提交/文件/测试数必须等于快照；② 正文标题必须来自候选库；③ 正文引用的 commit 必须与快照一致。

**这一轮的意义**：这篇文章的主题是"AI 会编造格式合法的东西"，而 AI 在写它的时候编了 3 个数字。**如果不核对，这篇骂 AI 幻觉的文章本身就是一次幻觉。**

## 第 6 轮 · 标题评分器（2 版 + 1 个人工否决）

**Prompt v1**
> 帮我起 20 个公众号标题。

**AI 的产出**：20 条标题，风格高度雷同（全是"我 + 数字 + 学会了 X"）。

**我的判断**：问题不在质量，在**不可比较**——没有公式分类，没有评分口径，选哪个全凭感觉，也无法复盘。

**Prompt v2**
> 不要直接给标题。先定义 5 种可命名的标题公式，每种的适用场景写清楚；再定义 5 个可打分的维度（加起来 100 分），把规则写成 JSON，我可以用脚本打分。

**产出**：`数据/title_rubric.json`（5 维 + 长度分档 + 标题党扣分）+ 32 条候选。

**迭代细节（v2 → v3）**：

- v2 的问题：32 条分数挤在 56–77，`主推` 阈值 78 导致**一条都进不去**；两条"震惊体"对照标题拿到 54 分（"备选"），惩罚太轻。
- v3 的修正：① 提高 `hook` 权重上限的触发词；② 阈值改成 75/64/52；③ 增加**一票否决**（`veto.words` 命中即封顶 40、强制"弃用"）。
- 结果：F1/F2 掉到 40 分"弃用"；E4/B1 77 分、D6/A6 76 分、A2 75 分，五条进"主推"，用 `tieBreak`（具体性 → 钩子 → ID）定序。

**然后是我的人工否决**（比评分器更重要的一次判断）：

B1「AI 生成的东西，90% 的工夫花在证明它没骗你」77 分（第 2），钩子分最高（16 vs A2 的 12）。**我否了它**——因为那个 90% 没有出处，而整篇文章骂的就是"编一个格式合法的数字"。

接着我又否了两条更高的：E4（第 1，77 分）标题承诺的是"六关全景"，正文只讲验收；A6（第 4，76 分）承诺"每份交付物上线前都过一遍"，而这个流程我自己并不严格执行。最终用了 A2（75 分，第 5）——**评分器排序，人判断"这条我能不能兑现"**。完整否决记录写在 `文章/标题库.md` §5。

评分器抓不到这一点（`credibility` 里没有"百分比是否有出处"这条规则）。这件事写进了 [文章/标题库.md](文章/标题库.md) §5，也写进了 AAR §3：**评分器用来排序，判断留给人工。**

**顺带发现的 bug**：复用 C4B 的 `wechat_publisher` 渲染正文时，目录只出 5 条，而正文有 6 个小标题——它把第一个 `h2` 漏掉了。修法不是改 C4B（那是上一关的交付物），而是在 `build_article.py` 里按 `h2` 全集重排目录，并加了一条测试断言"目录条数 = 小标题数"。

## 第 8 轮 · 编码坑（BOM 害人不浅）

**现象**：`chartgen.py` 报 `KeyError: 'metric'`——`数据/projection_params.csv` 第一行的字段名变成了 `\ufeffmetric`。

**原因**：我用 PowerShell 的 `Set-Content -Encoding UTF8` 改过这个文件，那版 PowerShell 会给文件加 BOM；Python 的 `csv.DictReader` 不会自动去掉它。

**Prompt**
> CSV 读出来第一列名带 \ufeff，怎么改最稳？

**AI 的产出**：两个方案——① 每次写入时保证无 BOM；② 读取时用 `utf-8-sig`。建议**两者都做**，因为读者很可能用 Excel 打开再存一次（Excel 默认带 BOM）。

**处理**：① 所有读取改 `utf-8-sig`；② 我不再用 `Set-Content` 写这个仓库里的文本文件，改用编辑工具；③ 写了个一次性脚本把已污染的文件的 BOM 剥掉。

**副作用**：把 `utf-8-sig` 也误加到了**写入**路径上（会给输出加 BOM），被下一次 diff 发现后回滚。

## 第 9 轮 · 两套实现必须给同一个分

**Prompt**
> 标题评分要能在浏览器里实时算（JS），也要能在 CI 里批量算（Python）。怎么保证两边不会分叉？

**AI 的产出**：三条建议——

1. **规则单一真源**：所有词表、权重、阈值只写在 `title_rubric.json`，两边都读它；
2. **fixture 对账**：Python 生成 `tests/fixtures/title_scores.json`，JS 测试逐条比对；
3. **同序迭代**：两边都按 `dimensions` 数组顺序、规则数组顺序累加，连"先加 hook 再加 specificity"这种顺序也保持一致（浮点相同，顺序才有意义）。

**结果**：32 条 × 6 个字段 = 192 个数字，0 处不一致。**第一次跑就全绿，反而让我警惕**——所以又补了三条性质测试（越界、否决、排序）来确认不是"两边都错得一样"。

## 第 10 轮 · 控制台 app

**Prompt**
> 做一个零依赖的静态站，把文章、标题实验室、渠道、数据、复盘放在一起；要能在 `file://` 下跑。

**AI 的产出**：UMD 风格的 core 模块（`titlescore` / `metrics` / `utm` / `csv`）+ 纯渲染层 `ui.js` + 唯一持有状态的 `app.js`。数据不进 `fetch`，而是编译成 `data.js`。

**我的自查方式**：用 headless Edge 截图每个页签。

**抓到的两个问题**：

1. 增长图的图例压在 X 轴标签上（`D1..D7` 和"公众号/知乎/…"叠在一起）——加大 `viewBox` 高度、把 X 轴标签上移；
2. 标题页 h2 写"32 条候选"，旁边 tag 又显示"32 条"，重复——改成"候选标题 + tag"。

**为什么不用框架**：这一关的 app 只有 5 个页签、6 个纯函数模块。引入 React + 构建链，会让"双击就能用"变成"先 `npm i` 再 `npm run dev`"——对评审来说是一次不必要的失败机会。

| v1 | 用脚本画 6 张数据截图 | 3 处布局硬伤、字形缺失、数字不一致 |

**差异**：v2 把"好看"换成"可复算 + 可追溯"，也把我从"评审者"变成"必须看图的人"。

## 我在这 12 轮里学到的

1. **AI 最擅长生成"看起来完成了"的东西**：格式完整的表格、结构完整的文章、能跑的脚本。真正的时间花在"证明它真的完成了"。
2. **人工干预的价值集中在"选题"和"否决"两处**：选题决定有没有人看，否决决定会不会翻车。中间的执行环节，AI 比我快。
3. **把规则外化成 JSON 之后，AI 的两个实现才能被对齐**——这也解释了为什么"评分器"本身值得交付：它把我的判断变成了可复算的东西。
4. **每一次"跑起来看"都值得**：3 个数字硬伤、3 处图表硬伤、2 处 UI 问题，全是"看起来对"的东西被真正的执行暴露出来的。
