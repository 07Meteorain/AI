# 拿来说明

> 这一页写"为什么这么选"。每一条都是一个当时可以走另一条路的岔口。

## 1. 为什么写"验收"，而不是写"AI 提效"

**备选**：5 个"受众广"的题目（AI 提效、副业、读书法……）。

**选了验收**，三个理由：

1. **我有别人没有的证据**。3 条被拦下的引用幻觉、一个 4 档判定链、131 项测试、446 项测试总数——这些在仓库里能一条条点开。
2. **它能反驳主流叙事**。"AI 提效"是共识，"生成成本归零之后最贵的是验收"不是。反驳性观点才有被转发的理由。
3. **它解释了前面 6 关为什么长这样**。一个系列文章如果没有一个统一观点，就只是 6 篇作业。

**代价**：受众窄。关心"交付质量"的人远少于关心"如何用 AI 搞钱"的人。但窄受众的高认同，比宽受众的无感更适合第一篇。

## 2. 为什么标题里用"63 次提交"，而不是更有冲击力的"90%"

B1「90% 的工夫花在证明它没骗你」钩子分更高（16 vs 12），但它有一个致命问题：**90% 没有出处。**

而整篇文章的主题就是"AI 编了一个格式合法的数字"。用编造的数字换来点击，这篇文章就自我否定了。

所以选了 A2：每个数字都能在 `master@099371a` 上数出来。**具体数字反而比百分比更可信**——读者知道 63 次提交是真的，就更容易相信后面的话。

这条决策也暴露了评分器的边界（见 AAR §3 失败 2）：它能识别"震惊体"，识别不了"伪精确"。

## 3. 为什么"设计完 A/B 却决定不做"

原本计划把 A2 和 B1 各投一半流量测 CTR。算完放弃：

- 要在 9% 与 11% 之间分胜负，每臂需要 3,531 个样本；
- 首篇可用曝光 860，每臂只有 430，**12%**。

硬做的结果是：拿到一个 p≈0.4，然后写一句"B 组略高，可能更好"。这不是数据，是自我安慰。

**替代方案**：三条标题按周轮换做序贯观察，主指标换成转发率与收藏率（小样本下方差更小）。

**这个决策本身就是内容的一部分**——"先算做不做得了"比"做了一个不可判定的实验"更值得写进传播设计。

## 4. 为什么复用 C4B 的转换器，而不是自己写 Markdown → 微信 HTML

**理由**：C4B 的 `wechat_publisher.py` 是上一关自己写的、确定性的（同一输入必得同一输出），已经处理了公众号编辑器的坑（内联样式、外链清理、callout、目录）。

**代价**：它带了 4 个 pip 依赖（`markdown` / `beautifulsoup4` / `lxml` / `python-docx`），还会在缺依赖时**自动 pip 安装**——这在离线环境里是个隐患（已写进 README 的依赖说明）。

**收益**：少一套实现，就少一处会漂移的地方；而且**用它才发现它的目录会漏掉第一个 h2**（正文 6 个小标题，目录出 5 条）。这个 bug 是"读代码看不出来、用起来才现形"的典型，正好是本文主题的注脚。

**处理方式**：不改 C4B（它是上一关的交付物，改了会影响那关的验收），而是在 `build_article.py` 里按 `h2` 全集重排目录，并加测试固定住。

## 5. 为什么用 Pillow 手绘坐标系，而不用 matplotlib

**表面理由**：环境里没装 matplotlib。

**真实理由**：这一关交付的是"别人能复现的截图"，不是"一张好看的图"。

- matplotlib 的输出受版本、后端、字体配置影响，同一份数据在不同机器上像素不同；
- 手绘虽然啰嗦，但字号、颜色、坐标全写死，**同一份数据在任何机器上都落在同样的位置**；
- 更重要的是，手绘逼我把"这张图要证明什么"想清楚——标题、副标题、页脚（数据来源 / 口径提醒 / 生成脚本）都是画布上的固定位置，不写不行。

**代价**：改一次布局要重跑一次、看一次图。第一版根本不能看（AAR §3 失败 3）。

**折中**：`--check` 比对的是**数据指纹**（SHA256），不是像素——这样跨 Pillow 版本不会误报，又能抓住"数据变了图没重画"。

## 6. 为什么把仓库事实钉在 `master@099371a`，而不是动态计算

**问题**：文章写"63 次提交"。C7 一提交，这个数就变成 64+，文章立刻说假话。

**方案 A（动态）**：CI 里现算。**不行**——GitHub Actions 默认 `fetch-depth: 1`，浅克隆下 `git log -- <dir>` 只能看到 1 条记录，算出来是错的。

**方案 B（快照 + 截止点）**：`repo_facts.py` 在本地按完整历史生成 `repo_facts.csv`，钉死 `as_of_commit`；正文同时写明"截止 `master@099371a`"。

选 B。**数字必须带时间与出处，否则它一定会过期**——这就是文章里"12 条验收清单"的第 10 条，我自己的文章不能违反。

**代价**：快照会旧。所以 `--check` 校验"内部一致性"（自报=实测、合计对得上），而不是"和最新 HEAD 一致"。

## 7. 为什么只投 4 个渠道，而不是"全平台分发"

| 渠道 | 判断 |
| --- | --- |
| 公众号 | 主阵地：能放全文、能做转化位、能沉淀订阅 |
| 知乎 | 长文匹配、搜索长尾强，内容能被反复检索到 |
| 小红书 | 卡片形式匹配"清单"类可收藏内容 |
| 即刻 | 单条即可，成本最低，适合测钩子 |
| 微博 / B站 / 视频号 | **不做**：需要持续高频或视频能力，一次投放 ROI 为负 |

**"全平台"是传播里最常见的错觉**：每个平台都要一套编排、一套互动、一套数据回收。4 个渠道已经需要 10 条发布清单；7 个渠道的结果通常是"每个都发了，每个都没人管"。

**写清楚边界比硬凑诚实**：`多平台改编.md` §5 明确列出不投的平台与原因。

## 8. 为什么 app 不用框架（React/Vue/构建链）

**判据**：这个 app 有 5 个页签、6 个纯函数模块、1 份静态数据。

**结论**：引入 React + Vite 的收益（组件复用、状态管理）在这个规模下几乎为零，成本（评审要先 `npm i`）却是确定的一次失败机会。

**做法**：普通 `<script>` + UMD，浏览器挂 `window.*`，Node 里 `module.exports`——**同一份文件**既被 app 加载、也被测试加载。这就是"测的就是跑的"。

**代价**：没有按需加载、没有类型检查。用 47 项测试补一部分。

## 9. 为什么截图里的传播数字是"推演"而不是"实测"

因为还没发布。三个选项：

1. 不画传播图，只画"能算的"（标题评分、正文体检、仓库事实）；
2. 画假的实测数据（**不可接受**）；
3. 画推演，并把参数、公式、误差范围全部公开。

选 3。理由：**复盘需要"预期 vs 实际"**。没有事先写下的预期，发布之后只能说"还不错"。`projection_params.csv` 就是这份可被证伪的预期——它现在写着 962 次进入正文，如果实际是 200，那张图会把我的高估直接画出来。

这也是为什么每张传播图的页脚都有一句："这是发布前的推演，不是线上截图。"

## 10. 为什么"一票否决"用词表，而不是更聪明的模型判断

标题评分里加了一条：命中"震惊 / 必看 / 99% / 绝对 / 史上最"即封顶 40 分、强制弃用。

**为什么这么粗暴**：因为粗暴的规则**可解释、可复算、可争论**。模型判断"这个标题有点标题党"没法写进 JSON，也没法在测试里断言。

**代价**：会误伤。比如"99% 的人都忽略的一步"其实是好标题的写法，但在我的规则里直接封顶。

**接受这个代价**：这类标题在我的账号定位下不值得冒险；如果将来要放宽，就改 `veto.words`，而不是改逻辑——**规则和数据分开**，这是我在这 6 关里最常用的一条设计。
