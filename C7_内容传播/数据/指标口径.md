# 指标口径

> 这份文件只有一个作用：让每一个出现在文章、图表、app 里的数字，都能被指到"它是从哪来的、能不能复算"。

## 一、三类数据，必须分开标注

| 类型 | 含义 | 例子 | 谁生成 | 能不能复算 |
| --- | --- | --- | --- | --- |
| **仓库事实** | 仓库里客观存在的数 | 127 次提交、1,355 个文件、464 项测试 | [`tools/repo_facts.py`](../tools/repo_facts.py) | ✅ 有完整 git 历史即可复算 |
| **正文实测** | 从文章源文件直接解析 | 2,529 字、36 段、8.4 分钟阅读 | [`tools/chartgen.py`](../tools/chartgen.py) | ✅ 解析同一份 Markdown |
| **评分结果** | 由公开规则算出来的分 | 32 条标题的五维得分 | [`tools/title_score.py`](../tools/title_score.py) | ✅ 规则在 `title_rubric.json` 里 |
| **推演值** | 还没发生、按公开参数算出来的数 | 曝光 9,860、进入正文 962 | `projection_params.csv` → `chartgen.py` | ✅ 可复算，但**它不是实测** |

**没有第四类。** 这张表里不存在"我估计大概有几千阅读"这种数字——要么有脚本，要么写在参数里，要么不写。

## 二、仓库事实（`数据/repo_facts.csv`）

| 指标 | 定义 | 计算方式 |
| --- | --- | --- |
| `files` | 该目录下的文件数 | 递归遍历，排除 `.git` |
| `kb` | 该目录总字节数 / 1024 | 同上 |
| `commits` | 触及该目录的提交数 | `git log -- <dir>` 的行数 |
| `tests_computed` | 可执行测试用例数 | Python: `^\s*def test_`；JS: `test(` / `it(` 静态计数 |
| `declared_tests` | 该关 README 自报的测试数 | 手工登记在 `declared_tests.csv`，**带出处与证据串** |

两条硬规则：

1. **自报与实测必须相等**，不等就是 README 或代码有一方在说假话（`repo_facts.py --check` 会红）。
2. **快照钉在 `master@165f7d3`**（2026-11-15，C7 提交之前，含 C6A）。提交数每天都在涨，所以文章写"63 次提交"必须同时写明"截止哪个 commit"，否则三天后这句话就是假的。

> **计数必须在非浅克隆上做。** 我第一次统计用的是 `--depth 50` 的克隆，`git rev-list --count` 安静地返回了 63（真实 127）——
> 命令没报错，数字错了一半。这是「可复算」最容易骗人的地方：**能跑出数字 ≠ 数字对**。

> 为什么不在 CI 里现算：GitHub Actions 默认 `fetch-depth: 1`，浅克隆下 `git log -- <dir>` 只能看到 1 条记录，算出来的提交数是错的。所以 CI 只校验快照的**内部一致性**（自报=实测、证据串存在、合计对得上），重算放在本地。

## 三、正文实测（`chartgen.py` 直接解析 `文章/正文.md`）

| 指标 | 定义 | 备注 |
| --- | --- | --- |
| 正文字数 | 去掉 `#`、`|`、`>`、`---` 开头的块后，去空白字符数 | 不含标题、表格、引言块 |
| 段落数 | 上述块的个数 | 按空行分段 |
| 平均段长 | 字数 / 段落数 | 手机屏一屏约 90–110 字 |
| 预计阅读 | 字数 / 300 | 中文默认 300 字/分钟，**是估算** |
| 小标题数 | `## ` 开头的块数 | — |

## 四、推演值（`数据/projection_params.csv`）

首篇发布前后的真实数据还没产生，所以先按**公开的参数**推演。参数全部可改，改完重跑 `python tools/chartgen.py` 就得到新图。

| 参数 | 含义 | 公众号 | 知乎 | 小红书 | 即刻 | 取值理由 |
| --- | --- | --- | --- | --- | --- | --- |
| `exposure` | 首日可用曝光 | 860 | 4,200 | 3,600 | 1,200 | 公众号=粉丝+群转发；其余=推荐流首日曝光（新号量级） |
| `open_rate` | 打开率 | 9% | 100% | 100% | 100% | 公众号新号常见 6–12%，取中位偏低；其余平台"看到封面即算曝光" |
| `click_rate` | 进入正文比例 | 100% | 6.5% | 11% | 18% | 公众号打开即正文；信息流平台封面点击 6–18% |
| `read_through` | 读完率 | 42% | 35% | 28% | 55% | 短文 + 强结构，读完率高于图文均值 |
| `engage_rate` | 互动率（点赞/收藏/评论任一） | 3.5% | 2.2% | 6.0% | 9.0% | 小红书收藏率高，即刻互动密度高 |
| `convert_rate` | 回复关键词领清单 | 1.6% | 1.2% | 0.8% | 2.0% | 引导语在文末，转化递减 |

**为什么敢写推演值而不是空着**：复盘需要"预期 vs 实际"。没有事先写下的预期，发布之后只能说"还不错"。这张参数表就是可被证伪的预期——真实数据回收后覆盖 `数据/metrics.csv`，同一张图会把误差暴露出来（见 AAR 复盘 §4）。

## 五、A/B 的统计口径

- 判据：双比例检验（双侧 α=0.05，功效 0.8）
- 所需每臂样本：`n = (z_a·√(2·pm(1-pm)) + z_b·√(p1(1-p1)+p2(1-p2)))² / (p2-p1)²`，`pm=(p1+p2)/2`
- 想区分 9% 与 11%：**每臂 3,531**，合计 7,062
- 首篇实际可用：860 次曝光 → 每臂 430，**只有所需量的 12%**

结论写在截图 04 里：**这个账号量级做不了 A/B**，硬做只会得到"看起来有差异"的噪声。替代方案是三条标题按周轮换做序贯观察，主指标换成转发率与收藏率（在小样本下方差更小）。

## 六、已知误差与局限

1. **推演 ≠ 实测**。参数取值来自公开经验与同类账号，个体差异可能到 ±50%。图的标题与页脚都标了"推演"。
2. **读完率无法直接测**。公众号后台只有"阅读完成率（估算）"，其他平台不提供；这里的 42% 是估计值。
3. **"回复关键词"转化无法离线验证**。真实转化需要公众号后台数据，本期只能给设计，不能给实测。
4. **测试计数是静态的**。`def test_` 计数会把被 `@skip` 的用例也算进去；它衡量的是"写了多少测试"，不是"跑了多少通过"。
5. **文件数与字节数含二进制**。`C1_交付` 39.9 MB 主要来自 PDF 源材料，不代表工作量。
