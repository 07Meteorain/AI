127 次提交、464 项测试：验收的三条硬结论

Meteorain · 2026-11-15

从一个「测试全绿但按钮是坏的」下午，到一个点开能访问却指向别的论文的 arXiv ID，我发现真正贵的不是"让 AI 写出来"，而是"确认它写对了"。这是一份关于验收的实录，和一张可以逐条打勾的清单。

我用大半年的时间做了 6 个 AI 方向的主关挑战（前后 14 个交付目录）：翻译一套课程资料、写一篇带参考文献的论文、做一个 prompt 静态检查器、做一个上线前的 prompt 体检工具。最后攒下 127 次提交、1,355 个文件、464 项自测。

如果只看结果，这像是一条"AI 帮我干了很多活"的进度条。

但真正让我印象深刻的，是另外三个瞬间：

  • C2，论文里 17 条参考文献，AI 生成了 3 条幻觉：一个格式合法、点开能访问、但指向另一篇论文的 arXiv ID，和两个凭空编出来的标题。
  • C4C，我把这套核验做成通用审计器。第一版拿 C2 那 17 条已核验的真文献当测试集，误报了 3 条。
  • C6，交付当天的最后几分钟，我发现"忽略这一条"按钮从写下的那一刻起就是坏的。点下去没反应，控制台里也没有任何报错。

这三个故障有个共同的形状：它们都不是"跑不起来"，而是"跑起来了，而且看起来是对的"。

这就是我今天想说的那件事。

一、最贵的假，是「格式合法」的假

C2 的 3 条幻觉里，最危险的不是那两个编出来的标题——它们经不起一次搜索。

最危险的是那个 arXiv ID：2406.14405，格式完全合法，链接能打开，页面有标题、有作者、有摘要。它甚至真的存在。只不过它指向的是另一篇论文（Hetzel 与 Starke 关于 $L^p$ 逼近的工作），而不是 AI 声称的那篇。

你点开链接，浏览器告诉你"这是一个 arXiv 页面"，然后你就信了。

这就是 AI 幻觉最难防的形态：它伪造的不是内容，是证据的格式。 格式是标准化的、公开的、可枚举的：你知道 arXiv 的 ID 长什么样，它就给你一个长得一模一样的；你知道 BibTeX 有 12 个字段，它就把 12 个字段填满，一个不空。

格式越标准，越难靠"读一遍"发现。

后来我的验收方式变成了一份核验台账：每条引用同时查 Crossref 和 OpenAlex，标题的 token-set F1 ≥ 0.90、年份差 ≤ 1、双源交叉确认，才算通过。3 条幻觉全部被拦下，17 条真文献全部留下（台账在仓库 C2_交付/refs_check/VERIFICATION_LEDGER.txt）。

这件事改变了我对"验收"的理解：

验收不是"再读一遍"，而是"找一条独立于生成过程的、能被机器裁定的证据"。

"再读一遍"用的是同一套语言模型直觉，它当然看不出自己刚编的东西哪里不对。核对元数据用的是外部数据库，它不需要相信任何人。

二、第一版审计器误伤真文献，我差点把它做废

C4C 里我把这套流程做成了通用工具：解析参考文献，查 DOI，查不到就报错。

第一版拿 C2 那 17 条真文献当测试集——它报了 3 条"疑似编造"。那 3 条是真的，只是没有 DOI（会议论文与 arXiv 条目）。

那一刻我差点放弃这个工具。逻辑上它没错，"查不到"确实是"查不到"。但它没用，因为它把"我不确定"说成了"它是假的"，而这两种错误对使用者的代价完全不同：

  • 漏掉一条假引用，你丢的是一次严谨；
  • 冤枉一条真引用，你丢的是对工具的信任。

改法是把它拆成四档，只有最后一档才报错：

判定 条件 处理
可核验 DOI/arXiv 命中且元数据一致 通过
可检索 无 DOI，但标题能在数据库中命中 通过，标注"无 DOI"
待人工 查不到，但格式与主题都合理 不报错，进人工队列
明确矛盾 元数据互相冲突（年份/作者/期刊不符） 报错

改完之后，同一批双语料，零误报。

这条规则后来被我复用到所有工具里：工具的第一版不是用来"抓错"的，是用来"不冤枉人"的。

三、静默失效：没人验收的功能等于不存在

C6 那个按钮的问题更隐蔽。它的事件处理需要从 data-line 属性里读行号，重构的时候这个属性丢了。点击时读到 undefined，抛错，被一个 try/catch 吞掉。于是：按钮是灰的，但它看起来就应该那样。

130 项测试全绿。因为测试覆盖的是纯逻辑模块——解析、规则、门禁、导出——而坏掉的，是"逻辑"和"DOM"之间的那根线。

这个 bug 在 git 历史里只活了 3 分 12 秒（638b101 引入，e94f2a1 修复）。但它不是被测试抓住的，是我在浏览器里点了一下才发现的。第 131 项测试，是修完它之后补上的。

我补了三样东西：

  1. 一条 UI 测试：渲染 → 模拟点击 → 断言状态真的变了。不测"函数被调用"，测"界面有反应"。
  2. 一条资源存在性测试：解析 index.html 里的 <script src> 和 Service Worker 的预缓存清单，断言这些文件都在。线上 404 是最难在本地复现的故障。
  3. 一条"反向测试"：断言合格的样例必须零命中。任何人加规则时如果误伤了正常内容，这条测试立刻变红。

第 3 条现在是我认为最重要的一条测试。它保护的正是第二节那类错误：不是"该抓的没抓到"，而是"不该抓的抓到了"。

四、把验收拆成三层

做到这里，我发现"验收"其实可以拆成三个可独立设计的层，而且一层比一层便宜：

层 问题 做法 成本
能跑 换台机器能不能起来？ 一条命令从零跑通，零依赖优先 一次性
能复算 同样的输入，输出一样吗？ 所有数字由脚本产出；文档由代码生成，带 --check 漂移检测 一次性
能截图 别人凭什么相信？ 结论要能变成一张图、一份报告，且别人能复现这张图 一次性

三层都不贵，但都要求同一件事：在开始做之前就设计好"它将来怎么被验收"。

反过来，凡是做完才想"怎么证明"的活，最后都会变成"我读了一遍，感觉没问题"。

五、12 条验收清单

以下是我现在每个交付物上线前会逐条过的东西，可以直接抄：

  1. 有没有一条命令，能从干净环境跑通全部？
  2. 有没有一条反向测试：正确的输入必须不被判错？
  3. 所有出现在报告里的数字，是不是都由脚本生成，而不是手打的？
  4. 生成的文档有没有漂移检测（改了代码忘了改文档会红）？
  5. 有没有一条测试，专门验证"声称存在的文件真的存在"？
  6. 依赖是不是越少越好？每多一个依赖，第一次打开的人就多一次失败机会。
  7. 失败时会不会说话？报错能不能定位到行、到文件、到规则？
  8. 有没有把"我不确定"和"它是错的"分开处理？
  9. 有没有一个可以在 30 秒内验收的入口（一个链接、一张图、一条命令）？
  10. 结论有没有注明时间与口径（价格快照日期、样本量、估算误差）？
  11. 有没有写清楚"这个工具做不到什么"？
  12. 如果我现在把这份东西交给一个陌生人，他能不能只靠 README 跑起来？

第 11 条很多人会跳过，但它是可信度的来源之一。一个敢说"我做不到 X"的工具，它说的"我能做到 Y"才值钱。

六、三条硬结论

现在让 AI 写出一份看起来专业的交付物，几乎不要钱。所以稀缺的东西变了，我把这半年的结论压成三条：

结论一：验收的第一步是找到"AI 控制不了的证据"。
不是"再读一遍"，而是 DOI 元数据、测试断言、可复算脚本。只要证据来自同一套语言直觉，它就验不出幻觉。

结论二：好工具的标志是"不冤枉人"，不是"抓得多"。
把"不确定"和"是错的"分开，把正确样例零命中当成最高优先级的回归测试。误伤一次，工具就废了。

结论三：验收要能被别人重跑，否则它只是你的自信。
数字有脚本、截图有指纹、文档有漂移检测。一条结论如果换个人复现不出来，它就不是结论，是说法。

我见过太多团队在同一个地方摔跤：生成环节上了工具，验收环节还在靠人眼。结果就是产能上去了，事故密度也上去了，而人的注意力全被拖进了"再读一遍"里。

把验收做成基础设施，是我这半年最确定的一个结论。它不性感，但它是唯一能让产出规模变大的同时不增加风险的做法。
