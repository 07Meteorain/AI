## 3. 做对的三件事（想保留）

### 3.1 先让工具在**真实数据**上跑，再写文档

第一版没有写任何文档就跑真实数据，结果 10 分钟内暴露了 5 个 bug。
如果先写 README 再跑，文档会自信地描述一个错误的工具 —— 而且很难回头改。

**证据**：`demo/复跑对比.md` 里三轮运行结果，每轮都对应一次真实修正。

### 3.2 用「不可验证就标需人工」代替「猜一个分数」

第一版把不认识的维度算成 0 分，于是 C3 只有 25 分 —— 看起来像学生做得差，实际是工具看不懂。
改成「需人工」并单列覆盖率后，报告第一次变得可信：能看的地方给证据，看不见的地方直说。

### 3.3 每条结论都能被核对（给路径，或给缺失对象名）

报告里命中的条目后面跟文件路径；缺失的条目给不出路径，就给出**缺的是哪个文件名**。
助教可以点开反驳，我也在核对时用这个功能反查了 10 个误判
（例如「C5 没有使用说明」→ 打开 README 发现第 6 行就是「## 30 秒验证」）。

> 这条起初写成「每条 ❌ 都带证据路径」，验收脚本第一次跑就把它判为不成立 ——
> 缺失文件本来就没有路径可给。**声明要跟着事实改，而不是让脚本放宽标准。**

## 5. 五个为什么：为什么第一版给 C3 打 25 分？

1. **为什么是 25？** 因为 6 个维度里 3 个拿了 0 分（参与质量 25 + 内容实质 20 + 协作贡献 15）。
2. **为什么这 3 个是 0？** 因为检查项挂在不存在的维度 id（`delivery`/`problemSolving`…）上，真实维度没人认领。
3. **为什么挂错？** 设计时只打开了 C8 的 `challenge.json`，没看其他 10 份。
4. **为什么只打开一份？** 我把「C8 的 rubric」当成了「平台的 rubric 模型」—— 一个没有验证的假设。
5. **为什么这个假设没被拦住？** 因为第一版的验证方式是「它在我自己的挑战上能不能跑」，而输入多样性从来没有进入检查清单。

> 根因不是编码错误，是**验证策略错误**：只验证了单一输入。
> 改法也不是「再仔细一点」，而是把「用全量真实输入跑一遍」变成流程的固定一步（见 §6 改进 1）。

## 8. 真实项目与练习的差异（C8 的核心问题）

| 维度 | 练习（C3–C7） | 真实项目（C8） |
| --- | --- | --- |
| 输入 | 自己造的数据，边界自己定 | 平台导出的 11 份记录 + 1331 个真实文件，**改不了** |
| 需求 | 挑战文件写死 | 写着写着会被真实数据改（5 个通用维度 → 23 个自定义维度） |
| 失败成本 | 改一版重跑 | 一次误判就会让学生去补不存在的文件，**误报比漏报更贵** |
| 验证 | 自己觉得对 | 必须能被别人逐条反驳（证据路径） |
| 完成标准 | 测试全绿 | 测试全绿 **且** 在真实数据上说真话 |
| 时间 | 想多久都行 | 2.4 小时（含三轮核对），超时就要砍范围 |
| 评价者 | 自己 | 助教 / 老师，且他们不会装环境 |

最直接的一条体会：**练习里「跑通」就是完成，真实项目里「跑通」只是开始 —— 后面还有「说的是不是真的」。**

## 9. 未解决与边界（不藏）

1. **文件名 ≠ 语义**：C9 的 AAR 叫 `反思报告.md`，平台要 `AAR_W`，工具判缺失。语义等价需要人判断，工具只报事实。
   目前靠 `mapping.json` 只能映射目录，不能映射文件；下一步可以加 `file_aliases`。
2. **维度映射仍是硬编码表**（23 个 id）：平台若新增维度，只能落到关键词兜底或「需人工」。
3. **没有真实第三方反馈**：三轮核对都是自己做的，视角单一。助教视角的检查清单是「模拟」的，不是真的。
   补救办法已写进验收单（让使用者勾选）。
4. **阈值是经验值**：AI 日志 ≥2000 字符、≥3 轮、README ≥400 字符 —— 都是这次数据上试出来的，换一批交付可能要调。
5. **C3 类维度天生不可验证**：群内参与、内容实质，工具永远只能看「有没有记录」，看不到「记录是不是真的」。

> 这 5 条不是免责声明，是**下一版的任务清单**。

## 10. 交付期间的外部变更（真实项目专有，练习里没有）

这次在「本地做完、准备推送」的窗口里，发生了一件练习项目永远不会发生的事：

```text
$ git push origin master
 ! [rejected]  master -> master (fetch first)
error: failed to push some refs
```

远端 `master` 在我构建期间前进了 1 个提交 —— 另一个会话交付了 `C6A`（`165f7d3`，约 40 个文件）。
我的本地是浅克隆（`--depth 1`），既没有那个提交，也没有它的历史。

三件事值得记下来：

1. **没有硬推**。`--force` 能让我「成功」，但会抹掉别人的提交 —— 这是真实项目里最不可接受的省事方式。
2. **先合并、再重跑、后改文档**。合并带来的冲突在根 `README.md`（双方都插了目录行与章节）：
   我以远端版本为底，重新插入 C8 的目录行与章节，然后 `git add` → merge commit。
3. **C6A 一出现，我文档里的数字就过期了**。解决方式不是改口，而是**重跑**：C6A 从「无目录」变成 84/100，
   缺 12/40（原 16/40），7/11 通过（原 5/11）。文档跟着重跑结果改，并注明「C6A 是并发补交」。

这次外部变更没有增加「工具 bug」，但它验证了一件事：**真实项目的输入会在你收尾时改变**。
AAR 上次写「需求会被数据改」，这次是「仓库会被别人改」。
