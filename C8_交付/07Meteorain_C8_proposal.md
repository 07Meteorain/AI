## 一、真实需求从哪里来

C8 的要求是「明确真实需求与验收标准」。这一节是我的需求证据链 —— 不是编的访谈，是可复现的三个来源。

`challenge.json` × 11 份，字段里写着硬约束：

| 字段 | 实际内容 | 意味着什么 |
| --- | --- | --- |
| `required_deliverables` | 40 条，4 种写法 | 少一个文件就是「核心交付物缺失」，该项最高 5 分 |

## 二、需求（R1–R6，按优先级）

| 编号 | 需求 | 优先级 | 验收方式 |
| --- | --- | --- | --- |
| R1 | 一条命令检查全部挑战，结果可导出 | P0 | AC1 |
| R2 | 每条必需交付物都有「命中/缺失 + 证据文件」 | P0 | AC2 |
| R3 | 按**每个挑战自己的**维度给出可核对信号，而不是套 5 个通用维度 | P0 | AC3 |
| R4 | 红旗项按平台规则封顶，且可复现 | P0 | AC4 |
| R5 | 零依赖、离线、双击可用（助教不会装环境） | P1 | AC5 |
| R6 | 明确说出「哪些维度工具看不见」 | P1 | AC8 |

明确**不做**的（非目标）：

- 不给成绩、不做排名 —— 评分是人的事，工具只提供证据；
- 不判断内容质量（观点对不对、文笔好不好）—— 需要阅读，不需要匹配；
- 不接 LLM、不联网 —— 结论必须可复现，同一份仓库两次跑必须一致；
- 不做 Web 服务 —— 助教不该为了抽查去装 Node、起端口。

## 三、验收标准（AC1–AC8，全部可执行）

| 编号 | 标准 | 怎么验证 | 结果 |
| --- | --- | --- | --- |
| AC1 | 一条命令在真实数据上 2 秒内出三份报告，退出码 0（全通过）/1（有缺口） | `python -m submitgate check` | ✅ 1.0 秒，退出码 1（有真实缺口） |
| AC2 | 40 条必需交付物逐条有结论与证据文件 | 报告 §三 每挑战的「必需交付物」表 | ✅ 40/40 条有结论 |
| AC3 | 每个挑战的维度都标注「可验证/需人工」；可验证维度覆盖 ≥ 85% 的分数 | 报告顶部覆盖率 + 各挑战维度条 | ✅ 可验证 30/35 维（见 §五） |
| AC4 | 三类红旗各造一个反例，全部触发并封顶 5 分 | `python -m unittest tests.test_checks` | ✅ 3 个红旗测试 |
| AC5 | 无第三方依赖；Python 3.9+ 直接跑 | `pip list` 无关；`python -m submitgate selftest` | ✅ 仅标准库 |
| AC6 | 至少 3 轮真实运行记录 + 前后对比 | `demo/复跑对比.md`、`demo/终端_*.txt` | ✅ 3 轮（2.0.0 → 2.1.0） |
| AC7 | 报告三形态；HTML 单文件离线可开、无外部请求 | 断网双击 `demo/导航站.html` | ✅ 无 `<script src>`、无外链 CDN |
| AC8 | 边界写清楚：不可验证维度不计 0 分，且单列覆盖率 | 报告顶部声明 + README §八 | ✅ 7 条边界 |

## 四、约束（真实约束，不美化）

| 约束 | 具体表现 | 对设计的影响 |
| --- | --- | --- |
| 一个人 + 一个 AI agent | 没有团队 review，只能靠自动化验证 | 75 项测试先写；每条结论必须能被机器复算 |
| 无后端、无服务器 | 只有静态文件与本地 Python | 报告必须是**文件**，不能是接口 |
| 不能联网 | 助教的机器不一定能访问课程平台 | 11 份挑战记录随交付打包（`challenges/`） |
| Windows + 中文路径 | `E:\我的挑战\C8\C8_交付`，PowerShell 输出编码 GBK | 全程 `pathlib` + UTF-8；CLI 强制 stdout UTF-8 |
| 平台数据只读 | 不能改 `challenge.json` | 只解析、不改写；缺字段按空处理 |
| 截止 2026-12-31 | 实际 2026-11-15 交付 | 提前 46 天；余量用于 C9/C10 复跑 |

## 五、方案概要

```
challenges/*.json ──┐
                    ├─→ challenge.py（解析 40 条交付物 + 23 个维度 + 3 类红旗）
mapping.json ───────┘
                          ↓
仓库目录 ──→ mapping.py（C3 ≠ C3C；别名 C9→C2A_C9_交付；孤立目录）
                          ↓
              checks.py（交付物层 → 维度层 → 红旗层）
                          ↓
        report.py（Markdown / JSON / 单文件 HTML）
                          ↓
     退出码 0/1/2 ── 可接 CI；报告可被人逐条反驳
```

三个关键取舍（完整推理见 [`07Meteorain_C8_拿来说明.md`](07Meteorain_C8_拿来说明.md)）：

1. **维度不写死**：平台维度是每个挑战自定义的，写死 5 个 id 会让 3 个维度静默归零（第一版就踩了）。
2. **红旗照抄封顶**：加权平均会把致命伤稀释成小瑕疵。
3. **不可验证就标「需人工」**：把「工具看不见」写成「没做」，是评审工具最严重的说谎方式。

## 七、风险与对策

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
| 误报让学生「以为自己没交」 | 高 | 高 | 每条结论带证据路径；三轮真实数据人工核对（改掉 10 个误判） |

| 文件名匹配 ≠ 语义等价 | 高 | 中 | 明说这是边界（README §八 第 3 条），并保留 `mapping.json` 扩展 |
| 阈值是经验值 | 中 | 中 | 阈值集中代码常量，改一处生效；报告里写出具体数值 |
| 助教不看报告 | 中 | 高 | 三形态：Markdown（GitHub 直接读）、HTML（双击）、JSON（CI） |
