## 1. 拿了什么

| 来源 | 拿了什么 | 怎么用的 |
| --- | --- | --- |
| **平台 `challenge.json`**（本交付 `challenges/` 快照） | 11 个挑战的 40 条必需交付物、23 个维度、3 类红旗、截止时间 | **直接作为输入**，不转述、不改写；报告里每条检查都能回到这份原文 |
| 本仓库 **C4A_交付（技能评审器）** | 「一票否决」与「每条判定带证据」的两个原则；`low confidence` 要主动标记 | 红旗命中即封顶（不做加权稀释）；报告每条结论后面跟证据路径；不可验证的维度标「需人工」 |
| 本仓库 **C5_交付（promptlint）** | 「退出码 0/1/2 当门禁」的形态；「误报要留边界」的写作纪律 | `check` 的退出码 0/1/2；README「已知边界」7 条 |
| 本仓库 **C6_交付（PromptGate）** | 「门禁与健康分分离」的教训；单文件、离线、双击即开的报告形态 | 演化为「门禁结论（PASS/FAIL）」与「可验证分（仅定位用）」分离；`导航站.html` 单文件无外链 |
| 本仓库 **C1_交付** | 静态 HTML 站点「零环境可用」的取向 | HTML 报告内联 CSS、无 CDN、无 `<script src>` |
| 本仓库 **C3_交付（提问体检器）** | 一个真实排障案例：`0xC0000142` 进程创建失败 | 本次环境勘察遇到同一个错误码，直接复用当时的判断（沙箱失败 ≠ 命令写错） |
| 本仓库 **C5A_仓库分析** | 「读仓库要量化」的方法：文件数、目录结构、健康度 | 用 1331 文件 / 13 个交付目录 / 40 条交付物量化问题规模 |

**明确没有拿的**：

- **C4A 的 Python 代码**：它是「给一份提交打分」的单文件脚本，判定项硬编码在代码里；本项目要的是「按每个挑战自己的维度生成检查」，结构完全不同，照搬只会带回它的假设。
- **C5 的规则引擎**：C5 检查的是 prompt 文本结构（正则 + token），本项目检查的是文件系统事实（路径、体积、章节、git 时间），没有可复用的实现。
- **C6 的前端**：C6 是交互式应用，本项目只需要一个静态报告；引框架会把「双击即开」变成「先 npm install」。
- **C2 的文献核验逻辑**：与本题无关。

## 2. 五个关键决策

### 决策 1：维度不写死 —— 从「5 个通用维度」改成「23 个 id 的映射表」

**取舍**：最省事的写法是写死 C8 的 5 个维度（`delivery`/`problemSolving`/`artifactCompleteness`/`aiUsage`/`reflectionQuality`）。
第一版就是这么写的，结果真实数据上 C3 只有 25 分 —— 因为 C3 的维度是 `participationQuality`/`substance`/`collaboration`。

**改了什么**：新增 `profiles.py`，把 23 个维度 id 显式映射到证据类别（repo / community / engineering / product / data / content / collab / transfer / gitpractice / docs），未知 id 用关键词兜底，再兜不住就落「需人工」。

**代价**：多一个模块、多 23 行映射表；平台新增维度时仍需加一行。

**为什么值得**：写死维度会让 45–50 分**静默归零**，而报告看上去完全正常 —— 这是最危险的一类错误：**没人会去核对一个「看起来合理」的分数**。

---

### 决策 2：红旗照抄平台的惩罚逻辑，不做加权平均

**取舍**：常见的评分实现是「加权总分 → 低于阈值不通过」。这里把两件事彻底分开：

- **门禁**：必需交付物缺失 / 红旗命中 → 直接 FAIL，与其它维度得多少分无关；
- **可验证分**：加权通过率，只用来定位「该补哪里」，不参与判定。

**为什么**：C4A 里踩过这个坑 —— 一份硬编码本机路径的提交，因为有「安装说明」加分，最后拿到 57% 的「部分满足」。
平台的 `red_flags.maxScore = 5` 已经写明了它的态度：**这类错误不该被平均**。工具不应该比平台更宽容。

**代价**：会出现「C3 可验证 55 分但 PASS」这种反直觉组合。所以报告里必须解释：
「PASS 只看必需交付物与红旗；分数是阅读指标」。

---

### 决策 3：不可验证的维度标「需人工」，不计 0 分

**取舍**：C3 的「群内参与质量」、C10 的「记忆系统」，文件系统根本看不见。
两种做法：算 0 分（简单，但等于说学生没做），或标「需人工」（诚实，但要额外解释覆盖率）。

**为什么选后者**：第三轮核对时发现，C3 因为 3 个维度算 0 分，总分只有 25 —— 与真实的交付质量严重不符。
**把「工具看不见」写成「没做」，是评审工具最严重的说谎方式**：它会让学生去补一个根本不需要补的东西，也会让助教误判。

**代价**：总分不再是「满分 100」，而是「可验证 X/Y」。报告顶部必须解释覆盖率，否则助教看不懂 55/100 是什么意思。

**验证**：C3 现在覆盖 6/6 维（`participationQuality` 通过文件名点名命中「参与记录表」，但因是模板只得 8/25）；C9 覆盖 4/5（`initiative` 无证据 → 需人工）。

---

### 决策 4：文件名匹配 + `mapping.json`，不猜语义

**取舍**：C9 的交付里有一份 `反思报告.md`，语义上就是 AAR，但平台要的是 `AAR_W`。
工具应该判「缺失」，还是「聪明地认出它就是 AAR」？

**选了判缺失**，理由：一旦开始猜语义，就再也说不清「为什么这次算、那次不算」。
同理，目录名不匹配（C9 在 `C2A_C9_交付/`）用**显式配置**解决，不用模糊匹配 —— 配置可 review、可提交、可撤销。

**代价**：C9 现在显示 `missing_artifacts`（缺 `AAR_W`），是「形式上的真、语义上的误报」。这条写进了 README §八 与 AAR §9，作为已知边界。
**下一步**：加 `file_aliases`（把 `反思报告.md` 声明为 `AAR_W` 的别名），仍然是显式配置，不引入猜测。

---

### 决策 5：零依赖 + 三种报告形态

**取舍**：可以做 Web 服务（助教打开浏览器看），也可以做一个 CLI + 静态文件。

**为什么选后者**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| Web 服务 | 界面好看、可多人访问 | 要装 Node/起端口/维护；助教不会装 |
| **CLI + 三份静态报告（选了这个）** | `git clone` 后一条命令；HTML 双击即开；JSON 可进 CI | 没有交互、不能跨机器汇总 |

**具体形态**：Markdown（GitHub 上直接读）、JSON（字段稳定，可 `jq`/CI 断言）、单文件 HTML（内联 CSS，无 CDN、无 `<script src>`）。
零依赖的另一个好处是**结论可复现**：没有第三方库版本差异，同一份仓库两次跑结果一致。

**代价**：手写 Markdown 表格与 HTML 字符串，排版容易出错（第一版报告里链接前缀就错过一次，`README.md` 链到了仓库根）。

## 3. 从 C3–C7 到 C8 的变化（如果只看差异）

| 维度 | C3–C7（练习） | C8（真实项目） |
| --- | --- | --- |
| 输入 | 自己造 | 平台导出的 11 份记录 + 1331 个真实文件 |
| 需求来源 | 挑战文件写死 | 挑战文件 + 真实数据 + 使用者确认，**会被数据改** |
| 正确性标准 | 测试绿 | 测试绿 **且** 在真实数据上不说假话 |
| 失败代价 | 改一版重跑 | 误报会让人去补不存在的文件 |
| 交付形态 | 代码 + 文档 | 代码 + 文档 + **验收记录** + 可复跑证据 |
| 评价者 | 自己 | 助教视角（模拟）+ 使用者验收 |

## 4. 我没做的事（以及为什么）

| 没做 | 原因 | 如果要做，第一步是什么 |
| --- | --- | --- |
| 内容质量评分 | 需要阅读与判断，不是文件匹配能做的；做了就是假装 | 先做「人工抽查清单」，把要看的 3 个文件列出来 |
| 接 LLM 做语义判断 | 不可复现、不可离线、有成本；同一仓库两次结论可能不同 | 作为可选插件，结论标 `low confidence`，不进门禁 |
| 自动修文件（改名/补空文件） | 评审工具不该改被评审对象，改了就失去证据价值 | 只输出「建议改动清单」，人来执行 |
| 跨仓库汇总仪表盘 | 当前只有一个仓库，需求不存在 | 先把 JSON 输出做稳（已做） |
| `file_aliases` 文件级别名 | 这次只有 C9 一个例子，先记录为边界 | 在 `mapping.json` 加 `file_aliases` 段，用显式映射 |
| 真实第三方验收 | 拿不到第三方时间 | 验收单设计成可勾选，交给使用者完成（见 `验收/`） |

> 从 C3 拿的是「沙箱失败不等于命令写错」，从 C1 拿的是「零环境可用」。

> 那是另一个问题。
