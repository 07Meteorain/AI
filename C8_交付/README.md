# submitgate · 挑战交付验收门禁

> 11 个挑战、40 条必需交付物、1331 个文件、5 个评分维度 / 100 分。
> 学生怕漏交，助教怕看不完 —— 这一个命令同时回答两边的问题。

```bash
python -m submitgate check        # 一条命令，出三份报告
```

**它不做的事**：不给分数、不读内容好坏、不假装能评「群内参与质量」。
**它做的事**：把「该有的文件在不在、该有的证据有没有」变成一次可复跑的检查，并**逐条给出证据文件路径**。

---

## 一、为什么做这个（真实问题，不是练习）

课程平台给每个挑战定义了必需交付物和评分维度，但这些约束散落在 11 份 `challenge.json` 里：

| 事实 | 数字 |
| --- | --- |
| 挑战记录 | 11 份（C3、C3C、C5、C5A、C6、C6A、C7、C8、C9、C10、C10H） |
| 必需交付物条目 | 40 条，写法有 4 种（`*AI日志*`、`README.md`、`*AAR_W*`、`AGENT.md`） |
| 评分维度 | 每个挑战 5–6 个，**维度 id 由每个挑战各自定义**（共 23 个不同 id） |
| 仓库文件 | 1331 个，跨 13 个交付目录 |
| 红旗项 | 3 类，命中即把对应维度封顶 5 分 |

真实后果，在第一次运行时就被量化出来了：

- `C6A`、`C7`、`C10`、`C10H` **四个挑战在仓库里根本没有交付目录**（占 40 条必需交付物的 15 条）；
- `C9` 的交付物实际放在 `C2A_C9_交付/`，但缺 `AAR_W`（平台要求的是这个名字）；
- `C6` 的 CI 工作流在**仓库根**而不是交付目录里（GitHub 只认根目录），只看交付目录会误判为「没有 CI」。

这些都不是「感觉差不多」，是逐条文件核对出来的。所以它值得做成工具，而不是每次手查。

## 二、30 秒验证（不需要安装任何东西）

要求：Python 3.9+（仅标准库，无任何第三方依赖）。

```bash
cd C8_交付
python -m submitgate check          # 用随交付附带的挑战记录 + 上一级仓库根
```

预期输出（节选）：

```
[PASS] C5    必需 4/4  红旗 -                可验证 99/100（5/5 维）
[FAIL] C10   必需 0/4  红旗 missing_artifacts,no_ai_log   可验证 0/0（0/5 维）
...
结论：FAIL（5/11 挑战通过；估算总分 ... 非成绩）
```

- **退出码 0** = 所有挑战的必需交付物齐全且无红旗；**1** = 有缺口；**2** = 用法/环境错误。
  可以直接当 CI 门禁用。
- `python -m submitgate selftest` 会现场造一个最小样例跑通全流程（解析、匹配、缺失判定、红旗封顶），
  用来确认「装对了」。

打开 `reports/导航站.html` 双击即看：单文件、零外部资源、离线可读。

## 三、用法

```bash
python -m submitgate check [选项]

  --course PATH     课程记录根目录（含 <Cx>/challenge.json）。默认用随交付附带的 challenges/
  --repo PATH       交付仓库根目录。默认用本交付目录的上一级
  --mapping PATH    别名映射 JSON。默认 mapping.json（可不存在）
  --out PATH        报告输出目录。默认 reports/
  --formats LIST    输出格式，逗号分隔：md,json,html（默认三份都出）
  --github-base URL 报告里文件链接的前缀；传 "" 则只输出路径
  --quiet           只输出结论
```

三份产物：

| 文件 | 给谁 | 有什么用 |
| --- | --- | --- |
| `reports/交付验收报告.md` | 助教 / 学生 | 逐条核对：每项结论后面都跟着证据文件链接 |
| `reports/交付验收报告.json` | 脚本 / CI | 字段稳定，可直接断言 `summary.gate == "PASS"` |
| `reports/导航站.html` | 不想装环境的人 | 单文件、离线、双击即开；点开每个挑战看维度条与缺口 |

`mapping.json` 用来声明「目录名 ≠ 挑战编号」的情况：

```json
{ "aliases": { "C9": "C2A_C9_交付" } }
```

## 四、它检查什么

三层，客观性从高到低：

### 第 1 层：必需交付物（客观）

| 平台写法 | 匹配规则 | 为什么 |
| --- | --- | --- |
| `*AI日志*` | 相对路径**包含**「AI日志」 | 真实仓库里有 `AI日志.md`、`07Meteorain_C3_AI日志.md`、`AI日志/AI使用日志.md` 三种 |
| `README.md` | 文件名**全等** | 避免把 `README2.md` 也算命中 |
| `AGENT.md` | 同名，缺了就报缺 | — |

命中但**全是 0 字节**，按缺失处理（空文件不是交付）。

### 第 2 层：维度信号（启发式，逐条可反驳）

每个维度先归到一类证据（`profiles.py`），再拆成 3–5 条可观察信号。例如：

| 维度类别 | 观察什么 | 例 |
| --- | --- | --- |
| `artifact` | 必需交付物、README 体积、安装/使用小节、可运行入口、总体量 | C6 的 `app/index.html` + `package.json` |
| `ai` | AI 日志存在、迭代轮次（**认中文数字**：「第一轮/第二轮/第三轮」）、prompt 原文（代码块**或引用块**）、失败记录、体量 | C6 的「执行轮次（12 轮）」 |
| `reflection` | AAR 存在、四问覆盖、具体数字、**失败经验小节**、改进方案 | 「3. 失败经验（F1–F8）」 |
| `repo` / `community` | README、LICENSE、tests、CI、docs / Issue 模板、PR 模板、贡献指南… | C5 的 6 个社区要素全在 |
| `engineering` | 测试、入口、文档、CI（**允许在仓库根**，按 `c6-ci.yml` 这样的前缀匹配） | C6 的 `.github/workflows/c6-ci.yml` |

每条信号都带**权重**和**证据路径**，报告里可逐条反驳 —— 这是「估算」和「黑箱打分」的区别。

### 第 3 层：红旗（规则，照抄平台）

| 红旗 | 触发条件 | 后果 |
| --- | --- | --- |
| `missing_artifacts` | 任一必需交付物缺失或为空 | 产物完整性封顶 5 分 |
| `no_ai_log` | 没有任何 AI 使用记录 | 复盘质量封顶 5 分 |
| `one_shot_ai` | 日志里没有迭代证据（轮次 < 3，且 prompt < 2 或失败记录 < 2） | AI 使用封顶 5 分 |

**不做加权稀释**：一条致命项就是一条致命项。这条纪律来自 C4A 的教训（一次加权平均把硬编码本机路径的提交算成了 57%）。

### 一个不肯含糊的设计：不可验证的维度不装懂

平台 23 个维度里，有一半无法从文件系统观察（C3 的「群内参与质量」、C10 的「记忆系统」）。
本工具把它们标成 **「需人工」**，**不计 0 分、也不进分母**，并在报告顶部单列覆盖率：

```
可验证维度得分 477/575  ·  可验证维度 30/35
```

如果按 0 分算，报告会显示「C3 只有 55 分」，看起来像学生做得差；实际是工具看不见。
**把「看不见」写成「没做」，是评审工具最严重的说谎方式。**

## 五、真实运行结果（2026-11-15，仓库 HEAD 见报告）

| 挑战 | 结论 | 必需交付物 | 红旗 | 可验证分 | 维度覆盖 |
| --- | --- | --- | --- | --- | --- |
| C3 | PASS | 3/3 | — | 55/100 | 6/6 |
| C3C | PASS | 4/4 | — | 91/100 | 5/5 |
| C5 | PASS | 4/4 | — | 99/100 | 5/5 |
| C5A | PASS | 3/3 | — | 91/100 | 5/5 |
| C6 | PASS | 4/4 | — | 99/100 | 5/5 |
| C8 | PASS | 4/4 | — | 100/100 | 5/5 |
| C9 | FAIL | 2/3 | `missing_artifacts` | 42/75 | 4/5 |
| C6A / C7 / C10 / C10H | FAIL | 0/4、0/3、0/4、0/4 | `missing_artifacts`、`no_ai_log` | — | 0/5 |

**门禁结论仍是 FAIL —— 这是对的**：四个挑战还没做，C9 的 `AAR_W` 命名不符。
工具的价值恰恰在这一行：它把「还剩什么」写成了一张可执行的清单。

## 八、已知边界（诚实声明）

1. **只做文件级事实判断**：文件名、体积、章节标题、关键词、git 提交时间。不看内容对不对。
2. **`PASS` 只代表「该有的证据都在」**：一份六要素齐全但内容空洞的交付同样能 PASS。
3. **必须按文件名匹配**：平台要求 `AAR_W`，交付里叫 `反思报告.md` 就会被判缺失（C9 当前就是这样）。
   语义等价需要人判断，工具不猜。
4. **维度的证据类别是硬编码的映射表**（23 个 id），新挑战需要加一行，或落到关键词兜底。
5. **按时交付依赖 git**：没有 `.git` 或浅克隆无历史时，该条为「未验证」，不猜。
6. **启发式阈值是经验值**（AI 日志 ≥2000 字符、≥3 轮、README ≥400 字符…），改阈值会影响结论。
7. **不评价「做得好不好」**：这是助教的事，工具只负责把该看的地方指出来。
