# 拿来说明 · Recall 的五个关键取舍

> 「拿了什么、改了什么、为什么」——不是功能清单，是**备选方案与代价**。
> 每个决定都写：当时的选项、为什么选这个、付出了什么。

---

## 1. 为什么做「复习卡」，而不是第四个静态检查器

**当时的选项**

| 选项 | 吸引力 | 问题 |
| --- | --- | --- |
| A. 交付物证据审计器 | 与仓库 C1–C9 直接相关，能立刻用 | 只有 9 份提交，样本太小；与 C4A 评审器同质 |
| B. 论文阅读卡 | 有 C2 论文与 17 条文献 | 需要 PDF 解析，超出零依赖范围 |
| C. Recall 复习卡 | C1 有 33 篇 / 12.9 万字真实语料，能当天压测 | 与「AI 工具」主题弱相关 |

**选择 C 的理由**：只有 C 能当场拿到真实输入并验证。
「选题价值」不是靠描述证明的，是靠「今天下午能不能用真实数据打脸」证明的。

**代价**：它与课程前半段的「检查器」系列不同质，评审者需要重新理解问题域；
另外，复习效果需要长期数据，而本次只有单日——这一点直接削弱了「真实需求」的说服力。

---

## 2. 为什么排程用 SM-2，而不是 FSRS-5 或自创公式

**选项**

- **FSRS-5**：更现代、拟合效果更好；但我无法确认 19 个权重的来源、版本与训练集，
  写进代码就是「看起来很科学，实际上不可核对」。
- **自创**：可以讲一个漂亮的故事（「我设计了一个基于遗忘曲线的调度器」），
  但没有验证数据，最可能把复习节奏搞乱。
- **SM-2**：1987 年公开规格，每个数字能手算，双端容易对齐。

**选择 SM-2**：把「可核对」放在「更先进」前面。
`test_scheduler.py` 里直接断言 `1/6/15/38` 的间隔序列；`5 × 2.5 = 12.5 → 13`
这种舍入边界也被固化。

**代价**：没有参数拟合、没有 fuzz、没有负载均衡。
大卡组（>5,000 张）同一天到期的概率更高；SM-2 的「90% 召回」假设也不一定适合每个人。
这些都写进了 README 的「诚实边界」。

---

## 3. 为什么默认 approved，而不是全部 candidate

**选项**

- **全部 candidate**：审核成为第一道门槛，质量更可控；但第一次打开 `review` 会提示「没有可复习的卡」，
  新用户必须先理解「审核 → 导出 → apply」三步，流失率高。
- **默认 approved**：`build` 完就能复习，开箱即用；审核变成第二道闸（发现烂卡再剔除）。

**选择默认 approved**：先让用户跑起来，再谈质量。
`web` 的审核页可以对任何卡「剔除」，`apply` 写回数据库；`review` 只取 approved。

**代价**：如果用户跳过审核，会背到 60% 价值率里的那 40%。
缓解方式是 `sample` 命令与 README 的显著警告，但**不能消除**。
这也是 AAR F2 的根源。

---

## 4. 为什么 Web 用 `deck.js`，而不是 `deck.json` + fetch

**约束**：目标形态是「双击 `index.html` 就能用」，不起服务器。

**选项**

- **fetch JSON**：干净、可缓存、可按需加载；但 `file://` 下被 CORS 拦截，
  必须起 `python -m http.server`——正好违背「零安装」。
- **内联 `deck.js`**：`window.RECALL_DECK = {...}`，`file://` 直接可读；
  代价是卡组越大，页面越重。
- **IndexedDB + 导入按钮**：灵活，但多一步操作，且首次仍要读文件。

**选择 `deck.js`**：把「打开就能用」放在「优雅加载」前面。
同时做了一件事：把 `</` 转义为 `<\/`，防止卡片正文里的 `</script>` 提前闭合标签。

**代价**：10 万张卡不适合；页面首屏会变慢。README 明确写了这条边界。

---

## 5. 为什么零依赖，不用 `click` / `jinja2` / `rich`

**选项**

- **用现成库**：CLI 参数、模板、终端着色都能少写几百行，开发更快。
- **零依赖**：`git clone` 后两条命令就能验证；不需要虚拟环境、不需要联网装包。

**选择零依赖**：这个项目的目标用户是「第一次打开仓库的人」。
如果 README 第一段是 `pip install -r requirements.txt`，一部分人到这里就走了。
而 Recall 的功能规模（一个 CLI + 一个静态页）完全撑得起手写。

**代价**：

- `argparse` 的帮助信息不如 `click` 好看；
- HTML 模板是 Python 里写死的资源拷贝，不是模板引擎；
- 终端没有颜色与进度条，只有分隔线与计数。

这些代价都落在「体验的精致度」上，而不是「能不能用」上——在本次预算下，这个交换是划算的。

## 6. 附加：为什么在数据之后才加 `doctor`

原本没有 `doctor`。C1 第一次只出 62 张卡时，我的第一反应是「规则不够强」，
想再加几条正则。停下来问了一个问题：**这些文本真的适合自动出卡吗？**

`doctor` 把「为什么出不了卡」变成可解释的分数与建议：
标题数、列表项、加粗术语、问句标题、显式问答、实际卡片数。
它不能提高抽取率，但能阻止用户在错误的输入上继续调参。

**代价**：多了一个命令、154 行代码、11 项测试；但它把一个「产品缺陷」变成了「输入诊断」，
这是这次最像产品经理的一次决定。

## 附：没有做的取舍（同样重要）

| 没做 | 为什么 | 什么时候该做 |
| --- | --- | --- |
| PDF / 网页导入 | 需要第三方解析库，违背零依赖；且转写稿质量差（见 C1） | 有明确的 PDF 笔记工作流时 |
| 云同步 / 账号 | 隐私与后端成本；本地优先是刻意选择 | 有多设备用户明确要求时 |
| LLM 运行时判分 | 不可回归、有成本、可能编造；与「可追溯」冲突 | 只作为「建议」而非「判定」时 |
| Anki 导出 | 生态兼容有价值，但会引入格式细节与测试负担 | 有真实用户提出时 |
| 移动端 App | 离线网页已能在手机打开 | 需要推送/离线缓存时 |

**做减法比做加法难**：每砍一个功能，都意味着承认「这次不解决它」。
但 C9 的评分里，「选题价值」与「交付完成度」都指向同一件事：
**把一件事做完整，而不是把十件事做一半。**
